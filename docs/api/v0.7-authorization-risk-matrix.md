# v0.7 Authorization and Risk Matrix

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Authority #178/#180; W51 #181.

This matrix owns the proposed server-derived actions, exact targets, base risk floors and mandatory escalation rules for v0.7. Clients cannot choose a weaker risk class, omit required actions or widen target arrays. Existing v0.5/v0.6 authorization/risk rules remain authoritative for inherited effects.

## Principles

1. Read permission never implies mutation.
2. Provider-profile visibility is separate from provider mutation.
3. Compound operations require the conjunction of every child permission and use the maximum child risk plus blast-radius escalators.
4. HIGH requires explicit confirmation; CRITICAL also requires a distinct eligible approver under the existing mutation governance model.
5. Current authorization is rechecked immediately before each new external effect and before resuming durable work.
6. Ambiguous effects cannot be cleared by a weaker retry route.
7. Record-payload permissions remain independent from metadata/schema/Connect/ksql permissions.

## Exact target encoding

New targets use versioned, length-delimited canonical encoding. Do not concatenate user/provider identifiers with ambiguous separators.

Canonical target dimensions include as applicable:

- Kafdeck cluster profile ID and actual physical Kafka identity;
- ecosystem provider kind;
- stable provider profile ID;
- Schema subject/version/global compatibility scope;
- Connect connector/task/plugin identity;
- exact source/destination topic + partition/range;
- job ID + immutable plan fingerprint;
- ksql profile ID;
- registered application/topology identity.

Case, bytes and provider naming semantics are preserved where relevant. Validation rejects ambiguous canonicalization.

## Schema mutation details

### Registration

The immutable preview binds:

- provider profile/version;
- subject;
- schema type;
- canonical content/fingerprint;
- complete explicit reference closure;
- current compatibility policy/evidence;
- proposed expected provider identity/readback.

Registration never creates a Kafka topic or changes compatibility as a hidden side effect.

### Compatibility change

Global and per-subject compatibility are distinct targets. A client cannot send an empty subject string to mean global scope.

Relaxing compatibility is CRITICAL because it can admit future incompatible producer/consumer contracts across a broader blast radius.

### Delete

Soft and permanent deletion are distinct effect kinds. Permanent deletion cannot be represented as a boolean hidden inside a lower-risk soft-delete action.

## Connect mutation details

Connector create/update preview binds:

- exact Connect profile ID/origin fingerprint;
- connector name and class;
- allowlisted plugin/config schema identity;
- non-secret normalized configuration;
- secret-reference identities/digest bindings, never plaintext;
- provider validation evidence;
- current status/config fingerprint where applicable.

A class/endpoint/transform/converter/predicate change can elevate risk because it may change data movement or exfiltration boundary.

Recognized replication/MM2 connectors remain subject to the v0.6 replication classifier/guard. Satisfying generic Connect permissions is never sufficient to activate a Blocked replication path.

## Auto-restart effects

Enabling a policy grants no standing bypass. Before each actual restart attempt, Kafdeck rechecks:

- current requester/service automation principal;
- exact connector/task authorization;
- current connector identity/class;
- current deployment policy;
- remaining lifetime attempts;
- circuit-breaker state;
- MM2/replication guard;
- unresolved prior dispatch state.

A policy whose originating user is no longer eligible stops rather than manufacturing authority. Deployment may require a dedicated automation principal; its permissions are explicit and auditable.

## Data-job conjunction

Every replay/reprocess/forward preview requires:

- source `record.read`;
- source `record.export`;
- destination `record.produce`;
- `datajob.plan`;
- exact metadata/config visibility for any source/destination identity shown or fingerprinted;
- masking/data-policy eligibility.

Execution adds `datajob.execute`.

Metadata visibility does not follow from record permissions. An operator lacking required topology/config visibility receives an unavailable/denied plan rather than a misleading partially redacted immutable plan that cannot be safely revalidated.

## Generator conjunction

Generation requires no source record permission when content is locally synthesized, but schema-backed generation requires exact `schema.read` for the complete reference closure. Execution always requires destination `record.produce` plus `generator.execute`.

Production use is deny-by-default at deployment policy. An authorized user cannot override a deployment prohibition by selecting a lower environment classification in the request.

## ksql query boundary

`ksql.query` is a bounded execution permission, not a mutation/admin grant. The server parses/classifies admitted statement families before forwarding. Unsupported/ambiguous statements are rejected before provider I/O.

v0.7 has no action that permits:

- CREATE STREAM/TABLE;
- DROP;
- ALTER;
- INSERT;
- TERMINATE;
- persistent query creation;
- arbitrary provider endpoint forwarding.

## Risk integrity

Risk classification is server-owned. Numeric record/byte/mapping/task/version thresholds are evaluated from the canonical preview after provider resolution and cannot be supplied as "risk hints" by the client.

Policy may strengthen any risk floor but cannot lower the planning baseline without a reviewed contract change.
