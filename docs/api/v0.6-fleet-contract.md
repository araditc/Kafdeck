# v0.6 Fleet API / OpenAPI / UI Contract Principles

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Scope #145; tracker #146. Exact OpenAPI is a W49 deliverable after domain/provider admissions, not executable scaffolding in this PR.

## One versioned application boundary

Extend the existing mutation-operation API resource and stable v0.5 behaviors rather than exposing raw provider commands. The route shapes in earlier v0.5 planning documents are conceptual; W49 reconciles the actual admitted routes before extending them. Read-only fleet projections and typed preview/confirm/approve/reject/cancel/status controls use the same identity, authorization, safe audit and Problem Details boundary.

New request kinds are an explicit closed discriminated set. Proposed families are ACL changes, SCRAM upsert/delete, quota changes, dynamic configuration changes, preferred election, reassignment/RF change, throttle changes, broker/log-directory maintenance, finite transfer and replication integration. There is no arbitrary action name, HTTP method, URL, AdminClient operation, JSON workflow or provider config dictionary.

## Required request/preview fields

A typed preview request supplies intended finite targets, typed values/ranges and requested budgets within server limits plus `Idempotency-Key`. The server resolves profile/physical identities, complete compound requirements, capabilities, risk, policy version, effective limits, relevant fingerprints, safe material digests and exact operation/preview identity. Caller-supplied risk, approver, current state or hashes cannot replace server evidence.

A preview response includes safe target-level changes, evidence completeness/timestamp, plan/step summary, limits/horizon, irreversibility/partiality warnings, confirmation challenge, independent approval requirement and verification limits. It must not contain SCRAM secrets, HMAC bindings, raw records, raw connector configs or unfiltered provider messages.

Multi-cluster idempotency binds both cluster identities, exact mappings/ranges and schema version. Reusing the key with different admitted intent yields conflict; retrying the same transition cannot trigger another provider dispatch. Existing v0.5 hash/idempotency behavior stays byte-compatible.

## Confirmation, approval and finalization

Confirmation and approval bind operation ID plus preview hash and current state/expiry. CRITICAL uses a distinct eligible principal. SCRAM adds a narrowly typed material-finalization request by the original requester after approval; it enters the same coordinator, not HTTP-to-provider execution. It can only match already-approved material, not change secret metadata or bypass prerequisites. Concurrent finalizations get one durable claim.

Before dispatch, expired preview requires a new preview. Once a long-running plan starts, the bound dispatch horizon and current eligibility govern later steps; expiration cannot erase outstanding effects. Extending scope/horizon/risk/material requires fresh admission. Cancel means pre-dispatch cancel. Stop-transfer means no further Kafdeck batches; it does not roll back acknowledged writes or cancel an unrelated Kafka reassignment.

## Status, errors and visibility

Status returns parent outcome, safe per-step progress, observed time/completeness, remaining budget, outstanding effect status and what action is actually permitted next. Unknown is never presented as a Retry button. Applied-but-still-running, partial, waiting for material, authorization pause and external-action prerequisites are visually distinct. Per-target ambiguity dominates an aggregate success claim.

Use existing `mutation.*` Problem Details codes and bounded additions for unsupported profile, missing current authorization, source-range loss, outstanding-effect conflict, checkpoint ambiguity and external action required. Unknown operation IDs and hidden operation IDs have non-enumerating behavior. Error logs never echo raw request/provider material. HTTP failure alone does not imply provider non-application.

Cookie-authenticated unsafe methods require existing anti-CSRF validation; GET cannot mutate. Preview/status/finalization responses are `no-store`; secrets never enter URL/query parameters, browser storage, analytics or client error telemetry. Status/list/inbox authorization is resource-specific, including both sides of a transfer.

## UI and accessibility acceptance

UI affordances reflect server capability/permission rather than infer rights locally. Tables show exact bindings, ordered replicas and default-versus-named quotas. Keyboard/focus/error-summary and confirmation-dialog tests are required. Transfer progress includes finite end offsets and partial/unknown explanation; maintenance UI differentiates cordoned, evacuated, externally stopped and actually removed. API and direct-route negative tests are mandatory, not replaced by hidden buttons.
