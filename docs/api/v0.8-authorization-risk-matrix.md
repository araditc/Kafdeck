# v0.8 Authorization and Risk Matrix

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**

Authority: #208/#209; W61 #210.

Existing v0.5–v0.7 action/risk rules remain authoritative for inherited effects.

## Principles

1. Observability permission does not imply record access or mutation.
2. Alert configuration does not imply authority to execute the event's related mutation.
3. Automation clients use explicit principals.
4. Declarative ownership does not override server risk/approval.
5. MCP/CLI/Terraform/GitOps cannot choose risk.
6. Compensation is a new operation with fresh authorization/risk.
7. Resource-scoped telemetry/history remains visibility-filtered.

## Automation principal rules

A background service principal may be configured, but:

- permissions are explicit;
- it cannot approve its own CRITICAL effect;
- it is revalidated before every new effect;
- revocation stops future effects;
- it cannot reuse a human session token as durable standing authority.

## Declarative compound risk

A declarative apply risk is at least the maximum child risk.

Escalate to CRITICAL when:

- any child is CRITICAL;
- blast radius crosses configured cluster/resource thresholds;
- ownership/adoption changes security-sensitive resources;
- apply deletes multiple production resources;
- current plan contains unresolved/unknown external effects.

## Alert-driven automation

An alert may trigger:

- a notification;
- a read/diagnostic action;
- creation of a proposed governed operation if a typed automation rule is separately admitted.

An alert event itself is never authorization or approval.
