# v0.6 Authorization and Risk Matrix

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Scope #145; tracker #146; RFC-0006.

## Closed authorization requirements

Actions below are Kafdeck permissions, not Kafka broker ACL operation names. Provider credentials must independently possess the least privileges necessary; Kafdeck never treats provider access as user permission. Mutation precondition reads do not expose otherwise-unreadable metadata to the requester: preview/status projections must check the corresponding read permission.

Every row is a conjunction over exact targets. Extra actions and clusters cannot be supplied by a client. Authorization/approval is repeated for all targets before dispatch and before resumed effects. Uncertainty denies or pauses dispatch.

| Typed family | Kafdeck action and exact target | Base risk / mandatory escalation |
| --- | --- | --- |
| ACL inspect / access analysis | `acl.read` on each canonical binding/resource scope | Read-only; incomplete evidence is Unknown, not Denied/Allowed proof |
| ACL create/remove/replace | `acl.alter` on every exact old/new binding; `acl.read` for visible preview | HIGH; broad/prefixed/wildcard administrative grants, protected access removal or >25 bindings => CRITICAL |
| SCRAM metadata | `scram.read` on username/mechanism | Metadata only; never secret/verifier material |
| SCRAM upsert/rotate/delete | `scram.alter` on username/mechanism; `scram.read` for metadata preview | CRITICAL in every case |
| Quota inspect/change | `quota.read` / `quota.alter` on canonical entity dimensions and quota key | HIGH for change; default or broad entity blast radius => CRITICAL |
| Broker/default-cluster config | `cluster.config.read` / `cluster.config.alter` on explicit scope/broker/key | HIGH; security/durability/availability/election/replication-sensitive key => CRITICAL |
| Preferred leader election | `leader.elect` on each topic/partition; existing metadata-read permission for visible preview | MODERATE for one partition; >1 => HIGH; no unclean-election kind |
| Replica reassignment | `partition.reassign` on each topic/partition | HIGH; >50 partitions => CRITICAL |
| Replication-factor change | `partition.reassign` AND `replication.factor.alter` on every affected partition | HIGH; any reduction => CRITICAL |
| Reassignment throttle | `reassignment.throttle` AND applicable topic/broker-config alteration permissions on every changed key | HIGH; inherits larger parent risk |
| Broker/log-directory maintenance | `broker.maintenance` / `logdir.maintenance` AND every actual config/reassignment/RF-change requirement | CRITICAL for decommission and its admitted plan; cordon-only/uncordon-only also CRITICAL by conservative design |
| Transfer plan | `cluster.transfer.plan` on source/destination pair and source `record.read` + `record.export`, destination `record.produce` on each mapped topic | Side-effect-free; no payload exposed by plan |
| Transfer execution | `cluster.transfer.execute` plus all plan/read/export/produce targets; every exact mapped destination topic MUST already exist with the previewed identity/configuration before transfer dispatch; transfer never provisions topics and absence/drift is `StalePreview`/fail-closed | HIGH; >25 mappings or >100 MiB approved total => CRITICAL; destructive destination behavior is unsupported, not silently enabled |
| Replication integration | `replication.integration.alter` plus exact Connect mutation/read permissions; source `record.read` + `record.export`; destination `record.produce`; exact `topic.create` for every absent mapped destination topic or admitted internal topic; and every exact internal-write requirement listed below | HIGH; >25 mappings or broad topology => CRITICAL; every extra side effect requires its own action |
| Unresolved-effect reconciliation | `mutation.reconcile` on every conflict resource **AND** the complete current authorization conjunction of the unresolved original effect | CRITICAL always; distinct eligible approver; no provider mutation; cannot erase history or redispatch old effect |

Numeric escalators are proposed server-owned policy floors, not client-selected risk hints. Policy may strengthen them. Compound parent risk is the maximum of all children and parent blast-radius rules. HIGH uses typed confirmation; CRITICAL adds a distinct eligible principal. A read-only plan does not grant permission to execute it.

## Resource representation and privilege boundaries

Bindings and requirements use versioned length-delimited canonical encoding. Kafka LITERAL, PREFIXED and wildcard semantics must not be confused with Kafdeck's resource-pattern matcher. Preserve principal/host/name case and bytes where Kafka semantics require them; reject ambiguous or invalid representations instead of trimming into a different identity.

An ACL editor cannot grant arbitrary Kafka rights merely because it can edit one topic. Server deployment policy constrains permitted principals, resource types, operations, patterns and grant ceilings. Broad grants include future resources, even when the currently observed matching set is small; previews say so and remain CRITICAL. Destructive filter deletion dispatches only the exact observed binding tuples. Protect configured Kafdeck service, broker/controller and recovery principals against lockout. Unknown effective grant scope fails closed.

Quota targets distinguish an absent dimension, an explicit default entity and a named user/client/IP; these are not interchangeable empty strings. Dynamic config targets distinguish a broker override, cluster default and reset-to-inherited. A generic config path cannot edit SCRAM, ACLs, credentials, cordon or throttle keys under a lower action/risk.

## Replication integration internal-write conjunction

For every recognized MM2/replication integration, W41/W48 MUST derive internal-write requirements from the tested server-owned profile. These requirements are part of the immutable preview; `replication.integration.alter` or `connect.alter` never substitutes for them.

| Internal side effect | Required action | Exact target |
| --- | --- | --- |
| MM2 heartbeat write | `record.produce` | profile-declared physical cluster + exact heartbeat topic |
| MM2 checkpoint write | `record.produce` | profile-declared physical cluster + exact checkpoint topic |
| MM2 offset-sync write | `record.produce` | profile-declared physical cluster selected by tested `offset-syncs.topic.location` behavior + exact offset-sync topic |
| Connect worker config-state write | `record.produce` | Connect backing physical cluster + exact `config.storage.topic` |
| Connect worker offset-state write | `record.produce` | Connect backing physical cluster + exact `offset.storage.topic` |
| Connect worker status-state write | `record.produce` | Connect backing physical cluster + exact `status.storage.topic` |
| Creation of an absent mapped destination data topic when explicitly admitted for replication integration | `topic.create` in addition to destination `record.produce` | exact destination physical cluster/topic, with governed topic intent/configuration |
| Creation of any missing internal topic when explicitly admitted | `topic.create` in addition to subsequent `record.produce` | the same exact physical cluster/topic, with governed topic intent/configuration |

For replication integration only, pre-provisioning a destination or internal topic removes its `topic.create` requirement; writes still require `record.produce`. Broker/MM2/Connect implicit auto-creation is unavailable unless the exact topic-creation effect is separately materialized and authorized in the immutable preview. An absent mapped destination topic with no exact creation effect fails closed before replication activation. **Finite transfer/clone operations are stricter:** every mapped destination must be prepared before admission and transfer dispatch never contains a `topic.create` step.

The initial v0.6 profile keeps ACL sync, topic-config sync and consumer-group-offset sync disabled. If a later tested profile within the already accepted replication-integration scope admits one of these effects, the immutable preview MUST add the exact existing governed action/target for that effect (`acl.alter`, the applicable topic/config alteration action, or `consumer.offset.alter`). If the side effect cannot be represented by an already governed typed action, activation remains unavailable pending a new scope decision.

The same replication admission guard applies to any existing Connect action capable of starting/resuming movement: create, update, connector restart, connector resume, task restart and any equivalent tested activation path. Pausing/stopping may use its safe typed control path only when it cannot create a new external effect.

## Compound requirements without v0.5 weakening

W41 must retain `MutationAuthorization.ExpectedAction` and v0.5 target normalization behavior for existing kinds 1–14. New kinds use a separate closed requirement builder, with a schema discriminator included in intent/preview/idempotency hashing. A transfer binds both physical cluster identities and explicit profile versions; aliases resolving to the same cluster cannot masquerade as cross-cluster transfer.

The same independent approver must satisfy the complete required target set. Independent means canonical principal identity, not another tab, token, session or display name. The requester/approver/policy must remain eligible immediately before each new side effect. No permission can be delegated by an HTTP action array or persisted OIDC group list.

`FleetUncertaintyDisposition` is Kafdeck-local and cannot issue provider I/O. `ObservedNonApplication` and `ObservedTerminalEffect` require bounded readback evidence. `QuarantineUnknown` retains blocking. `SupersedeUnknownForNewIntent` preserves the old operation as `ExecutionUnknown`, retains a no-redispatch tombstone, and only permits a later separately created conflicting operation whose canonical preview binds the unresolved predecessor and is at least CRITICAL with fresh independent approval. There is no untyped clear/ignore path.

Status/list/approval-inbox reads enforce per-operation visibility. Safe recovery observation by the service does not make that evidence visible to an unauthorized caller and cannot mutate. Cross-cluster list/status output must not leak hidden source or destination identities.
