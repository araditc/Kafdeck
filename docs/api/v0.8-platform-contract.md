# v0.8 API / CLI / Declarative / MCP Contract Plan

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**

## API principle

All v0.8 clients use versioned Kafdeck HTTP contracts under `/api/v1`.

There is no client-specific privileged backend.

## Observability routes

```http
GET /api/v1/observability/capabilities

GET /api/v1/clusters/{clusterId}/metrics
```

Exact schemas must encode freshness, evidence source, partial/truncation and query budgets.

## Notification/webhook routes

**Admitted protected-main W66 observation and subscription CAS** (as of #283):

```http
GET  /api/v1/notifications/subscriptions
GET  /api/v1/notifications/subscriptions/{subscriptionId}
GET  /api/v1/notifications/deliveries/{notificationId}/{destinationId}
GET  /api/v1/notifications/destinations/{destinationId}/deliveries

# Only when Kafdeck:Notifications:ManagementEnabled=true:
GET  /api/v1/notifications/management/capabilities
PUT  /api/v1/notifications/subscriptions/{subscriptionId}
```

Read routes require OIDC + `AuthorizationAction.NotificationRead`, including
per-resource scope, bounded history and metadata-only projections. The
capability probe requires `AuthorizationAction.NotificationManage` collection
scope and never grants per-destination write permission. The create-only or
revision-bound CAS `PUT` requires OIDC, antiforgery and
`AuthorizationAction.NotificationManage` for subscription **and both old/new
destination** identities; a write-only operator does not gain `NotificationRead`.
`Retired` is terminal; no provider endpoint, credential or arbitrary HTTP
transport can be supplied in these requests.

The following **destination profile/test routes are planning proposals only**;
they are NOT currently mapped by `Program.cs` and must not be advertised
as Supported or called by CLI/GitOps/MCP:

```http
GET  /api/v1/notifications/destinations
GET  /api/v1/notifications/destinations/{destinationId}
GET  /api/v1/notifications/destinations/{destinationId}/capabilities
POST /api/v1/notifications/destinations/preview
POST /api/v1/notifications/destinations
PUT  /api/v1/notifications/destinations/{destinationId}/preview
PUT  /api/v1/notifications/destinations/{destinationId}
POST /api/v1/notifications/destinations/{destinationId}/delete/preview
DELETE /api/v1/notifications/destinations/{destinationId}
POST /api/v1/notifications/destinations/{destinationId}/test/preview
POST /api/v1/notifications/destinations/{destinationId}/test
```

The former `GET/POST /api/v1/webhooks/subscriptions` planning examples and
`webhook.manage` label **do not represent an implemented route or backend
action**. A future distinct webhook registration domain would need its own
review. Destination create/update/delete, if later admitted, must be governed
typed lifecycles over approved provider profiles, server-configured origins,
opaque credential references and immutable previews; arbitrary URL, headers,
SMTP or provider token from a request remain prohibited.

## Declarative plan/apply

Conceptual:

```http
POST /api/v1/declarative/plans
GET  /api/v1/declarative/plans/{planId}
POST /api/v1/declarative/plans/{planId}/apply
GET  /api/v1/declarative/operations/{operationId}
```

A plan is a server-issued immutable object. Its response includes:

- `planId`;
- `planFingerprint`;
- immutable initiating human/service principal identity (kind, issuer, subject and admitted client registration where applicable), separate from the resource owner; returned only as safe, authorized principal evidence, not an editable assertion;
- `createdAt` and finite `expiresAt`;
- canonical resource identity;
- ownership state;
- current/precondition fingerprint;
- desired fingerprint;
- create/update/delete/no-op/adopt action;
- server-derived risk;
- required approval;
- limitations;
- secret/write-only placeholders.

Apply identifies the exact stored plan by `planId` and binds the expected `planFingerprint` (for example in the body or an equivalent conditional contract). The server reloads the immutable plan, rejects expired plans, and revalidates every current-state/resource/provider/authorization precondition before admitting effects. **Plan detail, confirm and apply** are bound to the exact initiating principal identity persisted in that immutable plan; a different principal with broad action grants cannot replay/assume the plan without separately admitted governed transfer, and a caller-supplied `ownerRef` is never authorization evidence. **CRITICAL approval** independently checks an authorized principal distinct from the plan initiator, preserving audit identity and preventing self-approval. Drift or fingerprint mismatch returns an explicit stale/conflict result; apply never silently regenerates a stronger/new plan.

Apply may return AwaitingApproval.

## CLI contract

CLI commands map 1:1 to admitted APIs, for example:

```text
kafdeck clusters list
kafdeck metrics query
kafdeck slo list
kafdeck operations get
kafdeck plan --file desired.yaml
kafdeck apply --plan <id>
```

Machine output supports bounded JSON.

CLI does not implement provider-specific direct calls.

## Terraform contract

Terraform provider resources are added only after W68 declares the corresponding resource schema stable.

Provider lifecycle maps to:

- Read -> Kafdeck read/current-state;
- Plan -> declarative plan;
- Create/Update/Delete -> governed apply;
- Import -> explicit adopt/import API where supported.

Asynchronous AwaitingApproval is a first-class state, not bypassed.

## MCP contract

MCP exposes typed tools such as:

- list/read capabilities;
- observe metrics/SLO/lag;
- create side-effect-free plans;
- get operation status;
- submit an admitted governed apply/mutation request.

No generic `execute_sql`, `http_request`, `shell`, `kafka_raw` or `db_query` tool.

## Common response rules

All clients receive:

- explicit capability/status;
- stable problem/reason codes;
- safe bounded diagnostics;
- operation IDs for effects;
- risk/approval state;
- no plaintext secrets;
- no hidden provider bodies.

## OpenAPI

W62–W71 produce deterministic `docs/api/openapi-v0.8.json` and runtime `GET /api/v1/openapi/v0.8.json`.

CI must verify:

- all product routes documented;
- no undocumented effect route;
- no generic provider proxy;
- secret/write-only schemas;
- numeric request/response bounds;
- security/antiforgery requirements;
- released v0.7 route compatibility unless explicitly versioned.
