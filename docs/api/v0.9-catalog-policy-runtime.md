# W73 ownership catalog and W75 policy runtime

The W72 design is admitted through PR #437 / #426. This additive implementation retains all W73 C1–C4 and W75 P1–P4 criteria; exact runtime/main acceptance evidence is recorded in [#427](https://github.com/araditc/Kafdeck/issues/427), [#429](https://github.com/araditc/Kafdeck/issues/429) and [tracker #425](https://github.com/araditc/Kafdeck/issues/425). W74 and W76–W82 remain in the [complete plan](../implementation/v0.9-full-scope-delivery-execution-plan.md). No release/version promotion is implied.

## Configuration and authority

`Kafdeck:Governance:CatalogEnabled` and `PoliciesEnabled` default to false. Enabling either requires OIDC, durable governed mutations and an explicit nonempty `Kafdeck:Governance:DeploymentGeneration` UUID held outside database backups. Generate and retain the identity per deployment; change it through the quarantined restore procedure below. SQLite is standalone; PostgreSQL supports the existing admitted HA persistence. Both stores use the same mutation database and deterministic migration ledgers.

Existing authorization action numbers 1–63 and operation kinds 1–31 remain unchanged. New actions are CatalogManage=64, GovernancePolicyRead=65, GovernancePolicyManage=66 and GovernancePolicyActivate=67. New kinds are CatalogMutation=32, GovernancePolicyVersion=33 and GovernancePolicyActivation=34. No states are renumbered. CatalogRead=14 still governs reads. Critical activation requires current, durable human authority proof and a distinct eligible human; browser and registered bearer paths share the same kernel. Catalog/team assignment never grants RBAC, approval or declarative ownership.

Authority stores remain registered whenever mutation persistence is configured, even when mutation endpoints or policy management are disabled. Existing active policy continues to gate effects. An enrolled database with missing/wrong outside generation refuses startup/commit. A never-enrolled database with no policy retains v0.8 disabled-mode fingerprints. After enrollment or policy activation, monotonic generation/activation digests fence old plans, including transitions back to disabled policy. Direct and automation routes, resumed jobs/generators, Connect restart, ACL/SCRAM and declarative/global controls recheck current policy at their existing effect boundaries. Global NotificationManage control uses reserved server-derived `$deployment` policy scope while preserving its original null-cluster RBAC; it never refers to a Kafka cluster.

## Catalog API and CLI

All paths below start `/api/v1/governance/catalog`:

| Route | Result / authority |
|---|---|
| `GET /teams`, `/applications`, `/topics` | `clusterId`, default pageSize 50/max 200, scoped opaque cursor; authorized items only |
| `GET /{family}/{id}` | One scoped record; descriptive legacy owner text remains separate from any authority |
| `GET /{family}/{id}/history` | Immutable revisions, original attribution and bounded continuation |
| `POST /{family}/preview`, `/imports/preview` | `{clusterId,changes:[...]}`, Idempotency-Key, current CatalogManage; immutable staged plan |
| `GET /operations/{operationId}` | Exact operation/material/preview hash, generated IDs and observed topic identity |
| `POST /operations/{operationId}/recover` | `{previewHash}`; positive committed receipt, original actor/current CatalogRead/Manage/MutationReconcile; no redispatch |

Changes carry kind Team/Application/Topic, optional existing ID, expectedRevision, name, description, archived, teamId, applicationId, topicName, owner, domain, classification, documentationReference and tags. Rebinding a recreated topic is explicit; server-observed Kafka cluster/topic UUIDs are never accepted from a caller. Archived or recreated topics retain historical metadata and show current identity status separately; old ownership is not silently inherited. References and archive constraints are enforced transactionally. Imports are atomic, max 500 changes/1 MiB; ordinary requests max 256 KiB. A multi-resource import raises the existing risk floor to High and requires the exact typed confirmation challenge. CAS or authority conflict commits no partial records/history.

Named CLI commands use `catalog teams|applications|topics <cluster>`, `get|history <cluster> <family> <id>`, `change-preview <cluster> <family>`, `import-preview <cluster>`, `plan <operationId>` and `recover <operationId>`. Lists/history accept `--limit` and `--cursor`; previews take a closed `--request-file` and `--idempotency-key`. Use `operations confirm` with the returned hash/challenge, then `operations execute`. Metadata IDs and mutation operation IDs have different wire formats; preserve server-issued values exactly.

## Policy API and CLI

Import references use existing server-issued IDs. Create new reference targets first, then use their exact IDs in the atomic catalog import; no caller-chosen identity or alias execution language is introduced.

Paths start `/api/v1/governance/policies`:

| Route | Contract |
|---|---|
| `POST /validate` | `{document:"<closed JSON>"}`; canonical validation/hash, no effect |
| `POST /explain`, `/dry-run` | Exact authorized facts / up to 100 fixtures; current policy decision/version, no authority grant |
| `GET /versions`, `/versions/{versionId}`, `/active` | Scoped version history, immutable content and active epoch |
| `POST /versions/preview` | `{clusterId,document}`; Moderate governed version commit |
| `POST /activations/preview` | `{clusterId,versionId,expectedRevision,enabled}`; Critical typed confirmation and distinct human approval |
| `GET /operations/{operationId}` | Immutable material plus operation state for requester/eligible reviewer |
| `POST /operations/{operationId}/reconcile` | No body; original actor/current rights/MutationReconcile and positive committed receipt on owning CAS transaction |

Schema v1 is closed: ordered rules have id, priority, scope `{clusterId,resourceKind,resourceIds,action}`, conditions `{field,operator,value}` and outcome Deny or RequireApprovedRequest. Limits: 256 KiB, 100 rules, depth 12, 20 exact resource IDs/selector and 10 conditions/rule. No code, regex, SQL, remote lookup or provider command. Duplicate/unknown keys and unsupported operators/actions are rejected. Conditions use registered metadata/classification, risk and request facts. Until W74 provides genuine durable request approval, RequireApprovedRequest cannot be satisfied by caller-supplied facts. Missing required evidence or unavailable authority fails closed. Topic metadata conditions require matching current physical topic identity.

CLI commands are `policies validate|explain|dry-run`, `versions|state <cluster>`, `version-preview|activate-preview <cluster>`, `plan <operationId>` and `reconcile <operationId>`; structured commands use a closed request file, mutation previews require idempotency keys. Activation uses normal `operations confirm`, distinct human `operations approve`, then requester `operations execute`. UI shows exact immutable material, fingerprint, separate confirmation/approval and honest unknown/recovery states. CLI retains existing conflict/pending/unknown exit categories and never prints untrusted error bodies.

Actual generated discovery: `GET /api/v1/openapi/v0.9-governance.json` under SystemRead; released v0.8 bearer discovery remains available. Read/dry-run and mutation registrations remain separate from RBAC. No governance-management Terraform resource or model-driven policy activation is added; existing Terraform/MCP effects obey the shared gate.

## Restore and unknown effects

The generated governance document uses [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0.html) schema semantics, including nullable DTO fields.

Stop/fence old workers, verify the backup and positive effect evidence, restore in quarantine and choose a fresh outside generation. Run the API's offline `--governance-generation-admit` with `Kafdeck:Governance:RestoreMaintenanceMode=true`, exact PreviousDeploymentGeneration/current DeploymentGeneration, FencedWorkersEvidenceSha256 and RestoreEvidenceSha256. It performs only the recorded generation CAS/admission and exits before HTTP/workers start. Remove maintenance mode before normal startup; old workers/plans remain fenced and require fresh previews/current approval.

Version/catalog/activation commits persist immutable operation-bound receipts atomically with metadata. Lost acknowledgement remains ExecutionUnknown. Explicit recover/reconcile checks exact material, current original authority, generation and positive receipt inside the same guarded operation CAS transaction. Without that proof it cannot claim success or redispatch. Database restore, policy changes and authority revocation cannot be hidden by a stale receipt read. External broker effects continue to use their existing reconciliation protocol; no generic rollback is introduced.
