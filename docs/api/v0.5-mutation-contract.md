# v0.5 Mutation API Contract Principles

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **RFC:** RFC-0005

This document defines the shape and invariants for the v0.5 HTTP/OpenAPI mutation contract. Exact OpenAPI schemas are produced during W39 after domain contracts are admitted.

## Resource model

Kafdeck exposes a first-class **mutation operation** resource.

Conceptual endpoints:

```text
POST /api/v1/clusters/{clusterId}/mutation-operations/previews
GET  /api/v1/mutation-operations/{operationId}
POST /api/v1/mutation-operations/{operationId}/confirm
POST /api/v1/mutation-operations/{operationId}/approve
POST /api/v1/mutation-operations/{operationId}/reject
POST /api/v1/mutation-operations/{operationId}/cancel
```

These are not generic provider-command endpoints.

## Preview request

Preview creation requires:
- `Idempotency-Key` header,
- typed discriminated `operationKind`,
- operation-kind-specific body,
- anti-CSRF evidence for session-cookie callers.

Admitted operation kinds are an explicit closed set. Unknown kinds fail validation.

No request may provide:
- arbitrary provider URL,
- arbitrary HTTP method/path,
- arbitrary Kafka AdminClient command,
- client-chosen risk class,
- client-chosen authorization action.

## Preview response

Includes:
- OperationId,
- OperationKind,
- Cluster,
- Explicit targets,
- Safe current/target diff,
- Capability evidence,
- Risk class + reasons,
- Warnings / irreversibility,
- PreviewHash,
- ExpiresAtUtc,
- Confirmation requirement,
- Approval requirement,
- Verification expectation.

Sensitive fields are redacted/represented by change indicators/digests.

## Confirmation

Confirmation body includes:
- PreviewHash,
- server-issued confirmation challenge where required,
- ephemeral execution material only for operation kinds designed not to persist it.

The server:
- checks actor,
- checks state/expiry,
- rechecks hash,
- revalidates ephemeral material digest,
- applies the required state transition.

HIGH/CRITICAL typed challenge should include a human-recognizable canonical target such as topic/group/connector, but the server never trusts the challenge string as resource identity.

## Approval

Approval:
- requires a distinct canonical principal when independent approval is required,
- references only OperationId + PreviewHash,
- cannot carry a changed mutation body,
- rechecks approver authorization,
- records actor/time/policy evidence.

Self-approval returns a stable conflict/forbidden problem.

## Execution

There is no public privileged “execute this arbitrary body now” route.

When required confirmation/approval is complete, the operation becomes `Ready`. The mutation executor owns dispatch according to the durable state machine.

Operation kinds with intentionally non-persistent execution material may complete dispatch during the validated confirmation/finalization request; they still use the same operation-state transitions and audit boundary.

## Status response

Status is pollable and may include:
- current operation state,
- safe per-target results,
- dispatch/verification timestamps,
- stable outcome code,
- retry/re-preview guidance,
- safe provider evidence.

It never includes raw provider responses, credentials or record payloads.

## Error contract

Use RFC 9457 Problem Details with stable extension code.

Initial codes include:
- `mutation.authorization_denied`
- `mutation.capability_unsupported`
- `mutation.validation_failed`
- `mutation.idempotency_conflict`
- `mutation.preview_stale`
- `mutation.preview_expired`
- `mutation.confirmation_required`
- `mutation.approval_required`
- `mutation.self_approval_forbidden`
- `mutation.approval_expired`
- `mutation.conflict`
- `mutation.failed_before_dispatch`
- `mutation.upstream_rejected`
- `mutation.execution_unknown`
- `mutation.partially_applied`
- `mutation.applied_unverified`

A 5xx response does not by itself mean “not applied”; operation status is authoritative once an OperationId exists.

## Idempotency semantics

`Idempotency-Key` is required for preview creation.

If a network retry repeats preview creation:
- same scoped key + same canonical intent -> same OperationId/current representation,
- same scoped key + different intent -> 409.

Confirmation/approval transitions are also safe to retry against the same operation/state; incompatible repeated transitions return the current state rather than re-dispatching.

## CSRF and browser semantics

For cookie-authenticated sessions:
- unsafe methods require anti-forgery token validation,
- CORS/origin policy is not treated as a substitute for CSRF defense.

GET endpoints never cause mutation.

## Caching

Mutation responses are non-cacheable by shared intermediaries. Preview/status responses use appropriate `Cache-Control: no-store` semantics where sensitive operational metadata could be exposed.

## OpenAPI

W39 OpenAPI must:
- use explicit discriminated intent schemas,
- document permissions/risk/status codes,
- document Idempotency-Key,
- model OperationId/status resources,
- not expose raw provider DTOs,
- include examples for stale preview, approval-required and execution-unknown states.
