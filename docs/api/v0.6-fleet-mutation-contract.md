# v0.6 API / OpenAPI Contract — Fleet Operations

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Authority:** Issue #145 / RFC-0006
- **Tracker:** Issue #146

## Contract principles

v0.6 extends the existing typed mutation-operation API. It does not add direct provider-execution endpoints.

- Mutation creation/confirmation/approval/cancel are non-GET methods.
- Every mutation intent is a discriminated typed schema.
- `Idempotency-Key` remains mandatory when creating a mutation workflow.
- Preview/confirmation is server-owned and bound to `OperationId` + preview hash.
- Cookie/session authenticated writes require anti-CSRF protection.
- Errors use RFC 9457 Problem Details plus stable Kafdeck machine-readable codes.
- Long-running status/progress is read-only evidence; reading status never triggers dispatch.
- Provider SDK request/response types are not public API contracts.
- No endpoint accepts arbitrary provider URL, HTTP method, Kafka AdminClient request type, CLI string or opaque execution blob.

## Resource shape

The existing mutation-operation resource remains authoritative. v0.6 may add safe progress fields/resources:

```text
Operation
  id
  kind
  state
  risk
  preview
  approvalRequirement
  result
  progress? -> typed summary / paged target evidence
```

Progress is bounded, safe and secret/payload-free.

## Typed intent families

OpenAPI must use explicit discriminators for admitted kinds, for example:

- ACL create/delete,
- SCRAM create/rotate/delete,
- quota alter,
- dynamic cluster config alter,
- preferred leader election,
- partition reassignment,
- replication-factor change,
- reassignment throttle,
- broker maintenance/decommission,
- log-directory maintenance,
- cross-cluster transfer,
- replication integration mutation.

Implementation may split operation kinds further when needed for safer risk/verification semantics; it may not collapse them into a generic admin command.

## Preview requirements

Common preview fields include:
- operation identity/kind,
- exact cluster(s),
- materialized target resources,
- current-state/precondition summary,
- requested target state,
- risk class/reasons,
- capability evidence,
- irreversibility/partiality warning,
- approval requirement,
- expiry,
- preview hash.

Operation-specific preview:
- ACL: principal/host/resource-pattern/operation/permission and broad-grant warning,
- SCRAM: principal/mechanism only; never secret,
- quota/config: current -> requested value, source/mutability/sensitivity,
- reassignment: current -> target replicas, RF delta, leader/ISR evidence, estimate provenance,
- maintenance: broker/logdir, affected replicas, evacuation plan and blocking preconditions,
- transfer: source/destination mappings, budgets, source masking/export policy and destination behavior,
- replication integration: explicit topology/profile changes and provider evidence.

## Secret-bearing requests

SCRAM execution accepts secret material only in an execution/finalization request over the authenticated channel. The API:
- never returns the secret,
- binds it to the admitted preview using a digest,
- rejects digest mismatch,
- does not place it in Problem Details or audit/log DTOs,
- requires resubmission when execution occurs after an approval delay.

## Long-running status/progress

Status requests are bounded and may expose:
- phase,
- completed/remaining counts,
- safe per-target status page,
- latest evidence time,
- next poll/reconciliation hint,
- terminal/ambiguous result.

The server controls execution and polling. A client cannot force a provider re-dispatch through status refresh.

## Cancellation

Cancellation is typed. It is allowed only:
- before irreversible dispatch, or
- when the specific provider operation exposes a tested safe cancellation primitive.

If a cancellation request cannot prove non-application, Kafdeck preserves the operation's actual/ambiguous state instead of reporting cancellation as though the provider action never occurred.

## Stable problem codes

v0.6 should extend existing error taxonomy with typed codes such as:
- `capability_unsupported`,
- `authorization_denied`,
- `validation_failed`,
- `risk_policy_rejected`,
- `stale_preview`,
- `approval_required`,
- `approval_expired`,
- `conflict`,
- `unsafe_replication_factor`,
- `maintenance_precondition_failed`,
- `transfer_budget_exceeded`,
- `execution_unknown`,
- `partially_applied`,
- `verification_inconclusive`.

Codes must be stable; provider-native message text is diagnostic only and secret-safe.

## Direct-route authorization

UI hiding is not an authorization control. Every v0.6 API route independently enforces the action/resource conjunction described in the v0.6 authorization/risk matrix.

## OpenAPI and UI parity

Each admitted operator UI mutation has a versioned OpenAPI contract using the same application service/state machine. There is no UI-only privileged provider call. CLI/Terraform/MCP remain out of v0.6 publication scope unless separately approved in a later phase.

## Compatibility behavior

When a provider capability is absent/partial, API capability discovery indicates that state and mutation creation fails closed with a stable problem code. Configuring a cluster/provider URL does not imply write compatibility.
