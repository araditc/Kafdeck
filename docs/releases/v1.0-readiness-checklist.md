## Scope and existing evidence

The scope is stabilization of delivered v0.9 capabilities against the [Roadmap v1.0 criteria](../../ROADMAP.md#v10--stable-release). [Current availability](../product/current-capabilities.md) and existing provider/topology limits remain authoritative. Gateway, public runtime plugins, indexed historical search, blanket provider/CNI support, automatic multi-application Helm HA and unrelated features are excluded. A newly discovered blocker is triaged against these gates, not silently added as a new subsystem.

[Baseline evidence](../implementation/evidence/v1.0-readiness-baseline-20261113.json) records equality of the complete `src` tree and 103 default-build inputs with released v0.9. All ten existing main workflow runs succeeded. [Final v0.9 admission](../implementation/evidence/v0.9-release-published-20261112.json), W78 review, W79 observations, W80 recovery, W81 signed platforms and W82's 136 measured bounds are reused with their original source, hardware and limitations. This is source/build identity comparison, not a new runtime test or v1.0 acceptance.

## Small execution sequence

1. **Contracts and highest-priority gaps:** record the compatibility/support decisions and close G01-G04 in focused PRs. Existing accepted Kafka operation families are retained.
2. **Integrated operator stabilization:** close G05/G06, prove the new upgrade path and measure existing UI flows. Optimize only measured violations; retain 30-minute in-memory Kafka credential semantics unless a separate reviewed change admits otherwise.
3. **One RC and delivery:** prepare final artifacts, perform changed-input/upgrade/verification checks, assemble reused plus new evidence, complete normal review and exact owner release decisions.

Policies can be drafted while code fixes proceed; candidate-media checks depend on the selected RC. Each gate has a finite exit, not an indefinite request to collect more evidence. Existing 0.9 success is not reported as a new 1.0 pass. Findings in the [code-gap audit](../implementation/v1.0-code-gap-audit.md) are open work, not fixes included by this planning PR.

## Test and reuse rules

- This planning/audit package runs no product, load/soak, recovery or distribution acceptance again. Documentation/JSON/link/identity checks and automatic required PR CI are sufficient for this package.
- Reuse the exact signed v0.9 records and observed support limits. The accepted two-hour W82 runs are not repeated just for a version label or document edit.
- Before reusing performance acceptance after a code/build-input change, check the existing build/source identity gate. A differing identity needs an explicit reviewed comparability decision or new evidence scoped to the affected behavior; do not relax the verifier or assume all changes are equivalent.
- New user-creation failure cases, managed-route regression and v0.9 -> v1.0 upgrades are genuinely new evidence. A historical v0.8 -> v0.9 pass cannot close them.
- No critical-path auth, masking, audit, idempotency, policy or recovery control is disabled to make acceptance pass. Unsupported features remain explicit and do not become blanket v1.0 promises.

## Definition of release readiness

Every gate must be closed against the exact candidate or admitted reusable evidence; completion of V1-2 does not close the remaining gates. A real blocker is a failed required condition with a reproducible cause or missing mandatory decision. Proposed optimizations, untested provider expansion and unrelated dependency churn do not automatically enlarge scope. Dates and effort are assessed after the first focused fix/upgrade results; the checklist does not manufacture a release ETA.
