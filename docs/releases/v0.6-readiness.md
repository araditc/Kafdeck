# Kafdeck v0.6 Release Readiness

Status: **RELEASE CANDIDATE — OWNER AUTHORIZED FOR PUBLICATION**

Authority: #145 and #176. Governing tracker: #146.

## Release decision

The owner explicitly authorized completion of the v0.6 workstream and publication of v0.6 as the active Kafdeck release. Readiness is capability-driven: a feature may close with an explicit `Unsupported` or `Blocked` disposition when the pinned provider client or the admitted production boundary cannot safely implement it. Such a disposition must never be presented as delivered mutation support.

## Pinned-client evidence

Repository compile probes against Confluent.Kafka 2.15.1 establish:

Available typed primitives:
- ACL describe/create/delete;
- SCRAM describe/alter;
- configuration describe/incremental alter;
- preferred leader election.

Unavailable typed primitives:
- `DescribeClientQuotasAsync`;
- `AlterClientQuotasAsync`;
- `AlterPartitionReassignmentsAsync`;
- `ListPartitionReassignmentsAsync`.

No CLI, provider REST, reflection, raw-protocol, native escape hatch, or runtime sidecar is authorized to hide these gaps.

## Security boundary

- Local web access mode remains loopback-only.
- Remote/wildcard web binding requires Token or OIDC mode.
- Non-loopback OIDC requires HTTPS.
- Existing operator RBAC remains authoritative for OIDC requests.
- Existing antiforgery controls remain mandatory for state-changing browser routes.
- Fleet capability reporting is read-only.
- No generic provider command, AdminClient proxy, shell route, or obligation-clear route is introduced.
- Unknown or ambiguous external effects retain no-replay/uncertainty semantics.
- Raw SCRAM secrets and raw transfer record payloads are not durably staged by the fleet progress layer.

## Persistence and recovery

v0.6 retains the existing mutation persistence providers and W41 durable fleet extensions. Upgrade validation must preserve:

- optimistic version fencing;
- execution leases and cluster slots;
- sticky conflict obligations;
- no redispatch after a durable dispatch marker when external application is ambiguous;
- SQLite and PostgreSQL upgrade/recovery behavior covered by the existing persistence suite.

Rollback to an older binary must not be used to bypass unresolved v0.6 obligations or to reinterpret blocked fleet capabilities as safe operations.

## Deployment compatibility

Remote web binding is backward compatible:
- legacy `ListenUrl` is accepted;
- preferred `ListenUrls[]` supports multiple endpoints;
- default configuration remains `http://127.0.0.1:8080`;
- wildcard binding is allowed only after non-local access-mode validation.

The Tabler frontend is package-managed and bundled. No CDN is required at runtime.

## Compatibility matrix

Release validation retains Kafka 4.3.1, 4.2.1, 4.1.2, and 3.9.2. Capability reporting is authoritative over blanket version assumptions.

## Required exact-head publication evidence

The final release PR must complete all applicable checks on its exact source head:

- quality-gate;
- dependency-review;
- CodeQL C# and JavaScript/TypeScript;
- release-supply-chain;
- Kafka smoke/compatibility where triggered;
- v0.3/v0.4 regression benchmarks;
- v0.5 persistence where triggered;
- publish-release preflight/quality/compatibility/evidence jobs triggered by the v0.6 release manifest.

The protected-main publication run must then verify:
- immutable `v0.6` source tag;
- GitHub Release on the exact source SHA;
- GHCR image digest promoted to the v0.6 tag;
- SPDX SBOM and vulnerability-scan evidence;
- keyless signature/provenance steps successful.

## Stop conditions

Do not publish if any required exact-head gate fails, a High/Critical vulnerability blocks the release workflow, the compatibility matrix fails, CODEOWNER approval is stale/missing, or the release tag/version is already owned by a different SHA.
