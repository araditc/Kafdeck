## Assemble verified evidence

Inside PowerShell7, use the exact post-merge main SHA and successful run IDs from that SHA:

```powershell
& ./scripts/release/assemble-v08-readiness.ps1 `
  -SourceSha FULL_MAIN_SHA `
  -RunId $verifiedRunIds `
  -Mode Main -OutputDirectory artifacts/v08-readiness-MAIN_SHA
```

Set `$verifiedRunIds` to a PowerShell array of numeric IDs for the complete quality, CodeQL, live, identity, upgrade, Kafka, supply-chain and benchmark run set. Use a fresh directory: previous
downloads are never silently overwritten. The script uses read-only GitHub
queries and downloads; it never tags, changes release identity, pushes a registry,
deploys or sends notifications. It rejects a run from another SHA, PR evidence in
Main mode, failed/incomplete runs, missing expected jobs, missing physical-provider
proof, absent exact-build SBOM/provenance and selected TRX with failures/skips.
The required matrix is versioned in `scripts/release/v08-required-gates.json`.
Do not remove a gate simply to get an empty missing list.

The output `v0.8-readiness-packet.json` records source SHA, GitHub run/job links,
GitHub-reported artifact digests, hashes of downloaded safe files and TRX counters.
Reported archive digests are not claimed independently verified: extracted-file
SHA256 values are separately computed. Candidate mode can aid PR review, but
cannot substitute for the final Main packet. Overlapping test totals are not added.

The exact-build `candidate-provenance.json` must contain `sourceSha`, a nonempty
`imageId`, `published: false`, `sbomSha256` and `imageArchiveSha256`. The collector
checks those hashes against the downloaded SPDX and offline image archive from
the same run. It describes the nonpublished candidate build;
it is not a keyless signature or SLSA attestation. The SPDX SBOM, scan and offline
image test must refer to the same candidate. The G6 publishing workflow retains
its separate provenance/signature obligations.

## Verified G6 workflow and future execution requirements

Candidate v0.8 identity/package versions are prepared before the final Main packet.
The manifest's `publishedBaselineVersion` is historical context; it does not assert
registry state. PR/main pushes run validation and cannot publish. Publication uses
`workflow_dispatch` on current main with exact `source_sha`, completed `run_ids`,
owner-reviewed `archive_sha256` and `owner_approval` text `PUBLISH v0.8 FROM SHA`.
Both original and triggering actors must belong to the protected
`.github/release/release-owners.json` allowlist, which must match CODEOWNERS.
A typed phrase or PR approval alone is not owner identity. Nonowner/re-run-owner
mismatches fail before GitHub evidence queries, artifact loads or registry login.

The readonly readiness job verifies the strict Main packet and binds the selected
archive, source SHA, image config ID, SBOM and package bytes. Only the explicitly
gated publication job receives write/OIDC permissions. It loads that same archive;
it never rebuilds against floating base images. The official Skopeo container is
immutable-digest pinned in `.github/release/publication-tooling.json`; its actual
version is recorded. Conversion creates a compressed `dir:` image, verifies the
config ID against the accepted image, and computes the manifest digest before
`--preserve-digests` copy to `docker://ghcr.io/araditc/kafdeck@sha256:DIGEST`.
[The transport supports digest destinations](https://github.com/containers/image/blob/main/docs/containers-transports.5.md)
only when the manifest matches. Registry digest/config are verified afterward.
No candidate/version/sha/latest mutable image tags are created or promoted.
Operators use the immutable digest reported in the Release. Signatures and
attestations bind that digest and are verified under the main workflow identity.

A readonly CI job exercises the pinned tooling against a LOCAL registry, including
owner rejection before IO, digest/config preservation, no image-tag writes and an
existing foreignv0.8 image tag remaining unchanged. This is transport proof, not
permission to contact external GHCR or publish a Release. The external action
remains gated by the owner's exact decision.

Git sourcev0.8 is created atomically if absent, and an existing different or
ambiguous target is rejected; existing tags are never moved. The GH Release uses
that verified source tag. Five approved Terraform target ZIPs, the MCP nupkg and
their SHA256SUMS are attached from the strict same-SHA packet, without clobbering
existing assets. This does not publish Terraform Registry or NuGet packages.
