# v0.9 CPU/RSS/startup/load budget admission

Status: W82 measured candidate pending review and enforcement. Existing v0.3/v0.4 bounded in-process benchmarks do not define end-to-end production budgets or SLAs.

## Reproducible reference protocol

W82 records exact source/artifact, CPU model/count, RAM, OS/architecture, container/runtime, persistence/broker/identity versions, network topology, storage, limits and runner noise. Use release binaries and isolated fixtures. Run 5 cold starts (process invocation → authenticated ready read), then 5-minute warmup, 15-minute steady load repeated 3 times and a 2-hour soak. Use fixed seed and retain raw per-second process CPU/RSS, container memory/CPU, GC/allocation, request latency/errors and cleanup evidence; report median, p95/p99 and max separately.

Reference datasets: 10 clusters, 1,000 topics, 100 teams, 200 applications, 100 policy rules, 10,000 historical requests and 30 days of one-minute aggregate measurement windows; use bounded pagination for ingestion/reads, never one giant response. Exercise SQLite standalone and PostgreSQL two-node separately. Reference loads: 1/10/50 concurrent clients, 80% scoped catalog/request/attribution reads, 15% validate/explain/preview, 5% submitted governed mutations. Separate real fixture-effect latency from service-only latency. Document achieved throughput, backpressure/429, failures and completeness; do not hide retries or use a mock effect as broker throughput evidence.

Fault/soak runs retain open connections/handles/thread counts, growing queues/database size, cancellation cleanup and post-load idle RSS. Stop and fail safely at configured fixture resource/time limits; no host or production fault injection. Regression jobs use equivalent hardware class or explicitly normalize/rebaseline with review; uncontrolled runner comparisons cannot establish a regression.

## Numerical budget admission and enforcement

After the actual baseline, commit a versioned budget artifact through a reviewed PR before final W82 gating. Required fields per scenario: source/baseline run IDs, hardware class, dataset/load, metric/unit, measured distribution and variation, absolute ceiling, permitted relative regression, error/quality ceiling, repetitions, comparison algorithm and rationale. CPU, steady/peak RSS, cold startup, p95/p99 latency and achieved load/error rate all require finite numeric ceilings; memory slope/cleanup requires explicit finite limits. A schema with null limits, absent scenarios or a baseline marked unmeasured cannot pass readiness.

Ceilings must be justified from measured variation and product constraints, not invented here or automatically relaxed after failure. Regression compares median-of-three steady runs and all cold starts to both absolute and admitted relative ceilings, rejects missing metrics/mandatory skipped runs, and preserves raw outliers for review. Breach blocks readiness until fixed or a separately reviewed justified budget change is admitted. Publish methodology and actual bounded results with limitations; do not present fixture performance as production SLA.

## Executable verification

Run the verifier from a clean checkout of the proposed release source after downloading and extracting both successful provider artifacts. Each directory below contains `run-provenance.json`, `container-samples.csv` and its provider reference directory.

```sh
python3 scripts/ci/check-w82-budget.py \
  --sqlite /evidence/sqlite/w82-evidence \
  --postgres /evidence/postgres/w82-evidence
```

The default gate requires an admitted budget with an explicit review reference, a reviewed per-provider artifact-comparability decision, and complete numeric soak limits. The current candidate remains `requires-review` and the gate fails until those decisions are recorded. Candidate auditing uses the same command with `--candidate-audit`; a passing audit records `releaseAdmission: false`.

The verifier recomputes successful operation counts, the 80/15/5 mix, latency distributions, process and container metrics, soak growth and cleanup from the raw evidence. Every mandatory phase and API node must appear, and GC/allocation/queue telemetry must cover the run. Errors, HTTP 429 responses, missing metrics, non-finite limits and incomplete phases fail verification. It compares all cold starts and each median of three steady repetitions with both the absolute and relative limits. Idle peaks and soak growth ceilings are also enforced.

Each provider must match its recorded CPU, runtime, topology, dataset, API DLL and checkpoint identity. The current checkout's `src` Git tree must match the protected performance source tree and the recorded tree hash. These checks retain the distinct provider binaries and hardware. Auditing the existing runs validates the proposed limits against their baselines. Admission still requires explicit soak CPU/RSS/latency/throughput bounds and the artifact-comparability review described above.

Build identity also binds a canonical sorted snapshot of Git paths, file modes and blobs for root MSBuild, packages, SDK, NuGet, solution and response files, `build/**`, `.config/**`, Dockerfile, `.dockerignore` and `.gitattributes`. Newly added, deleted, modified, dirty, untracked or ignored matching inputs affect verification. A default build must match the measured snapshot or an exact equivalent snapshot with an explicit rationale and review reference. The native-only targets and RID locks require such a recorded equivalence; their paths receive no general exemption. `KafdeckNativeRid` must be unset. `--repository PATH` selects the checkout whose source and build inputs are verified.

`python3 -B -m unittest discover -s scripts/ci -p test_w82_budget.py -v` exercises the verifier's failure cases in the quality gate. It uses small fixtures and the checked-in candidate.
