# v0.3 Benchmark Methodology — Safe Data Explorer

- **Status:** W24 release-evidence methodology
- **Target:** v0.3

## 1. Principle

Kafdeck publishes measured evidence, not unqualified throughput claims.

The v0.3 benchmark workflow intentionally measures bounded in-process processing paths separately from Kafka compatibility/integration workflows. Results must not be presented as Kafka end-to-end throughput, cluster capacity, or a public SLA.

## 2. Exact-source rule

Benchmark results are valid only for the exact source SHA executed by `.github/workflows/v03-benchmark.yml`.

Any source change requires a new benchmark run before the result can be used in the release-readiness record.

## 3. Environment captured by the harness

Each benchmark output line records:

- scenario,
- measured operation count,
- elapsed milliseconds,
- derived operations/second,
- .NET runtime version,
- visible processor count.

The GitHub Actions run supplies the operating-system/runner image and SDK setup in its immutable workflow log.

## 4. Workloads

### Structured filter evaluation

The filter benchmark:

- compiles a deterministic CEL subset expression once,
- uses a small representative structured JSON value,
- performs a warm-up phase,
- runs 20,000 measured evaluations,
- verifies every evaluation matches the expected result,
- records elapsed time and derived operations/second.

The scenario measures the compiled in-memory filter evaluator. It excludes Kafka network fetch, Schema Registry access, HTTP serialization and browser rendering.

### Structured server-side masking

The masking benchmark:

- compiles one immutable masking policy,
- uses a representative structured record with key/header/value,
- masks the key and one nested structured field,
- performs a warm-up phase,
- runs 20,000 measured projections,
- verifies every projection remains structured and masked,
- records elapsed time and derived operations/second.

This scenario includes the v0.3 structured masking/projection work performed by `RecordMaskingService`; it excludes Kafka network fetch and external export destination I/O.

## 5. Warm-up and iteration counts

Current evidence harness:

- warm-up: 1,000 operations per scenario,
- measured: 20,000 operations per scenario.

These counts are intended to produce a stable enough release comparison without extending CI into a load-testing system.

Changing iteration counts or scenario shape changes the benchmark definition and must be recorded in the release evidence rather than compared blindly with older output.

## 6. No hard CI threshold

The workflow deliberately has no operations/second pass/fail threshold.

Reasons:

- hosted CI hardware varies,
- noisy-neighbor effects are outside Kafdeck control,
- early release evidence should identify regressions without fabricating a hardware-independent SLA.

Correctness assertions remain mandatory. A benchmark test fails if the processing result is wrong or the scenario does not complete.

A future performance-regression gate may introduce calibrated thresholds only after a stable runner profile and sufficient historical baseline exist.

## 7. Kafka integration/load evidence

The microbenchmark is complemented by:

- `kafka-smoke`,
- `kafka-compatibility`,
- bounded real-Kafka record-read integration tests,
- cancellation/bulkhead/budget tests,
- Schema Registry adapter/decoder tests.

The accepted Kafka matrix is:

- 4.3.1 Tier 1,
- 4.2.1 Tier 1,
- 4.1.2 Tier 1,
- 3.9.2 Tier 2.

A compatibility success demonstrates supported behavior on the test matrix; it is not a maximum throughput measurement.

## 8. How to reproduce

From the exact source revision:

```bash
dotnet restore Kafdeck.slnx --locked-mode

dotnet test tests/Kafdeck.Architecture.Tests/Kafdeck.Architecture.Tests.csproj \
  --configuration Release \
  --no-restore \
  --filter 'FullyQualifiedName~V03BenchmarkEvidenceTests' \
  --logger 'console;verbosity=detailed'
```

Look for output lines beginning with:

```text
V03_BENCHMARK
```

The authoritative release result is the output from the final exact-head GitHub Actions run, whose run ID is recorded in `docs/releases/v0.3-readiness.md`.

## 9. Result interpretation

Derived `ops_per_sec` is meaningful only for the named scenario on the recorded environment.

Do not translate it into claims such as:

- messages/second searchable in a production Kafka cluster,
- maximum concurrent users,
- universal memory footprint,
- network throughput,
- end-to-end tail latency.

Those claims require separate representative workload design and measured deployment evidence.

## 10. Release use

W24 is considered to have performance evidence when:

1. the benchmark workflow succeeds on the final exact head,
2. both scenario result lines are captured from the workflow log,
3. the exact SHA, run ID and measured values are copied into the v0.3 readiness record,
4. no unsupported public performance claim is derived from the measurements.
