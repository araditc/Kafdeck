# v0.6 Test Strategy — Fleet Operations, Broker Maintenance & Kafka Security

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Authority:** Issue #145 / RFC-0006
- **Tracker:** Issue #146

## Objective

Prove that v0.6 security/maintenance mutations remain governed, capability-correct, recoverable and bounded under real Kafka behavior, process failure and ambiguous provider outcomes. Test evidence must demonstrate safety; mock-only happy-path coverage is insufficient for release readiness.

## Test layers

### Domain and architecture tests

Required:
- every v0.6 `MutationOperationKind` maps to exactly one explicit authorization action,
- unknown operation kind fails closed,
- every mutation kind has a built-in server-owned risk floor,
- policy cannot lower the floor,
- CRITICAL requires an independent eligible approver,
- canonical plan hashing is deterministic,
- changed cluster/target/current-state evidence invalidates confirmation/approval,
- no HTTP/API handler can call provider clients directly,
- provider ports remain typed and do not expose arbitrary method/path/body execution,
- durable DTOs contain no SCRAM plaintext/password or raw transfer record payload fields.

### Persistence/concurrency tests

Run against SQLite standalone semantics and PostgreSQL HA semantics where applicable:
- unique idempotency binding,
- optimistic operation versioning,
- execution claim CAS,
- resource claim ordering/conflict,
- long-running progress optimistic versioning,
- progress update rejected for stale fencing generation,
- lease renewal/expiry/takeover,
- process crash before dispatch,
- process crash after possible dispatch,
- takeover performs observation/reconciliation before further dispatch,
- migration forward/restart behavior.

### Authorization/risk matrix tests

Negative tests are mandatory for every action. Cross-cluster transfer must prove conjunctive authorization:
- transfer permission without source `record.read` => denied,
- data leaving source boundary without `record.export` => denied,
- source rights without destination `record.produce` => denied,
- destination rights without transfer permission => denied,
- broad ACL grant => CRITICAL,
- SCRAM mutation => CRITICAL,
- RF reduction => CRITICAL,
- decommission => CRITICAL.

### Secret and leakage tests

Inject sentinel secrets/payloads and assert absence from:
- persisted operation state,
- progress/checkpoint store,
- HTTP responses after submission,
- Problem Details,
- audit records,
- structured logs,
- traces/metrics labels,
- exception messages,
- test artifacts/snapshots.

### Real Kafka integration tests

At minimum the release compatibility matrix must exercise supported Apache Kafka lines already governed by the repository plus any version explicitly required for Kafka 4.x maintenance primitives.

Evidence should cover where supported:
- ACL create/list/delete and wildcard risk cases,
- SCRAM create/alter/delete using write-only material,
- client quota read/alter/readback,
- dynamic config capability detection and mutation/readback,
- preferred leader election,
- reassignment planning/execution/progress/readback,
- replication-factor increase and guarded reduction,
- throttle application/removal,
- broker/log-directory evacuation or explicit capability-unavailable behavior,
- partial target failure,
- controller/broker connection interruption during dispatch/progress.

A provider/version with incomplete semantics must be reported as unsupported/partial rather than passing via mocks.

### Long-running fault injection

Required scenarios:
- kill worker after durable dispatch marker before provider response,
- kill worker during progress polling,
- expire lease while another worker attempts takeover,
- stale worker attempts checkpoint update after takeover,
- provider reports in-progress then becomes unreachable,
- provider accepted plan but final verification is temporarily unavailable,
- one target fails while others complete,
- state drifts after preview but before dispatch,
- provider capability changes/disappears between preview and execution.

Expected behavior must preserve `ExecutionUnknown`, `PartiallyApplied`, `AppliedUnverified` and `StalePreview` accurately.

## ACL/SCRAM/quota/config tests

ACL:
- exact/prefixed/literal/wildcard resource patterns as supported,
- principal/host normalization,
- broad grant escalation,
- delete preview materialization,
- access analysis confidence/provenance.

SCRAM:
- mechanism capability discovery,
- create/rotate/delete,
- no credential retrieval,
- secret resubmission/digest mismatch rejection,
- no blind retry after possible dispatch.

Quota/config:
- entity/key allowlists,
- unsupported/static key rejection,
- current-value fingerprint drift,
- risk escalation for sensitive keys,
- verification readback.

## Reassignment and maintenance tests

- deterministic plan canonicalization,
- invalid broker/partition target rejection,
- unavailable target broker rejection,
- minimum RF guardrail,
- target-count blast-radius escalation,
- placement/skew computation determinism,
- measured/derived/unknown estimate labels,
- progress monotonicity where provider evidence supports it,
- evacuation must enumerate all affected replicas,
- decommission cannot finalize until required evacuation preconditions pass,
- stale plan detection after out-of-band reassignment.

## Cross-cluster transfer/replication tests

- explicit source/destination identity binding,
- topic mapping materialization,
- rate/byte/time/concurrency ceiling enforcement,
- checkpoint restart without payload persistence,
- source masking/export policy enforcement,
- destination produce authorization,
- timeout/partial destination acknowledgement semantics,
- no unrestricted wildcard copy,
- MirrorMaker/provider adapter routes fixed and capability-gated,
- provider redirect/origin/deadline protections where HTTP control-plane adapters are used.

## Load and isolation evidence

Publish repeatable evidence for:
- planning target limits,
- concurrent long-running operation limit per cluster,
- poll cadence/backoff,
- progress row/cardinality bounds,
- reassignment status polling under cluster load,
- transfer rate/byte ceilings,
- proof that long-running polling cannot starve metadata/read views.

No fixed performance marketing claim is accepted without repeatable measurement.

## CI admission gates

Planning PR:
- documentation/link/lint/quality checks applicable to the repository,
- no executable v0.6 mutation surface.

Implementation workstreams:
- exact-head quality gate,
- applicable dependency/CodeQL/security checks,
- targeted unit/architecture tests,
- real Kafka/provider fixtures for changed capability,
- fault/recovery tests for long-running semantics where relevant,
- fresh CODEOWNER approval after head changes.

Final v0.6 readiness requires a reconciled compatibility matrix and a release-readiness evidence record. Tag/release/publication remains separately owner-approved.
