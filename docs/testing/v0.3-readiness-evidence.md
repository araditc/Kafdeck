## 1. Evidence rule

A v0.3 release-readiness claim is valid only for the exact source head on which the required checks ran. Any source-head change invalidates prior exact-head readiness evidence and requires fresh applicable checks.

Because an in-repository document cannot name its own final commit SHA without creating a new commit, this document identifies the authoritative evidence sources rather than embedding self-invalidating final IDs. The stabilized exact source SHA, workflow run IDs, benchmark values and readiness verdict are recorded in governed Issue #88 and PR #92 after the source stops changing.

## 4. Schema Registry evidence

v0.3 does not require an external public registry in CI. Controlled integration fixtures exercise the read-only adapter and decoders.

Required outcomes:

- Avro success/failure paths,
- Protobuf success/failure paths,
- JSON Schema success/failure paths,
- schema references where required,
- authorization failure,
- unavailable/timeout behavior,
- malformed/incompatible schema response,
- no registry secret in returned errors or audit/log projections.

## 5. Cross-cluster isolation evidence

Release evidence must demonstrate:

- Kafdeck deny avoids record I/O where practical,
- an identity authorized for Cluster A cannot read/export Cluster B,
- cluster/topic scopes are applied to the exact record target,
- one slow record-read cluster does not consume all record-read capacity,
- metadata browsing remains isolated from record-read pressure.

## 6. Leakage suite

Sentinel cleartext values are used in security tests and must remain absent from:

- unauthorized responses,
- Problem Details,
- security audit events,
- application logs exercised by tests,
- trace/metric label projections covered by the architecture contract,
- fully-redacted masking results,
- exports when policy requires redaction.

The safe projection may intentionally contain an allowed/unmasked value; the test concern is that a value designated secret by the active scenario does not escape through an alternate path.

## 9. Performance evidence

Performance/resource claims are evidence-based. W24 records:

- benchmark environment/toolchain,
- workload shape and budgets,
- operation counts/bytes,
- elapsed time / derived rate for bounded in-memory processing scenarios,
- integration workflow durations where relevant,
- limitations of the measurement.

No W24 microbenchmark is represented as universal Kafka-cluster throughput or a public SLA.
