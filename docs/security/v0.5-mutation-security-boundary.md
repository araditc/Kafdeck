# v0.5 Mutation Security Boundary

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **RFC:** RFC-0005
- **Scope authority:** Issue #121

## New trust boundary

v0.5 crosses from observation to controlled mutation. This creates a privileged external-effects boundary across:
- Kafka Admin APIs,
- Kafka producer APIs,
- consumer-group administration,
- Schema Registry write APIs,
- Kafka Connect write/control APIs,
- DeleteRecords.

Existing v0.2 identity/RBAC and v0.3 payload/masking boundaries remain authoritative. v0.4 provider-origin/secret-redaction rules also remain authoritative.

## Security invariants

- default deny for every mutation action,
- no read action implies mutation authority,
- no broad `admin` action bypasses typed permissions,
- risk floor is server-controlled,
- preview is immutable and bound to operation identity,
- confirmation/approval is bound to the exact preview,
- CRITICAL actions require an independent principal,
- durable mutation state is mandatory,
- mutation state changes use transactional compare-and-set semantics,
- execution is single-claim and idempotency-aware,
- no blind retry after potentially successful external dispatch,
- resource drift is revalidated before dispatch,
- external capability is proven before mutation,
- no generic Kafka/provider command proxy,
- no secret/payload leakage through API/log/audit/telemetry,
- destructive wildcard patterns are materialized to explicit finite targets before confirmation,
- unknown/partial outcomes are represented truthfully,
- audit evidence cannot be modified through mutation APIs.

## Threat: privilege escalation / confused deputy

Controls:
- per-operation authorization action,
- cluster/resource-pattern scope,
- authorization checked at preview and again before dispatch,
- target resources derived server-side from typed intent,
- no client-controlled risk lowering,
- no provider credential exposure to the caller.

## Threat: CSRF against authenticated operators

Controls:
- mutation is never performed through GET,
- OIDC/session cookie mutation endpoints require ASP.NET anti-forgery protection,
- same-site cookie policy remains enforced,
- unsafe cross-origin mutation requests fail before operation creation.

Token/local modes remain subject to their existing authentication boundary and do not bypass authorization/state checks.

## Threat: stale-preview / TOCTOU

Controls:
- preview stores relevant observed resource fingerprints,
- confirmation binds preview hash,
- executor re-observes material preconditions immediately before dispatch,
- material drift yields `StalePreview`,
- provider capability is rechecked.

## Threat: confirmation replay

Controls:
- confirmation references operation ID + preview hash,
- operation/preview expiry,
- state transition accepts confirmation once,
- actor identity is recorded,
- changed preview invalidates confirmation,
- approval evidence is scoped to exactly one operation.

## Threat: same-actor approval laundering

Controls:
- CRITICAL operations require distinct requester and approver principal IDs,
- approver must independently satisfy required authorization,
- server rejects self-approval,
- OIDC issuer+subject identity semantics remain canonical.

Local/deployment-token modes cannot pretend to provide two independent human principals; CRITICAL mutation is disabled there unless a future approved identity mechanism establishes that property.

## Threat: duplicate execution

Controls:
- required Idempotency-Key,
- persisted key-to-operation binding,
- atomic execution claim,
- operation fencing generation,
- resource-conflict claims,
- no automatic post-dispatch retry.

## Threat: ambiguous network outcomes

A timeout can occur after Kafka/provider accepted a mutation.

Controls:
- record `DispatchStartedAt` before external invocation,
- distinguish pre-dispatch failure from possibly-dispatched failure,
- possibly-dispatched timeout becomes `ExecutionUnknown`,
- verification/reconciliation may prove a post-condition,
- no blind retry from `ExecutionUnknown`.

## Threat: destructive wildcard / blast-radius expansion

Controls:
- destructive inputs become explicit finite target sets,
- configured target limits,
- preview lists every target or produces a bounded downloadable/summarized artifact with immutable target digest where UI count is large,
- risk escalates with target count,
- topic delete/purge remain CRITICAL regardless of caller role.

v0.5 does not execute an unbounded wildcard deletion.

## Threat: out-of-band resource mutation

Kafdeck cannot lock Kafka against other administrators.

Controls:
- resource fingerprint/preconditions,
- pre-dispatch revalidation,
- stale-preview rejection,
- post-operation verification,
- audit distinguishes Kafdeck evidence from provider truth.

## Threat: secret leakage

Connector configs and upstream credentials may contain secrets.

Controls:
- known secret-field projection + conservative secret-name heuristics,
- no raw provider-body pass-through,
- no secret values in preview/audit/log/problem details,
- ephemeral secret execution material is digest-bound,
- traces/metrics use safe low-cardinality dimensions.

## Threat: record-payload persistence

Record production introduces user-supplied payload bytes.

Controls:
- raw key/value/header bytes are not persisted in mutation state by default,
- preview stores safe metadata/digests,
- payload is re-submitted for immediate admitted execution and digest-matched,
- payload is never logged/audited/traced,
- bounded record/byte ceilings.

## Threat: provider command escape

Controls:
- Kafdeck-owned typed mutation ports,
- fixed provider routes/methods,
- no arbitrary HTTP method/path/body proxy,
- no arbitrary AdminClient command name/payload,
- supported config keys/capabilities are validated.

## Threat: Kafka Connect SSRF/redirect

v0.4 protections remain:
- configured validated origin only,
- fixed endpoint construction,
- redirect cannot escape origin,
- request/response size deadlines,
- no user-supplied upstream URL.

## Threat: bulk partial application

External providers may not provide transactionality across a bulk set.

Controls:
- preview states atomicity/partial semantics,
- execution records per-target outcomes,
- no “all succeeded” when only a subset is proven,
- compensation is offered only for typed operations with a safe inverse.

## Threat: persistence failure / split brain

Controls:
- mutation mode disabled without writable persistence,
- SQLite mutation mode is single-instance,
- multi-instance mutation mode requires PostgreSQL,
- operation/lock transitions are transactional,
- executor stops dispatch when durable state cannot be updated safely.

## Audit requirements

Each security-relevant transition records:
- actor,
- approver when present,
- operation and preview identity,
- cluster/resource,
- authorization action,
- risk class/reasons,
- state transition,
- conflict/idempotency outcome,
- dispatch classification,
- verification result.

Audit excludes secrets and Kafka payloads.

## Security exit gate

Implementation readiness requires:
- direct-route authorization tests,
- CSRF tests,
- self-approval/replay/expiry tests,
- idempotency race tests,
- stale-preview tests,
- conflict/lock tests,
- ambiguous-timeout tests,
- secret/payload sentinel leakage tests,
- generic-proxy absence tests,
- persistence-failure fail-closed tests,
- v0.2-v0.4 authorization/masking regressions.
