# v0.3 W24 Threat-Model Reconciliation — Safe Data Explorer

- **Status:** W24 readiness evidence
- **RFC:** RFC-0003
- **Scope authority:** Issue #75 / Issue #88
- **Date:** 2026-09-21

## 1. Purpose

This document reconciles the implemented v0.3 record-data surface against the accepted security boundary before the explicit release-decision gate.

It does not create new product scope. It records the concrete controls and residual risks for the implementation delivered through W18-W23.

## 2. Preserved invariants

The implementation must continue to prove all of the following:

- no Kafka mutation,
- no record produce/replay,
- no consumer-group offset commit or mutation,
- no payload persistence/indexing by default,
- no unbounded whole-topic scan,
- no arbitrary server-side JavaScript,
- no general-purpose SQL stream-processing engine,
- metadata permissions never imply `record.read`,
- `record.export` remains separately authorized,
- masking is authoritative on the server and has no v0.3 bypass permission,
- structured masking fails closed when safe decoding cannot be established,
- Schema Registry access is read-only and used only for decoding.

## 3. Threat reconciliation

### Unauthorized payload access

**Threat:** an operator with topic metadata visibility obtains Kafka key/value/header payloads.

**Controls:**

- `record.read` is a distinct authorization action.
- Record endpoints authorize before record I/O in OIDC mode.
- Local/Token operation remains governed by the existing deployment boundary rather than being silently converted into OIDC identity semantics.
- Cluster and topic scopes are evaluated for the exact target.
- Direct-route and authorization tests remain part of the architecture suite.

**Residual risk:** a deployment intentionally operated in legacy Local/Token mode has a coarser human-principal model. The UI and operator documentation must continue to identify that mode accurately.

### Cross-cluster or stale-response leakage

**Threat:** data fetched for one cluster/topic/partition is rendered under another target or reused across authorization contexts.

**Controls:**

- Record payloads are not placed in shared durable caches.
- UI browse requests are cancellable and guarded by active-request identity before state is committed.
- Record queries carry an explicit cluster/topic/partition target.
- Per-cluster record-read isolation is distinct from metadata browsing.

### Masking bypass

**Threat:** raw, hex, API, tail, or export paths expose a value that an active policy requires Kafdeck to redact.

**Controls:**

- All browser/API/export output is derived from the safe projection.
- Mandatory structured masking returns `FullyRedacted` when required structure cannot be established safely.
- Raw/hex presentation is unavailable as a bypass when structured masking is mandatory.
- Header names and JSON-pointer paths preserve exact identity, including significant whitespace.
- Aggregate masking traversal is bounded and fails closed.
- Export accepts the safe projection rather than raw Kafka contracts.

### Parser and schema confusion

**Threat:** malformed framing, malicious schemas, excessive nesting, or registry responses produce unsafe decode behavior or data exposure.

**Controls:**

- Schema Registry is behind a read-only adapter.
- Avro, Protobuf, and JSON Schema decoding return typed outcomes.
- Decode depth/size and cache behavior are bounded.
- Registry failures degrade decode rather than authorization.
- If masking requires structure, decode failure cannot fall back to clear payload projection.

### Filter-expression denial of service or code execution

**Threat:** regex/CEL/jq-style expressions cause unbounded CPU work or escape into host/network/filesystem execution.

**Controls:**

- Filter compilation is deterministic and bounded.
- Invalid or over-budget expressions are rejected as safe client-query errors.
- Regex execution is bounded.
- CEL/jq-style support is a constrained Kafdeck subset; no arbitrary host-code execution is permitted.
- Filter evaluation participates in operation budget accounting and cancellation.

### Oversized records and memory amplification

**Threat:** raw bytes, decoded structures, base64/text projection, or wide masking trees consume excessive memory.

**Controls:**

- Per-record and aggregate raw-byte bounds.
- Aggregate projected-byte bound enforced while constructing `RecordSafePage`.
- Decode structural limits.
- Masking traversal budget.
- Export row/byte/time budgets.
- No payload persistence/indexing by default.

### Kafka scan amplification

**Threat:** a UI request becomes an unbounded or high-fan-out consumer against production Kafka.

**Controls:**

- Explicit topic/partition assignment; no group subscription workflow.
- Explicit anchors and bounded page reconstruction.
- Record count, byte, time, rate, global-concurrency, and per-cluster concurrency budgets.
- Cancellation is propagated through the record-read path.
- Metadata and record-read work use separate isolation boundaries.

### Live-tail resource exhaustion

**Threat:** long-lived or abandoned tails consume Kafka consumers, server memory, or response capacity indefinitely.

**Controls:**

- Server-to-client SSE only for v0.3.
- Bounded tail duration/rate/bytes.
- Disconnect cancellation.
- Admission controls by identity/cluster as defined by the W21 runtime contract.

### Export exfiltration

**Threat:** an operator who may browse data performs an unbounded or differently authorized export.

**Controls:**

- `record.export` is distinct from `record.read`.
- Authorization is evaluated against the exact export target.
- Export consumes only the masked safe projection.
- JSON/NDJSON/CSV exports are bounded by rows, bytes, and duration.
- Export audit metadata reports only the rows/offsets represented by the result.

### Export destination uncertainty

**Threat:** a slow or non-cooperative output stream commits bytes after the deadline while Kafdeck reports a definitive non-commit result.

**Controls:**

- Write invocation is isolated from the request deadline path.
- Outstanding non-cooperative writes are retained in a bounded ownership registry.
- Once a destination write has started, timeout/cancellation/abort settlement remains `Indeterminate` unless completion is known; unchanged stream length or cancellation/disposal exceptions are not treated as proof of non-commit.
- Regression coverage includes late commit, overwrite without length growth, and commit-before-disposal-exception cases.

**Residual risk:** the generic .NET `Stream` abstraction does not provide a universal atomic abort/commit primitive. `Indeterminate` is therefore the correct fail-safe outcome for uncertain destination ownership in v0.3.

### Audit, log, error, and telemetry leakage

**Threat:** record key/value/header/decoded fields or secrets appear in audit events, Problem Details, logs, traces, or metric labels.

**Controls:**

- Successful browse/tail/export paths emit payload-free security-audit events.
- Audit metadata contains actor/access mode, target/range, masking policy/version, budget/filter/export outcome, and bounded counts only.
- Problem Details uses stable safe categories.
- Record-derived values are excluded from default metric labels and tracing payloads.
- Sentinel leakage tests remain release evidence.

### Schema Registry secret leakage

**Threat:** registry credentials are returned to the browser, logs, audit, or error details.

**Controls:**

- Secret references remain server-side.
- Schema Registry adapter output contains schema/decode evidence, not credentials.
- Registry failure is isolated from browser-visible secret material.

## 4. Failure posture

Security ambiguity fails closed. In particular:

- missing or invalid authorization does not downgrade access,
- mandatory masking with unsafe decode does not return clear payload,
- over-budget traversal/projection/export stops work or returns an explicit partial/indeterminate outcome,
- registry failure does not silently disable masking,
- export commit uncertainty is not converted into a definitive success or non-commit claim.

## 5. Residual risks accepted within existing scope

The following are implementation realities rather than new product decisions:

1. Legacy Local/Token mode has coarser operator attribution than OIDC; it remains a compatibility deployment mode.
2. A generic export `Stream` cannot prove transactional abort; uncertain writes remain explicit `Indeterminate` outcomes.
3. Bounded record search is not exhaustive once a budget is exhausted; the API/UI must continue to expose partial-result state.
4. Schema-assisted decoding depends on the configured registry being available and semantically compatible; decode uncertainty never expands access.

None of these residual risks authorizes mutation, unbounded scanning, payload persistence, or masking bypass.

## 6. W24 security exit evidence

W24 readiness requires fresh exact-head evidence for:

- authorization separation and cross-cluster isolation,
- no producer/offset-commit/group-mutation path,
- Kafka compatibility matrix,
- Schema Registry decode/failure integration,
- filter/masking/export budget and cancellation behavior,
- sentinel leakage checks across API/audit/log/error surfaces,
- W22 export-ownership regressions,
- all required review threads resolved.

The explicit v0.3 release decision remains a separate owner gate after this evidence is assembled.
