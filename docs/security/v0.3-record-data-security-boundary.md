# v0.3 Record Data Security Boundary

- **Status:** PROPOSED
- **RFC:** RFC-0003
- **Scope authority:** Issue #75

## New trust boundaries

v0.3 adds:

1. Kafdeck record reader to Kafka record payloads,
2. Kafdeck to optional Schema Registry,
3. clear record bytes to decoded normalized representation,
4. decoded representation to masked safe projection,
5. safe projection to browser/API/export.

Existing OIDC/RBAC, Kafka, secret, audit, and telemetry boundaries remain.

## Core security invariants

- metadata access does not imply payload access,
- `record.read` is explicitly required,
- `record.export` is separately required,
- authorization is checked before record I/O,
- masking is server-side and authoritative,
- no active masking rule has a v0.3 bypass permission,
- clear payload never reaches logs/traces/audit,
- no payload persistence by default,
- no Kafka produce/offset commit/mutation,
- all record work is bounded and cancellable,
- ambiguity fails closed.

## Threats and controls

### Unauthorized payload access

Controls: backend `record.read` enforcement, cluster/topic scope checks, direct-route tests, no UI-only enforcement.

### Cross-tenant/cluster cache leakage

Controls: record payloads are not placed in shared long-lived caches; any bounded decode/schema cache contains no user authorization decision and response projection is re-authorized.

### Masking bypass

Controls: one authoritative projection pipeline; export/UI/API consume only masked projection; raw/hex is disabled where policy requires structured redaction that cannot be safely applied.

### Decode confusion

Controls: explicit content/codec detection, bounded schema lookup, strict parser limits, stable decode-failure categories, no trust in payload-declared executable behavior.

### Regex/expression denial of service

Controls: expression-size limits, deterministic CEL/jq subsets, regex timeout/engine limits, evaluation record/byte/time budgets, cancellation.

### Large payload memory exhaustion

Controls: per-record byte caps, aggregate byte caps, streaming where possible, bounded decode depth/collection/string sizes, no unbounded buffering.

### Scan amplification against Kafka

Controls: explicit partition/range, page limits, byte/time/rate budgets, per-cluster/global concurrency, cancellation, no hidden N+1 fetch pattern.

### Live-tail resource exhaustion

Controls: session/rate/byte/duration caps, server cancellation, disconnect propagation, per-identity/per-cluster admission control.

### Export exfiltration

Controls: separate `record.export`, server-side masking first, explicit export bounds, audit, no background unbounded dump.

### Schema Registry credential/data leakage

Controls: secret references, adapter boundary, no secret projection, bounded cache, no full registry API exposure in v0.3.

### Side-channel leakage through errors/telemetry

Controls: stable safe error categories; no key/value/header/decoded field values in Problem Details, traces, metric labels, or audit.

## Payload handling lifecycle

```text
Kafka bytes
 -> bounded decode
 -> deterministic filter evaluation
 -> masking/redaction
 -> safe projection
 -> response/export
 -> memory released
```

Payload bytes are ephemeral application memory unless a future approved persistence/indexing RFC says otherwise.

## Masking fail-closed rule

When a policy requires a structured field to be masked and Kafdeck cannot establish the required structure safely, Kafdeck does not return clear payload. The response may include non-sensitive metadata and a redacted payload marker.

## Audit requirements

Audit includes actor, target scope, range/budget/result, policy identity/version, export metadata, and correlation identifiers.

Audit excludes record payloads, record keys, header values, decoded fields, secrets, tokens, and cookies.

## Security exit gate

Implementation cannot complete until tests prove:

- direct payload bypass attempts fail,
- masking applies across browse/tail/export,
- raw/hex cannot bypass mandatory masking,
- record filters cannot escape sandbox/budget boundaries,
- no payload leakage through logs/audit/errors,
- cancellation and budgets terminate work,
- no commit/produce/mutation call exists,
- v0.2 authorization/session invariants remain intact.
