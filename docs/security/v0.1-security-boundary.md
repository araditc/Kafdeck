# v0.1 Security Boundary

- **Status:** ACCEPTED
- **RFC:** RFC-0001
- **Gate:** Gate 1 — ACCEPTED

## Trust boundaries

v0.1 has four material boundaries:

1. Browser/user to Kafdeck HTTP endpoint
2. Kafdeck to configured Kafka clusters
3. Kafdeck process to secret sources
4. Kafdeck process to telemetry/log sinks

## Browser-to-Kafdeck access

Full identity/RBAC remains v0.5 scope. v0.1 nevertheless requires a minimum deployment boundary:

- local-only binding is the default,
- remote binding requires token mode,
- no unauthenticated remote mode is supported,
- token values are supplied by secret reference,
- tokens are compared using appropriate constant-time/safe primitives where applicable,
- failed token attempts are rate-limited/bounded,
- tokens are never logged,
- browser storage strategy must minimize token persistence/exposure.

The token represents the deployment boundary, not a human identity.

## Kafka credentials

v0.1 does not persist Kafka passwords/private-key passwords in Kafdeck database state.

Allowed secret sources:

- environment variable reference,
- mounted file/Docker/Kubernetes secret file reference.

Future providers such as Vault/KMS may be added behind a secret-provider port.

## TLS

- Certificate verification is enabled by default.
- Disabling TLS verification is not a normal supported production setting.
- Custom CA files are supported.
- mTLS certificate/private-key paths are supported.
- Key/password material is not exposed through API responses.

## Authorization at Kafka

Kafdeck SHOULD be deployed with a Kafka principal that has only the read permissions required for intended v0.1 capabilities.

A missing ACL is surfaced as a capability/access limitation rather than encouraging broad administrator credentials.

## Sensitive metadata

Kafka metadata can still disclose infrastructure names, broker hosts, topic names and operational state. Therefore v0.1 metadata access is treated as sensitive even though message payloads are absent.

## Logging

Never log:

- runtime access token,
- SASL username/password pair when the username is considered sensitive by operator policy,
- SASL password,
- private key/private key password,
- raw credential-bearing connection strings,
- HTTP Authorization header,
- secret-file contents.

Topic names may appear in application logs only where useful and must not be uncontrolled metric labels.

## Threats and controls

### Credential disclosure

Controls: external secret references, response redaction, structured logging policy, no debug dumps of client configuration.

### Remote unauthenticated access

Controls: loopback default; non-loopback requires token mode.

### SSRF-like cluster targeting

Cluster destinations are operator-defined configuration, not arbitrary user-supplied URLs/endpoints through HTTP APIs.

### Kafka overload

Controls: per-cluster/global bulkheads, snapshot caching, single-flight refresh, deadlines, no per-row configuration fan-out.

### Cross-cluster data confusion

Controls: cluster-scoped client/cache keys and stable configured cluster IDs; tests must verify cache isolation.

### TLS downgrade/misconfiguration

Controls: secure defaults, explicit insecure-protocol warning, configuration validation.

## Security gate for implementation

Gate 1 accepted the v0.1 runtime access boundary. Implementation remains blocked only by the Phase 0 administrative repository controls required by the release/governance process.
