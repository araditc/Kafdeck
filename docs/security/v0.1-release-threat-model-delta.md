# v0.1 Release Threat-Model Delta

- **Baseline:** `docs/security/v0.1-security-boundary.md`
- **Release scope:** Kafdeck v0.1 Cluster Explorer
- **Disposition:** no expansion of the accepted Kafka privilege or mutation boundary

## Purpose

This document records the security-relevant implementation deltas introduced while packaging the accepted v0.1 design for operator use and release. It is a review aid for the v0.1 release gate; it does not replace the accepted Gate 1 security boundary.

## Delta 1 — bundled browser UI with deployment-token mode

The API and React operator UI are shipped in the same OCI image. Static UI assets are reachable without the deployment access-token header so that a browser can bootstrap, while `/api` remains protected by the deployment-token middleware whenever token mode is required.

The browser accepts the deployment token only through the URL fragment `#access_token=...`. URL fragments are not transmitted in HTTP requests. The client removes the fragment from the address bar immediately, stores the token only in `sessionStorage`, and sends it as `X-Kafdeck-Access-Token` on API calls.

### Threats and controls

- **Token leakage through server/access logs:** mitigated by fragment bootstrap; the fragment is not part of the HTTP request.
- **Persistent browser credential exposure:** mitigated by session-only storage; no localStorage/cookie persistence is introduced.
- **Unauthenticated API access through static bootstrap:** static assets are public within the deployment boundary, but all product API routes remain token-protected in token mode.
- **Browser compromise/XSS:** sessionStorage is readable by same-origin script. v0.1 therefore still requires an approved management boundary and trusted operator browser; the deployment token is not a substitute for future human identity/RBAC.
- **Token disclosure by operator handling:** operators must not place tokens in query strings, bookmarks, screenshots, logs, or persistent browser storage.

## Delta 2 — container reachability

The image remains loopback-safe by default at application configuration level. Container deployments that publish the application explicitly bind the process to the container interface and must provide the accepted deployment-token secret reference. The documented Docker example publishes the container port only to host loopback by default.

### Threats and controls

- **Accidental unauthenticated remote exposure:** non-loopback application binding fails closed without the access-token configuration.
- **Network eavesdropping outside the host:** remote exposure must occur only behind an approved TLS-protected management boundary.

## Delta 3 — release supply chain

The tagged release workflow builds and publishes one immutable OCI candidate. SBOM generation and vulnerability scanning target that exact digest, unresolved High/Critical findings remain blocking, and Sigstore/cosign signs the same published digest. NuGet restore in the image build uses locked mode with no unlocked fallback.

### Threats and controls

- **Scan/sign mismatch caused by rebuild drift:** eliminated by scanning and signing the single published digest.
- **Dependency graph drift during image build:** locked restore fails rather than silently re-resolving packages.
- **Known unfixed severe vulnerability escaping the gate:** High/Critical findings remain included and release-blocking.
- **Mutable workflow dependency risk:** third-party actions remain SHA-pinned.

## Unchanged boundaries

The release work does not add Kafka mutation routes, record browsing, direct ZooKeeper connectivity, durable Kafka credential persistence, or broader Kafka privileges. Per-cluster isolation, bounded concurrency, deadlines, stale semantics, TLS validation, and read-only least-privilege Kafka guidance remain unchanged.

## Residual limitations

v0.1 deployment-token mode is a deployment boundary rather than user identity/RBAC. Static UI assets are intentionally bootstrap-accessible inside that boundary. Operators remain responsible for TLS termination, host/network access control, least-privilege Kafka credentials, and protecting browser sessions.

## Release-review requirement

This delta must be reviewed together with the final release-gate PR. Any later security-boundary or authentication change invalidates this review and requires a new threat-model delta assessment.
