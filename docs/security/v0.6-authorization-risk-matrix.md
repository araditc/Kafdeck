# v0.6 Authorization & Risk Matrix

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Authority:** Issue #145 / RFC-0006
- **Tracker:** Issue #146

## Principles

- Every v0.6 operation has an explicit authorization action; no broad `admin` bypass exists.
- Read actions never imply mutation actions.
- Mutation actions never imply record read/export unless explicitly required by the typed workflow.
- Risk is computed server-side. Deployment policy may raise but never lower the built-in floor.
- CRITICAL requires durable approval by a distinct eligible principal.
- Bulk/wildcard inputs are materialized before preview and may escalate risk based on target count/blast radius.

## Authorization evaluation order

1. Authenticate principal.
2. Resolve typed operation kind.
3. Authorize operation-specific action on every materialized target.
4. For composite workflows, authorize all conjunctive permissions.
5. Discover provider capability.
6. Validate intent and current state.
7. Compute built-in risk floor + escalators.
8. Apply deployment policy, which may only raise requirements.
9. Build preview and confirmation/approval requirement.
10. Reauthorize/revalidate before dispatch when policy/current-state rules require it.

A denied target in an operation represented as one atomic intent denies the operation unless the typed operation explicitly defines partial semantics and the preview states that behavior.

## CRITICAL approval rules

CRITICAL operations require:
- durable parent operation state,
- current non-expired preview,
- typed target confirmation,
- approver principal different from requester,
- approver eligible for the operation/resource,
- approval bound to preview hash and policy version,
- revalidation before dispatch.

A deployment unable to establish two distinct principals fails closed for CRITICAL execution.

## Cross-cluster authorization detail

Transfer/clone is a separate exfiltration boundary. `cluster.transfer.execute` alone is insufficient.

Minimum execution conjunction:

```text
source:
  cluster.transfer.execute
  + record.read
  + record.export (when bytes leave the source trust boundary)

destination:
  cluster.transfer.execute
  + record.produce
```

The server evaluates permissions independently against the source and destination resource scopes. An identity mapping between clusters does not imply authorization symmetry.

## Access-analysis constraint

`acl.read` may support an evidence-based principal/resource access analysis. Results must carry the observable evidence source and limitations. Kafdeck must not claim complete effective authorization when managed-provider IAM, network policy or external authorizers are not observable.

## Implementation gate

Code introducing a v0.6 operation kind must include its explicit action mapping, risk floor, resource scope/canonicalization and negative tests in the same governed workstream.
