# v0.5 W40 Threat-Model Reconciliation

- **Status:** W40 release-readiness evidence
- **RFC:** RFC-0005
- **Scope authority:** Issue #121
- **Implementation scope:** W32-W39
- **Readiness workstream:** Issue #140 / PR #141
- **Protected-main baseline:** `f8e6b702d54bf68edffb3e672dec282f0b499c87`

This reconciliation evaluates the implemented v0.5 mutation surfaces against the
security boundary in `docs/security/v0.5-mutation-security-boundary.md`. It does
not grant release authority. Any source change after the recorded evidence head
requires fresh applicable exact-head CI and security evidence before W40
admission.

## Preserved global invariants

The candidate continues to require all of the following:

- every mutation action is explicit and default-deny; read authority does not
  imply write authority;
- there is no broad `admin` bypass for typed mutation permissions;
- server-owned risk floors cannot be lowered by a caller;
- CRITICAL operations require independent eligible approval;
- preview, confirmation, approval, preconditions and material digests remain
  bound to the admitted intent;
- durable mutation state, idempotency, execution claims and resource claims are
  mandatory;
- current requester authorization and stale-preview preconditions are rechecked
  immediately before dispatch;
- no blind retry is permitted after dispatch may have occurred;
- ambiguous post-dispatch outcomes remain `ExecutionUnknown` unless bounded
  verification proves a stronger outcome;
- raw Kafka key/value/header bytes and provider secrets are not durable mutation
  state by default;
- provider evidence is bounded and rejects secret-bearing fields/values;
- there is no generic Kafka CLI/AdminClient command surface, arbitrary provider
  HTTP proxy or arbitrary server-side script/SQL/JavaScript execution surface;
- no release, tag or publication action is implied by W40 readiness.

## Kernel and persistence boundary — W32

**Threat: caller-controlled risk lowering or approval bypass.**

Controls are implemented in the mutation kernel. `V05MutationKernelTests` proves
that topic deletion and purge are always CRITICAL, permanent schema deletion and
durability-sensitive changes are escalated by server policy, bulk scope can only
raise risk, and a deliberately weak caller-supplied risk decision cannot lower
those floors. `Critical_operation_requires_distinct_approver` proves requester
self-approval is rejected and that the second principal must possess the expected
typed mutation authorization.

**Threat: replay, duplicate execution and cross-instance races.**

Mutation identity binds principal, cluster, operation kind, resources,
preconditions, policy/risk and execution-material digests. The persistence lane
covers SQLite idempotency/CAS/resource claims and PostgreSQL cross-repository
idempotency, resource claims, cluster concurrency and recovery races. Mutation
mode fails closed without the required deployment posture; SQLite HA mutation
mode is rejected.

**Threat: process interruption or ambiguous external side effect.**

The persistence suite proves interrupted pre-dispatch execution becomes
`FailedBeforeDispatch`, interrupted post-dispatch execution becomes
`ExecutionUnknown`, unknown execution retains its conflict/resource claim, lease
recovery respects active ownership, and timed-out provider work retains its
cluster slot until the late task completes. Null and malformed provider results
are also durably classified as `ExecutionUnknown`.

**Threat: unsafe execution material or evidence persistence.**

HMAC material digests require a strong key. Re-submitted ephemeral material must
match the admitted digest before dispatch and is not persisted. The audit
contract contains no payload/secret fields. Provider evidence is bounded and
rejects credential-like names and values.

## Topic administration boundary — W33

Topic administration remains a typed mutation surface rather than a generic
AdminClient bridge. Server-side planning freezes exact resources and relevant
preconditions; risk classification is independent of caller role. Destructive
topic deletion inherits the kernel CRITICAL floor and independent-approval gate.
Execution remains subject to the same claim, stale-preview and outcome rules as
other mutation classes.

No v0.5 route introduces arbitrary Kafka command names or opaque AdminClient
payload pass-through.

## Governed record production boundary — W34

**Threat: durable payload leakage.**

`V05RecordProductionTests.Planner_binds_payload_only_by_hmac_digest_and_safe_metadata`
proves raw value, key and header bytes do not appear in the canonical plan or
persisted operation snapshot. Durable intent contains safe metadata and HMAC
material digests only.

**Threat: unbounded or programmable production.**

The planner enforces per-record and aggregate key/value/header/execution-material
ceilings before preview. Template assistance is bounded and typed; unknown
variables and over-expansion fail closed. `IRecordProduceMutationPort` exposes a
single typed produce method and the mutation contract does not expose generic
configuration, command, script, SQL, URL, method or payload-control properties.

**Threat: schema-validation or broker ambiguity.**

Optional schema validation fails closed when unavailable and does not leak raw
payload in errors. Batch execution records broker acknowledgement evidence,
represents a proven partial batch as `PartiallyApplied`, preserves
`ExecutionUnknown` for unknown producer outcomes, and retains known
acknowledgements when cancellation occurs after an accepted record.

**Threat: stale topic shape.**

The pre-dispatch validator detects topic drift and returns `StalePreview` before
record dispatch.

## Consumer offset/group administration boundary — W35

Direct-route authorization requires the exact consumer group and every explicit
topic target. Missing target authorization denies the request rather than
partially applying it. Malformed target material fails before authorization
materialization. The workstream uses typed consumer mutation planning and the
shared pre-dispatch/persistence kernel; it does not expose a generic consumer
command surface.

## Schema Registry mutation boundary — W36

`SchemaMutationAdapterTests` proves Confluent-compatible mutation support uses
fixed typed routes for compatibility testing, registration, compatibility-mode
changes and bounded deletion forms. Redirects and authorization failures fail
closed. Provider private error text is not surfaced in mutation evidence.
Post-dispatch server failures are represented as `ExecutionUnknown`; definitive
provider conflict remains a definitive failure rather than being retried blindly.

No arbitrary registry URL/method/body proxy is exposed to callers.

## Kafka Connect mutation boundary — W37

`KafkaConnectMutationAdapterTests` proves create, alter, pause, resume, connector
restart, task restart and delete map to fixed typed Kafka Connect routes. A
configured endpoint without an admitted mutation profile fails closed before
network access. Redirects are rejected, provider private response text is not
returned, and provider response bodies are bounded. HTTP timeout/rate-limit/server
failure after possible dispatch is conservatively mapped to `ExecutionUnknown`.

The inherited PR #139 CodeQL High finding in the Connect secret-preview test
fixture was remediated without suppression. W40 exact-head GHAS evidence must
remain green after this reconciliation commit before final admission.

## Controlled purge / DeleteRecords boundary — W38

`V05RecordsPurgeTests` proves purge planning freezes an explicit finite
(topic, partition, before-offset) target set, deduplicates targets, bounds target
count, rejects unresolved or out-of-range offsets, marks the operation
irreversible/no-undo, and always requires CRITICAL typed-target confirmation plus
independent approval. Low-watermark drift is revalidated immediately before
dispatch; safe high-watermark growth does not create a false stale-preview.

Post-dispatch readback distinguishes verified success from partial/inconclusive
verification without claiming full success. The surface does not expose wildcard
or generic DeleteRecords commands at execution time.

## REST/OpenAPI/operator UI boundary — W39

`V05MutationRequestAuthorizationTests` proves dispatch authorization covers every
frozen authorization target and fails closed if any target is no longer allowed.
A missing current identity is unauthenticated; identity is not reconstructed from
stored OIDC claims/groups.

`V05W39PreDispatchGuardTests` proves provider observation is not reached without a
live requester identity, current authorization and preconditions are revalidated
before dispatch, and a different currently authenticated operator is rejected
even when that operator independently has the target permission. This prevents a
stored-operation confused-deputy handoff.

`V05AntiforgeryTests` proves state-changing OIDC/session endpoints carry ASP.NET
anti-forgery metadata and use explicit strict-cookie posture for HTTPS deployments.

## Cross-surface outcome and retry rules

The mutation state machine requires a persisted dispatch marker before
post-dispatch outcomes can be recorded. Once dispatch may have happened, a
pre-dispatch failure cannot be substituted for the real state. Timeouts,
provider-result corruption, process interruption and other unresolved effects
remain `ExecutionUnknown`; known partial effects use their explicit partial or
applied-unverified classifications. These states are terminal for blind retry and
must be reconciled against provider truth before any new operation is admitted.

## Cross-surface secrecy and boundedness

The security boundary is cumulative with v0.2-v0.4 RBAC, masking and provider
origin controls. v0.5 adds no authorization path that converts read permissions
into mutation permissions. Payload/secret-bearing execution material remains
ephemeral; durable representations use digests and safe bounded evidence.
Mutation intent collections, provider evidence, record-production material and
provider responses have explicit bounds. The execution kernel also enforces
bounded per-cluster concurrency across repository instances where HA is enabled.

## Residual operational risks

The following risks cannot be eliminated by Kafdeck and must remain explicit in
operator procedure:

- Kafka, Schema Registry and Connect can be changed out-of-band after preview;
  Kafdeck therefore revalidates what it can immediately before dispatch but
  cannot globally lock external control planes;
- `ExecutionUnknown` may require provider-side investigation and must never be
  treated as permission to replay the same side effect blindly;
- provider readback can be delayed or inconclusive, so `AppliedUnverified` and
  partial outcomes are intentionally distinct from verified success;
- restore of mutation persistence without the corresponding deployment-owned
  HMAC digest secret can make previously admitted ephemeral material impossible
  to validate; the safe behavior is fail-closed, not digest bypass;
- HA correctness assumes the configured PostgreSQL deployment itself provides
  the durability/availability guarantees required by the operator's environment;
- secret redaction intentionally sacrifices provider-detail visibility when
  disclosure and diagnostics conflict.

## W40 security conclusion

No material departure from Issue #121/RFC-0005 was identified in the implemented
W32-W39 mutation surfaces reviewed above. The implemented contracts and tests
preserve the v0.5 mutation security boundary: typed least-privilege authorization,
server risk floors, independent CRITICAL approval, durable fenced execution,
pre-dispatch revalidation, conservative ambiguous-outcome semantics, payload and
secret non-persistence, and absence of generic execution surfaces.

This conclusion is **candidate evidence only** until the final W40 source head has
fresh green quality, dependency, CodeQL/GHAS, persistence, Kafka-smoke,
compatibility and applicable regression evidence, plus zero unresolved substantive
review threads and fresh CODEOWNER approval. It grants no release/tag/publication
authority.
