# v0.6 Security Boundary & Threat-Model Delta

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Scope:** v0.6 Fleet Operations, Broker Maintenance & Kafka Security
- **Authority:** Issue #145 / RFC-0006
- **Tracker:** Issue #146

## Security posture

v0.6 expands the blast radius of an authorized Kafdeck mutation: ACLs can grant privilege, SCRAM can affect credentials, broker configuration can affect availability/durability, reassignment can move large volumes of data, maintenance can remove capacity, and cross-cluster transfer can move record data across trust boundaries. The v0.5 mutation kernel therefore remains the single enforcement point and v0.6 adds stricter typed controls rather than an administrative bypass.

## Trust boundaries

1. **Human/API principal -> Kafdeck API**: authenticated identity, explicit authorization, anti-CSRF for cookie sessions.
2. **Kafdeck API -> mutation coordinator**: typed intents only; no provider request envelopes.
3. **Mutation coordinator -> durable store**: operation/idempotency/approval/progress state; no raw secrets or record bodies.
4. **Executor -> Kafka/provider adapter**: narrow capability-gated ports with bounded deadlines/concurrency.
5. **Source cluster -> transfer worker -> destination cluster**: separate data-exfiltration boundary requiring authorization and budgets at both ends.
6. **Provider observations -> access analysis/impact estimate**: evidence boundary; incomplete evidence must be represented as incomplete.

## Threats and mandatory controls

### Privilege escalation through ACL mutation

Threat: an operator grants themselves or another principal broad administrative access, possibly through wildcard patterns or bulk targets.

Controls:
- `acl.alter` is independent from `acl.read`,
- typed ACL resources/patterns only,
- materialized target set,
- server-owned HIGH floor,
- wildcard/broad administrative grants escalate to CRITICAL,
- independent approver for CRITICAL,
- before/after ACL evidence and bounded verification,
- no generic provider ACL payload passthrough.

### Credential theft or persistence through SCRAM workflow

Threat: Kafdeck becomes a credential store/logging path or returns secrets after write.

Controls:
- `scram.read` reports safe metadata only; it never retrieves credentials,
- secret material is write-only and request-memory scoped,
- durable state may store only safe metadata and digest binding,
- secret values are excluded from preview, audit, logs, traces, errors and progress,
- delayed execution requires secret resubmission and digest match,
- SCRAM mutation is CRITICAL and requires independent approval,
- no automatic retry after potentially-applied credential dispatch.

### Unsafe dynamic configuration

Threat: arbitrary/static configuration mutation causes outage or silently bypasses policy.

Controls:
- current provider must prove dynamic mutability,
- server-side allowlist and sensitivity classification,
- current value/fingerprint is part of preview,
- security/durability/availability/controller/election/replication-sensitive keys are CRITICAL,
- drift => `StalePreview`,
- no generic AlterConfigs endpoint.

### Reassignment/decommission data loss

Threat: replica movement or capacity removal reduces redundancy, strands replicas or overloads brokers/disks.

Controls:
- finite explicit plan,
- current replica/leader/ISR/broker/logdir fingerprints,
- configured minimum replication and placement guardrails,
- replication-factor reduction is CRITICAL,
- decommission is CRITICAL,
- target capacity/skew checks when evidence exists,
- pre-dispatch current-state revalidation,
- bounded progress polling,
- partial/ambiguous results remain explicit.

### Split-brain long-running execution

Threat: worker failover causes two workers to progress or dispatch the same operation.

Controls:
- one durable operation identity,
- operation execution lease and fencing generation,
- subordinate progress records are conditional on current fencing generation,
- lease renewal is durable,
- takeover must observe previous lease expiry and current operation state,
- potentially-applied provider actions are verified/reconciled before any further dispatch,
- no in-memory mutex as HA authority.

### Data exfiltration by cross-cluster transfer

Threat: a principal with maintenance rights copies record data to an unauthorized destination.

Controls:
- transfer permissions are independent from security/maintenance permissions,
- source `record.read` and, when bytes leave the source trust boundary, `record.export`, are required,
- destination `record.produce` is required,
- source/destination cluster/topic mappings are explicit and materialized,
- byte/rate/time/concurrency ceilings,
- masking/export policy remains applicable where source policy requires it,
- destination behavior is explicit; destructive overwrite semantics raise risk,
- audit records source/destination identities, mappings, budget and operation identity,
- no unrestricted pipe/clone primitive.

### Provider capability confusion

Threat: Kafka-compatible or managed-provider semantics are assumed to match Apache Kafka and Kafdeck executes unsupported/unsafe actions.

Controls:
- per-capability tested provider profiles,
- read/plan/execute/verify capabilities tracked independently,
- unknown/partial mutation capability fails closed,
- provider-native IAM or replication semantics are not inferred from Kafka protocol support,
- access analysis includes evidence source and completeness/confidence.

### Denial of service by maintenance polling or broad planning

Threat: large fleet analysis/reassignment progress consumes resources needed for operator visibility.

Controls:
- hard target/byte/request ceilings,
- bounded per-cluster planning and execution concurrency,
- isolated long-running polling bulkheads,
- bounded poll intervals with backoff/jitter,
- pagination/materialization limits,
- cancellation only at safe typed boundaries,
- ordinary metadata/read visibility retains separate capacity.

## Security invariants

- unknown operation kinds/actions/risk floors fail closed,
- no read-to-write implication,
- no broad admin bypass,
- CRITICAL always uses a distinct eligible approver,
- preview/approval cannot be replayed against a changed plan, cluster or resource set,
- raw SCRAM secret and transferred record payload are not durable operation state,
- no generic provider tunnel or arbitrary code,
- no blind retry after possible dispatch,
- audit events use bounded-cardinality identifiers and redact secrets/payloads,
- `ExecutionUnknown` remains legitimate when execution state cannot be established safely.

## Security tests required before release readiness

- privilege expansion/wildcard ACL risk escalation,
- current-head authorization recheck after ACL/policy changes,
- SCRAM secret leakage tests across response/log/audit/trace/persistence,
- stale dynamic-config preview rejection,
- RF reduction and decommission guardrails,
- lease/fencing race and crash/restart tests,
- cross-cluster permission-conjunction negative cases,
- provider capability downgrade/unknown tests,
- timeout after dispatch -> no blind retry,
- partial reassignment/transfer truthfulness,
- bounded polling/load-isolation tests.

## Planning conclusion

No new v0.6 mutation surface is considered admitted until this boundary, RFC-0006, runtime/ADR/API/test contracts and implementation plan merge through protected-main governance.
