# W66 G2 authenticated Webhook vertical and remaining acceptance

State: implementation and laboratory verification in progress; this does not
close W66 #215 or G2. Full N1–N5 scope remains unchanged.
Baseline: protected-main `e570637`.

## Implemented vertical

- Closed `WebhookAuthentication` values `Anonymous` and `Bearer`. Bound profiles
  without an explicit admitted mode cannot silently become authenticated or fall
  back to anonymous. Unknown modes, unsupported schemes and arbitrary headers fail.
- Exact destination/provider/profile-fingerprint/binding resolution from bounded
  server-owned references. The HTTP factory validates bounded ASCII Bearer token
  grammar before constructing a handler/socket. Credentials enter only the private
  Authorization header, never a safe event body or persisted receipt.
- Explicit destination and credential binding `Enabled` switches. A disabled
  destination stops routing and dispatch; a disabled binding fails before secret
  resolution or network I/O. These owner-provisioned changes require restart.
- Versioned binding rotation changes the profile fingerprint. Previously routed
  pending work is fenced as `UnknownExternalEffect`; new approved events use the
  newly admitted binding. No blind resend or destination downgrade is introduced.
- Existing enabled anonymous profile fingerprints remain byte-for-byte compatible.
- Existing DNS pinning, SSRF/redirect/TLS constraints, complete-dispatch deadline,
  retained outstanding concurrency, finite payload/rate budgets and unknown-effect
  recovery remain required regressions.

The physical laboratory uses the same production hosted worker, credential
resolver and transport. Only DNS observation/TCP routing and private CA trust are
substituted for an isolated local TCP/TLS fixture. Production hostname validation
is retained. Temporary randomly generated credentials are never printed; checks
compare safe booleans/hashes and scan actual database/WAL bytes for leakage.

credential references. Email has its own default-false `EmailDeliveryEnabled`
switch and closed `Smtp` profile. Inactive profiles may remain in the catalog.

A mounted-file content change under the same binding intentionally preserves
identity and affects later resolutions. It is not evidence of pending-work fencing
or atomic revocation. Use a versioned binding/profile change when such fencing is
required. A file/config update cannot recall a credential already resolved or an
external request already in flight.

`V08W66PostgreSqlHostedTlsTests` proved two actual scenarios using independent

The next material failover scenario should establish a real primary and standby,
confirm the `InFlight` claim replicated, let the TLS peer read the complete POST
without returning a receipt, abruptly terminate the sender, physically fence the
old primary, promote the standby and start the surviving sender. Require actual
database elapsed stale time, one POST/attempt, durable unknown state and zero
replay. A companion failover before claim should deliver once. This would add
specific crash/promotion evidence; it would not prove safe stale-backup restore,
rolling upgrade, hot credential revocation or all HA operating conditions.

## Concrete HTTP protocol contract and laboratory

The host uses the existing typed provider adapters and durable dispatcher. Its
physical transport accepts only fixed code-owned HTTPS origins/methods and
revision-bound `ProviderResourceId` / `ProviderSecondaryResourceId` values:

- Slack: exact encoded channel ID; fixed `https://slack.com/api/chat.postMessage`,
  Bearer header, plain text with markdown/unfurls disabled, matching channel/`ok`
  and timestamp receipt. [Official method](https://docs.slack.dev/reference/methods/chat.postmessage).
- Teams: exact team GUID and closed channel ID; fixed Graph channel-message
  endpoint, Bearer header and text body; HTTP 201 with a bounded message ID.
  Delegated channel-send authority is required. App-only permission is documented
  by Microsoft for migration and is not claimed as general notification authority.
  [Official Graph contract](https://learn.microsoft.com/graph/api/chatmessage-post).
- Telegram: exact canonical numeric chat ID; fixed Bot API `sendMessage`, token
  only in the private protocol-required URL path, link previews disabled, `ok`
  plus positive message ID and exact chat receipt. No arbitrary Bot API method or
  named mutable chat alias is accepted. [Official Bot API](https://core.telegram.org/bots/api#sendmessage).
- PagerDuty: fixed Events API v2 endpoint, secret routing key in its private
  protocol-required JSON field, event UUID dedup key and trigger-only action.
  HTTP 202 needs an exact `success` and matching dedup receipt; it acknowledges
  provider acceptance, not final incident processing.
  [Official event contract](https://docs.pagerduty.com/developer/api/reference/events-v2/send-event/create-v2-event).

Provider response bodies are limited to 16 KiB, finite total request deadlines and
JSON depth eight. Duplicate required fields, malformed or wrong-target receipts,
redirects, throttling, transport failures and unknown responses remain terminal
`UnknownExternalEffect`. Conclusive HTTP/auth rejection maps to `Exhausted`.
Only a SHA-256 digest of a validated provider receipt enters durable
`ProviderReceiptFingerprint` metadata; raw `ProviderRequestId` remains forbidden.
Schema v3 adds that nullable receipt column atomically. v2 pending work retains
its original profile revision; v1 still requires governed draining/reconciliation
before its existing v2 revision fence can upgrade. Older binaries fail closed on
v3. Back up and verify migrations before deployment; mixed-schema rollback is
not claimed supported. Raw response bodies, IDs, URLs, headers and credentials
never enter the ledger.

`V08W66ProviderPhysicalTlsTests` exercises each family through a real Generic Host,
the production typed adapters/dispatcher/transport and SQLite ledger. Its 32-case
matrix covers accepted, denied, provider-level denied, ambiguous, malformed,
wrong-receipt, oversized and duplicate-field replies. The isolated fixture keeps
the actual official hostname/SNI/certificate identity; only test DNS/TCP route a
valid public pin at port 443 to a local TLS listener. Actual SaaS egress, tenant
permission and operator approval are separate acceptance evidence.

Telegram's protocol requires a bot token in the URL path; configured Webhook
paths can also be confidential. A private HttpClient alone does not prevent
.NET EventSource/Activity URL capture. Both transports therefore use bounded raw
HTTP/1.1 over the same approved pinned TCP/TLS connection, with
normal hostname/certificate validation, finite content-length/chunked framing,
header/line/count/body limits and zero redirects/proxy. No HttpClient diagnostic
pipeline receives its secret URI. Tests install real HTTP EventSource and
Activity listeners and check their captures through safe booleans. A separate
real HttpClient request and recorded Activity canary prove the capture listeners
are active. The private Webhook scenario exercises the production hosted worker,
SQLite ledger, exact path and Bearer header through a physical TLS connection.
No global telemetry suppression is used.

Email uses implicit TLS (465 default), the same public DNS/IP pin policy and
normal certificate/SNI checks, then bounded EHLO/AUTH PLAIN/MAIL/RCPT/DATA.
Server, sender, exact recipient, username and binding are revision-bound; only
the password comes from the protected reference. MIME content is a closed safe
event projection, UTF-8/base64 encoded within the payload budget. Only final 250
acknowledgement creates a receipt hash; a lost final response remains unknown
and is never blindly resent. No AUTH advertisement or rejected authentication
can downgrade to anonymous. SASL lines are bounded to 512 bytes, multiline replies
to 16 lines of 512 bytes, and the complete submission to 15 seconds.
The physical matrix covers acknowledgement, authentication/recipient rejection,
absent AUTH, lost acknowledgement, oversized reply and invalid TLS hostname.
See [RFC 8314](https://www.rfc-editor.org/rfc/rfc8314.html),
[RFC 4954](https://www.rfc-editor.org/rfc/rfc4954.html) and
[RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html).
