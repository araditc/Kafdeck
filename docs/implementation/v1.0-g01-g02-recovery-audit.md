# G01/G02 managed provisioning recovery and Kafka registration audit

Scope: tracker [#469](https://github.com/araditc/Kafdeck/issues/469), findings G01/G02 only. Initial-owner setup, Kafka mutation controls, credential persistence, other v1.0 gaps, signed v0.9 media and release/publication authority are unchanged.

## Runtime change

- Ordinary-user creation persists a bounded private request intent (requester, normalized email, requested role/clusters, random proof and receipts) before provider dispatch. Passwords are not persisted. Exact retries inspect the existing intent; an unknown outcome is never dispatched again.
- Recovery is owner-only, CSRF-protected, current-authority checked and bound to the original requester/material. It checks an exact Keycloak user/username/email and the private admin-only `kafdeckProvisioningId` proof; email alone is insufficient. Missing or user-editable profile permissions prevent dispatch/recovery. The service client retains manage-users only; no runtime realm-administration grant is added.
- Confirmed membership and its operation receipt are written atomically to managed state before audit delivery. Audit completion is durable; delivery is at least once under the stable request correlation. A missing account or unknown provider result remains pending, not a safe-to-retry creation. Definite precondition/provider rejection is retained as a terminal receipt.
- Manage users shows pending operations and an explicit recovery action. The original temporary password remains in effect; recovery never resets it. See [operator setup/recovery](../operator/managed-identity-setup.md#safe-ordinary-user-provisioning-and-recovery-main-after-v09).
- Kafka target registration emits appended event type `KafkaTargetRegistration = 15`, retaining prior enum values. Success, authorized duplicate reuse, denied and failed attempts carry actual principal/session correlation, stable authorized target ID where available, outcome and fixed reason category. Names, brokers, usernames, passwords and certificate/private-key material are excluded. A connection test alone emits no registration success; failed persistence cannot produce a success event. CSRF rejection before the handler performs no registration.

## New focused tests and provenance

`V1ManagedProvisioningTests` covers durable-before-dispatch ordering, lost acknowledgements/restart, actual filesystem write failure, rejected/foreign evidence, provider outage/no blind retry, profile permissions, changed material/current authority, file-lease concurrency and retained audit recovery. `V1ManagedRegistrationHttpTests` uses real loopback ASP.NET/CSRF and managed state with a controlled Kafka metadata seam; it verifies successful/reused/denied/failed outcomes, redaction, failed writes and HTTP pending/recovery access. Those controlled seams are not real Kafka or real human login evidence.

`V1ManagedProvisioningLiveTests` uses the existing pinned HTTPS Keycloak G1 server with a **separate** ephemeral realm. The new preparation script creates a manage-users-only application client plus a laboratory-only profile-control identity. Three real provider cases cover a dropped already-committed response, failed local receipt persistence and an unrelated preexisting account. The normal source suite explicitly skips these cells without its lab configuration; the configured G1 producer must actually pass them with zero skips. Only sanitized TRX is public; test secrets/import files are not uploaded.

No successful v0.9 load/soak, recovery or distribution suite is manually repeated. Applicable automatic PR CI and the new focused cases provide changed-source evidence. The historical v0.9 source/build equivalence record remains historical; this product-code change is not automatically equivalent for future W82/RC admission. Other gaps in the [audit](v1.0-code-gap-audit.md) remain open.

## Local validation record

On Windows with .NET SDK 10.0.404, 26 distinct new focused cases passed with no skips: 15 provisioning service cases and 11 loopback HTTP/registration cases. The first 24-case run passed 23; its sole remaining failure was a test expecting HTTP 400 where the existing CSRF boundary correctly returns 403. The correction plus two added retry/CSRF cases then passed 3/3. Earlier development failures exposed a test's array-reference comparison and a real requester-state read after a simulated filesystem failure; both were corrected before these results. Successful cases were not manually rerun.

Frontend locale generation and TypeScript typecheck passed locally on the available Node 22.21.0; that environment is below the supported Node 24 floor. The automatic frontend CI uses Node 24 for supported-environment validation. Real Keycloak acceptance is supplied by the new configured G1 cells; local controlled HTTP tests are not relabeled as live provider proof.

## Provider contract sources

The implementation follows Keycloak's official [user profile admin endpoint](https://github.com/keycloak/keycloak/blob/26.4.7/services/src/main/java/org/keycloak/services/resources/admin/UserProfileResource.java) and [user create/query contract](https://github.com/keycloak/keycloak/blob/26.4.7/services/src/main/java/org/keycloak/services/resources/admin/UsersResource.java). These references explain the contract; actual integration acceptance uses the repository's pinned Keycloak 26.8.1 producer, not inferred compatibility with every version.
