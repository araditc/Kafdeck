For original #216, parity is against **supported UI operations**. Missing runtime
kinds that are already Unsupported/Blocked in the UI retain their exact inherited

reflection, CLI or provider-REST tunneling. The new complete capability matrix
must preserve that reason. Hosted/UI-supported families require genuine effects,
not that inherited limitation. A catalogue entry alone cannot satisfy A4/A5.

inherited limits. The complete machine-readable capability result preserves

## Complete named read source inventory

Existing UI read surfaces extend beyond system/cluster/topics/consumers/schemas:
broker/topic configuration; masked bounded record browse/tail/export; Connect
profiles/plugins/validation/config/task status; ksql metadata and bounded SELECT;
Streams/topology/state stores/lineage; schema capabilities/reference graph/mock
and compatibility explanation; operational analytics/SLO; data-quality policy and
evidence; notification subscriptions/delivery/evidence and fleet capabilities.
Some bounded read operations use POST and retain their own typed input contract.

The next source checkpoint contains a shared closed catalogue of **67** named
reads (62 GET and five bounded POST tools), linked into the API and CLI. It adds
`GET /api/v1/automation/capabilities/reads` and the corresponding OpenAPI paths.
`views <exact-versioned-name> <path-identities...>` chooses a compiled route;
it cannot choose an HTTP method, arbitrary URI, handler or authority. Contracts
with query fields or a POST body require `--request-file`; a GET file supplies
only its fixed query keys (`{}` retains defaults). Example:

```text
kafdeck --service-profile service.json views v03-records-browse dev orders 0 --request-file bounded-query.json
kafdeck --service-profile service.json views v07-connect-profile-connectors-detail dev connect-profile connector
kafdeck --oidc-profile human.json views v07-schema-registry-capabilities dev
kafdeck --oidc-profile human.json views v08-bearer-read-capabilities
```

Every named read requires explicit live registration and current direct backend
scope. Services use the same filtered read projections. Notification management
metadata remains human-only; aggregate status requires unconstrained manage.
Only the five exact POST read contracts bypass browser CSRF when the middleware
has established a verified bearer identity and validated their closed request.
Cookies/legacy collisions remain denied. Export checks genuine current bearer
authority without constructing an OperatorIdentity; record masking and finite
stream/output budgets remain in the existing service.

This source inventory is not evidence that every real provider read has passed.
The integrated owner records exact subsequent build, regression and physical
provider results. Inherited Unsupported responses remain truthful results.

Read parity requires exact action registration plus current resource filtering,
safe response schemas, cursor/output semantics, capability/errors and audit
identity. A provider or metadata field must not confer authority. Audit helpers
that currently fall back to Anonymous/LegacyDeployment for a bearer need exact
bearer attribution before admission; no synthetic cookie/session is allowed.
Record payloads retain masking, row/byte/time limits and export-specific rights.
OpenAPI must describe actual admitted read paths; enumerating future paths does
not activate them or establish their provider acceptance.

Idempotency-Key. Structured files are at most 65536 bytes, recursively reject
unknown/duplicate fields and are checked before token acquisition. Backend

effects retain their existing exit categories. Legacy deployment credentials
never acquire governed effect, approval or recovery rights.
