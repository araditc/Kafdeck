# Governed notification restore and resumption

Implementation and acceptance are tracked separately. Local SQLite and physical
PostgreSQL scenarios now exercise governed reconciliation and safe resumption.
Their evidence below does not establish exact revision Linux CI or protected
main acceptance.

## Authority and effect disposition

The operator anchor is outside the database backup. Its generation and exact
SHA256 are pinned in sender configuration. A restored database cannot select its
own generation, activate an anchor, or enroll itself during startup or a status
read. Every sender must use the interlock; unregistered historical senders are
outside this protocol and must be physically fenced by the operator.

Recovery runs in a dedicated maintenance instance with notification senders and
product source routing disabled. The external anchor remains `quarantined` at
the proposed new generation throughout review and database changes. Stop and
fence both original database nodes and their sender processes first. An already
accepted external request cannot be recalled by changing configuration.

The two reviewers must each have current, unconstrained deployment-wide
`NotificationManage`. Approval also requires current `MutationApprove` and the
explicit human approval registration for bearer access. The requester and
approver must identify different humans, including when the same human uses
different browser or CLI sessions. Revalidate the saved approver at application.

Each bounded batch records one explicit effect disposition:

| Disposition | Meaning |
| --- | --- |
| `ExternalAcceptanceObserved` | Reviewers observed provider evidence of acceptance. |
| `ExternalNonAcceptanceObserved` | Reviewers observed evidence of nonacceptance. |
| `UnresolvedRiskAccepted` | Reviewers accept suppressing an unresolved historical effect. |

All three suppress automatic sending of the reviewed restored intents. They do
not create a provider delivery receipt or mark the intent `Delivered`. The ledger
retains `UnknownExternalEffect` and its original attempt count. Immutable separate
receipts bind the disposition, evidence SHA256, sender-fence evidence SHA256,
actors, policy, row revisions and operation. Retrying an effect is a separately
reviewed new product action, never a reset of the old intent to `Pending`.

## Closed operation sequence

1. Publish a new external quarantined generation and record its SHA256. Keep all
   prior sender processes stopped. Verify provider effect and original-node
   fencing evidence; store evidence privately and retain only reference hashes
   in the operation.
2. Restore the verified backup into a fresh read-only node. With the native lab,
   `FenceOriginalNodes` stops both exact recorded originals;
   `AdmitRestoreMaintenance` separately verifies both closed ports, original
   system identity, read-only restored quarantine, and the exact external
   quarantined anchor before explicitly allowing maintenance writes. Neither
   action activates sending or overwrites a backup.
3. Preview a `FenceBatch`, review its immutable hash, and obtain a distinct human
   approval. Apply using its expected revision and preview hash. Batches contain
   at most 500 unresolved intents; a row change invalidates application. Repeat
   until no unreconciled intent remains.
4. Inventory the actual restored product outbox using the explicitly configured
   source database. Its dedicated connection is read-only and never creates a
   database, installs mutation conflict guards, changes SQLite journal mode, or
   acknowledges source events. Missing database/schema refuses maintenance.
   Preview, independently approve and apply `FenceSourceBatch` operations of at
   most 500 source IDs. Each preview binds the source identity and full bounded
   inventory hash; source drift invalidates application. The inventory includes
   future-clock events and source IDs with no delivery row.
5. Separately preview, approve and apply `AdvanceGeneration`. It rechecks zero
   unreconciled intents under a database transaction and atomically stores the
   new generation, a reviewed trusted database timestamp cutoff and the immutable
   operation receipt. The cutoff is chosen at preview and bound into the hash.
   All current restored source IDs must already have reviewed historical fences.
   Missing initial enrollment uses the separate `EnrollEmpty` action, permitted
   only for empty delivery/source stores and missing generation.
6. Review the applied receipt. Only the operator then publishes an **active**
   anchor for that exact generation and a new SHA256 in normal sender
   configuration. Disable recovery maintenance before starting normal senders.
   Keep the old nodes and old sender configuration fenced.

Explicitly inventoried historical source IDs, regardless of their event or
database timestamp, and events at or before the approved cutoff are terminally
suppressed before endpoint resolution, secret resolution or transport. This
includes source/outbox replay for which the stale backup has **no delivery row**.
Suppression records reference the approved generation advancement. Fresh product
events after the cutoff may be delivered using normal profile, credential,
address, TLS, rate and concurrency admission. Restarting a sender does not erase
the persisted cutoff.

The source database and notification database can be separate. Full inventory
hashes are checked before changes and before commit; this is not an atomic
transaction across two databases. The protocol requires source writers and old
senders to remain physically fenced during inventory, review and advancement.
The retained source identity and explicit ID fences prevent a restored event
with a future application clock from being reclassified as fresh after restart.
Database capture provenance is retained separately from payload projection;
anonymous Webhook and safe-event fingerprints remain unchanged.

## Configuration and operator commands

Maintenance uses `Kafdeck:Notifications:Recovery:Enabled=true` and an explicit
canonical `TargetGeneration`, together with the existing absolute
`DeliveryInterlockPath` and exact `DeliveryInterlockSha256`. It requires OIDC,
notification observation and management, disabled Webhook/HTTP/Email senders,
disabled `ProductEventsEnabled`, and disabled administration mutation effects.
The mutation persistence configuration must still identify the actual source
database; it is opened through the dedicated read-only inventory connection.
An empty source database must already have its legitimate product source schema
and stable source identity from reviewed provisioning; recovery never installs
them while reading inventory.

The native laboratory exposes two explicit commands after normal read-only
`Restore`. Set the variables from the retained reviewed laboratory manifest and
the outside anchor; the hashes are evidence identifiers, never credentials:

```powershell
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action FenceOriginalNodes -OutputDirectory $recoveryLab
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action AdmitRestoreMaintenance -OutputDirectory $recoveryLab -TargetGeneration $reviewedGeneration -ExternalAnchorSha256 $quarantinedAnchorSha256
```

The closed CLI uses a human profile for the requester and a different human
profile for approval. Request files contain the exact typed preview or
revision/hash body; actor identities are always taken from authentication.

```powershell
kafdeck --oidc-profile requester.json notifications recovery status
kafdeck --oidc-profile requester.json notifications recovery preview --request-file recovery-preview.json
kafdeck --oidc-profile approver.json notifications recovery approve $operationId --request-file recovery-revision.json
kafdeck --oidc-profile requester.json notifications recovery apply $operationId --request-file recovery-approved-revision.json
kafdeck --oidc-profile requester.json notifications recovery get $operationId
```

Use separate previews for `FenceBatch`, `FenceSourceBatch` and
`AdvanceGeneration`. Approval increments the expected revision, so the apply
file must use the approved response revision and the same immutable preview
hash. `ItemCount` counts ledger rows; `SourceItemCount` counts historical source
IDs. Every response includes the source identity/inventory hash used for review.
`ReadyForOperatorActivation` describes a completed database advancement; it does
not mean that the external anchor was activated or that an external effect was
delivered. Retain the operation ID, immutable preview hash, evidence reference
hashes and audit receipt with the operator change record.

The protocol does not automatically detect an undeclared database rollback. It
depends on the operator moving the outside authority into quarantine before
restore. It does not establish provider-specific exactly-once delivery or permit
blind resending of unresolved external effects.

## Local acceptance evidence

The local PostgreSQL artifact at
`artifacts/g2-complete/native-v11/postgres-governed-restore-safe-resume-evidence.json`
has SHA256 `af63c4573c1b292167912aa2b2f1a1a5f07d554c6c9191cf3624402e0ecc3475`.
It records a real physical backup and restore, independent HA sender processes,
both original nodes physically fenced, old and quarantined configurations
refused, terminal fencing of the restored old intent, and explicit suppression
of a historical source missing from the restored ledger despite its future
application clock. After reviewed epoch advancement, a new durable product
transition delivers once and a restarted sender preserves the cutoff. There
are exactly two TLS connections and two POSTs: one original accepted POST and
one fresh post-cutoff POST; old source POSTs and automatic resends are zero.

The SQLite artifact at
`artifacts/g2-complete/regression-v11/sqlite-governed-restore-safe-resume-evidence.json`
has SHA256 `e2cfc73f31e9db90fefc8e0a87e94545c653d9ad3f655f36c7d39947214662ec`.
It records an actual separate backup and restore, old intent suppression,
zero historical absent-ledger source POSTs, one fresh product POST, and cutoff
persistence after a new host. Both artifacts distinguish a generic Webhook
HTTP204 acknowledgement from a provider receipt; no receipt identifier is invented.

These physical scenario artifacts exercise distinct humans at the recovery
store. Genuine Keycloak and shipped CLI approval are covered by the separate
human recovery CLI suite; the physical artifact does not claim OIDC coverage.

## Required acceptance matrix

- Actual restored `Pending` backed up before an original accepted POST is fenced
  without a second POST; both original nodes and old sender configurations remain
  fenced.
- An old genuine product source event absent from the restored delivery ledger
  cannot send after epoch advancement, including on a restarted independent node.
- A genuine post-cutoff product transition delivers once through the resumed
  physical TLS sender and persists its delivery outcome. A generic Webhook
  HTTP204 is an acknowledgment with no provider receipt identifier; no receipt
  hash is invented. Typed provider receipts are stored only when the provider
  protocol actually supplies them.
- Same-human approval, current role/registration revocation, changed policy,
  expired or stale preview, stale row revision, nonempty enrollment, and
  advancement with unreconciled rows all refuse without a physical send.
- Process HA admission and rate fairness evidence, exact revision Linux CI,
  and protected main acceptance are recorded by their separate evidence runs.
  The local artifacts above do not alone establish completed G2 acceptance.
