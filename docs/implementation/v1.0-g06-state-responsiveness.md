## G06: format freeze and recoverable encryption context

The accepted policy is a **format freeze**, not a new envelope or automatic down-migration. The v0.9 JSON object retains its exact case-sensitive fields: `Issuer`, `OwnerId`, `Provisioning`, `CodeHash`, `CodeExpires`, `Users`, optional `Connections`; the admitted G01 optional `UserProvisionings` receipt array is also accepted. Users retain ID/email/role/cluster IDs/enabled/session validity; connection definitions retain bootstrap/protocol/mechanism and optional SchemaRegistry/Connect/KsqlDb settings with protected credentials/revision. Receipt fields follow `ManagedUserProvisioning`. No password becomes a JSON field.

Unknown fields at any record depth, duplicate object properties and malformed/truncated JSON are rejected. No writer may replace an unreadable or unsupported existing file. Issuer/owner and provisioning validation remains mandatory; startup reads existing state before hosting/migration/setup work. Atomic temporary write, disk flush, exclusive operation lock and rename remain unchanged. A missing file is an uninitialized installation, not an upgrade; operators must restore the complete private backup before starting. Do not delete an unreadable file to reopen onboarding.

Existing default ASP.NET Data Protection behavior is preserved when no new option is configured. A restore may explicitly select `Kafdeck:DataProtection:KeyDirectory`, an **existing absolute private directory**. Optional `Kafdeck:DataProtection:ApplicationName` must match the original application's discriminator; omitting it retains the content-root discriminator, so keep the same content root when upgrading. Copy the matching original key ring, not a newly generated one. Windows new keys remain current-user DPAPI protected; a ring copied to another account/machine is not promised portable. On other platforms protect the directory with private filesystem permissions and the deployment's existing backup encryption controls. These options do not introduce a new key-management service.

Stop writers; back up the managed JSON, matching decryptable key ring and application context, issuer/realm/client configuration, material-digest key and mutation database together. SQLite uses a consistent backup API/checkpoint; PostgreSQL uses `pg_dump`/`pg_restore`. Verify backup hashes/integrity, restore in isolation, then start the candidate. On failure stop the candidate and restore the verified backup plus original binary/configuration. Never point an old binary at newly written state and assume it can downgrade. Keep the same issuer; changing realms requires a separate identity migration.

`deploy/dev/v1-managed-upgrade/run.cjs` runs the actual signed-release native executable extracted from the unchanged v0.9 win-x64 archive and an identified development candidate, genuine isolated Keycloak and Kafka, and native SQLite/PostgreSQL. Each provider covers first-owner login, another scoped user, target registration, protected HTTP credentials, unchanged users/roles/targets/state bytes, unsupported-format startup refusal, missing-key denial without clearing state, process termination and verified database/state/key restore. Pending/approved/unknown mutation snapshots are **synthetic compatibility fixtures**, not proof of actual provider effects or a genuine human approval. Their state and snapshot hashes remain identical after upgrade/restore. Integration HTTP providers are controlled physical HTTP fixtures, not genuine Schema Registry/Connect/ksqlDB installations. Existing W80 recovery/outside-generation evidence retains its original scope; unchanged guard source is fingerprinted, not silently re-executed.

This closes G06's file/key compatibility gap after admission. V1-4 remains open for the selected final RC/media binding and applicable operator acceptance; these development-candidate results must not be relabeled as signed-RC acceptance.

## Q01: confirmed admission defect and bounded fix

The pre-fix loopback API probe returned 200 after a real full MemoryCache refused retention. Admission now serializes contenders, verifies the exact new lease is retained and returns a boolean. Full capacity produces 409 `connection-credential-capacity`, `clusterId` and `targetSaved: true`; the definition can already be saved while credentials are unavailable. Registration audit still describes definition persistence. Reload/reuse that target after a lease expires instead of duplicating registration. A successful secured registered-target test now has a retained lease. Existing admitted leases are not compacted away to admit a new one. Capacity remains 128, absolute expiry 30 minutes, in memory only; restart/revocation/expiry still requires reconnection. No capacity increase or new supported-scale claim.

Focused cases cover default 128/129, concurrent admission, full-cache same-key replacement, expiry releasing capacity, explicit loopback test failure and saved-definition/no-secret/audit behavior. The expected pre-fix failure and corrected results are separately fingerprinted.

Automated review identified an incomplete browser path: the new capacity problem initially fell through to generic broker/credential remediation and did not reload a partially saved target. The connection form now explains lease-expiry retry, refreshes target metadata, clears stale test success and never auto-opens or repeats registration. A separate actual compiled-Chrome wire fixture verifies that behavior, one registration attempt, target visibility and no secret in local storage. CI's three old registration fixtures also now register the actual bounded credential runtime instead of testing secured success without one; their precise failed cases pass with that dependency present. No production capacity/authority check was weakened to satisfy the fixture.

## E01: session retention and finite browser reads

Managed session scope previously appended role/cluster text to a 64-character fingerprint. The UI correctly rejected that malformed scope; returning to a tab consequently cleared observations/drafts as if authority had changed. The server now hashes current policy, managed user ID/role/enabled/session validity and sorted cluster scope into a valid stable scope. Real authority changes still rotate the scope and clear prior state. Private content remains hidden/inert during authoritative revalidation; this does not trust stale authority to avoid a loading state.

Shared JSON reads now have a 15-second deadline including body consumption, retain caller cancellation, clean up timers/listeners, and show an actionable timeout. There is no implicit retry, mutation redispatch or new deadline pretending an uncertain write had no effect. Long-running bounded streaming/mutation APIs retain their separate semantics.

The finite single-user Chrome reference budget is feedback p95 <=250ms / p99 <=500ms, destination-surface readiness p95 <=5s / p99 <=10s on numeric loopback. Readiness means the destination heading/form/surface is visible; provider-complete latency is not inferred. Quantiles use nearest rank with ten observations per listed journey; they are finite acceptance observations, not a population/WAN p99 or replacement for W82. Dataset: 20 Kafka topics, three partitions each, 100 records, five groups; 20 controlled registry subjects and two controlled connectors. Genuine Keycloak login, topic/group/subject detail, page navigation, ecosystem configuration, quiet refresh and return-to-tab input/focus/scroll retention are measured separately from API latency. Exact raw traces, counts, browser version and accepted limitations accompany the evidence packet. No Admin-client pooling or broad performance rewrite was introduced.

The release baseline actually cleared the search draft and lost focus on return to the tab. With scope fixed, a separate nonzero-scroll probe still observed 250px -> 0px: hiding the private shell collapsed document height. A public geometry-only spacer now reserves that height synchronously while the private content remains hidden/inert; it contains no private text or controls. Focus restoration uses `preventScroll`. The changed-layout follow-up passes at 250px on both databases. Foreground navigation traces were reused because this follow-up changes only verification layout; affected scroll/focus tests were rerun.
