# W67 job/generator reconciliation: required proof contract

State: implementation source present; coherent compilation and physical acceptance pending. This closes
a supported UI lifecycle parity gap; it is not an inherited SDK Unsupported case.

The existing direct request `{batchId, disposition:"provenNonApplication"}` is
insufficient authority to clear DispatchStarted. A caller's label, proof hash or
later absence of a payload does not prove an earlier Kafka write never happened.
The old bearer path refuses that request with 501; the browser path refuses it
with 409 and directs the operator to the governed preview.

## Durable observation before dispatch

Before a hosted job/generator marks a batch DispatchStarted, its actual typed
Kafka observation must be durably bound to that batch:

- Configured destination profile and physical Kafka cluster ID.
- Actual topic UUID, exact topic and partition.
- Low/high watermarks, observation time and worker generation.
- Parent operation, immutable plan fingerprint and pending batch identity.

Record keys, values, null/tombstone semantics and ordered duplicate headers are
preserved. No synthetic tracking header is added to byte-preserving transfer.
Missing UUID/provider evidence cannot be replaced with a caller field. Legacy
pending rows without this boundary remain unresolved.

## Immutable reviewed disposition

An exact original requester may plan a no-effect reconciliation. The server loads
the parent operation and pending batch, current progress/version/worker fence and
fresh destination observation. The request supplies only exact batch/progress
references and SHA256 references for external proof and physical worker fencing;
it cannot supply an observed UUID, watermark, requester or provider command.

The stored plan binds all those facts and current policy. CRITICAL confirmation
and a distinct currently authorized human approval are required. The approver
must hold MutationApprove, MutationReconcile and applicable underlying resource
permissions; changing client/browser does not create a different human. A machine
cannot approve. Execution belongs to the original requester and rechecks current
registration, direct RBAC, policy, proof, batch identity and progress CAS.

Only unchanged exact destination identity **and both watermarks**, after physical
old-worker fencing, can establish non-application and permit clearing/fencing the
batch for normal guarded resumption. Appended data, a recreated topic, a changed
or missing boundary, stale version, unavailable observation or an unapproved plan
must preserve unknown state. Reconciliation never invents an acknowledged record
or rewrites an external effect as successfully applied.

The same protocol must secure browser UI and named CLI commands. Ordinary
operation status/approval/confirm/execute carry the reviewed plan. Successful
activation/reconciliation is distinct from completion of the background data job;
the CLI retains unknown/executing, paused authorization, stopped and completed
progress semantics.

### Concrete source contract

Both transports use the same typed handler and common mutation kernel:

- `POST /api/v1/automation/data-jobs/{operationId}/reconcile/preview`
- `POST /api/v1/automation/data-jobs/generator/{operationId}/reconcile/preview`
- Browser paths omit `/automation`; browser writes retain CSRF validation.
- Closed request: `{batchId, expectedProgressVersion, proofReferenceSha256, fencedWorkerEvidenceSha256}` and a bounded `Idempotency-Key`.
- CLI: `data-jobs reconcile-preview <parent-id>` or `generator reconcile-preview <parent-id>` with `--request-file` and `--idempotency-key`.
- The returned operation has existing kind `fleetUncertaintyDisposition`, a CRITICAL typed confirmation and an immutable `reconciliationReview`. Use the existing named `operations confirm`, `approval`, `approve`, `reject`, `execute` and `status` commands.
- Job/generator status exposes nullable `progressVersion`; null means durable worker state has not been created.

Progress schema 2 stores the observation. Schema 1 can still be read, but a legacy
pending batch has no proof boundary and remains unknown. CAS permits only the
additive 1→2 promotion; a schema 2 row cannot be written back as schema 1.
Existing workers leave dispatched unresolved pending rows unchanged while the
review is outstanding. Clearing a proven non-application advances the worker
generation and preserves record index/source checkpoint and acknowledgement
counts. It never marks an external record delivered.

## Required actual evidence

The integrated proof must use the real Keycloak requester/approver, shipped API
and CLI, production SQLite/PostgreSQL state and actual Kafka observation:

1. Abruptly kill the worker before physical enqueue after its durable boundary
   and dispatch marker. Physically fence it, observe unchanged UUID/watermarks,
   review/approve the immutable plan and resume exactly once.
2. Append a genuine destination record while the batch is unresolved. The new
   readback must refuse non-application/resume and retain unknown state.
3. Deny same-human approval, changed hashes/policy, stale progress, wrong owner,
   revoked permissions/registration, absent legacy evidence and topic recreation.
4. Independently read the actual destination after resumption and reopen durable
   actor, approver, proof and batch/fence state. No fabricated token or provider
   success substitutes for these observations.

`V08JobReconciliationBoundaryTests` contains source regressions for changed
offsets/topic UUID/physical cluster/partition, legacy evidence, live leases,
version/generation changes, CRITICAL/full-target authority and one-time fencing.
These tests and the physical acceptance scenarios above have not yet been run
against this source checkpoint. No provider acceptance is claimed.
