## G01 - ordinary user creation has no durable cross-system recovery (P1)

**Observed static control flow.** [ManagedIdentityEndpoints.cs](../../src/backend/Kafdeck.Api/ManagedIdentityEndpoints.cs) lines 86-109 calls `provider.Create`, then writes the local managed user and audit. The ordinary-user path has no persistent request intent/receipt or reconcile operation. [ManagedKeycloakUsers.cs](../../src/backend/Kafdeck.Api/ManagedKeycloakUsers.cs) lines 41-55 sends the create request and depends on its response Location. First-owner setup separately persists `Provisioning` before dispatch (endpoint lines 54-58); that protection does not cover ordinary users.

**Failure-path inference, not an executed fault test:** if Keycloak creates the user but the response or subsequent local write is lost, the account can exist in Keycloak without a managed-state row. A retry may return duplicate/conflict and cannot reconcile the intended ID through this endpoint. Local default-deny prevents an unregistered account from gaining managed access; the gap is consistent completion/recovery, not a demonstrated authorization bypass.

**Finite closure:** persist a scoped idempotent provisioning intent; reconcile only a positively identified outcome for that exact request; expose honest unknown/recovery status. Do not adopt an arbitrary preexisting email account. New tests: lost reply after creation, failed local write, exact retry/restart, unavailable Keycloak and unrelated-email collision; demonstrate one intended account and one correct local row/audit, with no accidental role grant.

## G02 - successful Kafka target registration lacks a dedicated audit event (P1)

**Confirmed source gap.** [KafkaConnectionWorkspace.cs](../../src/backend/Kafdeck.Api/KafkaConnectionWorkspace.cs) lines 91-116 saves a registered target and remembers its credentials. The module does not receive/use `ISecurityAuditSink` or emit a registration event; its mapped routes have CSRF and local authorization checks but no registration-audit endpoint filter. Generic access logs are not actor/target/result security audit. In contrast, [registered HTTP settings](../../src/backend/Kafdeck.Api/RegisteredHttpServiceEndpoints.cs) explicitly emit audit events.

**Finite closure:** emit a bounded structured registration result with actual principal, stable target ID and outcome; exclude passwords, certificate/key material and secret-bearing connection data. Tests cover success, duplicate/denial and failed persistence without a false success event. Preserve current auth, network checks and 256-target limit.

## G03 - managed onboarding/connection routes lack a released machine-readable contract (P1)

**Confirmed contract inventory gap.** [ManagedIdentityEndpoints.cs](../../src/backend/Kafdeck.Api/ManagedIdentityEndpoints.cs) maps `/api/v1/setup` and `/api/v1/identity/users`; [KafkaConnectionWorkspace.cs](../../src/backend/Kafdeck.Api/KafkaConnectionWorkspace.cs) and [RegisteredHttpServiceEndpoints.cs](../../src/backend/Kafdeck.Api/RegisteredHttpServiceEndpoints.cs) map registered target/settings/catalog routes. No matching managed route declarations were found in the committed OpenAPI providers/documents. [GovernanceOpenApi.cs](../../src/backend/Kafdeck.Api/GovernanceOpenApi.cs) lines 13-16 only discovers metadata-bearing `/api/v1/governance/` endpoints; [KafdeckApiEndpoints.cs](../../src/backend/Kafdeck.Api/KafdeckApiEndpoints.cs) lines 28-29 serves the static v0.1 contract, not all mapped endpoints.

**Finite closure:** classify the actual managed routes as stable or explicitly internal/experimental, document exact request/response/problem/CSRF/auth/bounds semantics and add route/schema compatibility checks. Avoid renaming existing `/api/v1` or retained v0.8 declarative wire contracts solely to match the product version. General REST/CLI/provider parity beyond admitted families is not introduced here.

## G04 - managed workflows have no matching committed regression cases (P1)

**Confirmed search result, bounded claim.** The recorded search across `tests`, `src/frontend/tests`, `scripts` and non-generated `deploy/dev` found no exact managed class names, setup/users/connections route strings, setup-code flag or initial-owner audit identifier in matching test/script languages. The release-identity test checks documentation links; that is not onboarding regression. This does not claim that indirect coverage is impossible or that historical real manual acceptance never occurred.

**Finite closure:** commit focused managed setup/code expiry/replacement/concurrent owner/unknown provisioning tests, current role/cluster/session checks, target test/save/open and credential expiry/restart cases, and HTTP-service credential retention/denial cases. Use existing Keycloak/Kafka fixtures where feasible. Cover G01/G02 fixes in the same focused tests rather than creating a second broad acceptance project. Preserve truthful mock-vs-live provenance.

## G05 - managed-role capabilities and governance navigation disagree (P2)

**Confirmed static integration mismatch.** [AppShell.tsx](../../src/frontend/src/app/AppShell.tsx) lines 479-483 exposes catalog/policy/requests/attribution pages whenever a user and selected cluster exist. [AuthorizationEnforcement.cs](../../src/backend/Kafdeck.Api/AuthorizationEnforcement.cs) lines 135-139 and 163-168 delegates managed users to [ManagedIdentityEndpoints.Allows](../../src/backend/Kafdeck.Api/ManagedIdentityEndpoints.cs), lines 149-170. That finite allowlist does not grant CatalogRead, governance policy/request/attribution actions, even to the managed owner. [Program.cs](../../src/backend/Kafdeck.Api/Program.cs) lines 63-67 rejects combining managed identity with external subject/group bindings. This is safe denial, but a visible navigation item is not a usable admitted workflow for that mode.

**Finite closure:** publish an identity-mode capability matrix and make menu/disabled-state behavior agree with authoritative capabilities. Keep externally managed OIDC governance support distinct. Do not solve navigation by granting broad new rights or treating owner labels as governance authority. New UI/API checks verify the allowed and denied modes without changing existing effect controls.

## G06 - managed identity/connection state has no explicit version/migration contract (P1)

**Confirmed persistence-contract gap.** [ManagedIdentityStore.cs](../../src/backend/Kafdeck.Api/ManagedIdentityStore.cs) lines 12-14 and 36-69 serialize/deserialize a record directly, without a schema version or managed-state migration ledger. Its atomic rename, disk flush, exclusive lock and issuer/owner validation are existing safeguards. This finding does not allege that current v0.9 files are corrupt.

**Finite closure:** document the legacy v0.9 representation, define accepted/newer-format behavior and an explicit migration-or-format-freeze policy. Any new envelope/migration must preserve verified backups and reject unsupported state instead of silently losing fields. Prove v0.9 -> actual v1.0 restore for users/roles/targets and protected service credentials with the matching key ring and issuer. Database-only upgrade evidence cannot establish this separate file/key contract.

## Q01 - secured credential-cache admission needs a focused probe (not a confirmed defect)

[RegisteredKafkaRuntime.cs](../../src/backend/Kafdeck.Api/RegisteredKafkaRuntime.cs) lines 15 and 34-42 caps the cache at 128 entries and `Remember` returns void; [KafkaConnectionWorkspace.cs](../../src/backend/Kafdeck.Api/KafkaConnectionWorkspace.cs) lines 116-130 returns a successful test after calling it without verifying retention. Examine/test capacity, eviction and lease expiry with concurrent sessions before declaring a defect or raising supported scale. Expected result: usable admitted lease or explicit capacity/reconnect status, never a misleading success. Preserve the intentional 30-minute in-memory lifetime and no-secret persistence. This is one bounded test candidate, not a new load/soak campaign.

## E01 - browser click responsiveness is not established by W82 API budgets

[AppShell.tsx](../../src/frontend/src/app/AppShell.tsx) preserves quiet refresh/page state, and the registered Kafka runtime creates Admin clients per request (lines 57-74), an intentional lifetime boundary that may have handshake cost. [api.ts](../../src/frontend/src/shared/api.ts) lines 701-707 uses caller cancellation without a shared browser deadline; setup also performs a fetch without caller cancellation. These observations do not prove a measured performance regression or justify an unmeasured client-pooling refactor.

W82's admitted API latency distributions are not browser click-to-feedback/navigation results. Collect a small bounded trace for login, cluster selection, topic/group/subject details and ecosystem actions under a stated dataset/network. Agree finite feedback/timeout/cancellation behavior and p95/p99 navigation targets from product needs and measurements; fix only observed violations and verify preserved inputs/focus. Do not relabel a fixture API p99 as UI responsiveness.

## E02 - future upgrade and v1 publication are new evidence/work

The current [publisher](../../publication/v09/driver.py) intentionally pins the accepted v0.9 source/manifest; the legacy release workflow also has version-specific owner phrases. Those are correct immutable release safeguards, not a generic v1.0 publisher. The actual 0.9 -> 1.0 upgrade, chosen RC archives/signatures and a version-specific owner-reviewed release selection do not exist yet. Prepare them after focused fixes and contract decisions; keep the old publisher/tag/signed bytes untouched. Existing W80/W81 success is reusable reference evidence, not a future-version pass.
