# W66 G2 process crash, promotion and stale-backup refusal

Status: all three actual local recovery scenarios passed. Full
N1–N5 and protected-main acceptance remain required. This batch does not widen
production notification HA or claim safe stale-backup resumption.

## Closed recovery contract

The [operator interlock](../operator/v0.8-notification-recovery-interlock.md)
combines an external immutable anchor hash/generation with a separately
offline-enrolled database generation. Host startup never enrolls/advances the
database generation. Quarantine, missing/invalid/hash-changed anchors and epoch
mismatch fail before claims and the concrete physical transport boundaries.
Activation remains optional for legacy deployments; an undeclared rollback with
both old authorities is not detected automatically.

The new test executable `Kafdeck.NotificationSender.Lab` is a separate OS process
using production Generic Host/DI, worker, routing/delivery stores and pinned TLS
transport. It is a tests-only solution project, absent from the production API
dependency graph. Its private input contains references to test connection/CA
files, not credentials in command-line arguments. Output is bounded and does not
export private exceptions. Tests require its actual Release binary.

## Actual native PostgreSQL laboratory

`prepare-postgres-g2-recovery.ps1` uses existing same-version PostgreSQL 16–19
tools. It creates a physical synchronous primary/standby pair, uses
`pg_basebackup` and `pg_verifybackup`, configures `remote_apply`, and retains
barrier/replication evidence. Promotion requires the old primary to be stopped
and its port fenced. Restore uses a verified old physical backup in a fresh third
node with read-only quarantine. Fresh per-case directories are retained; there
is no reset, failback, arbitrary path deletion or automatic sender activation.

The native script has been separately exercised with real replication, a
post-backup commit, old-primary fencing/promotion and a restored older marker
set. Its integrated process-host/TLS scenarios also passed independently below.

## Required integrated proofs

| Scenario | Required real evidence | Current state |

| Crash after physical POST | Read complete TLS POST; query replicated InFlight/one attempt on actual standby; kill independent sender process; fence primary; promote standby; survivor reaches unknown only after real DB stale time; one POST/attempt, no resend | Passed locally: 10,742 ms real DB stale time, one TLS connection, one POST, one attempt, durable UnknownExternalEffect |

| Restore stale Pending backup | Backup Pending/E1, then actually deliver; stop original sender; put new external E2 anchor in quarantine; physically restore old Pending/E1; old hash, quarantine and even active E2/new hash must fail; no new socket/POST | Passed locally: three Release sender processes refused; direct production gate proved epoch mismatch; restored Pending/zero attempts and E1 remained unchanged |

The TLS peer accepts concurrent connections while withholding the first receipt,
so an accidental second connection cannot be hidden behind a blocked first
request. It retains at most eight connection tasks and bounds request bodies.
The restored-epoch check invokes the production gate directly against the actual
restored database before child startup. Thus a read-only DDL failure cannot stand
in for interlock proof. Reads must leave E1 and restored Pending/zero attempts
unchanged.

## Remaining acceptance

This is refusal-only restore safety. Governed offline enrollment, reconciliation
of every restored unresolved intent, terminal fencing, explicit epoch advancement
and safe resumption are not implemented or accepted. The external anchor must
stay outside the restored backup boundary, and the operator must fence all old
senders. Bytes already sent cannot be recalled. Broader production HA, failback,
rolling upgrade and provider-specific operational acceptance remain open.
