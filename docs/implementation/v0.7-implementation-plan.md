# v0.7 Implementation Plan — W51 to W60

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Scope #178; tracker #180.

No W52–W60 source implementation may start until W51 is admitted to protected `main`.

## Global rules

Every workstream starts from the latest protected `main`, reconciles live issues/PRs/checks/reviews, and preserves:

- existing protected-main governance;
- DCO / Conventional Commit policy;
- exact-head CI and review evidence;
- expected-head guarded merge;
- server-authoritative RBAC/risk/approval/audit;
- provider capability truth;
- no generic execution/proxy bypass;
- finite budgets and cancellation;
- durable ambiguity/fencing semantics;
- air-gap/no mandatory SaaS boundary.

Material head changes invalidate prior exact-head CI/review evidence.

## Dependency graph

Primary conservative sequence:

`W51 -> (W52 + W53) -> (W54 + W55) -> W56 -> (W57 + W58) -> W59 -> W60`

Permitted overlap after planning admission:

- W53 may begin while W52 is active only after schema read/reference contracts used by W53 are stable on an admitted branch/main baseline.
- W55 may begin while W54 is active only after typed restart/status/profile contracts are stable; it may not invent its own Connect execution path.
- W56 is architecturally independent and may move earlier if doing so does not destabilize W57/W58 interfaces.
- W59 read-oriented topology/lineage work may move earlier if it does not depend on unfinished data-job/Connect mutation contracts.
- W60 UX scaffolding may begin against merged stable APIs, but release readiness waits for all admitted v0.7 dependencies.

The tracker #180 records live dependency-valid activation.

## Branch/PR discipline

- feature branches start from exact latest protected `main`;
- prefer simple branch names if connector constraints require;
- use high-level GitHub writes where practical;
- no meaningless heartbeat commits;
- every source-head change requires fresh exact-head CI/review;
- independent reviewer must be requested at review readiness;
- never self-approve;
- expected-head guarded merge only;
- tracker/active issue updated immediately after advancement.

## Stop/escalation conditions

Escalate to owner only for:

- material scope/architecture/security departure;
- provider capability gap that would require bypass/unsafe substitute;
- release/publication decision;
- external credentials/access not available to normal CI/fixtures;
- required CI failure that cannot be deterministically repaired;
- persistent remote write failure;
- stalled mandatory independent review.

Ordinary deterministic defects are fixed autonomously within the admitted scope.
