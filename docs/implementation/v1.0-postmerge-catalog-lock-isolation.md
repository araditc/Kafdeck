## Cause and finite fix

`G2CliPostgreSqlDatabase` ordinarily isolates rows using a fresh schema in one configured database. PostgreSQL advisory lock key `64964007301` is database-wide, so a different schema does not isolate it. The catalog concurrency test holds a shared lock while expecting other shared readers to proceed. An unrelated fixture's queued exclusive catalog writer can block those readers; PostgreSQL does not let them bypass that writer. The observed Npgsql read timeout occurred at the shared advisory lock in `StageAsync`, not at the deliberately blocked commit assertion.

A physical PostgreSQL probe confirms that an exclusive holder in schema A blocks the same shared key in schema B (`55P03` with a 500ms lock deadline), while the same key succeeds in another database. This is fixture interference, not evidence that reader transactions should bypass pending product writers.

Only this advisory-lock scenario now requests independently named private databases. Its competing foreign writer also owns a private database, so the strengthened regression does not impose its own lock on other tests. Ordinary fixtures retain their existing schema isolation. The database is created/dropped using only a generated `g2_cli_<GUID>` identifier; no caller-controlled database name, operator database deletion or forced backend termination is added. A dedicated test role needs `CREATEDB`; production role requirements are unchanged. CI's explicit PostgreSQL laboratory role already has this permission.

The test keeps eight concurrent previews, matching/different-payload idempotency, unchanged entities, a shared generation holder, the three-second command timeout, the expected same-database exclusive commit timeout, and a successful commit after releasing that holder. Product SQL, lock keys/order, authorization, restore generation and timeouts are unchanged. No retry, skip, longer deadline or test quarantine hides the failure.
