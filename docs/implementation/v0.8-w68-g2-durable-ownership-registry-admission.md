# W68 G2 — Durable Ownership Registry: CAS and HA Admission Contract

Evidence: W67 #332, W68 G0 #345, G1 #346–#348 and ownership-proof guard #349. Last admitted protected-main revision at drafting: `b881def33a359545b82a7d90928cce93396cae6d`. Keep #217 OPEN.

## Resource identity and claim authority

The canonical storage key must be the exact tuple `(deployment_id, admitted_scope_kind, admitted_scope_id, resource_kind, resource_id)`. Each component is server-normalized, bounded, nonblank and compared with ordinal/case-sensitive semantics, not repository-path or user-display-name semantics. Only resource kinds separately admitted by the capability matrix may be owned. A registered `source_id` resolves to a server-allowlisted repository/path and source revision; client `ownerRef` is never itself owner registration evidence.

An ownership record must bind `registered_owner_id`, `registered_source_id`, a strictly increasing `ownership_revision` allocated from a durable per-key high-water ledger and never-reused `ownership_generation_id` (UUID), a fenced `lease_epoch` that MUST match the authoritative controller lease in the very same transaction where controller-issued ownership CAS occurs, state, issuer/subject/registered client identity of the authorized claimant, current evidence fingerprint, policy version and immutable audit operation reference. `generation_id` prevents stale proof reuse after relinquish and recreation with identical owner/source strings. Ownership revisions must not reset on the same canonical resource key after relinquish. Soft tombstones must survive a configured bounded retention period; no implicit delete/recreate to evade competing claims.

**Candidate SQL shape (design only):**

```sql
CREATE TABLE kafdeck_declarative_ownership (
  deployment_id VARCHAR(128) NOT NULL,
  admitted_scope_kind VARCHAR(64) NOT NULL,
  admitted_scope_id VARCHAR(128) NOT NULL,
  resource_kind VARCHAR(64) NOT NULL,
  resource_id VARCHAR(128) NOT NULL,
  registered_owner_id VARCHAR(128) NOT NULL,
  registered_source_id VARCHAR(128) NOT NULL,
  registered_source_generation_id VARCHAR(36) NOT NULL,
  generation_id VARCHAR(36) NOT NULL,
  ownership_revision BIGINT NOT NULL,
  lease_epoch BIGINT NOT NULL,
  ownership_state VARCHAR(32) NOT NULL,
  evidence_fingerprint CHAR(64) NOT NULL,
  claimant_principal_id VARCHAR(256) NOT NULL,
  policy_version VARCHAR(128) NOT NULL,
  audit_operation_id VARCHAR(128) NOT NULL,
  updated_at_utc VARCHAR(40) NOT NULL,
  PRIMARY KEY (deployment_id, admitted_scope_kind, admitted_scope_id, resource_kind, resource_id),
  CHECK (ownership_revision >= 1),
  CHECK (lease_epoch >= 0)
);
```

A permanent `kafdeck_declarative_ownership_key_versions` table must retain each scoped resource key's **monotonic revision high-water mark and previously allocated generation IDs** after claim/tombstone retention expires. New generations and revisions are allocated atomically with the ownership row, in the same transaction. Registered source registrations must be immutable per registration generation: rebinding an existing source ID to a different repository/path requires a newly registered generation and separately admitted transfer, never silent inheritance. The controller lease epoch must be checked against its **authoritative lease row** and the expected epoch included in the ownership CAS predicate in that same transaction; row locks alone do not fence expired actors.

For a deployment-global resource, the scoped pair must use a reserved, server-defined scope kind and ID rather than client-provided blank strings. For cluster/profile-bound families, bind the exact server-approved cluster/profile pair and reject cross-scope read/adoption even where resource IDs match.

This is not a portable approved migration: SQLite/PostgreSQL timestamp, locking and monotonic generation handling must be specified in provider-specific migrations and proven by tests. No production table is created by this PR.

## Transactional CAS and claim protocol

1. Authenticate via the existing backend OIDC principal, verify registered client and current action/scope rights, including `declarative.adopt` **and exact current-state read**. Denial precedes identity disclosure. The manifest itself confers zero permission.
2. Read the authoritative resource state with capability evidence, fresh timestamp and complete exact-scope authorization. `Unknown`, `Inaccessible`, `Unsupported` or source ambiguity cannot issue a claim.
3. On PostgreSQL, begin transaction and lock exact key or transaction-scoped advisory lock; on SQLite, use a bounded immediate writer transaction. Do not use process-local locks for cross-node correctness.
4. In the transaction, check current registered owner/source, `generation_id`, registered source generation, revision, policy version, authoritative current lease epoch and claim evidence. New adoption requires absence of a previous active claim and an authorized explicit adopt action; never silently adopt on YAML equality.
5. Execute a single conditional `INSERT` for a genuinely unowned key or conditional `UPDATE ... WHERE ownership_revision = :expected AND generation_id = :expected_generation AND registered_source_generation_id = :expected_source_generation AND lease_epoch = :expected_lease_epoch AND ...` for a separately admitted lifecycle transition. Exactly one changed row constitutes acceptance. Any zero rows, deadlock, timeout, ambiguous commit or duplicate key is `Conflict/Unknown` pending durable readback, never success or blind retry.
6. Audit and operation/ownership ledger must commit atomically or through an admitted transactional outbox; no state transition without durable attribution. Return a server-issued immutable ownership proof bound to exact resource, owner, source, generation, revision, issue time and expiry.
7. Independent cross-principal approval (where risk requires it) is never satisfied by Git commit identity or CI signature. Apply/destroy remain separately gated by stored plans and all underlying effect rights.

## Ownership read and drift truth

Read observation is not a claim. The read adapter must bind its current rights to the initiating principal and revalidate after every async boundary before disclosure. It must compare a fresh, exact registered ownership generation/revision with current persisted state **after** observing the subscription, so interleaved adoption, transfer, retirement and revocation cannot yield false `InSync`, `Missing` or `OutOfSync`. An owner mismatch is `Conflict`. Unavailable persistence, uncertain commit or stale read is `Unknown`. No read right is `Inaccessible`. Terminal `Retired` is `Conflict`, never repairable drift.

The current candidate `CandidateOwnershipEvidenceGuard` validates revision/identity/expiration but has no backing registered owner read, no generation UUID and no source authorization. It must NOT be described as a live ownership registry.

## Required real-DB gates

- SQLite and PostgreSQL migrations, unique-key / case semantics and schema upgrade/rollback tests.
- Two independent connections/processes race to adopt one exact key: one winner only; other conflict; no hidden-owner disclosure.
- Revision and never-reused generation reject stale proof after release/recreate with identical owner/source; stale lease epoch is fenced.
- Competing registered repository/path sources sharing the same owner must conflict, including HA failover and racing controller retries.
- Concurrent owner transfer, withdrawal/relinquish, subscription retirement and destination move cannot create false successful drift.
- Crash before/after SQL commit; ambiguous commit reconciles from ledger and does not reissue mutation.
- Current policy/input and bearer identity revocation across awaits, scope collisions, missing source registry, unauthorized read/adopt and exact test of distinct-principal critical approval.
- No plaintext credentials in schema, log, manifest, preview, state or error; no GitOps ownership without registered service-principal grant.
