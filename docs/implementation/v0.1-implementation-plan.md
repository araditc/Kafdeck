# v0.1 Implementation Plan — Cluster Explorer

- **Status:** READY AFTER PHASE 0 ADMINISTRATIVE GATE
- **Scope authority:** Gate 1 / RFC-0001
- **Long-term alignment:** Gate 2
- **Implementation start blocker:** GitHub Issue #3 must be closed before product source implementation begins.
- **Language:** English

## 1. Objective

Implement the accepted Kafdeck v0.1 Cluster Explorer as a read-only, multi-cluster, bounded-impact Apache Kafka control-plane observer.

The implementation MUST preserve the accepted v0.1 invariants:

- no Kafka mutation endpoints,
- no direct ZooKeeper connectivity,
- no credential persistence in Kafdeck durable state,
- local-only HTTP binding by default,
- mandatory deployment access token for non-loopback binding,
- capability-first behavior rather than guessed server-version behavior,
- per-cluster isolation and bounded Kafka load,
- explicit partial/denied/stale states,
- no Kafka payload browsing in v0.1.

This plan decomposes the accepted design. It does not create a new architecture gate.

## 2. Delivery strategy

Implementation uses short-lived PRs against `main`. Each workstream must be independently reviewable, testable and revertible.

Recommended sequence:

`W01 -> W02 -> W03 -> W04 -> W05 -> (W06 + W07) -> W08 -> W09 -> W10 -> W11`

Parallel work is permitted only where contracts are already stable and merge-base drift is controlled.

## 3. Workstreams

### W01 — Solution and application scaffold

Deliverables:

- .NET 10 solution and backend project structure aligned with the accepted modular-monolith boundary,
- React + TypeScript frontend scaffold,
- deterministic local build commands,
- central dependency/version management where appropriate,
- baseline unit-test projects,
- frontend unit/component test harness,
- development configuration examples containing no real secrets,
- source-aware CI activation for backend/frontend jobs.

Initial logical backend boundaries:

```text
src/backend/
  Kafdeck.Api/
  Kafdeck.Core/
  Modules/
    Kafdeck.Modules.Clusters/
    Kafdeck.Modules.Topics/
  Infrastructure/
    Kafdeck.Infrastructure.Kafka/
    Kafdeck.Infrastructure.Configuration/
    Kafdeck.Infrastructure.Security/
```

Frontend boundary:

```text
src/frontend/
  src/
    app/
    features/clusters/
    features/brokers/
    features/topics/
    features/health/
    shared/
```

Exit criteria:

- clean backend build,
- frontend build succeeds,
- empty test suites are replaced by at least one meaningful architecture/configuration test,
- existing quality gates remain green.

### W02 — Configuration, secret references and deployment access boundary

Deliverables:

- strongly typed Kafdeck configuration model,
- immutable v0.1 cluster profiles loaded at startup,
- `env:` secret references,
- mounted `file:` secret references,
- validation for bootstrap servers and connection/security combinations,
- loopback-only default binding,
- fail-closed non-loopback binding without access token,
- deployment access-token middleware/filter boundary,
- secret-safe diagnostics/redaction.

Negative tests MUST prove:

- raw configured secret values are never serialized through product APIs,
- access tokens are not logged,
- missing remote token fails closed,
- invalid secret references fail configuration validation,
- TLS validation is never silently disabled.

### W03 — Kafka ports, models and error/capability contracts

Deliverables:

- Kafdeck-owned Kafka administration port,
- Kafdeck-owned cluster/broker/topic/partition models,
- capability model from Gate 1,
- normalized failure categories,
- observation/freshness model,
- no `Confluent.Kafka` type visible outside the Kafka infrastructure adapter.

Required inner operations:

- `GetClusterMetadata`
- `ListTopics`
- `GetTopicMetadata`
- `GetTopicConfiguration`
- `GetBrokerConfiguration`
- `GetCapabilities`

Architecture tests MUST reject infrastructure-client type leakage into application/API contracts.

### W04 — Kafka adapter and per-cluster client lifecycle

Deliverables:

- Confluent.Kafka adapter behind W03 ports,
- one long-lived client lifecycle per configured cluster,
- connection support for accepted v0.1 combinations:
  - `PLAINTEXT`,
  - `SSL`, including client-certificate mTLS,
  - `SASL_PLAINTEXT` with accepted mechanisms,
  - `SASL_SSL` with `PLAIN`, `SCRAM-SHA-256`, and `SCRAM-SHA-512`,
- authentication/TLS/configuration error normalization,
- authorization-denied differentiation,
- capability probing without authoritative broker-version guessing.

The adapter MUST be cancellable and deadline-aware.

### W05 — Snapshot coordinator and load-protection runtime

Deliverables:

- immutable per-cluster metadata snapshots,
- independent per-cluster concurrency limiters,
- global limiter,
- single-flight refresh,
- accepted cache TTL defaults,
- stale-on-transient-error behavior,
- cancellation propagation,
- bounded retry with backoff/jitter for transient reads only,
- cache-isolation tests across clusters.

Accepted starting budgets from Gate 1:

| Control | Default |
|---|---:|
| Kafka operation deadline | 10 s |
| Per-cluster admin concurrency | 8 |
| Global admin concurrency | 64 |
| Cluster/broker metadata TTL | 5 s |
| Topic metadata TTL | 10 s |
| Topic/broker config TTL | 30 s |
| Stale-on-error maximum age | 60 s |
| Topic page size | 50 |
| Maximum topic page size | 200 |
| UI overview refresh minimum | 10 s |

No unbounded configuration value is accepted for concurrency, page-size or retry controls.

### W06 — Cluster, broker and health module

Deliverables:

- cluster listing/detail projection,
- cluster ID and current-controller visibility when observable,
- broker list/detail,
- broker configuration read on demand,
- evidence-based `Healthy`, `Degraded`, `Unavailable`, `Unknown`,
- authorization/capability limitations separate from operational health,
- observed timestamp/freshness on every Kafka-derived projection.

Health must remain explainable. It must not collapse ACL denial into outage.

### W07 — Topics and partitions module

Deliverables:

- searchable topic list over cached snapshot,
- bounded cursor pagination,
- topic detail,
- partition leader/replica/ISR views,
- offline/no-leader/under-replicated anomaly projection,
- topic configuration read on demand,
- internal-topic marker only where reliably observable,
- no per-row Kafka request fan-out.

Tests MUST cover very large topic counts and prove absence of N+1 config reads.

### W08 — HTTP API, OpenAPI and observability

Deliverables:

- `/api/v1` endpoints accepted by the v0.1 API contract,
- RFC 9457 Problem Details semantics,
- common observation/limitation envelopes,
- OpenAPI document checked into or reproducibly generated by CI,
- W3C trace context/OpenTelemetry integration,
- bounded-cardinality metrics,
- health/readiness endpoints that do not disclose credentials.

Contract tests MUST enforce that no Kafka mutation route exists in v0.1.

### W09 — React operator UI

Deliverables:

- application shell,
- cluster selector,
- cluster overview,
- broker list/detail,
- topic search/list/detail,
- partition table,
- configuration views,
- explicit loading/empty/error/denied/partial/stale states,
- keyboard navigation,
- accessibility baseline,
- visibility-aware refresh behavior where practical.

No mutation control may be present.

### W10 — Integration, security and compatibility validation

Deliverables:

- real containerized Kafka integration suite,
- accepted Kafka compatibility matrix,
- TLS and mTLS tests,
- SASL PLAIN/SCRAM tests over accepted transports,
- authorization-denied and partial-access tests,
- unavailable/slow cluster tests,
- single-flight/cache-stampede tests,
- high-topic-count and memory-behavior tests,
- remote-access negative security tests.

Tier 1 is recalculated against Apache Kafka supported releases at release-candidate time. The Gate 1 design-date matrix remains historical evidence, not a permanently frozen future matrix.

### W11 — Packaging, operator documentation and v0.1 release evidence

Deliverables:

- single OCI image,
- self-contained deployment path where practical,
- local Docker/Kafka development instructions,
- configuration reference,
- connection/security examples using secret references only,
- troubleshooting guide,
- compatibility matrix documentation,
- known limitations,
- SBOM/container scan/signing workflow as release infrastructure becomes active,
- exact-head release evidence bundle/reference.

v0.1 release remains blocked unless Phase 0 repository/security administration requirements are satisfied.

## 4. Pull-request slicing rules

- Prefer one workstream per PR; split a workstream further if review becomes too large.
- Do not combine architecture changes with unrelated UI work.
- Kafka adapter changes require real integration evidence when behavior changes.
- Security-boundary changes require threat-model delta review.
- Public API changes require contract-test changes in the same PR.
- New configuration must include validation, documentation and secure defaults.
- New polling/fetch behavior must declare its Kafka request/load impact.
- New dependency additions require license and security review.

## 5. Definition of Done for every v0.1 workstream

A workstream is not complete until all applicable items are true:

- implementation complete,
- unit/module/integration tests appropriate to the boundary,
- negative/error paths tested,
- security/redaction behavior reviewed,
- load/concurrency behavior bounded,
- OpenTelemetry behavior added where relevant,
- documentation updated,
- no unresolved review thread,
- exact-head required CI green,
- no merge-base drift,
- squash merge with expected-head guard.

## 6. Dependency and license discipline

Kafdeck remains Apache-2.0. Dependency selection must preserve the accepted license policy.

Implementation should prefer platform/framework capabilities before introducing third-party packages. Every new runtime dependency must have a concrete purpose, active maintenance evidence, acceptable license and bounded supply-chain cost.

Avoid libraries whose current licensing would impose an unexpected commercial obligation on Kafdeck users or contributors.

## 7. Phase 0 implementation-start gate

Product source implementation SHALL NOT begin until Issue #3 confirms the repository's required administrative controls, including protected `main`/ruleset behavior and required status checks.

Documentation, issue decomposition, dependency housekeeping and non-product planning may continue while Issue #3 is open.

Once Issue #3 closes, W01 becomes the first authorized source implementation workstream.

## 8. v0.1 release exit gate

The v0.1 release candidate requires all of the following:

- W01–W11 complete,
- no Kafka mutation route/control,
- Tier 1 compatibility evidence green on exact release head,
- access/security negative tests green,
- threat-model delta reviewed,
- API/OpenAPI contract versioned,
- air-gapped operation documentation complete,
- operator docs complete,
- no unresolved Critical/High security finding accepted without an explicit governed exception,
- Phase 0 administrative repository controls verified.
