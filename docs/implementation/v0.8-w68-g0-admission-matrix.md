## 2. Canonical identity and immutable ownership

A candidate resource identity is a *tuple* of server-stable deployment ID, admitted cluster/profile ID where applicable, typed resource kind, and canonical resource ID. Repository path, YAML name, operator display label and upstream resource name are not sufficient identity.

Proposed durable ownership record:

- `resourceKey`: canonical tuple with exact case and normalization policy
- `ownerId`: server-registered owner identity (not trusted from `ownerRef` in a manifest)
- `ownerRevision`: monotonic CAS version
- `sourceIdentity`: backend-registered GitOps source ID scoped to an allowlisted repository and manifest path, plus exact source revision/fingerprint. A different source sharing the same owner must not alternate desired state without a separately authorized source-transfer CAS; a manifest-supplied source claim is never authority.
- `ownershipState`: `Unowned | Managed | Relinquished | TransferPending` (names provisional; `ObservedOnly` is an observation classification, **not an ownership claim**)
- `adoptionEvidenceFingerprint`, last-authorized observation revision, server time, claimant principal identity and audit operation reference
- Unique persistence constraint on `resourceKey`, transactional CAS and fencing across nodes

No owner is inferred from a manifest, source-control author, service principal label or matching remote object. Adoption and transfer are independently governed actions with exact read rights. Owners cannot be silently stolen during drift repair.

## 3. G0 closed desired-state shape

Candidate manifest keys: `apiVersion`, `kind`, `metadata.deploymentRef`, `metadata.name`, `metadata.ownerRef`, `spec.destinationRef`, `spec.state`, `spec.eventClasses`, `spec.eventTypes`. Existing candidate JSON `CandidateSubscriptionManifest.ParseJson` requires a top-level `deploymentRef`; G1 must explicitly version and test an unambiguous migration/mapping to the proposed YAML `metadata.deploymentRef` before treating it as stable. Neither position is authority by itself: the backend resolves and authorizes the registered deployment scope. Allowed values and normalization must be pinned from actual NotificationSubscription typed DTOs before an API or CLI contract is marked stable.

A future strict parser must reject all unknown and duplicate keys, aliases, anchors, YAML merge keys, unsupported versions, excessive bytes, depth/nodes and non-normalized identities **before** any effects or object graph expansion. No free-form URL, provider configuration, custom headers, arbitrary JSON, script or plaintext secret field is allowed. `ownerRef` is only a lookup hint: server authorization resolves the owner.

## 4. Staged delivery and admission gates

**G0 — candidate selection (this PR):** propose the initial family and exact scope, review identity normalization, name/type versioning, readback/CAS guarantees and owner/adoption policy; Codex and CODEOWNER review before protected-main merge. **Neither G0 merge nor this candidate list admits a resource family or authorizes G1 runtime.** Admission is a separate owner decision and evidence gate. No runtime action.

**G1 — pure validate / inspect:** strict schema and bounded parser + canonical projections, typed filtered observation, truth-valued drift `InSync | OutOfSync | Missing | Unknown | Inaccessible | Conflict | Unsupported`, negative authorization and fuzz/alias/budget tests. No ownership acquisition, mutation, controller or hidden metadata disclosure.

**G2 — durable owned planning:** owner registry migrations for actual supported SQL providers; conflicting claims and HA CAS/fencing proof; if adoption is authorized, require a positive read-authorized + `declarative.adopt` + fresh-evidence + CAS successful ownership claim and simultaneous competing-claim rejection (in addition to negative proofs); otherwise adoption remains expressly unsupported. Immutable server-stored `planId`, `planFingerprint`, initiator registration and authorization scope, desired/current evidence, policy version/input fingerprint, expiry and redacted approver view. No code generation from client plans. Deny cross-principal plan takeover and unauthorized current-state reads.

**G3 — governed apply:** separate `declarative.apply` AND every underlying `NotificationManage` permission at effect time; stored immutable plan and current owner/plan/policy revision must match. Reuse the admitted effect path and human CRITICAL approval; never treat `AwaitingApproval` or `ExecutionUnknown` as success or blindly retry. No terminal `Retired` reversal or implicit destroy.

**G4 — CLI/GitOps:** versioned REST/CLI parity; runner with registered OIDC service principal, scope-bound manifest sources, bounded reconciliation, dry-run safety, durable operation polling. Git commit and CI identity never grant Kafdeck ownership/permission.

**G5 — acceptance:** real SQLite/PostgreSQL concurrency, current-state drift, stale policies, revocation, denied plan/adopt/apply and (only if adoption was independently admitted) positive read-authorized adoption with fresh evidence/unique ownership CAS and competing-source denial, distinct-human CRITICAL approval, restart recovery, redaction and cross-tenant/owner negative tests; exact-head Quality/CodeQL/provider tests, fresh Codex/CODEOWNER and protected-main post-merge checks.

Each slice requires an explicit PR and evidence. Do not describe partial G1/G2 support as completed GitOps and do not unlock W69 Terraform until one lifecycle family is stable end-to-end.
