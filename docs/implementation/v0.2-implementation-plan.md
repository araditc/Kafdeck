# v0.2 Implementation Plan — Operator Identity and RBAC

- **Status:** PROPOSED
- **Scope authority:** Issue #57 / RFC-0002
- **Implementation start gate:** RFC-0002 planning PR must be independently approved and merged
- **Language:** English

## 1. Objective

Implement OIDC-backed operator identity and default-deny RBAC while preserving the v0.1 Kafka read-only and metadata-only boundaries.

## 2. Workstream sequence

```text
W12 Identity contracts & access-mode foundation
      |
      +--> W13 OIDC session adapter
      |
      +--> W14 Authorization policy engine
                |
                v
W15 API/UI authorization enforcement
                |
                v
W16 Audit & security hardening
                |
                v
W17 Integration, operator documentation & v0.2 readiness
```

W13 and W14 may proceed in parallel after W12 contracts are stable.

## 3. W12 — Identity contracts and access-mode foundation

Deliver:

- Kafdeck-owned identity/session contracts,
- AccessMode Local/Token/Oidc configuration model,
- canonical issuer+subject identity,
- authentication/authorization error categories,
- bootstrap/session response contracts,
- regression tests preserving v0.1 Local/Token behavior.

Exit criteria:

- no OIDC provider SDK types in inner contracts,
- no Kafka mutation/payload surface,
- existing v0.1 tests green.

## 4. W13 — OIDC session adapter

Deliver:

- OIDC Authorization Code + PKCE flow,
- discovery/JWKS validation,
- state/nonce/correlation handling,
- server-managed session/ticket store,
- secure cookie configuration,
- login/logout endpoints,
- OIDC client-secret secret-reference integration,
- controlled test OIDC authority.

Exit criteria:

- protocol negative tests green,
- no OIDC tokens in browser storage/API,
- invalid provider state fails closed.

## 5. W14 — Authorization policy engine

Deliver:

- permission/action vocabulary,
- role model,
- subject/group bindings,
- cluster/resource scopes,
- bounded glob matcher,
- immutable compiled authorization snapshot,
- startup validation,
- fast in-memory evaluator with explanation/reason categories.

Exit criteria:

- default deny proven,
- invalid policy cannot activate,
- deterministic pattern bounds,
- unit matrix green.

## 6. W15 — API/UI enforcement

Deliver:

- server-side route authorization,
- cluster-list filtering,
- topic/broker/config-read permission enforcement,
- 401 vs 403/Kafka-denied semantics,
- UI operator identity/sign-out state,
- unauthorized/forbidden UX,
- client cache/session reset on identity change,
- OpenAPI authorization documentation.

Exit criteria:

- direct-route bypass tests green,
- UI cannot reveal unauthorized cluster/resource metadata,
- backend remains authoritative.

## 7. W16 — Audit and security hardening

Deliver:

- security audit event contract/sink,
- login/logout/denial audit events,
- sensitive-read audit policy hooks,
- log/Problem Details redaction tests,
- session fixation/CSRF/open-redirect hardening,
- legacy-token bypass regression tests,
- v0.2 threat-model reconciliation.

Exit criteria:

- no secret/token leakage,
- no Token-mode bypass in OIDC mode,
- security review findings resolved.

## 8. W17 — Integration, documentation and v0.2 readiness

Deliver:

- operator OIDC configuration guide,
- RBAC policy examples without secrets,
- upgrade guide from v0.1 Local/Token,
- air-gapped/private IdP guidance,
- complete identity/RBAC integration suite,
- performance evidence for authorization evaluation,
- release/readiness evidence.

Exit criteria:

- exact-head required CI green,
- Kafka compatibility matrix still green,
- no mutation/payload regression,
- independent final review,
- v0.2 release decision handled by a separate release gate.

## 9. Data/persistence posture

v0.2 does not require a local-user database.

Role/policy configuration is deployment configuration.

Active sessions are ephemeral server state; restart invalidation is acceptable for v0.2.

Durable audit history/UI and shared multi-replica session persistence are deferred.

## 10. API/security invariants

Every workstream MUST preserve:

- no Kafka mutation route,
- no payload browse/produce/consume route,
- no deployment-token-to-user-identity conversion,
- default-deny authorization,
- no secret material in API/log/audit,
- Kafka ACL denial remains distinct from Kafdeck RBAC denial.

## 11. Merge discipline

Each workstream uses:

- branch from exact live `main`,
- exact-head CI,
- independent approval,
- resolved review threads,
- expected-head merge guard,
- post-merge reconciliation before activating dependent work.
