## Runtime shape

```text
UI / API client
      |
      v
Mutation HTTP API
      |
      v
Mutation Coordinator
  |   |    |     |
  |   |    |     +--> Authorization + Risk Policy
  |   |    +--------> Preview Builder / Canonicalizer
  |   +-------------> Operation Repository / Idempotency / Approvals
  +-----------------> Audit

Durable Operation Store
      |
      v
Bounded Mutation Executor
      |
      +--> Conflict Claim / Precondition Revalidation
      +--> Typed Kafka Admin Port
      +--> Typed Producer Port
      +--> Typed Consumer Admin Port
      +--> Typed Schema Registry Write Port
      +--> Typed Connect Write Port
      +--> Typed DeleteRecords Port
```

No provider adapter is callable from the public API without the coordinator/state-machine boundary.

## Module boundaries

### Administration Operations
Owns:
- mutation operation aggregate,
- canonical intent types,
- risk decision,
- preview,
- confirmation/approval state,
- idempotency binding,
- conflict claims,
- execution orchestration,
- verification result.

### Identity & Access
Owns authorization decisions. The mutation module asks for an explicit action/resource decision; it does not interpret groups/claims directly.

### Audit
Receives structured state-transition/security events. Mutation persistence is not a replacement for audit.

### Kafka / Schema / Connect adapters
Implement Kafdeck-owned typed ports. Vendor/client SDK types do not cross into application/domain contracts.

## Persistence prerequisite

Read-only Kafdeck remains database-optional.

When mutation mode is enabled, Kafdeck requires durable operation persistence:
- SQLite: supported only for standalone/single-instance mutation execution,
- PostgreSQL: required for multi-instance/HA mutation execution.

Startup validation exposes mutation capability as unavailable when the configured provider cannot satisfy these requirements.

## Canonicalization

Every typed intent has a deterministic canonical serializer:
- stable property order,
- normalized resource names,
- explicit null/optional semantics,
- sorted target sets where order is not semantically meaningful,
- normalized numeric/time representation,
- no culture-dependent formatting.

`PreviewHash = SHA256(canonical-intent + cluster + targets + preconditions + risk + policy-version + expiry)`

The hash is evidence/binding, not a substitute for server-side persisted state.

## State machine

```text
Previewed
   |
   v
AwaitingConfirmation
   | confirm
   +-------------------+
   |                   |
   v                   v
Ready            AwaitingApproval
                     |
               approve/reject
                     |
                     v
                   Ready
                     |
                atomic claim
                     v
                 Executing
                     |
       +-------------+-------------+-------------------+
       |             |             |                   |
       v             v             v                   v
AppliedVerified  AppliedUnverified PartiallyApplied ExecutionUnknown
```

Additional terminal/interruption states:
`Expired`, `Cancelled`, `Rejected`, `StalePreview`, `FailedBeforeDispatch`, `FailedDefinitive`.

Only allowed transition methods exist on the aggregate; database code cannot freely assign arbitrary states.

## Idempotency

The repository owns a unique binding on:
`PrincipalId + ClusterId + OperationKind + IdempotencyKeyHash`.

Creating the same intent returns the existing operation. Different intent under the same binding is a conflict.

Execution claim uses a transaction/CAS transition `Ready -> Executing` and increments a fencing generation. A second worker cannot dispatch the same operation.

## Conflict claims

Before dispatch, the executor atomically claims all canonical resource keys in sorted order.

A claim includes:
- operation ID,
- resource key,
- fencing generation,
- lease/heartbeat where execution may be long-running.

The claim coordinates Kafdeck workers only. It does not replace resource precondition checks against Kafka/provider state.

## Executor behavior

The executor:
1. claims a Ready operation,
2. validates durable state and expiry,
3. acquires conflict claims,
4. re-authorizes requester/approval policy when required by policy versioning,
5. rechecks provider capability,
6. re-observes material preconditions,
7. marks dispatch start durably,
8. invokes exactly one typed mutation path,
9. maps provider outcome without unsafe retry,
10. performs bounded verification,
11. stores result,
12. emits audit transition,
13. releases conflict claims.

If durable state cannot be safely written before dispatch, execution stops.

## Ephemeral execution material

Some operations need bytes/secrets that Kafdeck intentionally does not persist:
- Kafka record payloads,
- secret connector fields.

For these operation kinds:
- preview stores cryptographic digest + safe metadata,
- confirmation/finalization request re-submits material,
- server recomputes digest,
- mismatch invalidates the operation,
- admitted execution occurs only while validated material is present in memory,
- material is cleared/released after request execution and never enters logs/audit.

Such operations remain MODERATE in the base model. If deployment policy escalates them to a delayed independent-approval workflow, Kafdeck v0.5 reports that policy combination unsupported rather than persisting plaintext material implicitly.

## Verification

Verification is typed:
- topic create/delete/config/partition count: re-read metadata/config,
- consumer offsets: re-read committed offsets,
- schema mutation: re-read subject/version/config,
- Connect: re-read connector/status/config projection,
- DeleteRecords: observe low-watermark/evidence where supported,
- produce: broker acknowledgement partition/offset is execution evidence; Kafdeck does not scan the topic to “prove” payload equality.

A successful provider call with inconclusive verification becomes `AppliedUnverified`, not failure.

## Failure and retry

Pre-dispatch transient failures may be retried within bounded policy.

After `DispatchStartedAtUtc`:
- retry is allowed only when the typed adapter can prove the previous attempt was not externally dispatched/applied,
- otherwise the operation becomes `ExecutionUnknown`,
- reconciliation/verification may later resolve it.

No generic Polly/retry policy wraps mutation calls indiscriminately.

## Per-cluster isolation

Mutation executors have independent concurrency budgets from:
- metadata refresh,
- record browsing,
- consumer read views,
- Schema/Connect/ksql read views.

A slow destructive operation must not starve read-only operator visibility.

## HA notes

SQLite mutation execution is single-instance only.

PostgreSQL mode uses transactional uniqueness/CAS rows for:
- operation state,
- idempotency bindings,
- resource conflict claims.

No in-memory mutex is considered sufficient for HA mutation coordination.

## API execution ownership

The HTTP API creates/confirms/approves/cancels operations. It does not invoke provider clients directly.

Once requirements are satisfied, the coordinator/executor controls dispatch. This preserves one policy boundary for UI and direct API clients.

## Architecture tests

CI must reject:
- public application contracts that expose raw Confluent.Kafka admin/producer types,
- generic provider URL/method/path execution,
- mutation adapters reachable directly from HTTP handlers,
- mutation mode without persistence prerequisite,
- CRITICAL path without distinct-principal approval,
- audit/log DTOs containing raw record payload/secret fields.
