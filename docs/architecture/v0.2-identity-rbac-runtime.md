# v0.2 Runtime Architecture — Operator Identity and RBAC

- **Status:** PROPOSED
- **RFC:** RFC-0002

## Architectural objective

Add identity and authorization as cross-cutting application capabilities without coupling Kafka modules to OIDC/provider SDKs and without changing the Kafka read-only port.

## Dependency flow

```text
Browser
  -> Kafdeck HTTP boundary
  -> Authentication Session
  -> Operator Identity
  -> Authorization Policy
  -> Existing v0.1 application modules
  -> Existing read-only Kafka ports/adapters
```

## New logical modules

### Identity

Owns Kafdeck identity contracts:

- `OperatorIdentity`
- `AuthenticationContext`
- `SessionId`
- authentication result/error categories.

OIDC library types remain in the outer adapter layer.

### Authorization

Owns:

- permission vocabulary,
- roles,
- bindings,
- scopes,
- compiled immutable authorization snapshot,
- authorization decision/explanation.

### Security Audit

Owns a Kafdeck audit-event contract and sink abstraction.

## Authentication adapter

ASP.NET Core OIDC/cookie infrastructure may implement the HTTP/OIDC adapter.

The adapter converts external claims into Kafdeck-owned identity evidence and passes only normalized data inward.

## Session architecture

v0.2 uses a server-managed authentication ticket/session.

Requirements:

- browser cookie contains no OIDC token,
- server-side session data is bounded,
- restart may terminate active sessions,
- session state is never used as durable product data.

Multi-replica shared session state is deferred.

## Authorization snapshot

Authorization configuration is compiled at startup into an immutable snapshot.

Conceptual structure:

```text
AuthorizationSnapshot
  Roles: roleId -> permissions
  SubjectBindings: (issuer, subject) -> roleIds
  GroupBindings: externalGroup -> roleIds
```

Authorization checks are synchronous/in-memory after snapshot creation.

Invalid references, duplicate conflicting identifiers or unsupported permission actions fail configuration validation.

## Permission evaluation

Evaluation inputs:

- canonical operator identity,
- requested action,
- resource type,
- Kafdeck cluster ID,
- optional resource name.

Evaluation output:

- Allowed / Denied,
- matched role/binding identifiers for audit/debug,
- stable reason category.

No policy evaluation performs Kafka I/O.

## Resource scope

v0.2 supports cluster lists and bounded deterministic resource globs.

Examples:

```text
clusters: ["payments-prod"]
topics: ["payments.*", "shared.audit"]
```

Pattern semantics are Kafdeck-defined glob semantics, not arbitrary regular expressions.

## HTTP pipeline

```text
Request
 -> deployment boundary/access-mode validation
 -> OIDC session authentication when AccessMode=Oidc
 -> canonical identity resolution
 -> authorization requirement resolution
 -> policy evaluation
 -> route/application handler
 -> Kafka-side capability/ACL evaluation
 -> authorization-safe response projection
 -> audit/telemetry
```

Kafdeck RBAC denial and Kafka ACL denial remain separate outcome categories.

## Cluster list projection

The configured cluster registry remains global application state, but API/UI projection filters it by `cluster.read` authorization before returning cluster identifiers or metadata.

## Cache posture

Kafka metadata snapshots may remain shared per cluster because they contain no user credentials, but every response projection MUST perform authorization after identity resolution.

User-specific authorized result lists are not stored in a way that can bleed across sessions.

## Configuration

Proposed sections:

- `access.mode`: Local | Token | Oidc
- `identity.oidc.*`
- `authorization.roles[]`
- `authorization.bindings[]`
- `audit.*`

OIDC client secrets use the existing secret-reference abstraction.

## API contract

Protected APIs return:

- 401/Authentication challenge for unauthenticated OIDC-mode access,
- 403/RFC 9457 authorization-denied response for authenticated but unauthorized access,
- existing Kafka capability/authorization Problem Details for downstream Kafka denials.

## Observability

Metrics/traces may include bounded-cardinality authorization outcome/reason and authentication mode.

Do not use subject/email/group/topic names as default metric labels.

## Performance target

In-memory authorization evaluation should add negligible latency compared with Kafka operations.

The implementation target is sub-millisecond typical authorization evaluation for a compiled snapshot; this is an engineering target, not a public SLA until benchmarked.
