# v0.1 Runtime Architecture

- **Status:** PROPOSED
- **RFC:** RFC-0001

## Runtime components

```text
Browser
  |
  v
Kafdeck HTTP Host
  |-- Runtime Access Boundary
  |-- Cluster Registry Module
  |-- Cluster Metadata Module
  |-- Topics Module
  |-- Health Projection
  |-- Snapshot/Cache Coordinator
  |-- OpenTelemetry Instrumentation
  |
  v
Kafka Administration Port
  |
  v
Confluent.Kafka Adapter
  |
  v
Kafka Brokers
```

## Proposed source layout

The exact project names may be refined during scaffold implementation, but dependency direction MUST remain equivalent to:

```text
src/backend/
  Kafdeck.Api/
  Kafdeck.Core/
  Modules/
    Kafdeck.Modules.Clusters/
    Kafdeck.Modules.Topics/
  Infrastructure/
    Kafdeck.Infrastructure.Kafka/
    Kafdeck.Infrastructure.Configuration/
    Kafdeck.Infrastructure.Security/

src/frontend/
  src/
    app/
    features/clusters/
    features/brokers/
    features/topics/
    features/health/
    shared/
```

`Kafdeck.Core` owns cross-cutting contracts only when they are genuinely shared. It is not a dumping ground.

## Kafka administration port

The inner contract expresses operations in Kafdeck-owned models, such as:

```text
GetClusterMetadata
ListTopics
GetTopicMetadata
GetTopicConfiguration
GetBrokerConfiguration
GetCapabilities
```

No `Confluent.Kafka` public type may appear in module/API contracts.

## Request flow

Example topic listing:

```text
HTTP GET
 -> authorize runtime access token/local mode
 -> validate cluster ID/query bounds
 -> Cluster Registry lookup
 -> Snapshot Coordinator
 -> cache hit? return snapshot slice
 -> cache miss? acquire per-cluster single-flight lock
 -> bounded Kafka Admin operation
 -> normalize adapter result/errors
 -> publish/update immutable snapshot
 -> project/search/page
 -> HTTP response with observedAt/freshness/limitations
```

## Single-flight refresh

Concurrent requests for the same expensive snapshot MUST coalesce where practical. Ten UI requests after cache expiry must not trigger ten concurrent full topic metadata refreshes.

## Per-cluster isolation

Each cluster has independent:

- client lifecycle,
- concurrency limiter,
- snapshots,
- health evidence,
- failure/backoff state.

A slow/unavailable cluster cannot consume all Kafka-operation capacity for other clusters.

## Client lifecycle

Kafka clients are long-lived per configured cluster rather than constructed per HTTP request.

Configuration changes are not runtime mutable in v0.1. Therefore client replacement occurs only during process restart/config reload if an approved reload mechanism is later included.

## Caching

Snapshots are in-memory in v0.1. No historical metadata database is required for Cluster Explorer.

This keeps v0.1 stateless with respect to Kafka observations and prevents stale operational history from being confused with current broker state.

## Persistence relationship

Gate 0's SQLite/PostgreSQL provider baseline remains valid for Kafdeck application state, but v0.1 does not introduce database persistence merely to satisfy the abstraction. Persistence is added when a feature has durable state that requires it.

## Partial-result semantics

A cluster view may contain both successful data and structured limitations.

Example:

```json
{
  "clusterId": "payments-prod",
  "observedAt": "2026-09-16T05:00:00Z",
  "health": "Healthy",
  "limitations": [
    {
      "capability": "BrokerConfigRead",
      "reason": "AuthorizationDenied"
    }
  ]
}
```

Partial results must never silently fabricate missing values.
