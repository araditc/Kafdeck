# v0.6 Fleet Operations Runtime Architecture

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **RFC:** RFC-0006
- **Scope authority:** Issue #145
- **Tracker:** Issue #146

## Architectural rule

v0.6 extends the v0.5 mutation runtime. It does not create a second executor, alternate authorization path or provider command surface.

```text
UI / API
   |
   v
Typed v0.6 Mutation Endpoints
   |
   v
Existing Mutation Coordinator
   |--- Authorization / Risk / Capability
   |--- Canonical plan + Preview
   |--- Confirmation / Independent Approval
   |--- Durable Operation / Idempotency / Audit
   v
Bounded Mutation Executor
   |--- Durable execution lease + fencing
   |--- Resource claims + current-state revalidation
   |--- typed provider port
   |--- durable typed progress/checkpoint record (long-running only)
   v
Verification / Reconciliation
```

## Shared kernel extension

The existing mutation aggregate remains authoritative for:
- operation identity,
- requester/approver,
- normalized intent,
- idempotency binding,
- target resource claims,
- risk/preview/approval,
- execution claim generation,
- dispatch boundary,
- terminal outcome,
- audit correlation.

v0.6 may add new `MutationOperationKind` values only together with closed authorization mapping, built-in risk floor, canonicalization, typed provider capability, resource-claim strategy and verification behavior.

## Durable long-running progress

Long-running operations use a subordinate typed progress record keyed by `OperationId`. This avoids unbounded mutation of the immutable intent/preview while preserving one operation authority.

Conceptual fields:

```text
OperationId
ProgressKind
Phase
SafeProviderExecutionId?
CompletedTargets
RemainingTargets
LastObservedFingerprint?
LastEvidenceAtUtc
NextPollAtUtc
AttemptSequence
ExecutionClaimGeneration
Version
SafeDiagnosticCode?
```

Rules:
- no raw record payload, SCRAM secret or generic provider response body,
- updates require optimistic version + current execution fencing generation,
- a stale worker cannot advance progress,
- progress does not authorize execution; the parent operation does,
- progress is bounded in size; large per-partition evidence is paged or summarized with finite child records,
- cleanup/retention follows operation/audit retention policy without deleting required audit evidence.

## Execution lease and fencing

For long-running operations:
1. worker atomically claims `Ready -> Executing` and receives generation `g`,
2. worker acquires sorted resource claims and durable execution lease,
3. every progress/checkpoint update asserts generation `g`,
4. lease is renewed before expiry while the worker owns execution,
5. on lease loss the worker stops provider dispatch and progress writes,
6. a takeover worker may claim only after the repository proves the lease expired/was released,
7. takeover first observes provider state before deciding whether a remaining step is safe,
8. a previously possibly-dispatched step is never blindly repeated.

## Poll scheduling

Long-running progress polling is repository-driven rather than an in-memory timer authority. `NextPollAtUtc` is durable. Workers use bounded polling cadence with backoff/jitter and per-cluster concurrency limits.

Separate bulkheads protect:
- metadata/read views,
- ordinary v0.5 mutations,
- v0.6 long-running progress polling,
- cross-cluster data movement.

## Typed provider ports

Planning admits narrow ports, not implementations yet:

- `IAclAdministrationPort`
- `IScramAdministrationPort`
- `IQuotaAdministrationPort`
- `IDynamicClusterConfigurationPort`
- `IPreferredLeaderElectionPort`
- `IPartitionReassignmentPort`
- `IBrokerMaintenancePort`
- `ILogDirectoryMaintenancePort`
- `ICrossClusterTransferPort`
- `IReplicationIntegrationPort`

Each port declares discoverable capability and typed plan/execute/observe/verify semantics appropriate to the operation. Public contracts never expose Confluent.Kafka/provider SDK request types.

## Reassignment runtime

The canonical plan stores explicit topic/partition current->target replicas plus safe evidence. Planning may query current placement and metric/log-size evidence under bounded budgets.

Execution:
- reauthorize/recheck capability,
- fingerprint current placement/ISR/broker state,
- reject material drift as `StalePreview`,
- mark dispatch boundary durably,
- submit the typed reassignment plan,
- persist only safe provider execution identity/evidence,
- poll progress under long-running lease,
- expose per-target partial state within bounded storage,
- verify final replica placement and RF,
- map unresolved timeout/connection loss truthfully.

Throttle change is a separate typed mutation and cannot be silently applied as an undocumented side effect.

## Broker/log-directory maintenance runtime

Maintenance is an orchestrated typed operation composed of safe phases, not arbitrary commands:

`Observe -> Materialize affected replicas -> Build evacuation plan -> Preview/Approve -> Execute movement -> Verify evacuation -> Provider-supported decommission/finalize -> Verify`

If the provider lacks the final decommission primitive, Kafdeck may support evacuation-only and must report that limitation explicitly.

Every phase reuses the same parent operation identity and fencing generation. Phase transitions are durable and auditable.

## SCRAM runtime

Secret material is never in durable progress. Preview records safe principal/mechanism metadata and digest binding. Confirmation/execution must resubmit the secret and match its digest. If independent approval delays execution beyond the secret-bearing request, the operation remains approval-ready but final execution requires a new authorized secret submission; no secret is reconstructed or retrieved.

## Cross-cluster transfer runtime

A bounded transfer job has a dedicated data-plane worker bulkhead but remains controlled by the mutation operation.

The canonical job plan includes:
- source and destination cluster IDs,
- finite topic mappings,
- selection/start/end semantics,
- byte/record/time/rate/concurrency ceilings,
- destination behavior,
- masking/export policy reference,
- schema/serialization policy where supported.

Durable checkpoints contain safe source offsets/provider tokens only. Record key/value/header bytes are streamed through memory and are not durable operation/progress state.

Authorization is rechecked before start. Long-running policy defines whether periodic reauthorization is required; at minimum, any resume/takeover after lease loss reauthorizes and revalidates both endpoints.

## Replication integration

MirrorMaker 2/provider replication is modeled as typed control-plane integration. Kafdeck manages supported topology/config/status actions through fixed adapters. It does not implement an internal continuous replication engine.

## Verification and reconciliation

Verification is typed and bounded:
- ACL: re-read matching ACL set,
- SCRAM: verify safe metadata only where provider exposes it,
- quota: re-read entity quota,
- dynamic config: re-read effective/current config source/value,
- leader election: observe elected leader state,
- reassignment/RF: observe replica placement and in-progress state,
- maintenance: verify affected replicas evacuated/final provider state,
- transfer: verify provider acknowledgements/checkpoint/final counts without persisting payloads,
- replication integration: re-read typed integration status/config projection.

Reconciliation may resolve `ExecutionUnknown` from observation; it cannot issue a new mutation unless the typed state machine proves that doing so is safe.

## HA persistence

SQLite supports standalone/single-instance mutation execution only. PostgreSQL is required for multi-instance/HA operation leases, progress records, resource claims and fencing.

Schema migrations for progress records must be transactional, restart-safe and backward-compatible for a rolling upgrade where the declared deployment model supports it.

## Architecture tests

CI must fail if:
- a v0.6 route calls a provider client directly,
- a new operation kind lacks explicit authorization/risk mapping,
- a provider port accepts arbitrary method/path/request payloads,
- long-running progress can update without current fencing generation,
- SCRAM secret or record payload fields appear in durable DTOs,
- transfer execution omits source/destination authorization checks,
- a mutation worker retries after possible external dispatch without proof of non-dispatch.
