# v0.1 Resilience and Kafka Load Protection

- **Status:** PROPOSED
- **RFC:** RFC-0001

## Objective

Kafdeck is an observer of Kafka in v0.1. Observation must be bounded so that a busy UI or failing cluster does not create material control-plane load.

## Default budgets

Proposed defaults:

| Control | Default |
|---|---:|
| Kafka operation deadline | 10 s |
| Per-cluster Kafka admin concurrency | 8 |
| Global Kafka admin concurrency | 64 |
| Cluster/broker metadata TTL | 5 s |
| Topic metadata TTL | 10 s |
| Topic/broker config TTL | 30 s |
| Stale-if-transient-error max age | 60 s |
| Topic list page size | 50 |
| Topic list maximum page size | 200 |
| UI overview auto-refresh minimum interval | 10 s |

Safe configuration bounds will be validated; zero/unbounded values are not accepted for concurrency/page-size controls.

## No N+1 policy

Prohibited pattern:

```text
List 500 topics
 -> for each topic call DescribeConfigs in background
```

Allowed pattern:

```text
List metadata once
 -> render cached snapshot
 -> DescribeConfigs only when a user opens a specific topic configuration view
```

## Retry policy

Metadata read retries are allowed only for clearly transient failures and only within the overall request/refresh budget.

- exponential backoff,
- jitter,
- small bounded attempt count,
- cancellation-aware,
- no retry storm across clusters.

Authentication, authorization, invalid TLS, and invalid configuration failures are not retried as transient errors.

## Stale-on-error

When a recent valid snapshot exists and a transient refresh fails, Kafdeck may serve the previous snapshot within the configured stale window.

Responses/UI MUST include:

- `freshness: stale`,
- original `observedAt`,
- refresh failure summary,
- no implication that stale data is current.

## Cancellation

HTTP cancellation propagates into application work. Shared single-flight refreshes are not necessarily cancelled because one subscriber disconnected; their lifecycle is governed by the refresh coordinator and bounded deadline.

## Bulkheads

Per-cluster bulkheads prevent one failing cluster from consuming the global concurrency pool. Global limits remain a final safeguard.

## Memory

Large metadata collections use bounded immutable/snapshot representations. Configuration inspection is not prefetched for every topic/broker. The UI receives bounded pages, not arbitrary full-cluster JSON payloads.

## Load testing

Before v0.1 release, tests must cover:

- repeated dashboard refresh,
- concurrent users reading the same cluster snapshot,
- multiple unavailable clusters,
- high topic counts,
- cache-expiry stampede prevention,
- slow Kafka responses,
- cancellation,
- partial authorization,
- memory behavior under large metadata snapshots.
