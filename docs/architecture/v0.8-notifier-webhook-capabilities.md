# v0.8 Notifier and Webhook Capability Matrix

Status: **PARTIAL IMPLEMENTATION WITH LOCAL PHYSICAL PROOF; FULL W66 ACCEPTANCE OPEN**

The approved N1–N5 scope is unchanged. A local protocol fixture is evidence of
actual transport behavior, not external tenant authorization or protected-main
acceptance. See the [current evidence and gaps](../implementation/v0.8-w66-g2-authenticated-webhook-evidence.md).

## Provider families

All six families have concrete typed physical transports. Each activation flag
defaults to false, requires enabled persistence and admits only standalone
execution. Production notification HA is **Unsupported** and fails closed.
Two independent PostgreSQL sender-host tests establish local contention and
interrupted-send recovery evidence; they do not widen production admission.

| Provider | Current typed physical contract | Explicit default-off flag | Local proof / environmental limits |
| --- | --- | --- | --- |
| Webhook | Exact configured HTTPS POST; closed Anonymous/Bearer; bounded private HTTP wire | `WebhookDeliveryEnabled` | Actual TLS, durable receipt, rotation and ambiguity; governed lifecycle and approved deployment ownership remain open |
| Email | Exact implicit-TLS SMTP server/sender/recipient; mandatory advertised SASL PLAIN | `EmailDeliveryEnabled` | Actual TLS acknowledgement/auth/recipient/ambiguity matrix; no STARTTLS/LOGIN/anonymous relay or general SMTP interoperability claim |
| Slack | Fixed Slack `chat.postMessage`, exact typed channel and Bearer credential | `HttpProviderDeliveryEnabled` | Actual TLS request/receipt and negatives; external token scope/membership remains owner acceptance |
| Microsoft Teams | Fixed Graph team/channel message, exact typed identifiers and delegated Bearer credential | `HttpProviderDeliveryEnabled` | Actual TLS 201/receipt and negatives; no general app-only authority or token-refresh support claim |
| Telegram | Fixed Bot API `sendMessage`, exact numeric chat and private token URL | `HttpProviderDeliveryEnabled` | Actual TLS message/chat receipt and negatives; external bot/chat ownership remains owner acceptance |
| PagerDuty | Fixed Events API v2 trigger, routing key and event-UUID dedup | `HttpProviderDeliveryEnabled` | Actual TLS 202/dedup receipt and negatives; acceptance does not prove downstream incident processing |

No family accepts a caller-selected generic endpoint, method, header, credential
or SMTP command. The Webhook endpoint and SMTP server are exact server-owned
profiles, governed by public DNS/IP pinning, TLS, payload/rate/concurrency limits
and revision fencing. Private/on-prem destination exceptions are unsupported
until an explicit allowlist contract is admitted. Disabled profiles can remain
in a mixed catalog; active profiles require the matching family flag.

Local proof currently covers all six positive/negative physical families.
All six also have actual restart-provisioned versioned credential rotation,
old-intent fencing, revoke/missing/disabled refusal and no-fallback/leak evidence.
Complete Supported state still requires provider ownership, credential lifecycle,
N4/N5 operational acceptance and protected-main evidence. The
[operator runbook](../operator/v0.8-notifier-provider-delivery-runbook.md) records
the exact fields, formats, flags and runtime restrictions.

## Destination identity

A destination profile has:

- stable ID;
- provider type;
- validated origin/endpoint;
- secret references;
- enabled event classes;
- deployment policy;
- safe display metadata.

Current profiles and versioned credential bindings are server-owned startup
configuration. Explicit disable/revoke and versioned binding rotation require
restart; they cannot recall an already resolved credential or physical send.
Runtime governed profile/credential create/update/delete, preview/risk/approval
and complete audit/UI lifecycle remain N2/N5 acceptance gaps. Their future
admission must bind normalized provider identity and approved secret references.

After creation, event/test requests select a destination profile ID; they do not supply URL, host, port, HTTP method, headers, SMTP server or provider token.

## SSRF/network rules

- remote destinations require HTTPS where provider supports HTTPS;
- redirects are disabled;
- DNS/IP validation must reject prohibited local/link-local/metadata ranges unless an explicit on-prem private allowlist contract permits a known private destination;
- origin/path are normalized once from configuration;
- no user-controlled path traversal/query forwarding;
- response bodies are untrusted and safely summarized.

## Delivery budgets

Default/hard:

- attempts 5 / 10;
- initial retry 5 s / minimum 1 s;
- max backoff 5 min / 30 min;
- lifetime 1 h / 24 h;
- payload 32 KiB / 256 KiB;
- rate 5/s / 50/s per destination;
- concurrency 2 / 8 per destination;
- redirects 0 / 0.

## Delivery state

Durable safe state:

- notification/event ID;
- destination profile ID;
- payload fingerprint and safe event metadata;
- attempt count;
- next attempt;
- last safe outcome code;
- optional SHA-256 fingerprint of a validated provider receipt;
- unknown-external-effect state where applicable.

Raw protected record payloads and secrets are not durable delivery state.
Raw provider request IDs remain prohibited. Schema v3 adds only the nullable
receipt fingerprint; prior pending revisions and the v1 drain gate are preserved.

## Payload policy

Default webhook/notifier payloads include safe projections:

- event type;
- Kafdeck cluster/resource identifiers the subscriber is allowed to configure;
- severity/status;
- timestamps;
- operation ID/link;
- safe reason codes;
- aggregate metrics/SLO values.

Protected record exemplars require a separate future admission and are not in v0.8 default scope.
