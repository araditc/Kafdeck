# v0.6 Reassignment and Maintenance Contracts

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Scope #145; tracker #146. Provider facts: [capability matrix](v0.6-provider-capabilities.md).

## Typed ports and immutable plans

W45/W46 may add narrow Kafdeck-owned ports for observing assignments/log directories, submitting a finite ordered reassignment, observing progress, electing preferred leaders, and the tested maintenance primitives. Vendor DTOs stay inside adapters. There is no command name/config dictionary/CLI string contract.

A plan binds physical cluster identity, stable topic identity, ordered current/target replica IDs, broker incarnations and rack information when available, log-directory identities, relevant ISR/minimum-ISR state, current configuration sources, explicit throttle changes, safe estimates, budgets, required permissions, risk, expiry and approved dispatch horizon. Targets and stages are finite before approval. Discovery may not silently add newly created partitions.

## Reassignment safety and progress

Reject duplicate/nonexistent replicas, same-source/target no-op ambiguity, inaccessible target inventory, missing required rack/capacity evidence, offline/cordoned destinations, incompatible existing reassignments, and RF below `max(provider minimum, deployment safety floor, effective min.insync.replicas)`. Safety policy cannot silently lower ISR or rack constraints to make a plan executable. No unclean election is available.

Preserve replica order: it affects preferred leadership. A successful submit only establishes provider acceptance. Completion requires readback of the intended replica set/order and required health constraints, with no incompatible pending assignment. Intermediate progress describes observed state and timestamp; absent byte metrics produce Unknown, not zero remaining bytes or an invented ETA.

If a submission partially applies, record each partition. Any unresolved potentially-applied target makes the parent `ExecutionUnknown`; if every effect is known but only a subset succeeded, use `PartiallyApplied`. Do not resubmit the entire plan after timeout. A new plan is required for remaining undispatched changes after material drift.

## Throttle ownership

Preview exact broker/topic throttle keys, values, prior values and configuration sources. The operation owns only its explicit changes. Restoration is a planned typed step with the same authorization and current-state checks; restore only when observed state still equals the operation's last written state. Otherwise retain a cleanup conflict for reconciliation, not a blind overwrite or global throttle deletion. Restoring an inherited value uses reset semantics, not a guessed numeric default.

Throttling must be finite and sufficient under deployment policy; performance tests assess contention with ordinary reads. No claim of compare-and-set atomicity is made for Kafka APIs that lack it. Last-moment external changes remain a readback/uncertainty boundary.

## Maintenance stages

1. Observe a complete bounded inventory and stable broker/log-directory identity. Reject an inventory larger than the admitted target envelope; require explicitly staged plans rather than silent truncation.
2. Preview cordon plus evacuation and external prerequisites. All provider mutations are typed, authorized and included in the parent risk.
3. Cordon only on a tested supported profile, then verify. This is not read-only mode and does not itself evacuate replicas.
4. Execute/observe explicit evacuation through the admitted reassignment/log-directory movement capability. Revalidate safety before each new effect.
5. Re-observe all affected placements, pending assignments, ISR and configured directory inventory. Unknown/incomplete inventory blocks the next destructive stage.
6. Show `WaitingForExternalAction` for shutdown/static configuration/restart tasks. Kafdeck executes no shell, host filesystem action, Kubernetes mutation or direct controller-quorum change.
7. A typed broker-unregister capability, when actually available through the admitted adapter, requires new current proof of evacuation and broker shutdown; it is not implied by a prior cordon. Unsupported transport/client profiles remain unavailable. Log-directory removal that requires static broker configuration remains an external step.
8. Verify the operation's specific terminal postcondition. `EvacuationVerified` is not `BrokerDecommissioned`; readiness for a human action is not completion of that action.

External actions are never trusted solely from a checkbox. Re-observe what the provider exposes; unobservable external completion remains unverified. Direct controller connectivity or a new runtime sidecar requires a separately reviewed architectural admission and, if it changes approved boundaries, an owner decision.

## Version/profile boundary

The initial test matrix retains 4.3.1, 4.2.1, 4.1.2 and 3.9.2. The Kafka 4.3 release documents cordon; do not assume it exists on every 4.x member. Negative capability tests for older/unsupported providers are part of W46 acceptance. Existing partition reassignments and out-of-band changes are expected concurrency cases, not reasons to disable preconditions.
