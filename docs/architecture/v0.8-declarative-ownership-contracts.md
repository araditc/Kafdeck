# v0.8 W68 — Typed Declarative Ownership, Drift and Plan/Apply Contract

**Status: PROPOSED / PLANNING-ONLY / NOT AN ADMITTED RUNTIME CONTRACT**

Authority: v0.8 scope #208; tracker #209; W68 #217. W67 non-browser identity design PR #278 is protected-main admitted; IdP, bearer principal registration, mutation/approval API and backend authority are **NOT** admitted by that documentation merge.

This document is a candidate for the **typed declarative resource-family and ownership decision**. It does not authorize a GitOps controller, apply/destroy API, Terraform provider, background service, release publication or generic data-plane access. Release of implementation is contingent on W67 runtime authority and the per-resource acceptance gates below.

## 1. Domain decisions and boundaries

- Every declarative resource must map to a **named, typed Kafdeck product contract**. There is no `raw`, `generic`, `http`, `sql`, `script`, provider-config passthrough or arbitrary JSON patch resource.
- Git is a desired-state input, **not** an identity, ownership or approval authority. CI runners are not automatically authorized Kafdeck principals.
- Resource observation (`read/drift`) is separate from declarative ownership. A resource that exists in Kafka/provider does **not** automatically become GitOps-managed.
- Kafdeck backend remains the sole authority for current-state evidence, protected/sensitive metadata projection, provider capabilities, action/resource RBAC, preview/hash, risk, approval, idempotency, leases and durable audit.
- An organization might manage the same Kafka cluster outside Kafdeck. Import/adoption must be an explicit owner-authorized operation with fresh evidence. Never silently import from a matching name.
- Scope must be represented by a stable deployment identity plus any admitted cluster/profile identity **and** canonical resource kind/name. A display name, upstream Kafka broker ID or repo path alone is not global identity.
- An explicit `OwnershipRecord` must durably associate one canonical identity with an admitted managed owner, revision, source and state. Define a migration/HA lock model before any writer. Do not create ownership for `ObservedOnly` resources.
- No proposed field containing a URL, code, arbitrary expression or untyped provider object may become an effects escape hatch.

## 2. Finite resource lifecycle

Each resource family is separately admitted with a published matrix:

| Capability | Minimum backend evidence |
| --- | --- |
| Observe | Typed current-state read, bounded list and authorization-safe omissions/cursors |
| Validate | Closed schema, version, semantics, deterministic normalized projection and hard limits |
| Plan | Governed immutable current-state + desired-state fingerprints, exact diff and risk |
| Drift | Readback with explicit evidence time/capability/authorization truth |
| Import/adopt | Stable canonical identity, authorized ownership claim, revision and conflict semantics |
| Apply | Same typed current-state/risk/approval/audit path as interactive mutation |
| Delete/relinquish | Explicit lifecycle with reversible vs irreversible truths; never generic destroy |
| Upgrade | Schema migration, old-client rejection rules, stable version pinning |
| Compensate | Only a separately admitted safe inverse with fresh evidence; no global rollback |

If any row is absent, the family **must not** advertise support for it. A `read-only` or `plan-only` capability is not proof that `apply` or `destroy` works.

### Candidate first families (none presently declaratively Supported)

**Notification subscription** (`W66`, opt-in only):
- identity: server-admitted subscription ID within the configured deployment;
- desired fields: destination **ID reference**, `Active/Paused` lifecycle, exact event classes/types, never provider URL/recipient/secret;
- current data: one-statement metadata-only snapshot, revision and terminal `Retired` state;
- write: the existing separately gated `NotificationManage` CAS route and **both old/new destination** authorization; declarative apply still blocked until typed ownership/plan and W67 auth;
- destructive semantics: `Retired` is terminal, cannot be reversed by Terraform/GitOps or “repair” logic; delete is **not** implicitly supported;
- subscription management can be enabled without a GitOps controller; no automatic Git ownership takeover.

**Data-quality policy** (`W65`):
- may be proposed after explicit versioned policy readback, lifecycle and bounded evaluator contract mapping;
- rules are closed typed evaluation contracts, not user scripts or general Kafka scans;
- payload sampling/monitoring opt-in is **not** implied by policy management; raw sample values do not belong in a GitOps manifest;
- current status remains **ObservedOnly/Unadmitted** for declarative ownership pending explicit resource contract review.

**Kafka topic / security ACL / connector profile**:
- **not admitted** as first declarative resource families merely because Kafdeck has a governed mutation API or can list the object;
- typed intent, capability matrix, provider ownership, drift and destructive-compensation rules need separate approval for each family.

## 3. Proposed manifest grammar (illustrative, not an admitted parser)

```yaml
apiVersion: kafdeck.io/v0.8-proposal
kind: NotificationSubscription
metadata:
  name: ops-subscription
  ownerRef: team-ops
spec:
  destinationRef: ops-notifier-01
  state: active
  eventClasses: [operational]
  eventTypes: [consumer.lag.alert]
```

This example does not grant an owner, create a service identity, select a provider URL or authorize a write. `ownerRef` must resolve through Kafdeck's admitted ownership registry; it is **not** trusted because the manifest says so. Preserve case/normalization rules of underlying event filters and resource IDs.

Reject unknown `apiVersion`, kind, fields, duplicate YAML keys, anchors/aliases where ambiguity matters, malformed Unicode and cross-scope references. Secret values and plaintext credential fields have no manifest representation; use preprovisioned server-side references and explicit redacted state projection.

## 4. Typed plan, drift and apply outcomes

A deterministic plan must bind:
- admitted schema version, resource family, exact scope/identity and owner identity/revision;
- normalized desired-state hash and current-state evidence hash/revision with observation time and source/capability truth;
- typed list of changes, non-secret safe projections, preconditions, risk and required approvals;
- creation/expiry timestamps, idempotency request key and immutable plan fingerprint;
- a finite maximum resource count, plan size, timeout and concurrent operations.

A declarative client never chooses `risk=low`, `approved=true`, a provider endpoint, execution principal or a new current-state revision.

**Drift outcomes** should be explicit:
- `InSync`: exact admitted normalized comparison and current evidence;
- `OutOfSync`: valid comparable evidence differs;
- `Missing`: authoritative permitted lookup proves absence;
- `Unknown`: stale/partial/unavailable observation or unadmitted provider;
- `Inaccessible`: current principal lacks rights; must not be converted to Missing;
- `Conflict`: ownership, version or concurrent writer clash;
- `Unsupported`: family/operation not admitted.

There must be no coercion of `Unknown` / `Inaccessible` to an empty list or a plan that creates missing objects. A read-only client may render these truths but cannot make them authoritative.

**Apply** (not yet admitted) must re-evaluate current evidence and principal permissions, reject stale ownership/plan hashes and exact preview identity, and use existing durable mutation semantics. Preserve `AwaitingApproval` and `ExecutionUnknown` operation states **exactly**; approvals stay distinct-principal for CRITICAL effects. A result may remain pending/non-final; GitOps and Terraform cannot claim synchronous success when an external effect is unknown or awaiting approval. Blind retries are prohibited.

## 5. Import, ownership transfer and release

- Import requires exact resource identity, current-state evidence, an explicit admitted owner principal and a compare-and-swap ownership claim; a resource name collision is a **conflict**.
- Ownership transfer from A to B is a **new governed mutation** with explicit source and target owner evidence, dual-authorization policy if required, and an auditable version transition. Never infer transfer from a changed Git repository path.
- Relinquish can remove Kafdeck declarative ownership metadata without deleting the underlying resource if that resource family explicitly supports that action.
- `destroy` must not be treated as `relinquish`; define distinct verbs and risk. Terminal `Retired` never “rolls back” into `Active`.
- Deleting/recreating a manifest file is not adequate identity to bypass an ownership dispute or replay a failed/ambiguous external effect.
- A controller handles ambiguous or interrupted operation evidence through bounded reconciliation against durable backend state, not by repeating the mutation.

## 6. Automation principal and GitOps runner

- No unattended controller implementation before W67 owner admission of exact IdP, Kafdeck API audience and registered service principal credential lifecycle.
- A manifest signer or GitHub identity can provide provenance, not Kafdeck authorization. Every apply is attributed to an independently authenticated registered client.
- Secrets are write-only references; never materialize bearer access tokens or provider credentials into state, diffs, logs, SCM comments, PR output or MCP tool results.
- Require explicit allowlisted manifest repositories/paths at deployment level; never arbitrary caller-supplied remote Git URL fetching from Kafdeck backend.
- Finite retry/backoff, deadlines, queue size, lease/fencing and per-resource serialization; no permanent silent plan refresh or automatic destructive remediation.

## 8. Required proof before any runtime PR

- typed schema generation and unknown-field rejection; deterministic canonicalization across CLI/REST/GitOps/Terraform;
- collision-safe resource identities, exact case rules, duplicate manifest keys and path traversal refusal;
- read authorization filtering and continuation; `Inaccessible` cannot leak hidden identity or become `Missing`;
- concurrent import/adopt/transfer CAS against real SQLite/PostgreSQL where supported, including HA/fencing;
- stale plan, current-state drift, pending approvals, CRITICAL distinct-approver, operation ambiguity and crash recovery;
- foreign owner/external writer interference, no self-authorized Git service, no arbitrary provider HTTP/protocol/callback;
- secret-sentinel tests of manifests/state/plan/traces/logs, unsupported provider truth, air-gap operation;
- exact-head CI, Codex no P1/P2, fresh CODEOWNER approval, protected-main merge and post-merge checks.
