# v0.7 Runtime Contracts — Ecosystem Effects, Automation and Finite Data Jobs

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Authority #178/#180; W51 #181.

This document owns the runtime/fencing/budget semantics for v0.7. It extends but does not replace ADR-0006/0007 and the v0.6 finite-transfer runtime.

## 1. Common operation state machine

All side-effecting v0.7 flows use the common durable mutation operation lifecycle.

Conceptual phases:

`Draft -> Previewed -> AwaitingConfirmation/Approval -> Admitted -> Executing -> Verifying -> Completed`

Exceptional terminal/intermediate states include:

- `Rejected`
- `Cancelled`
- `WaitingForExternalAction`
- `ExecutionUnknown`
- `PartiallyCompleted`
- `FailedBeforeDispatch`

The exact persisted enum/schema remains implementation-owned, but semantic weakening is prohibited.

## 2. Provider identity binding

Every provider effect binds:

- Kafdeck cluster profile ID;
- stable provider profile ID;
- provider kind;
- canonical validated origin fingerprint;
- TLS/auth policy fingerprint excluding secret bytes;
- current provider capability evidence;
- exact logical target;
- current policy version.

Before every new external effect, current provider identity and policy are compared with the immutable preview. Drift blocks undispatched effects and requires a fresh preview.

## 3. HTTP provider dispatch

Schema Registry and Connect operations are HTTP-provider effects.

### 3.1 Before dispatch

Persist, transactionally where supported:

- operation/step ID;
- effect kind;
- exact target;
- provider profile fingerprint;
- safe request fingerprint;
- current generation/fencing token;
- dispatch-start marker;
- reserved budget/attempt unit;
- audit intent sequence.

Secret values are not persisted.

### 3.2 After response

Persist:

- bounded status/readback evidence;
- provider resource identity/version where safe;
- acknowledged effect;
- updated operation/progress state;
- audit result.

A 2xx response is not always sufficient verification. Operations with readback semantics perform bounded verification.

### 3.3 Ambiguity

Timeout, connection loss, process crash or cancellation after dispatch-start can leave the effect ambiguous.

Rules:

- do not redispatch automatically;
- mark effect/operation `ExecutionUnknown` or domain equivalent;
- retain conflict/obligation state;
- allow only bounded readback/reconciliation;
- a new user request with the same intent does not clear the predecessor.

## 4. Schema Registry effects

### Register schema

Verification evidence should use the strongest provider-supported identity:

- returned version/id;
- subject/version readback;
- canonical schema/reference fingerprint.

If provider acknowledges but readback is temporarily unavailable, the operation may be completed with acknowledged provider identity only if the adapter contract proves that identity authoritative; otherwise it remains verifying/unknown according to the provider contract.

### Compatibility change

Bind exact global/subject scope, prior value/source, proposed value and readback.

### Delete

Soft and permanent delete are separate effect kinds.

No automatic rollback recreates deleted schemas because:

- IDs/versions may not be restorable;
- references/compatibility policy may have changed;
- recreation can create a different provider identity.

## 5. Connect lifecycle effects

Connector create/update/delete/resume/restart/task-restart can start/alter external data movement.

Before each effect:

- classify connector class/family;
- enforce deployment allowlist/policy;
- apply replication/MM2 guard;
- validate exact Connect profile;
- verify current connector/config/status fingerprint where needed;
- recheck authorization/risk/approval.

Pause may use a lower-risk path only when tested provider evidence shows it cannot start a stopped connector.

### Secret finalization

A connector preview stores only:

- non-secret normalized config;
- secret key names/reference identities;
- keyed/domain-separated binding over secret material where necessary to bind finalization;
- provider/plugin validation evidence.

The requester finalizes write-only secret material immediately before dispatch after approval. Missing finalization blocks dispatch.

## 6. Connect auto-restart runtime

A policy activation has a finite durable budget:

- attempt count;
- activation start/deadline;
- next eligible attempt time;
- consecutive failure count;
- circuit state;
- last known connector/task state;
- unresolved dispatch marker.

### Default policy

- attempts: 3;
- initial delay: 10 s;
- exponential factor: 2;
- bounded jitter;
- max delay: 5 min;
- activation lifetime: 30 min.

### Hard caps

- attempts: 10;
- minimum initial delay: 5 s;
- max delay: 30 min;
- activation lifetime: 24 h.

No unlimited value is valid.

### Circuit behavior

The circuit opens when:

- hard/attempt limit reached;
- ambiguous restart dispatch exists;
- authorization revoked;
- provider identity/capability changes;
- connector class/policy changes;
- MM2/replication guard blocks;
- audit/durable store cannot safely persist progress.

Only an explicit governed operator action can create a new activation after a terminal exhausted/blocked policy. It does not reset the history of the prior activation.

## 7. Finite data-job runtime

Replay/reprocess/forwarding uses exact frozen ranges.

### Immutable plan

Contains:

- source/destination physical cluster identities;
- exact source/destination topics;
- explicit partition map;
- frozen `[startInclusive,endExclusive)` source ranges;
- isolation policy;
- output mode;
- masking/data-policy fingerprints;
- total record/byte/time/rate budgets;
- destination existence/config identity evidence;
- source/destination authorization requirements.

`latest`/timestamp selectors resolve once during preview. The range does not follow the head of a growing log.

### Batch protocol

At most one unresolved write batch exists per job.

1. Revalidate current identities/policy/authorization/budgets.
2. Read a bounded batch from the exact durable checkpoint.
3. Apply admitted deterministic transform/masking policy in memory.
4. Reserve cumulative record/byte/rate units.
5. Persist batch identity/range + dispatch-start marker before destination I/O.
6. Produce exact target records.
7. Persist provider acknowledgement and next source checkpoint.
8. Verify bounded evidence where the mode requires it.
9. Continue only when no unresolved predecessor exists.

### Checkpoint semantics

Durable checkpoint stores safe metadata only:

- source partition;
- next acknowledged source offset;
- destination partition where fixed;
- cumulative counts/bytes/duration;
- batch identity;
- provider acknowledgement summary;
- unresolved-batch flag.

It never stores raw record bytes.

### Ambiguous produce

Produce acknowledgement cannot be atomically committed with the Kafdeck checkpoint. If produce may have succeeded but durable checkpoint acknowledgement was not committed:

- mark unknown;
- do not replay that batch;
- do not advance past it;
- require governed reconciliation/disposition.

Producer idempotence within one process is not represented as cross-restart exactly-once.

## 8. Transform boundary for reprocess

v0.7 does not expose arbitrary code.

Admitted transform families may include only closed deterministic operations documented by W57, such as:

- byte-preserving replay;
- server-side masking/redaction;
- supported SerDe decode + closed field projection/rename/default mapping;
- schema-compatible re-encode where all schemas/providers are explicit.

Any transform that cannot be canonically represented, bounded and audited is Unsupported.

## 9. Data generator runtime

Generator plans bind:

- exact destination;
- schema/template identity;
- deterministic seed if used;
- finite count;
- rate/byte/duration budgets;
- partitioning/key strategy;
- environment policy decision.

Generated records live only in bounded in-memory batches before produce unless a future separately approved persistence design exists.

### Default budgets

- 100 records/s;
- 1 MiB/s;
- 10,000 records;
- 10 MiB total;
- 10 minutes.

### Hard caps

- 1,000 records/s;
- 10 MiB/s;
- 100,000 records;
- 100 MiB total;
- 1 hour.

The first limit reached stops further production.

## 10. ksqlDB bounded query runtime

A query request is classified before provider I/O.

Admitted query execution binds:

- exact ksql profile;
- canonical statement text/fingerprint;
- statement class;
- row/byte/time/concurrency ceilings;
- current authorization.

Default limits:

- 30 s;
- 1,000 rows;
- 2 MiB.

Hard caps:

- 2 min;
- 10,000 rows;
- 16 MiB;
- 8 concurrent queries/profile.

Response processing stops at the first hard limit and returns explicit truncation/limit metadata rather than silently omitting rows.

Persistent query/DDL/DML statements are rejected before dispatch.

## 11. Resource isolation

v0.7 adds separate bounded bulkheads for:

- Schema Registry provider reads/mutations;
- Connect provider reads/mutations;
- ksql queries;
- data-job source reads;
- data-job destination produces;
- generator produces.

One failing provider/profile must not consume all Kafka/provider slots for unrelated clusters/profiles.

No per-row UI fan-out is allowed. Large collections use bounded provider pagination, server snapshots or bulk endpoints.

## 12. Cancellation

Cancellation stops future effects. It does not:

- undo already acknowledged provider mutation;
- retract produced Kafka records;
- restore deleted schemas/connectors automatically;
- clear an unknown effect.

If cancellation arrives after dispatch-start, the result follows normal ambiguity/readback semantics.

## 13. Audit

Audit records include:

- canonical operation/action/target;
- requester/approver;
- risk;
- provider profile ID and safe fingerprint;
- budgets;
- state transitions;
- dispatch/ack/readback outcome;
- cancellation/reconciliation.

Audit excludes:

- secrets;
- raw record payloads;
- generated payloads;
- unredacted connector config;
- arbitrary provider response bodies;
- ksql result rows.

## 14. Storage/backpressure failure

If durable state or audit cannot safely persist a new mutating/job effect, Kafdeck fails closed before dispatch.

For an effect already dispatched, storage failure must not free the conflict/fencing claim or trigger blind redispatch.

## 15. HA tests

W55/W57/W58 must include, where applicable:

- two-worker lease race;
- stale writer;
- crash before dispatch;
- crash after dispatch marker;
- crash after provider acknowledgement but before checkpoint;
- failover/restart non-reset of budgets;
- clock rollback/forward;
- integer overflow/cap-plus-one;
- audit backlog/store-full;
- authorization revocation;
- provider-profile retarget;
- unknown effect no-redispatch.

This contract is planning-only until W51 protected-main admission.
