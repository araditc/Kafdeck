# v0.6 Provider Capability & Compatibility Model

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Authority:** Issue #145 / RFC-0006
- **Tracker:** Issue #146

## Principle

Kafka protocol compatibility does not imply v0.6 administrative compatibility. Every security, configuration, reassignment, maintenance and replication capability is independently discovered, tested and admitted.

## Capability dimensions

For each provider/profile/version, the matrix records:

- capability ID,
- discovery support,
- read/inspect support,
- plan/preview evidence support,
- execute support,
- verify/readback support,
- cancellation support if any,
- ambiguity/partial-result semantics,
- known target/size constraints,
- tested versions,
- evidence source/test fixture,
- provider-specific limitations.

A capability may be `Supported`, `ReadOnly`, `Partial`, `Unsupported` or `Unknown`. Mutation execution requires `Supported` for every mandatory execution/verification semantic or an explicitly designed `Partial` contract whose limitations are represented in the preview and result model. `Unknown` fails closed.

- `kafka.preferred-leader-election`
- `kafka.partition-reassignment.plan`
- `kafka.partition-reassignment.execute`

- `transfer.bounded-copy`
- `replication.mirrormaker2.control`
- provider-specific replication capability IDs where separately tested.

Capability IDs are Kafdeck-owned contracts, not raw SDK method names.

## Apache Kafka reference profile

Apache Kafka is the semantic reference. Release readiness must test the repository's supported compatibility lines and explicitly record which v0.6 capabilities are available on each line. Kafka 4.x-specific maintenance behavior must not be backported in product claims to versions where the primitive is unavailable.

## Managed and Kafka-compatible providers

For Confluent, AWS MSK, Redpanda, Aiven, Google managed Kafka, Azure Event Hubs or other profiles:
- core Kafka-wire compatibility is insufficient evidence for security/admin features,
- cloud IAM is outside v0.6 unless a separate typed adapter is approved,
- provider REST control planes use fixed configured origins/routes and bounded deadlines/sizes,
- unsupported provider-native features are surfaced as unavailable rather than proxied generically.

Azure Event Hubs, for example, must never be assumed equivalent to full Apache Kafka administration solely because it supports Kafka protocol clients.

## Dynamic configuration capability

For each key Kafdeck must know:
- scope (cluster/broker/topic where applicable),
- provider-reported source/mutability,
- server allowlist membership,
- sensitivity/risk classification,
- verification readback behavior.

A public client cannot turn an unknown/static key into an executable dynamic mutation.

## Maintenance capability

Maintenance planning separates:
- observe affected replicas/logdirs,
- execute reassignment/evacuation,
- observe progress,
- provider-supported final decommission/cordon/finalization.

A profile may support evacuation but lack a final decommission primitive. Kafdeck reports the truthful capability split and must not fabricate a generic broker read-only mode.

## Replication capability

MirrorMaker 2/provider replication integration is a control-plane adapter. The matrix records exactly which topology/status/mutation operations are supported. Kafdeck does not infer that a Connect endpoint automatically permits unrestricted replication administration.

## Compatibility evidence schema

Release evidence should use a table equivalent to:

| Profile | Version | Capability | Discover | Plan | Execute | Verify | Result | Evidence |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Apache Kafka | x.y.z | reassignment | yes | yes | yes | yes | Supported | integration test/run |

Known limitations and failure semantics accompany the table.

## Fail-closed rules

- unknown capability => no mutation execution,
- incomplete authorization model => no execution,
- no safe verification for a destructive operation => execution blocked unless RFC explicitly admits `AppliedUnverified` semantics for that typed operation,
- provider-native IAM outside observable Kafka semantics => access analysis labeled incomplete,
- version change invalidating capability evidence => preview stale/recreated as policy requires.

## Release gate

No v0.6 capability may be claimed as supported in release documentation until its profile/version evidence is present in the final compatibility matrix and the required real-provider/real-Kafka tests pass.
