# v0.8 W67 — Governed Non-Browser OIDC and Automation Principal Contract

Status: **PROPOSED / ARCHITECTURE-SECURITY REVIEW REQUIRED / NOT ADMITTED FOR IMPLEMENTATION**

Authority: v0.8 scope #208, tracker #209, W67 #216; dependent W68 #217, W69 #218 and W70 #219.

This is an IdP-neutral design proposal, **not** permission to turn on a new authentication mechanism, automation mutation route, unattended approval, GitOps apply, Terraform or MCP mutation. v0.8 publication remains separately owner-gated.

## 1. Existing protected-main behavior (do not silently change)

- Browser OIDC currently runs Authorization Code + PKCE and creates a Kafdeck server-side **cookie** session; `OidcSessionAuthentication.cs` normalizes operator identity from claims and does not retain raw OIDC tokens.
- `AuthorizationEnforcement.cs` authorizes OIDC operator sessions via `OperatorSessionContextFactory` and existing action/resource RBAC. An OAuth access token is **not** yet a Kafdeck operator session.
- `KafdeckCliClient.cs` currently consumes an optional `KAFDECK_ACCESS_TOKEN` / `--token-file` and sends `X-Kafdeck-Access-Token`. The current CLI is intentionally GET-only and does not expose mutation, approval or operation-status actions.
- The deployment access token **must never be upgraded** into mutation-capable OIDC authority or interpreted as a bearer automation principal.

Implementing only an `Authorization: Bearer` client header would not satisfy any of the required server-side identity, issuer, RBAC or risk gates.

## 2. Explicit principal kinds and trust boundaries

| Principal kind | Authentication | Intended scope | Non-negotiable rule |
| --- | --- | --- | --- |
| Browser human | Existing OIDC login -> Kafdeck HttpOnly cookie | Existing UI + governed operations | Cookie and antiforgery behavior unchanged |
| Interactive CLI human | IdP-issued **access token** via Authorization Code + PKCE, exact loopback callback | Explicitly admitted versioned API routes | No browser-cookie forwarding or user impersonation |
| Unattended automation | IdP-issued OAuth client-credentials access token for a **registered service principal** | Narrow allowlisted actions/resources, no implicit operator privileges | No use of a human refresh token or shared deployment key |
| Legacy deployment CLI | Existing deployment access token | Existing supported read-only commands | Cannot be promoted to mutation/approval/status authority |

Treat each kind as a distinct server-side `AuthenticatedPrincipal` with `Kind`, `Issuer`, `Subject`, optional `ClientId`, validated audience, immutable policy registration identity, request correlation and credentials expiry. Do not manufacture a browser `SessionId` or `OperatorSessionContext` for service principals.

**Identity keys must be domain-bound and collision-resistant:** for humans use (kind, trusted issuer, subject); for registered services additionally bind the admitted client identity. Neither an arbitrary display name nor a caller-provided `actor` field is security evidence. A service account cannot satisfy a required distinct *human* approver simply by changing a client ID.

## 3. Token acquisition

### Interactive human CLI

1. Register a public CLI client with the configured IdP and allowed **exact loopback** redirect URI; use Authorization Code + PKCE (S256), cryptographically generated state and nonce, limited local listener lifetime, strict callback path/port/state matching and one-time exchange.
2. Validate the returned issuer and intended Kafdeck **API access-token** audience (the browser OIDC client ID alone is not a sufficient API audience), token type, expiry and allowed scopes/roles. Never use an ID token as an API bearer token.
3. Device Authorization Grant is optional and remains disabled unless the selected IdP explicitly supports it and its polling/verification controls are reviewed. No implicit/password flow, no copied browser cookies and no manually accepted `id_token`.
4. Tokens are memory-only by default. If local persistence is explicitly admitted later, require OS-protected, per-user encrypted storage, bounded retention, atomic permissions and an explicit `logout/forget` action. Never print tokens, use token-bearing argv, URL query strings, CLI diagnostics, CI artifacts or telemetry.

### Unattended automation

1. Explicitly register a Kafdeck service principal, with an owner, allowed audience/issuer, credential-rotation owner, action/resource grants, expiry/disable lifecycle and audit identity **before first use**.
2. Use OAuth 2.0 client-credentials with **asymmetric `private_key_jwt`** or mTLS client authentication if supported by the configured IdP. This is an access-token issuance flow, not an OIDC browser login.
3. Credential references must be provisioned outside GitOps/Terraform state and must never appear in manifest/plan/stdout. No fallback to shared `X-Kafdeck-Access-Token`, client secret in argv, or a human token.
4. Reject a provider that cannot issue signed, resource-audienced, attributable and expiring access tokens with a stable registered principal identity. Do not silently reduce required controls to match an IdP limitation.

## 4. Kafdeck API admission and validation

- Default: **disabled**. Enable a separate `nonBrowserOidc` configuration only after an owner-admitted IdP profile, issuer, **Kafdeck API audience** and per-principal policy mapping exist. No implicit activation from `AccessMode=Oidc`.
- On every request validate trusted HTTPS issuer (loopback test exception only), pinned discovery/JWKS origin, signature against allowed asymmetric algorithms, `exp`, `nbf`, token-purpose/type, exact audience and stable principal/client binding. Reject unexpected/multiple tenant audiences, issuer confusion, alg `none`, unregistered services and missing stable identity. Cap acceptable clock skew and token lifetime.
- When rotation/revocation is not immediately observable in an air-gapped installation, **do not promise instantaneous JWT revocation**: use bounded access-token lifetime, cached-key rollover with fail-closed stale-key policy and explicit service-principal disable/revocation controls; add introspection/denylist only where reviewed and operationally available.
- Select cookie versus bearer only through explicitly configured authentication schemes on **admitted, versioned API routes**. A bearer token cannot enter a browser cookie scheme; a cookie cannot be accepted as an unattended service principal. Reject conflicting credentials rather than selecting the more privileged one.
- Preserve cookie-route antiforgery. Explicit bearer clients do not inherit cookie auth or browser CSRF exemptions on unrelated routes. Protect CORS, HTTPS, redirects, upstream `Authorization` handling and outbound auth header scope. Do not expose a generic HTTP or raw provider proxy.
- The existing backend remains the **single authority** for action/resource/tenant/cluster authorization, capabilities, immutable preview/current-state identity, high-risk classification, durable-operation conflicts, lock/lease state and audit. CLI, Terraform, GitOps and MCP only call typed backend APIs.
- Mutating endpoints must reauthorize the **current** principal at confirm/execute time, not only at plan creation. Verify plan ownership, resource version, server-side nonce/expiry, action scope and approval state. Revalidate at actual external effect time as existing mutation architecture requires.
- Every mutation is attributed to the exact (kind, issuer, subject, client identity, correlation) principal. No prompts, CI actor strings, plan contents or config filenames become identity evidence.

## 5. Approval, risk and durable outcomes

- A service principal may request/plan/execute only the actions explicitly granted by backend policy. **CRITICAL** operations remain `PendingApproval` until a distinct independently authenticated and authorized principal approves. No non-interactive self-approval, swapped-service-identity approval, or approval by the subject who initiated the plan.
- Preserve exact preview/hash, current-state revision, bounded retry, idempotency and persisted admission evidence. Never convert `UnknownExternalEffect` into a blind replay, claim a synchronous Terraform apply succeeded while awaiting human approval, or hide a denied/conflicted execution behind HTTP 200.
- Define stable typed response/error mappings for `PendingApproval`, `Denied`, `Conflict`, `Expired` and `UnknownExternalEffect`, with safe operation reference IDs and no credential/provider payload.
- No generic shell, arbitrary SQL, arbitrary Kafka protocol or arbitrary provider HTTP command is admitted.

## 6. Required identity and API contracts before code

| Contract | Required admission evidence |
| --- | --- |
| `NonBrowserIssuerProfile` | Explicit discovery/JWKS origin, API audience, allowed grants/algs, deployment/tenant binding, cap on token lifetime/skew |
| `AutomationPrincipalRegistration` | Immutable principal key and kind, service owner, exact action/resource grants, disabled/revoked state, credential rotation ownership |
| `BearerPrincipalNormalizer` | Stable identity without forged browser session, strict issuer/audience/client binding, no arbitrary group elevation |
| `GovernedApiAuthentication` | Explicit scheme/route matrix, credential collision rejection, cookie/bearer CSRF separation |
| `ApiOperationOutcome` | Versioned typed error/state contracts; pending approval and unknown effects survive CLI/automation |
| `PrincipalAuditProjection` | Typed human vs service attribution, correlation, denied/approved/attempted action, safe fields only |

The implementation PR must link tested schemas and **prove authorization parity with existing browser paths** before any mutation/approval/status CLI command is exposed.

## 7. Dependency release rules

- **W67**: First admit non-browser identity and GET-only route parity under a real IdP. Mutation plan/status can follow only with backend risk/ownership/audit parity; approval pathways require explicit distinct-principal proof.
- **W68**: Define typed, versioned declarative ownership/resource identity and read/drift first. `plan/apply` stays blocked until W67 admitted bearer authorization and typed mutation API semantics.
- **W69**: No Terraform resource marked Supported before W68 lifecycle/import/drift/apply contracts are stable and provider acceptance tested. No raw JSON/provider-config passthrough.
- **W70**: Read-only typed MCP tools may be designed against **existing** stable GET contracts now, but external deployment must still authenticate. MCP mutation tools await W67 non-browser authority and action-specific server governance.
- **W71**: Verify release matrix by provider/IdP/CLI/runtime; unsupported features must report honest capability state and cannot be relabeled Supported to meet a date.

## 8. Minimum security and integration acceptance matrix

- Real IdP Authorization Code + PKCE loopback tests: bad state, nonce, redirect origin/path/port, expired code, replay, token audience mismatch and intercepted callback.
- Real service-principal token tests: valid `private_key_jwt`/mTLS grant as supported, unknown client, wrong issuer/audience, expired/nbf, rotated/stale JWKS, disabled registration and revocation-policy behavior.
- Human and service principal cross-use denial; token-kind confusion; deployment `X-Kafdeck-Access-Token` cannot access mutation/status/approval.
- Denied action/cluster/tenant/resource RBAC, redacted 403/404 behavior and no cross-tenant data in list continuation; no unbounded page.
- Cross-principal approval and replay tests, distinct approver on CRITICAL, stale preview/lease/decision, PendingApproval round trip and ambiguity preservation.
- Browser cookie + antiforgery still required where appropriate; bearer scheme cannot be used to bypass them through alternate routes.
- Secret sentinel tests for stdout/stderr, response bodies, logs, OpenTelemetry, shell/argv, Terraform state, GitOps manifests, MCP output and exception paths.
- Concurrency, HA, IdP outage, air-gap, JWKS rotation, token expiry mid-request, bounded retry and principal disable between plan and execution.
- Exact-head Quality, persistence/benchmark where applicable, dependency/supply-chain, CodeQL, Codex security review, CODEOWNER approval and protected-main verification.

## 9. Owner/architecture decision record — OPEN

Before implementation, record an explicit decision on:

1. **IdP(s) and grants:** which actual IdP(s) must be supported at v0.8, and whether Authorization Code + PKCE and client-credentials/`private_key_jwt` or mTLS are enabled there (Device Grant remains optional).
2. **Issuer/audience:** exact Kafdeck API resource/audience and discovery/JWKS deployment profile; no fallback to the browser client ID.
3. **Principal governance:** who registers/approves service principals, which resource families are initial automation candidates, and who can independently approve CRITICAL operations.
4. **Credential lifecycle:** machine credential storage/rotation/revocation, and whether human token caches are prohibited or explicitly allowed.

Until this decision is reviewed and admitted on protected main, **non-browser mutation/approval/status CLI, W68 apply, W69 mutating resources and W70 mutating MCP tools remain BLOCKED**. The RFC itself introduces no runtime behavior or publication authorization.
