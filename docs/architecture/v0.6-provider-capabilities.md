# v0.6 Provider Capability and Evidence Matrix

Status: **ADMITTED v0.6 RELEASE BASELINE**. Scope #145; tracker #146. Pinned-provider evidence is retained here; actual production availability is reported by the v0.6 capability catalog and release-readiness evidence.

## Evidence layers

Runtime support is the intersection of typed Kafdeck adapter admission, pinned .NET/librdkafka API availability, actual broker/provider feature support, configured profile, current authorization and required persistence. The inspected `Directory.Packages.props` pins `Confluent.Kafka` 2.15.1; this planning PR does not upgrade it. Online current-client documentation is not proof that an API exists in the pinned package. W41 must compile and retain a narrow API availability probe before admitting dependent implementations.

| Operation family | Reference primitive / semantics to validate | Evidence required before activation |
| --- | --- | --- |
| ACLs | Describe/Create/Delete ACL bindings; no atomic ACL update | Pinned-client compile probe, exact-filter semantics, per-binding errors, real authorized/denied Kafka tests |
| SCRAM | Describe metadata / alter typed credential operations | Pinned-client probe, mechanism/iteration metadata only, CRITICAL finalization/leakage tests |
| Quotas | Describe/alter client quotas; distinct default/named entity dimensions | Client availability and exact entity matching, unit/value/reset tests |
| Dynamic config | Incremental supported config alterations plus configuration-source metadata | Per-key versioned update-mode registry, no static/sensitive passthrough; provider rejection/readback |
| Preferred election | Preferred-only election on explicit partitions | Client availability, no null/all/unclean shortcut, per-partition results |
| Reassignment/log-directory movement | Submit/list assignment changes and observe actual placements | Pinned API availability, real multi-broker/directory fixtures, partial/unknown/drift evidence |
| Cordon/decommission | Kafka 4.3 cordon configuration and explicit maintenance sequence | Positive 4.3.1 fixture; negative 4.2.1/4.1.2/3.9.2 or feature-disabled fixture; exact shutdown/unregister semantics |
| Finite transfer | Bounded assigned source reads and acknowledged destination produce | Two physical clusters, auth/masking/range/rate/checkpoint/ambiguity tests; no exactly-once claim |
| MM2 integration | Fixed supported Connect/MM2 profile with enumerated side effects | Real profile fixture, hidden-write/secret tests and enforceable-control evidence, otherwise explicit unavailability |

## Initial compatibility targets

Retain the existing Kafka matrix: Tier 1 4.3.1 / 4.2.1 / 4.1.2 and Tier 2 3.9.2. This is not a blanket feature matrix: test both supported and deliberately unsupported behavior. KRaft is primary; no direct ZooKeeper path. Java Admin APIs, CLI capabilities or a vendor's Kafka-compatible endpoint do not justify fabricating an equivalent .NET method.

If an essential API is missing, record the exact missing pinned symbol, the affected operation and the safe unavailable behavior. Do not introduce a generic REST/CLI proxy, reflection-driven provider tunnel, raw protocol executor, native escape hatch or runtime sidecar to conceal the gap. A reviewed dependency change within approved architecture needs fresh CI and compatibility evidence; a material technology/trust-boundary change requires owner decision. Do not close the capability as delivered until its disposition is explicit.

Capability probes are bounded and non-mutating. A destructive test to find out whether a production API is supported is prohibited. Store evidence timestamp/profile/version/source and distinguish Unsupported, Unauthorized, Unknown, Unconfigured and Supported. Unsupported query shapes cannot be simulated by retrieving an unbounded response and paginating it in memory.

## Primary references and limited factual observations

- **S1 — Apache Kafka 4.3 release:** [release announcement](https://kafka.apache.org/blog/2026/05/22/apache-kafka-4.3.0-release-announcement/). It identifies KIP-1066 cordon support. Therefore the design must not assume all 4.x versions support this feature.
- **S2 — Apache Kafka operations:** [4.3 operations](https://kafka.apache.org/43/operations/basic-kafka-operations/). Cordon, evacuation, shutdown and removal are distinct stages. Its operational examples are reference semantics, not permission to embed CLI execution. Replica assignment order and throttle cleanup need explicit treatment.
- **S3 — Apache Kafka broker configuration:** [4.3 broker configs](https://kafka.apache.org/43/configuration/broker-configs/). Update mode varies by key; the cordon setting is not interchangeable with static log-directory configuration. Kafdeck's allowlist is an additional restriction.
- **S4 — Confluent .NET API:** [IAdminClient](https://docs.confluent.io/platform/current/clients/confluent-kafka-dotnet/_site/api/Confluent.Kafka.IAdminClient.html) and [client overview](https://docs.confluent.io/kafka-clients/dotnet/current/overview.html). The current reference documents typed ACL and SCRAM calls; availability of other families must be proven against pinned 2.15.1 rather than guessed from another language.
- **S5 — Apache Kafka MM2:** [4.3 MirrorMaker configuration](https://kafka.apache.org/43/configuration/mirrormaker-configs/). It describes automatic topic discovery, ACL/config sync and internal offset-sync/heartbeat/checkpoint behavior. Those are potential extra writes; typed Kafdeck profiles must enumerate/restrict them instead of forwarding defaults blindly.

References establish provider facts only. Proposed risk floors, quotas, state records and admission gates are Kafdeck design choices defined by the companion documents. Future version evidence must update this matrix through review without rewriting historical release evidence.
