# v0.6 Cross-Cluster Transfer and Replication Security

Status: **ADMITTED v0.6 CONTRACT BASELINE**. Scope #145; tracker #146. See [authorization](../api/v0.6-authorization-risk-matrix.md), [runtime budgets](v0.6-fleet-runtime.md), [release readiness](../releases/v0.6-readiness.md) and [ADR-0007](../adr/0007-durable-fleet-operation-progress.md). Public activation remains capability-driven.

## Finite transfer contract

A transfer is one explicitly initiated finite operation, not a scheduler, whole-cluster pipe or replay framework. The immutable plan contains source/destination deployment profile versions and physical cluster identities, exact source/destination topic identities, explicit partition mapping, frozen `[startInclusive, endExclusive)` offsets, isolation policy, record/byte/time/rate caps and data-policy fingerprints. Reject aliases for the same physical cluster and topology loops. Timestamp/latest selection resolves once before preview; the end never follows a growing log.

No implicit destination creation, config/ACL/schema copy, consumer offset mutation, destructive replacement or purge is included. Destinations must be explicitly prepared through separately admitted operations. Raw byte-preserving transfer preserves key/value/header ordering and null-versus-empty values, uses explicit destination partitions, and documents that offsets change, cross-partition order is not guaranteed and broker timestamp policy may differ. It is not a global consistent snapshot; source retention, compaction and aborted transactions can change the observable set. A source gap is reported, never silently widened or skipped as success.

## Authorization and masking

Require `cluster.transfer.plan`/`cluster.transfer.execute` for the exact pair, source `record.read` AND `record.export`, and destination `record.produce` for every mapped topic. All are independent. No maintenance/admin/Connect permission substitutes for these rights. Check current requester and required approver eligibility immediately before each new read/produce batch, and revalidate relevant topic/policy identity.

Transfer cannot bypass server-side masking through a raw byte path. For the initial byte-preserving contract, if any applicable source masking/redaction policy cannot be satisfied without changing key/value/header bytes, deny the transfer as an unsupported policy combination. Do not add a masking-bypass grant, silently remove fields or invent arbitrary serialization/transformation. External replication faces the same eligibility restriction; ordinary permission to see masked records is not permission to replicate originals.

## Checkpoints, acknowledgement and ambiguity

Read finite assigned ranges without joining a production consumer group or committing source offsets. At most one bounded batch is unresolved per operation. Persist a safe batch identity, source range/count/byte counters and dispatch marker before destination produce. Acknowledge per record/partition where available. Persist the next acknowledged source offset and acknowledgement metadata transactionally with parent progress/audit after successful I/O.

A broker acknowledgement does not atomically commit a Kafdeck checkpoint. A crash after produce but before durable acknowledgement/checkpoint leaves an ambiguous batch and `ExecutionUnknown`; do not replay it after restart, even with the same idempotency key. Producer idempotence may help within one live producer session but is not a cross-restart exactly-once claim. Resume only from a fully durable known checkpoint with no unresolved batch and current eligibility. Boundaries/budgets are lifetime totals, not reset on lease renewal.

Stopping future batches does not undo prior writes. Keep safe per-target progress and never persist raw payloads to enable resume. A raw-value hash is not a durable equality oracle: material binding, where needed, uses keyed safe evidence and is not exposed to callers. Verification does not scan destination records to guess duplicate status.

## External MirrorMaker 2 / replication integration

This is a separate typed integration profile, not the finite transfer engine and not arbitrary Connect configuration. Bind exact deployment-configured source/destination/Connect profiles, connector identities, fixed supported connector classes, exact escaped topic inclusion, naming policy and every provider side effect. No arbitrary URL, client overrides, transforms, converter/filter classes, scripts or runtime plugins.

Server-owned profiles disable topic/ACL/config/group-offset synchronization and discovery expansion unless an individually admitted typed effect is explicitly authorized and materialized in preview. The initial integration has no automatic ACL/config/consumer-offset sync. Internal heartbeat/checkpoint/offset-sync and Connect worker state topics must be inventoried, located and pre-provisioned or explicitly governed; they cannot be hidden writes to a source billed as read-only. Use safe deployment secret references; do not durably store JAAS strings or raw credentials.

The planning profile MUST enumerate the physical cluster and exact topic for every internal write and derive a closed permission target for it:
- MM2 heartbeat topic: `record.produce` on the exact configured heartbeat topic in the profile-declared physical cluster for that replication direction;
- MM2 checkpoint topic: `record.produce` on the exact configured checkpoint topic in its profile-declared physical cluster;
- MM2 offset-sync topic: `record.produce` on the exact configured offset-sync topic in the physical cluster selected by the tested profile/configuration; its location is never inferred from a generic default;
- Connect worker `config.storage.topic`, `offset.storage.topic`, and `status.storage.topic`: `record.produce` on each exact topic in the Connect worker's backing Kafka cluster.

Every exact mapped destination data topic MUST already exist before activation unless the same immutable preview separately materializes its governed creation intent and requires `topic.create` on that exact destination cluster/topic in addition to `record.produce`. Broker/MM2 producer auto-creation is never an authorization substitute: if the topic is absent and no exact governed creation effect is present, activation fails closed before any data movement. Pre-provisioning removes only the creation requirement, not the destination `record.produce` requirement.

If any internal topic does not already exist and the tested integration is allowed to create it, the same immutable preview MUST additionally include `topic.create` on that exact cluster/topic with the governed topic-creation intent/configuration. An external runtime's implicit/automatic topic creation is unavailable unless this creation effect is explicitly authorized and materialized. Pre-provisioning removes only the creation requirement; it never removes the `record.produce` requirement for subsequent internal writes.

The initial profile keeps ACL sync, topic-config sync and consumer-group-offset sync disabled. If a later admitted tested profile enables one of those effects, the preview must also enumerate its exact target/action using the already-governed mutation actions (`acl.alter`, the applicable topic/config alteration action, or `consumer.offset.alter`) rather than treating replication permission as a substitute.

Do not claim a standard externally running MM2 connector obeys Kafdeck's per-batch authorization, finite offsets or byte counters merely because its config was approved. Distinguish observation/configuration of an existing externally managed integration from Kafdeck-managed automatic start/resume of a data flow.

**Managed MM2 activation is explicitly unavailable in the admitted v0.6 baseline.** Standard MM2/Connect does not, by the evidence available to this planning package, provide a Kafdeck-enforceable lifetime record ceiling, lifetime byte ceiling, aggregate source/destination pair rate ceiling, finite activation lifetime, or guaranteed revocation/stop boundary. Kafdeck therefore MUST NOT create, update, resume, restart, task-restart or otherwise activate a recognized replication connector when that action can start or resume data movement. Best-effort polling followed by pause/stop is not a substitute for an enforceable budget and must not be presented as one.

W48 still implements the fixed-profile integration boundary: profile/class/endpoint restrictions, exact hidden-write inventory, source/export/destination authorization requirements, safe read/status observation, safe pause/stop where tested to be non-starting, and shared guards on all existing v0.5 Connect paths. It must record managed activation as a blocked capability with real provider/runtime evidence rather than silently omitting replication integration or weakening its safety contract.

A future Kafdeck-managed activation profile requires a separately reviewed material scope/security decision before implementation. That decision must define concrete finite record/byte/time/rate hard caps, identify the external mechanism that actually enforces every cap independently of Kafdeck polling, prove a bounded stop/revocation contract under loss of Kafdeck workers/connectivity, and add real compatibility/fault evidence. Merely placing numerical limits in a preview is insufficient. Any stronger delegated continuous-data authority remains outside this v0.6 admission.

## Existing-path bypass protection

Existing v0.5 Connect control routes must not become alternate entrances for a recognized replication connector with weaker permissions. W41/W48 must define and test one shared semantic classification/admission guard for **connector create, connector update, connector restart, connector resume, task restart, and any other existing action that can start or resume data movement**. `connect.alter` alone is insufficient for a recognized replication integration: the guard must derive and authorize the same source read/export, destination produce, transfer/replication actions and enumerated internal-write targets that direct v0.6 activation requires. In the v0.6 baseline, satisfying that conjunction is necessary but not sufficient: an action that would start/resume MM2 movement is still denied because managed activation is unavailable.

Pause/stop-like actions may remain available under their typed safe control contract only when they cannot create a new external effect; resuming from paused/stopped state always passes the stronger shared admission guard and, in the v0.6 baseline, remains denied when it would start movement. Unknown/custom replication classes or opaque configs capable of hiding cross-cluster endpoints are unavailable for Kafdeck-managed activation; they are not accepted through an unrestricted config field. This does not claim Kafdeck controls external administrators or already-running unregistered connectors.

W48 retains the existing one-Connect-profile-per-cluster constraint. Managing additional runtimes/cloud IAM, arbitrary topology generators or general replication scheduling is not implicitly approved. Any client/provider gap or unenforceable accepted capability is recorded in #146 and escalated before declaring that workstream complete.
