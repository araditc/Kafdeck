# v0.6 Reassignment & Broker Maintenance Contracts

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Authority:** Issue #145 / RFC-0006
- **Tracker:** Issue #146

## Purpose

Define the non-executable planning contract for partition/replica reassignment, replication-factor changes, preferred leader election, reassignment throttling, broker evacuation and log-directory maintenance before any provider mutation implementation is admitted.

## Reassignment plan identity

A reassignment preview is built from a finite, canonical plan. Each target contains:

```text
ClusterId
Topic
Partition
CurrentReplicas[]
CurrentLeader?
CurrentIsr[]
TargetReplicas[]
CurrentReplicationFactor
TargetReplicationFactor
ObservedBrokerStateFingerprint
ObservedPlacementFingerprint
EstimatedBytes? + EstimateProvenance
```

The plan is normalized and included in the preview hash. Patterns/filters used to discover candidates are not execution targets; execution uses only the materialized partition list.

## Plan construction rules

- no duplicate broker IDs in a target replica set,
- every target broker must be currently known and eligible under provider/policy constraints,
- target RF must satisfy configured minimum durability policy,
- RF reduction is CRITICAL,
- broker/log-directory exclusion sets are explicit,
- estimated bytes are displayed only when log/metric evidence exists and are labeled `Measured`, `Derived` or `Unknown`,
- plan size is capped by configured target/byte/time budgets,
- planner heuristics are deterministic for the same normalized evidence/policy version or record their seed/decision inputs when deterministic ordering alone is insufficient.

## Staleness / TOCTOU contract

Immediately before dispatch, Kafdeck re-observes material state:
- partition replica placement,
- leader/ISR where safety policy depends on it,
- target broker eligibility/availability,
- relevant log-directory availability,
- provider capability,
- policy version when material.

A material mismatch from the admitted preview yields `StalePreview`; the system does not silently recalculate and dispatch a different plan.

## Preferred leader election

Preferred leader election is a separate typed operation from reassignment. Preview materializes topic/partition targets and current leader/preferred replica evidence. Large target sets escalate from MODERATE to HIGH by server policy. It cannot be piggybacked invisibly onto reassignment.

## Reassignment execution

1. claim durable operation and resource keys,
2. reauthorize/revalidate,
3. persist dispatch boundary,
4. invoke typed reassignment provider port exactly for the frozen plan,
5. record safe provider evidence/token if available,
6. enter bounded long-running progress observation,
7. map partial/ambiguous state truthfully,
8. verify final placement/RF.

A timeout after possible submission never causes automatic resubmission.

## Throttling

Reassignment throttling is a typed operation with explicit current/requested throttle values and target scope. It cannot use a generic config endpoint. Throttle application/removal is HIGH risk by default and must be independently auditable from the reassignment plan.

Where a workflow needs both reassignment and throttle changes, preview must show both typed effects and their ordering/cleanup behavior. Failure to remove a throttle is reported and reconciled; it is not hidden as a successful reassignment.

## Broker evacuation

Broker evacuation means moving all materialized replicas away from an explicit broker using the admitted reassignment machinery. It does not by itself claim that the broker is decommissioned at Kafka/provider level.

Preconditions include:
- broker identity exists and matches the requested target,
- affected partitions are fully enumerated under configured bounds,
- a safe target placement can be built,
- minimum RF/ISR/durability policy is satisfied,
- target brokers/logdirs are eligible,
- placement/skew/capacity checks use only available evidence and label unknowns.

Broker evacuation/decommission is CRITICAL.

## Log-directory maintenance

When provider APIs support log-directory describe/reassignment, Kafdeck may plan replica movement away from an explicit broker/logdir. There is no generic filesystem operation. The target broker/logdir identity and affected replicas are materialized and fingerprinted.

## Final decommission / cordon capability

Kafdeck must not fabricate a generic broker read-only or cordon primitive. Provider capability is split into:
- observe broker/logdir state,
- evacuate replicas,
- observe evacuation progress,
- provider-supported final decommission/finalization.

If only evacuation is supported, the operation completes as an evacuation with a clearly stated remaining manual/provider step. It must not claim full decommission.

## Progress and partial results

Long-running progress uses ADR-0007 subordinate checkpoints under the parent operation fencing generation. Safe per-target statuses may include:
- Pending,
- InProgress,
- Applied,
- FailedDefinitive,
- Unknown.

A mixture of applied/failed/unknown targets yields `PartiallyApplied` or `ExecutionUnknown` according to available evidence; the UI/API never collapses it to generic success/failure.

## Verification

Final verification reads current provider state:
- target replica set exactly matches the admitted plan,
- RF matches target,
- reassignment no longer reported in progress where observable,
- evacuated broker/logdir has no required remaining replicas for the admitted scope,
- final provider decommission state where a tested primitive exists.

Verification inconclusive after provider acceptance => `AppliedUnverified` or `ExecutionUnknown` depending on whether application itself is established.

## Mandatory tests

- out-of-band replica drift between preview and dispatch,
- target broker disappears,
- RF reduction below guardrail,
- partial reassignment,
- timeout immediately after submission,
- worker crash and lease takeover during progress,
- stale worker checkpoint rejection,
- throttle apply succeeds but cleanup fails,
- evacuation discovers additional replicas after preview,
- provider lacking final decommission primitive returns truthful evacuation-only capability.
