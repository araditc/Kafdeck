# v0.6 Fleet Runtime and Bounded Progress

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Authority #145; tracker #146; decision [ADR-0007](../adr/0007-durable-fleet-operation-progress.md).

## Reuse and extension points

Inspected baseline files under `src/backend/Modules/Kafdeck.Modules.Administration/` are `MutationModel.cs`, `MutationAuthorization.cs`, `MutationPersistence.cs` and the existing executor/recovery contracts. W41 extends the shared module. Identity & Access remains the only authority for current principal eligibility; infrastructure owns SQLite/PostgreSQL and typed provider adapters. HTTP/UI never receive or instantiate a provider client.

```text
UI / API
   -> typed preview + compound authorization + risk
   -> existing operation coordinator / preview / confirmation / approval
   -> operation repository + versioned progress + outstanding-effect obligations
   -> bounded, fenced dispatcher -> one admitted typed provider step
   -> read-only observer -> safe evidence / checkpoint / audit
```

## Closed progress contract

Progress is subordinate to the parent operation, not a replacement final result. Proposed phases are `Planned`, `WaitingForMaterial`, `Submitting`, `Observing`, `PausedAuthorization`, `WaitingForExternalAction`, `Stopped`, `Completed` and `Unknown`. A parent stays `Executing` during acknowledged ongoing work. `AppliedVerified` requires the plan's actual terminal postcondition, not successful submission. Partial definitive effects become `PartiallyApplied`. Any step that may have applied but is unaccounted for dominates the aggregate as `ExecutionUnknown`; known per-step effects remain visible.

Each step records a stable ID, typed kind, exact target/hash, generation, safe precondition fingerprint, dispatch marker, acknowledged status, bounded evidence and observed timestamp. No arbitrary command, callback, script or serialized provider DTO is a step. Transfer checkpoints record source partition and next acknowledged source offset, target partition and safe acknowledgement metadata, cumulative counters and an unresolved-batch marker; never raw bytes.

## Dispatch protocol

1. Atomically claim the admitted operation and validate schema, version, generation and budgets.
2. Acquire all required cluster execution slots in deterministic cluster-ID order. A failed multi-cluster acquisition releases only the undispatched attempt's slots; it never clears older effect obligations.
3. Atomically materialize/check conflict obligations before dispatch. All v0.6 paths and conflicting v0.5 topic/config/produce/purge paths must consult the same conflict predicate. A topic deletion conflicts with partition work and transfers; unrelated safe reads do not.
4. Resolve current requester/required-approver eligibility through Identity & Access. Missing/expired context pauses dispatch. The worker may not reconstruct OIDC groups from stored strings.
5. Recheck actual cluster/topic/broker identity, capability, policy version, safety constraints and plan-relevant state. Drift requires a new preview for undispatched effects; already-applied effects remain recorded.
6. Persist the per-step dispatch marker and outstanding obligation before I/O. If this fails, make no call.
7. Invoke one typed bounded adapter step. Do not wrap mutation I/O in a generic retry policy.
8. Persist acknowledgement and progress transactionally, then perform bounded readback. Ambiguous network/cancellation/process failure remains unknown. Release the short dispatch slot only after recording the outstanding obligation; observation uses a separate bounded slot.

Fencing does not make a Kafka call transactional with the database. A stale worker must not perform another call; a successor cannot redispatch an already marked step just because its lease expired. Out-of-band administrators remain outside Kafdeck locking, so current-state readback and uncertainty handling are mandatory.

## Conflict key design

Keys use versioned length-delimited encoding, not ambiguous slash concatenation. Include actual cluster identity plus target type and exact ID. ACL bindings include the complete tuple; SCRAM includes username/mechanism; quotas include typed entity dimensions; configs include scope/broker/key; assignments include topic identity/partition; maintenance includes broker/log-directory identity; transfers include both topic identities and partition maps.

The shared conflict relation handles parent/child overlap explicitly. Implementations cannot assume string equality between a whole-topic key and a partition key catches conflicts. Multi-step plans acquire a finite full conflict set. Disjoint work may proceed only when the typed predicate proves it is non-conflicting. Unknown/in-progress external effects keep obligations until safely reconciled. When bounded observation cannot resolve an effect, ADR-0007's closed `FleetUncertaintyDisposition` contract governs any quarantine/supersession; there is no generic obligation-clear path.

## Numerical design budgets

These are initial Kafdeck defaults/hard caps, not benchmark claims. Policies may tighten them; changing a hard cap needs reviewed contract/test evidence. Apply the minimum of these and all existing v0.5 limits.

| Budget | Default | Hard cap / rule |
| --- | --- | --- |
| Materialized target entries per operation | 50 | 256; all derived action/resource entries must also fit v0.5's 1,024-key ceiling |
| Configuration/ACL entries per typed request | 25 | 100; whole-operation total still bounded |
| Steps per parent plan | 64 | 256; no recursive/unbounded child graphs |
| Canonical intent UTF-8 bytes | 64 KiB | 128 KiB plus existing character limit |
| Provider response bytes / returned entries | 1 MiB / 250 | 4 MiB / 1,024, enforced at transport and decode boundary, not only after allocation |
| Single read or mutation RPC deadline | 10 seconds | 30 seconds; expiry does not prove non-application |
| Preview lifetime | 5 minutes | 15 minutes before first dispatch |
| Approved dispatch horizon | 30 minutes | 24 hours; each later mutating step/batch requires current authorization; extension needs fresh preview/approval |
| Observation interval | 15 seconds | Minimum 5 seconds, jittered; bounded backoff to 60 seconds |
| **Cumulative active observation window per operation** | **2 hours** | **24 hours total across all workers, leases and restarts; durable elapsed accounting never resets on takeover/restart** |
| Observation concurrency per cluster | 2 | 4; separate from read browsing and mutation dispatch budgets |
| Observation request rate per cluster | 1 per second | 2 per second aggregate across replicas |
| Transfer in-flight batch | 100 records / 1 MiB | 1,000 records / 4 MiB including keys, values and headers; at most one unresolved batch per job |
| Transfer rate per cluster pair | 1 MiB/s / 1,000 records/s | 10 MiB/s / 10,000 records/s, aggregate and durable-accounted; no unlimited setting |
| Finite transfer total | 100,000 records / 100 MiB / 30 minutes | 1,000,000 records / 1 GiB / 24 hours, first limit wins |
| Active transfers per physical cluster | 1 | 2 across replicas; source and destination both consume budget |
| Persisted progress projection per operation | 64 KiB | 256 KiB; safe per-step history is separately retention-bounded |

Every count, byte and duration sum is overflow-checked. Zero, negative, NaN and oversized settings fail configuration/intent validation. A record larger than the batch cap fails before producing; no implicit split or truncation. Provider transport limits that cannot be enforced make that operation/profile unavailable. Fake API pagination over an unbounded SDK response is not accepted.

`ActiveObservationElapsed` (or equivalent typed durable counter) is persisted with progress and advances from monotonic observation-session start/end evidence under the current fencing generation. Lease renewal, process restart, failover and backup/restore do not reset it. Clock rollback cannot reduce the durable total; implementation uses bounded non-negative deltas and caps each update by the actual lease/session interval. W41 defines the precise provider-neutral representation and tests overflow/clock anomalies.

When an approved dispatch horizon ends, stop submitting new effects but retain observation and obligations for existing effects. When the cumulative active observation window reaches its configured limit, stop automatic hot polling, durably transition the progress phase to `WaitingForExternalAction`/reconciliation-required, and retain every conflict obligation and unknown/partial result. Reaching the observation limit never releases a safety claim, never implies completion/non-application, and never permits redispatch. A later operator-requested read-only observation is separately authorized/rate-limited and its active polling time also contributes to the lifetime hard cap unless a newly governed preview explicitly admits a fresh observation budget; uncertainty disposition remains governed by ADR-0007. Restore/restart must not reset any cumulative budget.

## Audit, load and recovery

State/progress/checkpoint changes and pending safe audit events are persisted transactionally in the same database. Bounded audit delivery retries deduplicate by operation/step/event sequence. No raw record, password, SCRAM verifier, connector secret or provider response is logged. Existing safe-evidence limits remain in effect; progress is not an overflow channel for unrestricted evidence.

Two-worker, lease-loss, checkpoint-failure, stale-writer, out-of-band drift and backup-restore tests are mandatory. W41/W50 also test cumulative observation at default/cap/cap-plus-one, failover/restart non-reset, clock rollback/overflow handling, and that observation exhaustion stops hot polling without releasing obligations. SQL/provider errors before durable admission cause no external call. A full store or undeliverable audit backlog rejects new work rather than dropping live safety evidence. The read-only operator surface remains separately budgeted throughout.
