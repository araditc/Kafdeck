# v0.5 Product Specification — Safe Administration & Controlled Mutations

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **RFC:** RFC-0005
- **Scope authority:** Issue #121
- **Tracker:** Issue #122

## User outcome

An authorized operator can perform a bounded set of Kafka and ecosystem administrative changes from Kafdeck while seeing exactly:
- what will change,
- which resources are targeted,
- why the operation has its risk class,
- what confirmation/approval is required,
- whether execution was verified, ambiguous or partially applied.

Kafdeck does not turn an administrator role into a generic provider command tunnel.

## Product surfaces

### Topics
- create topic,
- alter supported topic configuration,
- increase partitions,
- delete topic,
- bounded explicit-target bulk operations.

### Records
- produce one or a bounded batch of records,
- template-assisted production,
- optional schema validation,
- no replay/job engine in v0.5.

### Consumers
- reset/shift offsets using explicit offsets or timestamp resolution,
- delete groups/offsets where supported,
- preview current -> target movement before confirmation.

### Schemas
- register schema/new version,
- change compatibility mode,
- delete subject/version where provider capability is explicit.

### Kafka Connect
- create/update/delete connector,
- pause/resume/restart connector or task where supported.

### Purge
- DeleteRecords-based purge/truncate by explicit per-partition offsets,
- timestamp requests resolve to offsets before preview,
- CRITICAL flow with independent approval.

## Safe workflow

Every mutation uses:

`Preview -> Confirm -> Approve if required -> Execute -> Verify`

The preview is server-authoritative. It includes:
- operation type,
- cluster,
- explicit targets,
- current/target values where meaningful,
- provider capability evidence,
- risk class and reasons,
- destructive/irreversible warnings,
- verification expectations,
- expiry,
- preview identity/hash.

A changed target/intent produces a new preview and invalidates prior confirmation/approval.

## Risk UX

### LOW
Clear preview + explicit same-actor confirmation.

### MODERATE
Clear preview + explicit confirmation. The UI emphasizes operational effect and configured limits.

### HIGH
Typed confirmation names the affected target/resource. Policy may require an additional approver.

### CRITICAL
Typed destructive confirmation + mandatory second eligible principal approval. The UI explicitly states that rollback is not generally available.

The server owns the risk decision. UI controls cannot lower it.

## Operation status UX

Operators can distinguish:
- Awaiting confirmation
- Awaiting approval
- Ready
- Executing
- Applied and verified
- Applied but verification inconclusive
- Partially applied
- Execution outcome unknown
- Rejected
- Expired
- Cancelled
- Preview stale
- Failed before dispatch
- Definitively rejected/failed by provider

The UI must never collapse `ExecutionUnknown` into “failed”.

## Truthfulness rules

- “Preview” is not “dry-run” unless the provider genuinely supports a dry-run primitive.
- “Reversible” is shown only when Kafdeck has an explicit safe inverse.
- “Atomic” is shown only when the underlying operation guarantees it for the represented target set.
- “Not applied” is never inferred from a timeout after dispatch.
- Timestamp purge/offset operations display the frozen resolved offsets.
- Out-of-band changes may invalidate a preview.
- Capability uncertainty fails closed.

## Secrets and payloads

- record payload values are never written to audit/logs,
- connector secrets are not rendered back to the browser,
- secret changes are shown as redacted/change indicators,
- Kafdeck does not create a durable plaintext staging store for Kafka payloads,
- execution material that is intentionally non-persistent must be re-submitted and hash-match the preview.

## Availability behavior

If durable mutation persistence is unavailable:
- v0.1-v0.4 read-only capability remains available,
- v0.5 mutation UI is visibly disabled/unavailable,
- Kafdeck does not silently downgrade to non-durable destructive execution.

If independent approval cannot be established:
- CRITICAL operations are unavailable,
- they are not downgraded to same-actor confirmation.

## Acceptance scenarios

1. A user with `topic.read` but not `topic.create` cannot preview/create a topic.
2. Same idempotency key + same intent returns the same operation.
3. Same idempotency key + different intent returns conflict.
4. Changing target/config after preview invalidates confirmation.
5. Topic deletion is CRITICAL and requires another eligible principal.
6. Partition increase is HIGH and is never described as reversible.
7. Offset reset preview shows current and target offsets per partition.
8. Timestamp offset reset freezes resolved offsets before confirmation.
9. Produce confirmation cannot execute a payload whose digest differs from preview.
10. Produce timeout after dispatch becomes `ExecutionUnknown`, not an automatic retry.
11. Connector secrets never appear in preview/audit/errors.
12. Schema hard delete is CRITICAL when provider semantics are permanent.
13. Bulk requests enumerate concrete targets before execution.
14. Concurrent conflicting Kafdeck operations return a deterministic conflict rather than race silently.
15. Out-of-band state drift produces `StalePreview` when material.
16. DeleteRecords purge requires explicit offsets and independent approval.
17. Direct API calls enforce the same state machine as UI.
18. Cookie-authenticated mutation requests require anti-CSRF validation.
19. Read-only deployments continue operating when mutation persistence is disabled.
20. No v0.5 endpoint accepts arbitrary Kafka AdminClient commands or arbitrary provider URLs.
