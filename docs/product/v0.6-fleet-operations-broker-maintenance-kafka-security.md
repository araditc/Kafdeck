# v0.6 Product Specification — Fleet Operations, Broker Maintenance & Kafka Security

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Scope authority:** Issue #145
- **Tracker:** Issue #146
- **RFC:** RFC-0006

## Product outcome

v0.6 turns Kafdeck from a controlled single-resource administration plane into a governed fleet-operations control plane for Kafka security and maintenance, while preserving the v0.5 safety kernel. Operators gain typed workflows for security configuration, dynamic cluster changes, reassignment and maintenance without receiving a generic provider command console.

## User-facing capability groups

### Security administration

Operators can inspect and, when separately authorized, manage:
- Kafka ACLs,
- SCRAM credentials without credential retrieval,
- client quotas,
- principal/resource access analysis with evidence/confidence boundaries.

The UI and API must separate read, plan/preview, confirm/approve and execute states. Secret values are never rendered back after submission.

### Dynamic cluster configuration

Operators can inspect broker/cluster configuration and change only keys which Kafdeck's active provider profile proves are dynamically alterable and which server policy explicitly allows. Unsupported/static keys are visible as non-executable rather than being tunneled through a generic configuration endpoint.

### Reassignment and leadership

Operators can:
- analyze partition/replica skew,
- build explicit reassignment plans,
- inspect current-to-target replica movements,
- see replication-factor changes,
- see transfer-impact evidence as measured/derived/unknown,
- configure bounded reassignment throttling,
- track progress,
- request preferred leader election separately.

No wildcard reassignment executes until concrete topic/partition targets are materialized.

### Broker and log-directory maintenance

Where the Kafka/provider capability exists, operators can plan and execute broker/log-directory evacuation/decommission workflows. The product must present current preconditions, affected replicas, target placement, safety violations and current progress. It must not advertise a fictional generic broker read-only mode.

### Cross-cluster movement and replication integration

Operators can create bounded transfer/clone jobs and manage admitted MirrorMaker 2/provider replication integrations. Every job binds source/destination identities, finite scope, budgets and authorization at both ends. This capability must not provide an unrestricted data-exfiltration path or a hidden general replication engine.

## Product safety behavior

### Risk communication

Every mutating preview displays:
- risk class and reasons,
- exact materialized targets,
- destructive/irreversible characteristics,
- relevant current-state evidence,
- approval requirement,
- expiry,
- known uncertainty.

CRITICAL workflows always require a distinct eligible approver. Clients cannot lower risk.

### Long-running operations

Long-running operations remain durable Kafdeck operations. Product status surfaces show:
- current phase,
- completed/remaining targets where safe,
- latest evidence timestamp,
- lease/worker-independent operation identity,
- ambiguous/partial/final outcome truthfully.

A browser refresh or worker failover must not create a second operation or re-dispatch a potentially-applied plan.

### Failure UX

The UI/API must distinguish:
- unsupported capability,
- validation/precondition failure,
- stale preview/plan,
- confirmation/approval required or expired,
- conflict,
- failed before dispatch,
- upstream rejection,
- execution unknown,
- partial application,
- applied but unverified,
- applied and verified.

`ExecutionUnknown` is a first-class outcome, not collapsed into failure.

## Authorization model

v0.6 uses explicit actions:

`acl.read`, `acl.alter`, `scram.read`, `scram.alter`, `quota.read`, `quota.alter`, `cluster.config.read`, `cluster.config.alter`, `leader.elect`, `partition.reassign`, `replication.factor.alter`, `reassignment.throttle`, `broker.maintenance`, `logdir.maintenance`, `cluster.transfer.plan`, `cluster.transfer.execute`, `replication.integration.alter`.

Cross-cluster transfer additionally requires source record read/export permissions and destination record produce permission. One permission family never substitutes for another.

## Product defaults

- mutation remains disabled when durable persistence prerequisites are not satisfied,
- SQLite remains standalone/single-instance for mutation execution,
- PostgreSQL remains the HA/multi-instance mutation store,
- security/maintenance execution is fail-closed when capability evidence is unknown,
- mutation polling/execution budgets are isolated from read visibility,
- no raw secret/payload persistence is introduced.

## Explicit non-goals

No generic admin shell, CLI passthrough, provider REST proxy, arbitrary code, generic cloud IAM, automatic self-healing, public plugin runtime, Terraform publication, MCP mutation tools, general replay/DLQ platform, or v0.7 feature activation.

## Acceptance criteria

The v0.6 product contract is ready for implementation only when:

1. all capability families have typed authorization and risk floors,
2. provider support is capability-profile based and fail-closed,
3. long-running progress/lease/fencing semantics are durable,
4. reassignment/decommission preview and stale-plan rules are explicit,
5. cross-cluster movement has conjunctive source/destination authorization and budgets,
6. secret handling prevents retrieval/persistence of SCRAM credentials,
7. API/UI contracts preserve one mutation pipeline,
8. fault/compatibility test strategy covers ambiguous and partial execution,
9. planning package is governed-merged to protected main.

Release/tag/publication remains separately approval-bound.
