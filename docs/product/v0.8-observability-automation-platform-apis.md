# v0.8 Product Specification — Observability, Automation & Platform APIs

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**

Authority: Gate 8 scope #208; tracker #209; W61 #210.

## Product outcome

Kafdeck v0.8 should let operators answer four questions safely:

1. **What is happening?** — live and historical operational evidence.
2. **Is it healthy enough?** — trends, SLOs, data-quality evidence and explicit unknown/stale states.
3. **Who or what should be notified?** — bounded notifier/webhook delivery.
4. **Can this be automated?** — API/CLI/GitOps/Terraform/MCP clients over the same governed authority model.

## Primary user journeys

### Observe

An operator can inspect:

- Kafdeck request/provider latency and failure rates;
- Kafka broker/topic/consumer throughput where trustworthy evidence exists;
- consumer lag trends;
- operation/job durations, ambiguity and retry/fencing states;
- configured integration health;
- historical SLI/SLO windows.

Missing evidence is shown as unavailable/unknown/partial, never fabricated as zero.

### Define SLOs

An operator can create a bounded SLO definition over admitted metrics/evidence and view:

- target;
- window;
- current compliance;
- burn/violation state;
- evidence freshness;
- history source/retention limitation.

An SLO cannot directly mutate Kafka.

### Monitor data quality

An authorized operator can attach a closed declarative policy to an exact record scope and see aggregate violation evidence without creating an unbounded consumer or durable payload archive.

### Route alerts

An operator can select a configured notifier profile and event class. Delivery status is explicit:

- Pending;
- Delivered;
- RetryScheduled;
- Exhausted;
- Blocked;
- UnknownExternalEffect.

Notifier credentials never appear in the UI/API.

### Use CLI/API

A human or CI process can perform the same admitted Kafdeck actions through versioned API/CLI contracts. The backend, not the client, owns:

- authorization;
- risk;
- preview freshness;
- conflict detection;
- approval requirement;
- provider capability;
- effect verification.

### GitOps/Terraform

An operator can declare only supported resource families. A plan clearly separates:

- no-op;
- create;
- update;
- delete;
- import/adopt;
- drift;
- blocked/unsupported;
- awaiting approval.

A declarative client may stop at AwaitingApproval; it does not convert CRITICAL work into an ungoverned synchronous effect.

### MCP

An agent can discover capabilities, read masked state, generate plans and submit governed operations. It cannot approve its own CRITICAL action unless a separately authenticated eligible human/principal independently approves under existing rules.

## Current release inheritance

v0.8 inherits from v0.7:

- OIDC/RBAC;
- masking and record/export separation;
- durable mutation/fleet/data-job state;
- risk/confirmation/approval;
- capability truth;
- provider identity;
- finite job budgets;
- no-blind-retry ambiguity;
- air-gap/local-assets;
- exact-source release governance.

## UX truth

Every v0.8 surface must distinguish:

- Supported;
- Unsupported;
- Blocked;
- Unconfigured;
- Denied;
- Partial;
- Stale;
- Unavailable;
- Unknown;
- AwaitingConfirmation;
- AwaitingApproval;
- ExternalActionRequired;
- Drifted;
- DeliveryExhausted.

Color alone is insufficient.

## Product acceptance

v0.8 is not release-ready until:

- live metrics are bounded/cardinality-safe;
- historical metrics have provider/retention evidence;
- SLO and trend views distinguish missing evidence;
- data-quality monitoring proves bounded record access and no raw persistence;
- notifier adapters prove SSRF/secret/retry boundaries;
- CLI/API parity is tested;
- declarative ownership/drift semantics are stable;
- Terraform resources are limited to stable contracts;
- MCP parity/bypass tests are green;
- compensation catalog contains only proven safe inverses;
- accessibility/air-gap/security/performance/provider matrices are green;
- publication receives a separate owner decision.
