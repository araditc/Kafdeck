# v0.3 Product Specification — Safe Data Explorer + Server-Side Masking

- **Status:** PROPOSED
- **RFC:** RFC-0003
- **Scope authority:** Issue #75 — Option A accepted

## User outcome

An authorized Kafdeck operator can inspect a tightly bounded window of Kafka records for debugging and operations without gaining Kafka mutation capability or receiving data that server-side policy requires Kafdeck to mask.

## Personas

### Kafka operator

Navigates to an authorized topic/partition, chooses an offset/timestamp range, inspects bounded records, and may follow a short live tail.

### Security/privacy administrator

Defines deployment-time masking rules and record-access bindings.

### Read-only metadata observer

May keep metadata visibility while having no record access.

## Permissions

v0.3 adds:

- `record.read`
- `record.export`

Neither is implied by `topic.read`, `topic.list`, or configuration-read permissions.

## Record browser

The operator can:

- select partition,
- start from explicit offset,
- resolve a timestamp to an offset,
- page forward,
- request a bounded previous page,
- see offset/timestamp/key/value/headers subject to masking,
- switch display among structured/text/hex when policy permits,
- see explicit decode/masking/budget states.

## Live tail

Live tail is explicitly started by the operator, bounded in duration/rate/bytes, cancellable, and stops promptly on browser disconnect.

It is not a durable subscription and does not commit offsets.

## Filtering

Supported filters include:

- key,
- partition,
- offset range,
- timestamp range,
- headers,
- bounded regex,
- deterministic CEL,
- deterministic jq-style expressions.

The UI exposes filter cost/budget outcomes rather than pretending an incomplete bounded scan is exhaustive.

## Schema-assisted decoding

When a Schema Registry profile is configured and authorized for the cluster, Kafdeck may decode Confluent-compatible Avro, Protobuf, and JSON Schema payloads.

Schema Registry is used only as a decoding dependency in v0.3. Full subject/version browsing is deferred.

## Masking

Masking happens on the server before payload reaches browser/API/export.

The UI shows when fields are redacted and may show a stable reason/policy identifier without disclosing the clear value.

If required masking cannot be applied safely, clear payload is not returned.

## Export

Authorized operators with `record.export` may export only the bounded, masked result set.

Formats:

- JSON,
- NDJSON,
- CSV when the result projection is structurally compatible.

Export is never an unbounded topic dump.

## Product states

First-class states include:

- unauthenticated,
- Kafdeck authorization denied,
- Kafka ACL denied,
- unsupported record capability,
- schema unavailable/decode failed,
- masked/redacted,
- partial/budget exhausted,
- timeout/cancelled,
- offset out of range,
- empty result.

## Acceptance scenarios

1. User with topic metadata access but no `record.read` cannot obtain payload bytes.
2. User with `record.read` on Cluster A cannot read records from Cluster B.
3. Timestamp navigation resolves to explicit partition offsets and returns a bounded page.
4. Previous-page navigation never creates an unbounded reverse scan.
5. Live tail disconnect cancels underlying read work.
6. Masked fields never appear in browser/API/export/log/audit.
7. Undecodable structured payload with mandatory field masking fails closed.
8. User with `record.read` but no `record.export` cannot export.
9. Export respects row/byte/time limits.
10. Kafka ACL denial remains distinguishable from Kafdeck RBAC denial.
11. No consumer offset is committed.
12. No record is produced/replayed.
13. No payload is persisted by default.
14. Existing v0.1/v0.2 metadata/OIDC/RBAC behavior remains compatible.
