# v0.6 Product Specification — Fleet Operations and Kafka Security

Status: **PROPOSED FOR GOVERNED PLANNING ADMISSION**. Authority: #145. Tracker: #146. RFC: [RFC-0006](../rfcs/0006-v0.6-fleet-operations-kafka-security.md).

## Operator journeys and acceptance

| Journey | Required preview and result | Explicit boundary |
| --- | --- | --- |
| Inspect/edit ACLs | Exact bindings, additions/removals, affected principal/resource scope, risk and per-binding readback | No wildcard deletion at dispatch; no atomic-update claim |
| Inspect/rotate/delete SCRAM | Username/mechanism/iterations, write-only secret change indicator, independent approval, safe acknowledgement | No password/salt/verifier retrieval; describe cannot verify password equality |
| Inspect/change quotas | Exact entity dimensions including default versus named entity, units, effective/inherited values and bounded delta | No null/default entity ambiguity; no credential changes |
| Change dynamic configuration | Exact broker/default scope, key, source/update mode, safe diff and reset semantics | Static/unknown/secret-bearing keys unavailable; no arbitrary config dictionary |
| Plan leadership/reassignment | Explicit partitions, ordered current/target replicas, RF/ISR/rack checks, throttle changes, evidence timestamps | No unclean election or automatic rebalancer |
| Maintain broker/log directory | Inventory completeness, stable IDs, cordon/evacuation steps and external prerequisites | No shell, filesystem delete, process restart or controller membership change |
| Transfer finite records | Source/destination identity, ranges, mapping, masking eligibility, ceilings, partial/unknown status | No follow-tail/scheduled replay; no implicit topic or ACL provisioning |
| Manage replication integration | Fixed profile, exact topic allowlist, all internal/remote writes, stop/revocation limits and safe status | No arbitrary connector class, transform or provider endpoint |

## Defaults and operator truth

The published stable identity stays v0.5.1 while v0.6 is being planned and implemented. Read-only remains the default posture. Each new surface is independently capability-gated; no empty view may imply a verified empty resource set when access is denied or data is incomplete.

The UI must distinguish `Supported`, `Unsupported`, `Unauthorized`, `Unconfigured`, `Unknown` and stale evidence. Progress reports observed time, data completeness and whether effects may still be ongoing. Byte/time estimates are labeled measured, derived or unknown with assumptions. An unavailable estimate is not zero.

Planning and previews are side-effect-free. Confirmation does not claim completion. Acknowledged-but-running reassignment stays in progress. Partial effects are displayed per target. Potentially applied ambiguity prominently shows `ExecutionUnknown`, disables replay, and links to bounded reconciliation evidence. Pre-dispatch cancel is different from stopping future transfer batches; neither promises rollback of already applied work.

## End-to-end security acceptance

Both direct API clients and the UI follow identical permission/risk/approval paths. Scope visibility never enables a mutation control. HIGH/CRITICAL workflows use server-issued typed target challenges. CRITICAL approval requires another currently eligible principal. Approval does not supply or reveal a SCRAM secret; the requester finalizes it separately with matching material.

Security views are scoped to the caller and do not expose concealed principals or other operations by identifier enumeration. Mutation status is non-cacheable and contains safe evidence only. Browser state must not persist secrets in local storage, session storage, URLs, telemetry or error reports.

## Operating model

Deployment-configured Kafka/Connect profiles and environment/file secret references remain authoritative. No arbitrary bootstrap endpoints, worker credentials, cloud IAM permissions or multiple-Connect-profile product expansion are admitted here. External broker stop/restart and static file edits are explicit human prerequisites. Kafdeck may present typed readiness evidence for them, but does not execute them.

Finite transfers are append-only into explicitly prepared destinations. Any destination provisioning, purge or security change is a separate existing governed operation and is never hidden in clone. Retention/compaction may remove source records; the product must state that transfer is not a cross-cluster snapshot or backup guarantee. MirrorMaker integration is capability-dependent, not a promise to enforce Kafdeck policy inside an uncontrolled external engine.

## Release acceptance

Each accepted capability is tracked to W41–W50 evidence. Unsupported combinations remain explicitly unavailable; material loss of a promised capability is escalated to the owner rather than silently reported complete. W50 must reconcile tests, documentation, accessibility, provider limitations, persistence upgrade/rollback and measurable load before seeking separate release approval.
