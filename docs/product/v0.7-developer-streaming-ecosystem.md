# v0.7 Product Specification — Developer & Streaming Ecosystem Platform

- **Status:** PROPOSED FOR GOVERNED PLANNING ADMISSION
- **Scope:** Issue #178

- **Planning:** W51 / Issue #181

## User outcome

A Kafka/platform developer or operator can use Kafdeck as a governed workspace for schemas, Connect, bounded data jobs and streaming-system diagnostics without receiving a generic execution tunnel or bypassing Kafka/provider security.

The user can answer and act on questions such as:

- Which schema version is active and compatible with a proposed change?
- What references depend on this schema?
- Can I register a new version or alter compatibility under current policy?
- Which Connect runtime am I operating against?
- Is a connector/task healthy, paused, failed or restart-exhausted?
- Can I safely create/update/pause/resume/restart/delete a connector?
- Can a bounded auto-restart policy act on this connector?
- Can Kafdeck decode this payload as CBOR/XML/MessagePack within safe limits?
- Can I replay or forward a finite record range without creating an unbounded pipeline?
- Can I generate a finite controlled test data set from this schema?
- Can I run a bounded read-oriented ksqlDB query?
- Which streaming-topology/lineage facts are observed and which are inferred?
- What capability is unavailable because of provider/version/security policy?

## Personas

### Platform / Kafka operator

Needs controlled lifecycle administration, clear blast-radius/risk semantics and trustworthy provider limitations.

### Application developer

Needs schema tooling, connector diagnostics, bounded test-data generation, replay/reprocess and fast navigation without direct access to privileged provider credentials.

### SRE / incident responder

Needs task failures, stack traces, bounded restart controls, replay/DLQ tools and explicit ambiguous/blocked states.

### Security / governance reviewer

Needs every mutation/execution tied to exact targets, permissions, risk, approvals, budgets and immutable audit evidence.

## Information architecture

### Global shell

Retains the existing Kafdeck shell and adds:

- current Kafka cluster;
- active ecosystem profile selector where more than one profile exists;
- capability status;
- current operation/approval alerts;
- command palette;
- last observation/freshness state.

### Schemas

Views:

1. Subjects
2. Subject versions
3. Version detail / references
4. Diff
5. Compatibility
6. Register new version
7. Lifecycle history/status

Mutation UX shows exact subject/version/provider, risk, preview and irreversible/permanent-delete warnings.

### Kafka Connect

Views:

1. Connect profile selector
2. Connector list
3. Connector detail
4. Tasks
5. Configuration
6. Metrics/stack traces where exposed
7. Restart policy
8. Operation history

Connector forms distinguish normal fields, secret references, write-only secret material and unsupported provider options.

### Data tools

Views:

1. Decode/inspect
2. Replay/reprocess
3. DLQ forward
4. Cross-topic/cross-cluster forward
5. Mock/data generator
6. Job status/history

All job creation screens show exact source/destination, partition/range, record/byte/rate/duration budgets and remaining policy ceilings.

### Streaming

Views:

1. ksqlDB query/editor
2. Query result
3. Streams topology
4. State-store metrics where exposed
5. Lineage graph

Every lineage edge shows provenance/confidence and whether it is observed or inferred.

### Catalog / Command Palette

- quick cluster/topic/schema/connector navigation;
- topic documentation/catalog view;
- no command-palette shortcut may bypass the same API authorization/risk controls used by normal UI routes.

## State model

All v0.7 views treat the following as first-class:

- loading;
- empty;
- stale;
- partial;
- authorization denied;
- unsupported;
- blocked;
- unconfigured;
- provider unavailable;
- validation failed;
- approval required;
- executing;
- waiting for external evidence;
- execution unknown;
- cancelled;
- completed with partial/terminal evidence.

An empty array is never used to represent denied or unsupported capability.

## Schema Registry acceptance scenarios

1. Register an Avro version under a subject and verify returned version/fingerprint.
2. Register Protobuf/JSON Schema with references.
3. Reject invalid reference cycles/unknown references where provider semantics require them.
4. Run compatibility check without mutation.
5. Alter compatibility with explicit exact scope and risk.
6. Soft-delete a version where supported.
7. Require a distinct destructive path for permanent deletion.
8. Show provider-specific unsupported semantics rather than emulating them unsafely.
9. Keep provider credentials out of API/UI/audit/logs.

## Kafka Connect acceptance scenarios

1. Configure multiple Connect profiles and switch without state leakage.
2. Preserve legacy singular Connect configuration as the normalized `default` profile.
3. Reject mixed legacy + profile-list configuration.
4. Create/update a connector through typed provider contracts.
5. Keep secret config write-only/redacted after submission.
6. Pause/resume/restart/task-restart with explicit authorization.
7. Delete only after destructive preview/risk gate.
8. Surface task stack trace and metrics where exposed.
9. Never let recognized replication/MM2 connectors bypass v0.6 guards.
10. Never forward arbitrary provider paths or connector classes outside policy.

## Auto-restart acceptance scenarios

1. Disabled by default.
2. Policy starts only when explicitly enabled/authorized.
3. Retry count/backoff/circuit breaker are bounded.
4. Authorization or policy revocation stops future effects.
5. Unknown dispatch does not trigger a blind second restart.
6. Restart/failover does not reset lifetime attempt limits.
7. Exhaustion is explicit and requires operator action.

## SerDe acceptance scenarios

1. Bounded CBOR decode.
2. Bounded XML decode with entity/external-resource behavior disabled.
3. Bounded MessagePack decode.
4. Reject nesting/collection/expansion bombs.
5. Fail closed on ambiguous structured interpretation.
6. Preserve binary fallback without pretending unsupported data is structured.

## Replay/reprocess/forward acceptance scenarios

1. Preview a finite exact source range.
2. Require independent source read/export and destination produce permissions.
3. Deny byte-preserving forwarding when masking policy requires byte changes.
4. Enforce record/byte/rate/duration caps.
5. Resume only from durable known checkpoints.
6. After produce/ack ambiguity, stop with `ExecutionUnknown`; do not replay.
7. Destination topic creation is never an implicit side effect.
8. Cross-cluster aliases cannot masquerade as distinct physical clusters.
9. Cancellation stops future effects but never claims rollback of already-produced records.

## Mock/Data Generator acceptance scenarios

1. Generate from admitted schema/tooling.
2. Deterministic seed produces repeatable bounded output where format supports it.
3. Preview exact destination and limits.
4. Production environment policy denies by default.
5. Hard cap-plus-one attempt fails before extra production.
6. No arbitrary template/code execution.
7. Cancellation and HA failover preserve cumulative budgets.

## ksqlDB / topology / lineage acceptance scenarios

1. Execute a bounded read-oriented admitted statement.
2. Reject persistent-query/DDL/DML statements in v0.7.
3. Enforce query row/byte/time/concurrency caps.
4. Display Streams topology only from observable evidence.
5. Display state-store/RocksDB metrics only from exposed telemetry.
6. Mark inferred lineage edges distinctly from observed edges.
7. Inferred lineage cannot authorize mutations or data access.

## UX safety rules

- Mutation buttons are absent or disabled with reason when capability is not admitted.
- Risk/approval truth comes from the backend, not frontend inference.
- Sensitive values are write-only and cleared after submission.
- No browser local/session storage for provider credentials, secret values or record payload caches.
- Refresh pauses/reduces when hidden and never starts an unbounded external poll loop.
- Long collections are paginated/bounded.
- Keyboard and screen-reader semantics remain first-class.
- Reduced motion and responsive layout remain supported.
- All assets required for normal operation are local/air-gap compatible.

## Performance UX targets

These are interaction targets, not provider SLA promises:

- common cached navigation should not require per-row provider calls;
- page sizes remain bounded;
- large schema/connector collections use provider-aware pagination or bounded snapshots;
- query/job UIs stream or page bounded results rather than retaining unbounded browser data;
- cancellation is exposed for long finite jobs;
- visible progress uses server-authoritative durable counters.

## Explicit exclusions visible to users

The v0.7 UI contains no general-purpose:

- shell/CLI;
- provider REST explorer;
- raw Kafka protocol console;
- arbitrary JavaScript/Python transform;
- public plugin loader;
- infinite producer/generator;
- continuous replay/forward proxy;
- ksqlDB persistent-query/DDL administration;
- hidden Schema/Topic/ACL creation as a side effect of another tool;
- bypass for missing provider capabilities.
