# v0.2 Product Specification — Operator Identity and RBAC

- **Status:** PROPOSED
- **RFC:** RFC-0002
- **Scope authority:** Issue #57 — Option 2 accepted

## User outcome

A Kafdeck operator can authenticate with an organizational identity provider and see only the clusters and read capabilities they are authorized to use.

Kafdeck remains read-only and does not expose Kafka records.

## Personas

### Platform administrator

Configures OIDC and Kafdeck role bindings as deployment configuration.

### Kafka operator

Authenticates through OIDC and receives only the read capabilities and cluster/resource scopes granted by policy.

### Read-only observer

Can inspect permitted cluster/topic metadata but may be denied configuration reads or other sensitive metadata.

## Product behavior

### Sign-in

OIDC mode presents a clear sign-in entry point and redirects through the configured identity provider.

The product shows the authenticated operator identity after sign-in.

### Sign-out

Sign-out terminates the Kafdeck session and clears browser session state.

### Cluster selector

Only authorized clusters are listed.

A user cannot recover unauthorized cluster metadata by directly calling an API URL.

### Capability-aware UI

The UI distinguishes:

- not authorized by Kafdeck RBAC,
- denied by Kafka ACL,
- unsupported capability,
- temporarily unavailable capability.

These states are not collapsed into an empty or healthy state.

### Configuration reads

Topic and broker configuration views require dedicated permissions in addition to general cluster/topic visibility.

### Legacy access modes

Local and Token modes remain available for compatibility, but the UI clearly indicates that they do not represent human operator identity.

## Initial permission vocabulary

- `system.read`
- `cluster.read`
- `broker.read`
- `topic.list`
- `topic.read`
- `topic.config.read`
- `broker.config.read`

No write permission exists in v0.2.

## UX requirements

- current operator identity is visible,
- sign-out is always reachable,
- authorization-denied pages are explicit,
- hidden UI elements are usability only; APIs remain authoritative,
- cluster switching cannot expose a previously authorized cluster after policy/session change,
- stale cached UI data is cleared when authorization context changes,
- loading/error/unauthenticated/forbidden/Kafka-denied states are first-class.

## Product acceptance scenarios

1. Authenticate through a configured OIDC provider.
2. Reject invalid issuer/audience/signature/state/nonce flows.
3. Map an exact external group to a Kafdeck role.
4. Grant a user access to Cluster A while hiding/denying Cluster B.
5. Allow topic metadata but deny topic configuration.
6. Preserve Kafka-side authorization-denied semantics inside an otherwise Kafdeck-authorized view.
7. Expire/terminate a session without leaving protected data available in browser state.
8. Restart in v0.1-compatible Local mode.
9. Restart in v0.1-compatible Token mode.
10. Prove no Kafka mutation or payload browsing surface exists.
