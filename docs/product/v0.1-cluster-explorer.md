# v0.1 Product Specification — Cluster Explorer

- **Status:** PROPOSED
- **RFC:** RFC-0001
- **Approval:** Gate 1 pending

## User outcome

An operator can point one Kafdeck instance at multiple Kafka clusters and safely answer, without mutating Kafka:

- Is this cluster reachable?
- Which cluster am I looking at?
- Which brokers and controller are currently visible?
- Which topics exist?
- How are partitions distributed?
- Which partitions have missing ISR members or no leader?
- What are the topic/broker configurations I am authorized to read?
- Which Kafdeck capabilities are unavailable because of authorization, compatibility, or temporary failure?
- When was this information observed and is it stale?

## Personas

### Kafka operator

Needs fast cluster topology and partition-health inspection without granting Kafdeck write privileges.

### Platform/SRE engineer

Needs a consistent read-only view across multiple clusters and explicit failure/capability diagnostics.

### Developer

Needs topic/partition/configuration visibility without direct CLI access to every environment.

## UX information architecture

### Global shell

- Kafdeck identity/version
- current cluster selector
- connection/health indicator
- last-observed timestamp
- global refresh action

### Cluster Overview

Cards/sections:

- Cluster identity
- Brokers
- Topics
- Partitions
- Offline partitions
- Under-replicated partitions
- Current controller
- Access/capability limitations
- Observation freshness

### Brokers

Table columns:

- Broker ID
- Host
- Port
- Controller marker when applicable
- Metadata state

Broker detail:

- identity/endpoint metadata,
- configuration tab if capability is available,
- explicit access-denied/unsupported state otherwise.

### Topics

Searchable, paginated list:

- topic name,
- partition count,
- offline partition count,
- under-replicated partition count,
- anomaly state.

Topic detail tabs:

1. Overview
2. Partitions
3. Configuration

Partition table:

- partition ID,
- leader,
- replicas,
- ISR,
- offline replicas where observable,
- health explanation.

## UX rules

- Every view shows data freshness.
- Stale data is visually distinguishable from current data.
- Authorization denied is not rendered as `0`, `empty`, or `healthy`.
- Partial data is explicitly labelled partial.
- Loading/error/empty/denied/stale states are first-class designs.
- Large topic sets use server-side pagination over a cached metadata snapshot.
- Automatic refresh pauses/reduces when the browser page is not visible where practical.
- No auto-refresh path may generate per-row Kafka requests.

## v0.1 exclusions visible to users

The UI contains no controls for:

- create/delete topic,
- edit configuration,
- produce records,
- reset offsets,
- manage ACLs,
- manage SCRAM users.

If a future backend regression accidentally introduces a non-GET administrative route, contract/security tests must fail.

## Product acceptance scenarios

1. Connect to a TLS Kafka cluster and inspect topics/partitions.
2. Connect using mTLS.
3. Connect using SASL_SSL + SCRAM-SHA-256/512.
4. Configure multiple clusters and switch without leaking one cluster's state into another.
5. Show topic metadata when config-read ACL is denied.
6. Show stale cached metadata during a bounded transient failure, with stale marking.
7. Mark cluster unavailable after the configured evidence deadline without hanging the UI.
8. Handle a cluster with very large topic counts without N+1 Kafka calls.
9. Surface under-replicated/offline partitions with reasons.
10. Run entirely air-gapped after images/packages are supplied by the operator's artifact process.
