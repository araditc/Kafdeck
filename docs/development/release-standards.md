# Release Standards

## Versioning

Before v1.0, releases may evolve rapidly but must still document breaking changes. From v1.0 onward, Kafdeck follows Semantic Versioning.

## Release inputs

A release is produced only from an accepted commit on `main` with required checks passing.

## Required release artifacts (target baseline)

As Phase 0/1 automation matures, releases must include or produce:
- source tag/release notes,
- OCI container image,
- SBOM (CycloneDX or equivalent approved format),
- vulnerability-scan evidence,
- signed artifacts/images,
- provenance metadata aligned with SLSA goals,
- documented supported Kafka matrix.

## Supply-chain principles

- CI permissions follow least privilege.
- Third-party actions are pinned according to the project's supply-chain policy.
- Release workflows are protected from untrusted write paths.
- Release artifacts are generated by CI rather than manually rebuilt on developer machines.
- Secrets used by release automation are scoped to the minimum required operation.

## Release quality gate

A release is blocked by:
- failing required CI,
- unresolved known critical security vulnerability affecting the release,
- failed supported-version compatibility tests,
- required migration/upgrade documentation missing,
- artifact signing/provenance failure once those controls are mandatory for the current phase.

## Reproducibility and provenance

The project progressively targets stronger SLSA-aligned build guarantees. Early releases target documented CI provenance and signed artifacts; higher maturity may tighten to hermetic/reproducible build requirements where feasible.
