# RFC-0007 — v0.7 Developer & Streaming Ecosystem Platform

- **Status:** PROPOSED FOR GOVERNED PLANNING ADMISSION
- **Scope authority:** Issue #178 — owner accepted 2026-09-26
- **Tracker:** Issue #180
- **Planning workstream:** W51 / Issue #181
- **Implementation:** BLOCKED until protected-main planning admission
- **Release/publication:** separately owner-gated

## 1. Purpose

v0.7 extends Kafdeck from the v0.6 fleet-control baseline into a governed developer and streaming ecosystem platform. The phase adds Schema Registry lifecycle administration, richer schema developer tooling, multiple Kafka Connect runtimes, bounded Connect auto-restart, controlled SerDe extensions, finite replay/reprocess/forwarding jobs, a bounded mock/data generator, and streaming ecosystem integrations.

The phase does not weaken or replace the existing mutation governance pipeline. New external effects reuse the server-authoritative chain:

`Request -> Authentication -> Authorization -> Capability Check -> Validation -> Risk Classification -> Preview -> Confirmation/Approval -> Durable Admission -> Execute -> Verify -> Audit`

Existing v0.5/v0.6 ambiguity, fencing, durable-operation, approval and audit semantics remain authoritative.

## 2. Accepted scope

### 2.1 Schema Registry lifecycle

v0.7 admits typed Schema Registry lifecycle operations for supported providers:

- register subject/schema versions;
- Avro, Protobuf and JSON Schema;
- subject/version read and reference graph;
- compatibility testing and compatibility-mode changes;
- soft-delete subject/version where provider semantics support it;
- permanent delete only as an explicitly distinct destructive effect;
- Confluent-compatible baseline;
- Karapace and Apicurio only through separately tested capability adapters.

There is no generic Schema Registry HTTP proxy.

### 2.2 Schema developer tooling

v0.7 admits:

- deterministic schema/reference graph;
- deterministic diff;
- compatibility explanation;
- bounded mock-payload generation;
- safe examples and diagnostics.

Mock tooling is not a script engine. It cannot execute arbitrary user code, load public runtime plugins or persist generated payloads by default.

### 2.3 Kafka Connect multi-runtime administration

v0.7 introduces multiple stable Connect profiles per Kafka environment.

The existing single `Connect` configuration remains backward compatible through normalization to a stable profile ID `default`. A deployment MUST NOT configure both the legacy singular profile and the new profile collection simultaneously. Duplicate profile IDs or duplicate normalized provider origins fail validation.

Typed provider operations may include:

- list/inspect connectors and tasks;
- create/update/delete connector;
- pause/resume/restart connector;
- restart task;
- plugin/config validation when supported;
- task stack traces and metrics when exposed.

No arbitrary provider URL forwarding, raw HTTP tunnel, connector-class bypass, transform injection or credential echo is admitted.

### 2.4 Bounded Connect auto-restart

Optional automatic connector/task restart is disabled by default. When enabled, it is a finite policy with:

- hard retry ceiling;
- bounded exponential backoff and jitter;
- circuit-breaker state;
- explicit exhaustion/blocked states;
- durable progress and audit;
- current authorization, capability, connector identity and policy revalidation before each external effect;
- no retry after an ambiguous dispatch until bounded evidence establishes a stronger state.

An auto-restart policy cannot override v0.6 replication/MM2 guards.

### 2.5 Controlled SerDe extensions

CBOR, XML and MessagePack are admitted through internal controlled adapters. Public runtime plugin loading remains excluded.

Adapters enforce input-byte, depth/nesting, collection and expansion ceilings. Unsupported or ambiguous input is not coerced into a misleading structured representation.

### 2.6 Governed finite data jobs

Replay, reprocess, DLQ forwarding and cross-topic/cross-cluster forwarding are finite governed jobs rather than a data-plane proxy.

Every job binds:

- exact source/destination physical cluster identity;
- exact topic and partition/range selection;
- immutable policy/masking fingerprints;
- finite record, byte, rate and duration budgets;
- durable checkpoint/progress identity;
- requester/approver identity and current authorization requirements.

The data-job engine inherits the v0.6 transfer safety model where applicable: one unresolved external-write batch per operation, durable dispatch marker before effect, no blind replay after ambiguous acknowledgement/checkpoint failure, no raw-payload staging by default, and no budget reset through lease renewal/restart/approval refresh.

### 2.7 Smart Mock / Data Generator

The generator is a finite governed production job family, not an infinite stream.

It supports:

- schema-based generation;
- deterministic bounded templates;
- deterministic seed where practical;
- exact destination preview;
- record/rate/byte/duration ceilings;
- durable progress, cancellation and audit.

Production use is deny-by-default by deployment policy. Enabling production generation requires an explicit policy and does not bypass ordinary `record.produce` authorization or risk classification.

### 2.8 Streaming ecosystem

v0.7 admits:

- bounded ksqlDB read-oriented query/editor integration;
- Kafka Streams topology views only from observable evidence;
- RocksDB/state-store metrics only when application telemetry exposes them;
- lineage with explicit provenance/confidence labels.

ksqlDB is not a generic HTTP/SQL proxy. Persistent-query and DDL mutation are not silently admitted in v0.7. The initial statement policy is a closed read-oriented grammar/allowlist with row/byte/duration/concurrency ceilings.

Kafdeck does not implement a general stream-processing SQL engine.

## 3. Architectural decisions

### Decision 1 — Typed provider ports, not generic proxies

Every ecosystem mutation/execution is implemented behind Kafdeck-owned typed ports. Provider-specific response/error types terminate at the adapter boundary. Missing provider primitives become `Unsupported` or `Blocked`, not an invitation to shell, CLI, reflection, raw-protocol, generic REST or sidecar execution.

### Decision 2 — Existing governance pipeline is reused

Schema mutations, Connect mutations, auto-restart effects, replay/forward jobs and data generation all enter the existing server-authoritative authorization/risk/preview/durable-operation/audit pipeline. Read-only tooling can use bounded read contracts but cannot manufacture mutation authority.

### Decision 3 — Multi-Connect configuration is explicit and backward compatible

New deployments use stable `ConnectProfiles[]` identifiers. Legacy `Connect` normalizes to profile `default`. Ambiguous mixed configuration is invalid.

### Decision 4 — Secrets are write-only or referenced

Connector/provider secret material is never returned after submission. Sensitive configuration fields use server-side secret references or finite write-only request material resolved immediately before provider dispatch. Plaintext secret values are not persisted in operation snapshots, audit, logs, traces, errors or browser storage.

### Decision 5 — Automation is finite

Auto-restart, replay, forwarding and generation all have hard finite ceilings. No configuration value means "unlimited". Restarts, worker failover, lease renewal, new confirmation or new approval cannot replenish lifetime job budgets.

### Decision 6 — Data movement inherits masking/export boundaries

Metadata permission never implies record access. Source `record.read` and `record.export` and destination `record.produce` remain independent. A byte-preserving path is denied when active masking/data policy cannot be satisfied without changing protected bytes.

### Decision 7 — Ambiguity is durable truth

External HTTP/Kafka dispatch can succeed while Kafdeck loses the response. Such effects remain `ExecutionUnknown` until bounded provider evidence proves a stronger state. No idempotency key, UI retry or automation loop may blindly redispatch an ambiguous effect.

### Decision 8 — ksqlDB query execution is read-oriented in v0.7

The v0.7 editor supports only admitted read-oriented statement families. Persistent queries, DDL/DML mutation and arbitrary statement forwarding remain blocked unless a later explicit scope/security decision admits them.

### Decision 9 — Lineage distinguishes observed from inferred

Every lineage edge carries provenance and confidence. Observed broker/schema/Connect/telemetry evidence is not mixed with name-based inference. Inferred edges are explicitly labelled and cannot drive mutation authorization.

### Decision 10 — Public plugin loading remains deferred

CBOR/XML/MessagePack use internal extension ports. Public runtime DLL/package/plugin loading is outside v0.7 and requires a separate trust/sandbox/supply-chain RFC.

## 4. Runtime numerical budgets

These are planning defaults/hard caps, not throughput claims. Deployment policy may tighten them. Changing a hard cap requires reviewed contract/test evidence.

### 4.1 Replay/reprocess/forward

| Budget | Default | Hard cap |
| --- | ---: | ---: |
| In-flight batch | 100 records / 1 MiB | 1,000 records / 4 MiB |
| Rate per physical cluster pair | 1,000 records/s / 1 MiB/s | 10,000 records/s / 10 MiB/s |
| Finite job total | 100,000 records / 100 MiB / 30 min | 1,000,000 records / 1 GiB / 24 h |
| Concurrent active data jobs per physical cluster | 1 | 2 |
| Unresolved external-write batches per job | 1 | 1 |

These align with the v0.6 finite-transfer ceilings unless W51 review produces stronger evidence for a lower value.

### 4.2 Mock/data generation

| Budget | Default | Hard cap |
| --- | ---: | ---: |
| In-flight batch | 100 records / 512 KiB | 500 records / 2 MiB |
| Rate | 100 records/s / 1 MiB/s | 1,000 records/s / 10 MiB/s |
| Finite total | 10,000 records / 10 MiB / 10 min | 100,000 records / 100 MiB / 1 h |
| Active generators per physical cluster | 1 | 2 |

Production policy is deny-by-default regardless of these ceilings.

### 4.3 Connect auto-restart

| Budget | Default | Hard cap |
| --- | ---: | ---: |
| Restart attempts per policy activation | 3 | 10 |
| Initial backoff | 10 s | minimum 5 s |
| Backoff ceiling | 5 min | 30 min |
| Activation lifetime | 30 min | 24 h |
| Concurrent auto-restart policies per Connect profile | 10 | 100 |

A provider dispatch with unknown outcome consumes the attempt and opens a reconciliation/blocked path; it is not immediately retried.

### 4.4 ksqlDB query execution

| Budget | Default | Hard cap |
| --- | ---: | ---: |
| Query duration | 30 s | 2 min |
| Rows returned | 1,000 | 10,000 |
| Response bytes | 2 MiB | 16 MiB |
| Concurrent queries per ksql profile | 2 | 8 |

The minimum of Kafdeck and provider/network limits applies.

## 5. Authorization and risk ownership

The detailed action/risk matrix is owned by `docs/api/v0.7-authorization-risk-matrix.md`. Clients cannot choose a weaker risk class or omit server-derived actions. Compound operations take the maximum child risk plus blast-radius escalators.

## 6. API and UX

v0.7 extends versioned `/api/v1` product APIs. New non-GET browser routes use the same authentication/authorization/antiforgery boundary as existing mutations.

The UI must show:

- active cluster and provider profile;
- read vs mutation authority;
- `Supported` / `Unsupported` / `Blocked` / `Unconfigured` / `Unknown`;
- stale/partial/denied/ambiguous/external-step states;
- budget consumption and remaining finite limits for active jobs;
- operation/risk/approval state without exposing secrets.

## 7. Persistence

Existing durable mutation persistence remains the parent operation authority. New subordinate progress is bounded, versioned and migration-tested. Raw record values, generated payloads, connector secrets and provider credentials are not durable progress data.

Standalone mutation execution may use the existing supported standalone store; HA mutation/automation requires the production durable provider already required by the existing mutation architecture. No new mandatory Kafka internal state topic is introduced.

## 8. Compatibility strategy

Provider compatibility is evidence-based:

- Confluent Schema Registry is the reference lifecycle adapter;
- Karapace and Apicurio require real contract/fixture evidence and may expose narrower capabilities;
- Kafka Connect support is per tested Connect REST capability/profile, not assumed by Kafka broker version;
- ksqlDB query support is per configured tested profile;
- SerDe support is Kafdeck-internal and separately bounded;
- provider/version gaps are reported explicitly.

No provider is claimed compatible merely because its endpoint resembles another provider.

## 9. Non-goals

v0.7 does not admit:

- generic ecosystem HTTP proxying;
- arbitrary CLI/shell/raw protocol/reflection execution;
- public runtime plugin loading;
- arbitrary user code/transforms/scripts;
- unbounded replay/forward/generation;
- continuous mandatory data-plane proxying;
- automatic schema/config/ACL/topic creation as a hidden side effect of data jobs;
- persistent ksqlDB DDL/DML or persistent-query lifecycle;
- generalized Flink/stream-processing engine implementation;
- release/tag/OCI publication without a separate owner gate.
