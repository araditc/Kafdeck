# RFC-0003 — v0.3 Safe Data Explorer and Server-Side Masking

- **Status:** PROPOSED
- **Target:** v0.3
- **Scope authority:** Issue #75 — Option A accepted
- **Created:** 2026-09-20
- **Language:** English

## 1. Summary

Kafdeck v0.3 introduces the first Kafka record-payload read surface. It builds on the released v0.2 Operator Identity/RBAC foundation and preserves the no-mutation posture.

Every record path is separately authorized, bounded, maskable, non-persistent by default, cancellable, auditable, and isolated from metadata-only permissions.

## 2. Goals

v0.3 MUST provide:

1. topic/partition record browsing,
2. offset and timestamp navigation,
3. bounded forward reads and bounded backward-page reconstruction,
4. bounded live tail,
5. key/value/header inspection,
6. UTF-8, JSON, binary/hex views,
7. read-only Schema Registry-assisted Avro/Protobuf/JSON Schema decoding,
8. bounded deterministic key/partition/offset/timestamp/header/regex/CEL/jq-style filtering,
9. server-side masking before payload leaves the trusted application boundary,
10. `record.read` authorization independent from metadata permissions,
11. `record.export` authorization independent from interactive browsing,
12. bounded JSON/CSV/NDJSON export,
13. explicit message/byte/time/rate budgets,
14. cancellation and per-cluster isolation,
15. record-read/export audit events without payload leakage,
16. API/UI parity and measurable release evidence.

## 3. Non-goals

v0.3 does NOT provide:

- Kafka produce,
- replay/reprocess,
- consumer-group offset mutation,
- topic/configuration/schema mutation,
- full Schema Registry subject/version explorer,
- Kafka Connect management,
- payload persistence/indexing by default,
- whole-topic unbounded scan,
- arbitrary server-side JavaScript,
- a native general-purpose SQL/stream-processing engine,
- masking bypass permission,
- automatic data classification that grants access.

## 4. Authorization

New actions:

- `record.read`
- `record.export`

Metadata actions such as `topic.read` do not imply either action.

A record request requires the normal cluster/topic visibility permissions plus the relevant record action. Kafdeck authorization is evaluated before record I/O. Kafka-side ACL denial remains a separate downstream outcome.

## 5. Record-read model

The record adapter MUST:

- use explicit topic/partition assignment rather than subscription,
- never commit consumer-group offsets,
- disable auto-commit/auto-offset-store behavior,
- never produce records,
- honor cancellation and deadlines,
- bound records and bytes per operation,
- stop at explicit budget exhaustion,
- expose low/high watermark and actual returned offsets when available,
- isolate record-read concurrency by cluster and globally.

Backward navigation is reconstructed from an explicit anchor offset and a bounded earlier start offset; Kafka is still consumed forward.

Timestamp navigation first resolves the timestamp to explicit partition offsets, then performs bounded reads from those offsets.

## 6. Budget model

Budget enforcement occurs server-side and cannot be enlarged by arbitrary client values.

Initial engineering defaults are configuration-controlled and validated within hard caps. The implementation plan owns exact default values and release tests; public throughput claims require benchmark evidence.

Budget dimensions:

- record count,
- total raw bytes,
- total decoded/projected bytes,
- wall-clock deadline,
- live-tail duration,
- live-tail rate,
- concurrent reads per cluster,
- concurrent reads globally,
- export rows/bytes/duration.

Budget exhaustion is an explicit partial/result state, not a silent success.

## 7. Schema-assisted decoding

Schema Registry is an optional read-only adapter.

v0.3 decoding supports:

- Avro,
- Protobuf,
- JSON Schema.

The adapter may resolve schema IDs/references needed to decode an authorized record. It does not expose a general subject/version management API in v0.3.

Schema lookup/cache behavior is bounded and isolated. Registry secrets never enter API/UI/audit output.

Decode failure returns a safe typed outcome and may fall back to configured raw representation only when masking policy permits it.

## 8. Filtering

Filter execution is deterministic and bounded.

Supported classes:

- key equality/prefix where representable,
- partition/offset/timestamp bounds,
- header predicates,
- regular expression with execution limits,
- CEL expression subset,
- jq-style expression subset.

No filter may execute arbitrary host code, perform network I/O, access filesystem/process APIs, or bypass server-side masking.

Filtering occurs before final projection/export but MUST NOT expose unmasked values in errors, traces, metrics, or audit events.

## 9. Server-side masking

Masking is authoritative on the server.

Conceptual pipeline:

```text
Kafka bytes
 -> optional schema decode
 -> normalized record tree
 -> filtering
 -> masking/redaction
 -> safe projection
 -> browser/API/export
```

Masking rules are configuration-driven for v0.3 and compiled into an immutable snapshot.

If a policy requires field-level masking but a payload cannot be safely decoded into the required structure, Kafdeck fails closed for clear payload projection. It may return a fully redacted placeholder plus non-sensitive metadata.

v0.3 has no operator permission that bypasses an active masking rule.

## 10. Export

Export is a separate capability requiring `record.export`.

Formats:

- JSON,
- NDJSON,
- CSV for compatible structured projections.

Exports are generated from the already-authorized, already-masked projection. No export path receives pre-mask payloads.

Exports are streamed where practical and are not persisted by default.

## 11. Live tail

Live tail is read-only, bounded, and one-directional from server to client.

The preferred HTTP transport is SSE unless implementation evidence demonstrates a concrete need for WebSocket.

A tail session has bounded duration, message rate, byte rate, and cancellation. Disconnect cancels the Kafka read promptly.

## 12. Audit

Record access audit captures:

- actor identity/access mode,
- cluster/topic/partition scope,
- operation type,
- requested/actual range,
- budget/partial outcome,
- masking policy identifier/version where applicable,
- export format/row count/byte count where applicable,
- correlation/session identifiers.

Audit MUST NOT contain record key/value/header payloads, decoded fields, secrets, OIDC tokens, or cookies.

## 13. Observability

Metrics/traces use bounded-cardinality labels.

Topic names, record keys, subjects, operator subject IDs and payload-derived values are not default metric labels.

Record payload content is never written to traces/logs.

## 14. Failure semantics

Stable outcome categories include:

- Kafdeck authorization denied,
- Kafka authorization denied,
- unsupported capability,
- invalid range,
- offset out of range,
- schema unavailable,
- decode failed,
- masking required but unsafe decode,
- budget exhausted,
- timeout,
- cancelled,
- transient Kafka failure.

Partial/budget-exhausted results carry explicit metadata.

## 15. Compatibility and safety

The existing Kafka compatibility matrix remains mandatory.

v0.3 adds record-read tests without weakening metadata/admin load controls.

No v0.1/v0.2 release artifact is modified.

## 16. Exit criteria

RFC-0003 implementation is complete only when:

- record-read authorization isolation is proven,
- no offset commit/produce/mutation path exists,
- bounded navigation/live-tail tests pass,
- masking cannot be bypassed through API/UI/export/error/log paths,
- schema decode tests cover Avro/Protobuf/JSON Schema and failure modes,
- cancellation/budget/bulkhead tests pass,
- export bounds/redaction tests pass,
- compatibility matrix passes,
- representative benchmark/load evidence is recorded,
- independent final review is complete,
- release decision is handled separately.
