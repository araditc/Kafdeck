# RFC-0001 — v0.1 Cluster Explorer

- **Status:** ACCEPTED
- **Target:** v0.1
- **Decision gate:** Gate 1 — ACCEPTED 2026-09-16
- **Created:** 2026-09-16
- **Language:** English

## 1. Summary

Kafdeck v0.1 is a read-only, multi-cluster Apache Kafka explorer focused on reliable cluster metadata, topic/partition inspection, configuration visibility, capability detection, and bounded operational health summaries.

The release deliberately excludes Kafka record browsing, consumer diagnostics, mutation APIs, ACL administration, Schema Registry, Kafka Connect, full identity/RBAC, and audit-led mutation workflows.

The design preserves the Gate 0 principles:

- safe by default,
- read access is not data access,
- Kafdeck must not become a reliability risk to Kafka,
- air-gapped/on-premise operation is first-class,
- Apache Kafka semantics define the core,
- vendor-specific behavior is capability-gated.

## 2. Goals

v0.1 MUST provide:

1. multiple Kafka cluster definitions,
2. TLS and mTLS connectivity,
3. SASL/PLAIN and SASL/SCRAM connectivity,
4. cluster identity and broker metadata,
5. controller visibility through normal broker metadata APIs,
6. topic and partition exploration,
7. leader/replica/ISR visibility,
8. topic configuration inspection where authorized,
9. broker configuration inspection where authorized,
10. capability detection and partial-access reporting,
11. evidence-based health summary,
12. bounded refresh, timeout, concurrency and caching behavior,
13. a REST/OpenAPI contract consumed by the React UI,
14. real Kafka integration tests across the supported compatibility matrix.

## 3. Non-goals

The following are explicitly out of scope for v0.1:

- producing records,
- browsing record payloads,
- changing topics/configuration,
- resetting offsets,
- consumer-group diagnostics beyond any metadata incidentally required by the client,
- ACL/SCRAM administration,
- Schema Registry integration,
- Kafka Connect integration,
- persistent historical metrics,
- full multi-user identity, OIDC or RBAC,
- direct KRaft controller-quorum administration,
- direct ZooKeeper connectivity,
- guessed or fabricated Kafka server-version reporting.

## 4. Product surfaces

### 4.1 Cluster selector

The UI exposes configured clusters by stable Kafdeck cluster ID and display name. Secrets and raw credential configuration are never exposed.

### 4.2 Cluster overview

Displays:

- configured display name,
- Kafka cluster ID when observable,
- controller node when observable,
- broker count,
- topic count,
- partition count,
- offline partition count,
- under-replicated partition count,
- observation timestamp/freshness,
- capability/access limitations,
- evidence-based health state.

### 4.3 Brokers

Displays broker identity and metadata observable through standard Kafka client/admin APIs. Broker configuration is fetched on demand and may be unavailable because of authorization.

### 4.4 Topics

Displays searchable/paginated topic metadata from a bounded cached snapshot. Kafdeck does not make one Kafka request per visible UI row.

Topic detail includes:

- partition count,
- internal/non-internal state where observable,
- per-partition leader,
- replicas,
- ISR,
- partition anomalies,
- topic configuration on demand where authorized.

## 5. Architecture

v0.1 remains a modular monolith.

Conceptual dependency flow:

`React UI -> HTTP API -> v0.1 modules -> Kafka ports -> Confluent.Kafka adapter -> Kafka cluster`

The Kafka adapter owns all Confluent.Kafka types. Domain/application contracts use Kafdeck-owned records and capability/error models.

Initial logical modules:

- Cluster Registry
- Cluster Metadata
- Topics
- Operational Health
- Runtime Security Boundary
- Observability

## 6. Cluster registration model

### Accepted decision

v0.1 cluster definitions are configuration-driven and immutable at runtime.

A cluster definition includes only non-secret configuration and secret references. Built-in definition sources are application configuration plus environment/file-backed secret references.

Example conceptual configuration:

```json
{
  "clusters": [
    {
      "id": "payments-prod",
      "displayName": "Payments Production",
      "bootstrapServers": ["kafka-1:9093", "kafka-2:9093"],
      "securityProtocol": "SaslSsl",
      "saslMechanism": "ScramSha512",
      "username": { "secretRef": "env:KAFDECK_PAYMENTS_USERNAME" },
      "password": { "secretRef": "file:/run/secrets/payments-kafka-password" },
      "tls": {
        "caFile": "/etc/kafdeck/certs/ca.pem"
      }
    }
  ]
}
```

Raw secret values are not accepted in API responses and should not be encouraged in committed configuration.

Runtime UI/API creation/editing of cluster profiles is deferred until a secure settings/identity model exists.

## 7. Deployment access boundary

v0.1 has no full identity/RBAC system, but an unauthenticated remotely exposed admin console is incompatible with the safe-by-default principle.

### Accepted minimum boundary

- Default HTTP binding is loopback/local-only.
- Non-loopback binding requires `Token` access mode.
- Token material is supplied only by environment/file secret reference.
- The token protects both UI bootstrap/API access; no anonymous remote API is supported.
- The token is not a user identity, has no roles, and does not create an audit identity.
- OIDC, local users, sessions and RBAC remain v0.5 scope.

Deployment behind a reverse proxy remains supported; the Kafdeck token is still required unless a later approved trusted-proxy authentication mode is designed.

## 8. Security protocols

Required v0.1 Kafka connection modes:

- PLAINTEXT — allowed only by explicit configuration and visibly marked insecure,
- SSL/TLS,
- SSL with client certificate (mTLS),
- SASL_PLAINTEXT — explicit insecure transport warning,
- SASL_SSL with PLAIN,
- SASL_SSL with SCRAM-SHA-256,
- SASL_SSL with SCRAM-SHA-512.

GSSAPI/Kerberos and OAuthBearer are deferred unless implementation evidence shows they are required for the first compatibility milestone.

## 9. Capability model

Kafdeck does not assume that connectivity implies authorization for every read operation.

Capabilities are independently detected/represented, for example:

- `ClusterMetadataRead`
- `TopicListRead`
- `TopicMetadataRead`
- `TopicConfigRead`
- `BrokerConfigRead`

Each capability can be:

- Available
- Denied
- Unsupported
- Unknown
- TemporarilyUnavailable

A denied configuration read does not make the entire cluster unavailable.

## 10. Kafka version posture

Kafdeck MUST NOT infer a precise Kafka server version from unreliable heuristics and present it as authoritative.

The UI/API reports:

- Kafdeck client/adapter version,
- observable Kafka protocol/capability information,
- tested compatibility tier,
- any unsupported/unknown capability.

Kafka clients negotiate supported protocol API versions with brokers. Capability detection is therefore preferred over product behavior keyed to a guessed broker version.

## 11. Controller posture

v0.1 shows the controller node visible through normal cluster metadata APIs when available.

It does not:

- connect directly to controller-only endpoints,
- administer the KRaft quorum,
- require `bootstrap.controllers`,
- expose quorum mutations.

A future diagnostic RFC may add KRaft quorum inspection if client/library support and operator value justify it.

## 12. Snapshot, caching and refresh model

Kafka metadata is collected into bounded per-cluster snapshots.

Accepted defaults:

- cluster/broker summary cache: 5 seconds,
- topic metadata snapshot: 10 seconds,
- topic/broker configuration cache: 30 seconds,
- stale-on-transient-error presentation: up to 60 seconds with an explicit `stale` marker,
- per-cluster concurrent Kafka administrative operations: 8,
- global concurrent Kafka administrative operations: 64,
- default Kafka operation deadline: 10 seconds,
- UI automatic overview refresh: no faster than 10 seconds,
- expensive configuration reads: on-demand, not background fan-out.

All values are configurable within documented safe bounds.

A UI table page never causes a Kafka request per row. Topic pagination/search operates against a snapshot already collected from Kafka.

## 13. Health model

Health is evidence-based and explains its reasons.

States:

- `Healthy` — required metadata query succeeded and no known offline/under-replicated partition evidence is present in the current snapshot,
- `Degraded` — cluster is reachable but current evidence contains an operational anomaly such as offline or under-replicated partitions,
- `Unavailable` — required cluster metadata cannot be obtained within the bounded operation policy,
- `Unknown` — evidence is insufficient to classify safely.

Authorization limitation is reported separately from health. For example, a cluster can be operationally `Healthy` while `BrokerConfigRead` is `Denied`.

## 14. Failure model

Errors are normalized at the Kafka adapter boundary into Kafdeck-owned categories:

- AuthenticationFailed
- AuthorizationDenied
- TlsValidationFailed
- NameResolutionFailed
- ConnectionFailed
- Timeout
- UnsupportedCapability
- InvalidConfiguration
- KafkaProtocolError
- Cancelled
- Unknown

External API errors follow RFC 9457 Problem Details semantics. Partial results carry explicit limitations instead of failing an entire page when safe partial data exists.

## 15. Observability

Every Kafka operation records OpenTelemetry-compatible telemetry with bounded-cardinality dimensions:

- operation name,
- Kafdeck cluster ID,
- outcome category,
- latency,
- cache hit/miss,
- timeout/cancellation state.

Credentials, connection strings containing secrets, and Kafka payloads are never recorded.

Raw topic names MUST NOT become unbounded metric labels by default.

## 16. Compatibility matrix

For v0.1 release validation:

Tier 1 CI targets are the Apache Kafka releases currently supported by Apache Kafka at the time of release. As of 2026-09-16 this means:

- 4.3.1
- 4.2.1
- 4.1.2

Tier 2 validation target:

- 3.9.2

Tier 2 is compatibility-oriented and does not change the Gate 0 policy that currently supported 4.x releases define Tier 1.

## 17. Release exit criteria

v0.1 cannot be released until:

- Gate 1 design decisions are accepted,
- Phase 0 repository protection/security settings are closed,
- all required v0.1 read APIs are implemented,
- there are no mutation endpoints,
- Tier 1 Kafka matrix is green on exact release head,
- TLS/mTLS/PLAIN/SCRAM connection tests exist,
- authorization-denied partial-access cases are tested,
- operational concurrency/deadline/cache behavior is tested,
- threat-model delta is reviewed,
- OpenAPI contract is versioned,
- user/operator documentation is complete.
