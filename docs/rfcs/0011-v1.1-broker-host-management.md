# RFC-0011 — Broker host management in Fleet

**Status:** Review. The product owner approved the five-step v1.1 roadmap and the two required acceptance environments on 2026-11-17. Implementation and operational acceptance are tracked in the issues below.

## Operator workflow

An operator opens Fleet, selects a cluster and broker, and sees which actions the deployment supports. Today the [monitoring agent](../operator/kafka-agent.md) sends measurements from each broker JVM and an operator installs it locally. Fleet will support diagnosing a missing measurement from the corresponding service log and installing or upgrading that broker's agent from an offline package.

## Design

Identify the target by cluster and broker ID. A host may run multiple brokers. Bind each broker to a specific deployment service and check that binding against the observed identity before acting. The systemd adapter addresses a unit on the registered Linux host. The Compose adapter addresses a project and service on its host. Both expose service status, bounded log reads and the agent installation lifecycle through the same dashboard. Surface unavailable capabilities and the reason to the operator.

For host operations, test the dedicated SSH account against a separately trusted host-key fingerprint. Store a server-side credential reference. Limit the account to the defined operations on registered services. Give log readers, agent installers and configuration managers distinct permissions. Filter logs by broker and time window, cap returned bytes and lines, and redact secrets before returning any content. Keep SSH credentials, ingestion tokens and raw log bodies out of audit records.

For an agent change, preview the target, package version, deployment changes and required restart. Preserve JVM options and broker-specific settings. Track the last confirmed stage across connection loss. Before retrying, inspect actual state. Completion requires broker health and a new measurement attributed to that broker after the change. Before advancing to another broker, check replication, in-sync replicas and cluster health. Report the affected partitions and recovery action when a restart is unsafe.

Dynamic Kafka configuration uses the existing governed mutation path and Kafka Admin API. Preview the effective value, its source and the proposed scope. Recheck state before applying and verify the outcome by reading it back. Restoring an inherited configuration requires removing the override created by the operation. This flow is available without SSH.

## Delivery and acceptance

| Step | Operator acceptance | Issue |
| --- | --- | --- |
| 1. Hosts and identity | From the same dashboard register a systemd broker and map all three Arad Office brokers to separate services on one host. A host-key or broker identity mismatch blocks the action. | [#485](https://github.com/araditc/Kafdeck/issues/485) |
| 2. Status and logs | Find a controlled event from the broker page and from an alert at its event time. Verify the correct service, bounded redacted output and denial for a user without log access. | [#486](https://github.com/araditc/Kafdeck/issues/486) |
| 3. Agent lifecycle | Prove fresh install and upgrade with an offline package, restart when required, broker health and fresh per-broker metrics. Repeating a request must not duplicate installation or restart. | [#487](https://github.com/araditc/Kafdeck/issues/487) |
| 4. Dynamic configuration | On a real Kafka test cluster apply and restore a selected setting, read back both outcomes and reject a stale preview. | [#488](https://github.com/araditc/Kafdeck/issues/488) |
| 5. Operational acceptance | Exercise interrupted SSH, failure to recover broker health and missing fresh metrics. Verify the next broker stays untouched, the last confirmed state is visible, and audit and operator guides cover recovery. | [#489](https://github.com/araditc/Kafdeck/issues/489) |

**Both environments are mandatory for steps 1–3:** a Linux host running the broker under systemd with Docker absent, and Arad Office running Docker Compose. Record the environment, verified broker/service mapping, tested package identity and observed result for each. Start the Arad Office change pilot with one broker in a maintenance window. Run disruptive fault cases in isolated fixtures. Step 5 brings the evidence from both environments together.

## Release scope

v1.1 covers these two host adapters, defined broker operations and an explicit list of dynamic settings. General shell access, arbitrary file editing, static Kafka config changes, Kubernetes and Windows Service adapters are outside this release's scope. The [v1.0 release tracker](https://github.com/araditc/Kafdeck/issues/469) continues through its existing V1-6 and V1-7 gates independently of these five issues.
