## 1. Decision and authority

v0.6 extends the admitted v0.5 mutation kernel, not a parallel administration engine. Scope approval authorizes this planning package. Implementation begins only after the complete package is merged through protected-main governance. Publishing a release or activating v0.7 remains a separate owner decision.

All MUST/MUST NOT statements below are proposed Kafdeck design requirements, not claims that these features already exist. Kafka/provider facts and their limitations are catalogued in the [capability evidence matrix](../architecture/v0.6-provider-capabilities.md). The [package index](../implementation/v0.6-planning-package.md) identifies the companion contracts.

## 2. Scope

The accepted scope is typed ACL administration and evidence-based access analysis; write-only SCRAM administration; quotas; allowlisted dynamic broker/cluster configuration; preferred leader election; explicit reassignment/RF-change planning, throttling, progress and skew analysis; capability-gated broker/log-directory maintenance; bounded cross-cluster transfers; and tested MirrorMaker 2/replication integration.

No generic AdminClient/CLI/REST execution, arbitrary server-side code, public plugin loading, controller-quorum membership administration, OS/process orchestration, general replay/DLQ/backup engine, Terraform/MCP publication, automated self-healing, or later-roadmap capability is admitted. Static broker configuration and stopping/restarting broker processes remain external operator responsibilities.

## 3. Inherited invariants

Every mutation uses authentication, explicit authorization, capability checks, validation, server-owned risk, immutable preview, confirmation/eligible independent approval, durable claim, pre-dispatch revalidation, typed dispatch, bounded verification and safe audit. Read permission never implies mutation permission. A mutation permission is not a payload-read/export grant. Policy may raise, never lower, risk. CRITICAL requires a distinct eligible canonical principal. Raw records/credentials are not durable workflow material. Ambiguous potentially-applied dispatch is `ExecutionUnknown`, not a retryable failure.

## 4. Architectural decisions

1. **One authoritative operation identity.** Extend the existing operation aggregate/repository with versioned subordinate progress, per-step dispatch evidence and durable conflict obligations (ADR-0007). Lease expiry permits a new observer, not a fresh mutation of an uncertain target.
2. **Closed compound authorization.** Preserve every v0.5 single-action/single-cluster rule. New v0.6 kinds declare a server-derived, closed conjunction of action/resource/cluster requirements. Unknown kinds, extra actions, missing targets or cross-cluster substitution fail closed. Do not change the old normalizer into an arbitrary action-list API.
3. **Current identity remains authoritative.** Immediately before each external mutation, transfer batch or resumed step, Identity & Access must resolve current eligibility for the requester and required approver. Saved OIDC groups, client claims, preview grants and the worker's Kafka credential do not replace this check. Unavailable authoritative context pauses further dispatch; it is not invented by the worker.
4. **Ephemeral secrets after independent approval.** SCRAM preview persists only domain-separated HMAC binding and safe metadata. After independent approval, the original requester re-submits matching secret material into a one-shot coordinator finalization. No delayed plaintext queue. This narrowly extends the v0.5 restriction on delayed secret-material workflows; it does not remove independent approval.
5. **Bounded long-running steps.** Provider acceptance is not provider completion. Durable progress distinguishes admission, submission, observation and final effect. Read-only recovery may observe an outstanding effect; it cannot implicitly authorize the next mutation. Automatic hot observation has a durable cumulative lifetime budget and stops without releasing obligations when that budget is exhausted.
6. **Governed unresolved-effect disposition.** If bounded readback cannot resolve a potentially-applied effect, no generic clear/ignore path exists. ADR-0007 defines the closed Kafdeck-local `FleetUncertaintyDisposition` kind, dedicated `mutation.reconcile` authorization, CRITICAL floor, independent approval, immutable evidence/tombstone rules and the only permitted supersession semantics. This safety-only disposition performs no provider mutation and does not expand provider capability scope.
7. **Capability intersection.** Runtime availability requires an admitted typed adapter, pinned-client API support, broker/provider feature support, deployment policy, current authorization and required persistence. A version string, Java example or reachable URL alone proves none of these.
8. **Two transfer modes, not a replication engine.** Finite record transfer executes bounded in-memory batches. External replication integration uses a fixed tested profile with explicit side effects and control limitations; unsupported enforcement combinations remain unavailable.

## 5. Safety-critical semantics

ACL binding identity includes resource type, literal/prefixed pattern, name, principal, host, operation and allow/deny. Deletion expands filters into exact bindings before preview. ACL edits are additions/removals, not a fabricated atomic update. Broad grants and security-sensitive removals escalate to CRITICAL; grant ceilings and protected principals are server policy, not client flags.

SCRAM read exposes mechanism/iteration metadata only. A successful credential describe does not prove a particular password was installed. After an ambiguous rotation, unchanged public metadata cannot clear `ExecutionUnknown`. Any manual supersession of that uncertainty must use ADR-0007's CRITICAL reconciliation contract and preserves a no-redispatch tombstone.

Configuration update mode is not inferred from `isReadOnly` alone. A tested per-key/per-version dynamic-mode registry and broker evidence must agree. Sensitive, unknown or static keys are unavailable. Maintenance and throttle keys cannot be smuggled through the ordinary configuration route.

Reassignment preserves ordered replica lists, minimum ISR, rack/survival constraints, broker/log-directory identity and current topology fingerprints. Preferred election never permits unclean election. RF reduction is always CRITICAL. Unknown capacity cannot be displayed as a successful capacity check.

Cordon prevents new placement where supported; it is neither a read-only broker mode nor proof that replicas have evacuated. Decommission completion requires observed evacuation and the operation's precise terminal postcondition. External shutdown/static configuration steps are shown as external prerequisites, not silently executed by Kafdeck.

Transfer admission binds both physical cluster identities, topic identities, finite ranges, explicit partition mapping, budgets and policy versions. Source read/export plus destination produce plus transfer authorization are required together. Clone never implies topic/ACL/config/consumer-offset creation or deletion. Existing masking policy must not be bypassed; a byte-preserving path that cannot satisfy it is unavailable.

Replication integration must enumerate all internal data/control writes. Heartbeat, checkpoint, offset-sync and Connect worker-state topic writes require `record.produce` on the exact profile-declared physical cluster/topic, with `topic.create` additionally required for an explicitly admitted missing-topic creation. Existing Connect create/update/restart/resume/task-restart activation paths must share the same stronger admission guard; `connect.alter` alone never authorizes replication data movement.

## 6. Boundedness and compatibility

The [runtime design](../architecture/v0.6-fleet-runtime.md) defines numerical defaults/hard caps and aggregate accounting, including a default 2-hour / hard 24-hour cumulative active-observation window whose accounting survives lease/process restart. Existing tighter v0.5 limits always win. No server option means unlimited. Child steps cannot multiply the approved parent budget. Existing enum values, v0.5 intent hashes, idempotency identities and old API behavior must remain stable.

New persistence records are additive/versioned. Old executors must not operate while v0.6 state/claims they cannot understand exist; mixed-version mutation execution is refused. SQLite remains standalone; PostgreSQL remains the HA provider. No new database, Kafka state topic or runtime sidecar is introduced by this RFC.
