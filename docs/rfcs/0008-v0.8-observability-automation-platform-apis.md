## 1. Purpose

v0.8 advances Kafdeck from the v0.7 developer/streaming ecosystem platform into an observable, automatable and API-first Kafka control plane.

The release adds:

- OpenTelemetry and Prometheus-compatible observability;
- explicit historical-metrics persistence and retention;
- broker/topic/consumer operational analytics and SLOs;
- bounded data-quality monitoring;
- notifier adapters and activity/event webhooks;
- complete versioned REST/API parity and a Kafdeck CLI;
- configuration-as-code and GitOps workflows;
- Terraform over explicitly stable declarative resources;
- MCP tools over the same governed backend;
- safe compensation only where a real inverse exists.

v0.8 does **not** create a second authority plane. Every effect-capable client reuses the released server-authoritative chain:

`Request -> Authentication -> Principal -> Authorization -> Capability -> Validation -> Risk -> Preview -> Confirmation/Approval -> Durable Admission -> Execute -> Verify -> Audit`

## 2. Accepted architectural decisions

### Decision 1 — Observability is product evidence, not an exfiltration channel

Telemetry may describe Kafdeck/Kafka/provider behavior, but must not contain:

- provider credentials or secret references that reveal secret location;
- deployment/OIDC/session tokens;
- connector secret values;
- raw Kafka record/generated payloads;
- raw ksqlDB result rows;
- unbounded query text, headers or arbitrary exception bodies.

Safe fingerprints, bounded classifications, reason codes and stable operation/resource identities are preferred.

### Decision 2 — Cardinality is server-owned and bounded

Default exported metric labels are limited to low-cardinality dimensions such as:

- Kafdeck version;
- cluster profile ID;
- provider kind/profile;
- capability/action family;
- operation/risk/state/result family;
- coarse error/reason code.

Raw topic names, consumer-group IDs, connector names, schema subjects, query text, user subjects and resource paths are **not** default global labels.

Resource-scoped metrics require explicit bounded configuration and cardinality accounting.

### Decision 3 — Historical metrics use an explicit provider

Live metrics do not require durable history.

Historical trends/SLOs require an explicit Kafdeck metrics provider. The provider is not Kafka by default and has:

- retention;
- rollup/downsampling;
- bounded query windows;
- stale/partial/unavailable truth;
- schema/version migration;
- standalone/HA semantics.

### Decision 4 — Data-quality monitoring is bounded record access

Data-quality policies are not metadata-only. If a policy inspects record content it requires the released payload authorization/masking boundary.

The monitor:

- uses explicit topic/partition scope;
- never joins a consumer group or commits offsets merely for observation;
- has count/byte/rate/window/concurrency ceilings;
- does not perform unbounded historical scans;
- persists aggregate/evidence state rather than raw records by default;
- cannot execute arbitrary user code.

### Decision 5 — Alert destinations are configured providers, not arbitrary URLs

Notifier and webhook destinations are stable server-configured profiles with explicit provider type/capabilities and secret references.

There is no per-request arbitrary outbound URL, SMTP server, webhook method/body template, shell command or generic HTTP proxy.

### Decision 6 — API/CLI/GitOps/Terraform/MCP share one authority model

CLI, GitOps, Terraform and MCP are clients of versioned Kafdeck APIs.

They do not receive direct privileged access to:

- Kafka;
- Schema Registry;
- Connect;
- ksqlDB;
- notification providers;
- historical-metrics storage;
- Kafdeck's operation database.

Server authorization/risk/approval remains authoritative.

### Decision 7 — Automation principals are explicit

Long-running/background automation uses an explicit principal and policy. A user browser session is never silently promoted into immortal authority.

Before a new external effect, automation revalidates:

- principal eligibility;
- current authorization;
- current resource/provider identity;
- current capability/policy;
- conflict/fencing state;
- remaining lifetime budget;
- unresolved previous effects.

### Decision 8 — Declarative ownership is explicit and resource-specific

GitOps/Terraform may manage only resource families declared stable and declaratively ownable.

A declarative resource has:

- canonical identity;
- ownership/adoption/import rules;
- normalized desired state;
- safe diff/readback;
- drift state;
- plan/apply semantics;
- explicit secret/write-only fields;
- destruction risk.

There is no generic `resource { json = ... }` provider escape hatch.

### Decision 9 — MCP is typed tooling, not a privileged agent backdoor

MCP exposes Kafdeck product actions only.

Prompts/model responses cannot:

- authenticate;
- authorize;
- approve;
- lower risk;
- expand scope;
- waive stale preview/conflict;
- manufacture provider capability.

No shell, arbitrary SQL, provider HTTP, raw Kafka protocol or direct DB MCP tool is admitted.

### Decision 10 — Compensation is a new mutation, not rollback magic

A compensating action is admitted only when a safe inverse is explicitly defined.

Compensation requires:

- current-state evidence;
- current authorization;
- new preview;
- server-owned risk;
- confirmation/approval as applicable;
- durable execution/ambiguity semantics;
- verification/audit.

Irreversible effects are never labelled reversible.

## 4. Planning budgets and hard caps

These are safety contracts, not throughput claims. Deployment policy may tighten them.

### 4.1 Telemetry/cardinality

| Limit | Default | Hard cap |
| --- | ---: | ---: |
| Labels per exported metric series | 8 | 12 |
| Label value UTF-8 bytes | 64 | 128 |
| Active exported metric series per process | 10,000 | 50,000 |
| Resource-scoped series per configured resource family | 1,000 | 5,000 |
| Trace attributes per span | 24 | 48 |
| Log/event structured attributes | 24 | 48 |
| Safe diagnostic string bytes | 512 | 2 KiB |

Cardinality hard-cap exhaustion drops/aggregates new resource dimensions and emits an explicit telemetry-limit signal; it does not crash the runtime or silently allocate without bound.

### 4.2 Historical metrics

| Limit | Default | Hard cap |
| --- | ---: | ---: |
| Raw/high-resolution retention | 24 h | 7 d |
| Rolled-up retention | 7 d | 90 d |
| Interactive query range | 24 h | 31 d |
| Series per query | 1,000 | 10,000 |
| Returned points | 50,000 | 250,000 |
| Query duration | 10 s | 30 s |
| Concurrent history queries per tenant/process | 2 | 8 |

### 4.3 Data-quality monitoring

| Limit | Default | Hard cap |
| --- | ---: | ---: |
| Records inspected per policy | 100/s | 1,000/s |
| Bytes inspected per policy | 1 MiB/s | 10 MiB/s |
| Evaluation window | 5 min | 1 h |
| Active policies per cluster | 20 | 100 |
| Concurrent active policy readers per cluster | 2 | 8 |
| Durable violation exemplars | 0 raw payloads | 0 raw payloads |

### 4.4 Notifier/webhook delivery

| Limit | Default | Hard cap |
| --- | ---: | ---: |
| Delivery attempts | 5 | 10 |
| Initial retry delay | 5 s | minimum 1 s |
| Retry backoff ceiling | 5 min | 30 min |
| Delivery lifetime | 1 h | 24 h |
| Safe payload bytes | 32 KiB | 256 KiB |
| Events/s per destination | 5 | 50 |
| Concurrent deliveries per destination | 2 | 8 |
| Redirects | 0 | 0 |

### 4.5 Platform automation

- CLI/API page size default 100, hard 1,000.
- Declarative plan may contain at most 1,000 resource instances per apply and 10 MiB normalized desired-state metadata.
- Terraform/GitOps apply concurrency defaults to 2 governed effects per cluster and cannot exceed existing server operation/conflict limits.
- MCP tool result pages default 100 items and inherit API hard caps.
- No automation timeout/budget may exceed the underlying operation family's existing hard cap.

## 5. Explicit non-goals

v0.8 does not admit:

- generic APM/log-indexing SaaS dependency;
- unrestricted log ingestion/indexing;
- arbitrary telemetry remote-write destinations from requests;
- generic script/shell automation;
- public runtime plugin loading;
- generic notifier HTTP proxy;
- arbitrary Terraform provider/Kafka JSON forwarding;
- direct automation access to Kafdeck persistence;
- self-authorizing AI agents;
- automatic destructive remediation outside the governed mutation pipeline;
- generic rollback of irreversible operations;
- v0.9 governance/cost-attribution/self-service scope;
- release/publication without a later owner decision.
