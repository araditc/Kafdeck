# RFC-0006 — v0.6 Fleet Operations, Broker Maintenance & Kafka Security

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Target:** v0.6
- **Scope authority:** Issue #145 — owner accepted 2026-09-23
- **Tracker:** Issue #146
- **Predecessor:** RFC-0005

## 1. Summary

Kafdeck v0.6 extends the admitted v0.5 mutation kernel into fleet-scale Kafka security, broker configuration and maintenance operations. It does not create a second administration path. Every mutating capability remains represented as a typed durable Kafdeck operation and passes the existing server-authoritative lifecycle:

`Request -> Authentication -> Authorization -> Capability Check -> Validation -> Risk Classification -> Preview -> Confirmation/Approval -> Execute -> Verify -> Audit`

v0.6 adds longer-lived operations such as reassignment, broker/log-directory evacuation and bounded transfer/replication integration. These operations preserve one authoritative operation identity while adding durable progress/checkpoint evidence, leases and fencing.

## 2. Goals

v0.6 MUST provide governed support for:

1. typed Kafka ACL inspection and mutation,
2. SCRAM credential administration only where supported,
3. quota visibility and bounded quota mutation,
4. evidence-based principal/resource access analysis,
5. dynamic broker/cluster configuration only for server-allowlisted keys proven dynamically alterable,
6. preferred leader election,
7. explicit partition/replica reassignment planning and execution,
8. replication-factor change through reassignment,
9. transfer-impact estimates clearly classified as measured, derived or unknown,
10. reassignment throttling and durable progress observation,
11. partition/replica skew analysis,
12. capability-gated Kafka 4.x broker/log-directory maintenance, evacuation and decommission workflows,
13. bounded cross-cluster transfer/clone jobs with explicit source and destination authorization,
14. MirrorMaker 2/provider replication integration instead of a bespoke general replication engine,
15. API/UI parity for admitted v0.6 surfaces,
16. real Kafka compatibility/fault evidence before release admission.

## 3. Non-goals

v0.6 does NOT provide:

- a generic Kafka AdminClient, CLI, kcat or provider REST command tunnel,
- arbitrary ACL/SCRAM/quota/config payload passthrough,
- arbitrary shell, SQL, JavaScript or serializer execution,
- generic cloud IAM administration,
- a general-purpose backup/restore engine,
- full stream processing or ksqlDB execution,
- unrestricted replay/reprocess/DLQ workflows,
- automated self-healing without operator-governed intent,
- Terraform provider publication,
- MCP mutation tools,
- public runtime plugin loading,
- policy-as-code/governance catalog work reserved for later roadmap phases,
- v0.7+ activation.

## 4. Inherited mutation invariants

RFC-0005 remains authoritative unless this RFC strengthens a rule. In particular:

- read permissions never imply mutation permissions,
- there is no broad administrator bypass,
- risk floors are server-owned and policy may raise but never lower them,
- CRITICAL requires a distinct eligible principal and durable approval evidence,
- durable idempotency, operation state and conflict claims are mandatory,
- previews bind normalized intent, target set, current-state evidence, risk and expiry,
- current authorization/capability/preconditions are revalidated before dispatch,
- changed material preconditions result in `StalePreview`,
- dispatch ambiguity is `ExecutionUnknown` unless bounded verification proves a stronger outcome,
- potentially-applied mutations are never blindly retried,
- raw payloads/secrets are not durably staged by default,
- public/API handlers do not invoke provider clients directly.

## 5. Authorization actions

v0.6 adds explicit actions:

- `acl.read`
- `acl.alter`
- `scram.read`
- `scram.alter`
- `quota.read`
- `quota.alter`
- `cluster.config.read`
- `cluster.config.alter`
- `leader.elect`
- `partition.reassign`
- `replication.factor.alter`
- `reassignment.throttle`
- `broker.maintenance`
- `logdir.maintenance`
- `cluster.transfer.plan`
- `cluster.transfer.execute`
- `replication.integration.alter`

For cross-cluster movement these are conjunctive, not substitutive. Planning requires:

- source scope: `cluster.transfer.plan/execute` plus the applicable `record.read` and, where bytes leave the cluster, `record.export`,
- destination scope: `cluster.transfer.plan/execute` plus `record.produce`,
- explicit source/destination cluster and topic materialization.

Security-read actions never expose credential material.

## 6. Risk floors

| Operation | Minimum risk |
| --- | --- |
| ACL create/update/delete | HIGH |
| Broad/wildcard administrative ACL grant | CRITICAL |
| SCRAM create/rotate/delete | CRITICAL |
| Quota alteration | HIGH |
| Dynamic broker/cluster configuration | HIGH |
| Security/durability/availability/election/replication-sensitive configuration | CRITICAL |
| Preferred leader election | MODERATE; HIGH above configured target threshold |
| Partition reassignment | HIGH |
| Replication-factor reduction or broad reassignment | CRITICAL |
| Reassignment throttling | HIGH |
| Broker/log-directory evacuation/decommission | CRITICAL |
| Cross-cluster transfer execution | HIGH |
| Destructive destination behavior or broad transfer | CRITICAL |
| Replication integration change | HIGH; CRITICAL when topology/blast-radius threshold is crossed |

Risk escalators include target count, wildcard/regex materialization size, security privilege expansion, reduction in replicas, disk/broker concentration, destination overwrite/destructive semantics, provider uncertainty and policy-defined blast-radius thresholds.

## 7. Kafka security contracts

### ACL

ACL operations use typed resource/pattern/principal/host/operation/permission models. The public contract does not accept raw provider requests. Destructive/bulk requests are fully materialized before preview. Broad wildcard grants are CRITICAL.

Access analysis reports only what can be derived from observable Kafka/provider ACL semantics. It carries evidence/provenance and never claims completeness when provider-side IAM or external policy is not observable.

### SCRAM

SCRAM credential material is write-only and ephemeral. Kafdeck may persist mechanism, principal, safe timestamps/metadata and cryptographic digest bindings required for preview/confirmation, but never plaintext passwords or retrievable credentials. Rotation/deletion is CRITICAL. Delayed execution requiring secret material must require resubmission and digest match; Kafdeck must not create an implicit secret vault.

### Quotas

Quota entities and bounds are typed. Preview shows current and requested limits and affected entity scope. Unknown provider semantics fail closed.

## 8. Dynamic configuration

A provider capability result must prove that a configuration key is dynamically alterable in the current context. Kafdeck maintains a server-side allowlist/risk classification. Clients cannot supply arbitrary config keys through a generic escape hatch.

Preview includes current value, requested value, source/scope, provider mutability evidence, sensitivity classification and expected operational impact. Drift before dispatch invalidates the preview.

## 9. Leadership and reassignment

A reassignment operation contains a finite normalized plan:

`topic/partition -> current replicas -> target replicas`

and binds:

- current leader/ISR/replica fingerprints,
- broker/log-directory availability evidence where relevant,
- estimated bytes only when supported by observable log/metric evidence,
- throttle intent,
- replication-factor deltas,
- policy/risk decision.

Execution never begins from an unresolved pattern. Replication-factor reduction cannot violate configured server/provider safety constraints.

Preferred leader election is separate from reassignment and has its own typed capability and target set.

## 10. Long-running operation model

Reassignment, evacuation/decommission and transfer/replication integration may outlive one worker lease. They still use one `MutationOperation` identity.

Durable subordinate progress records MAY hold safe typed checkpoints such as:

- provider execution token/plan identity where safe,
- phase,
- completed/remaining target counts,
- safe per-target status,
- last observed provider generation/fingerprint,
- progress evidence timestamp,
- lease/fencing generation,
- bounded diagnostic code.

They MUST NOT hold raw record payloads, credentials or arbitrary provider responses.

Only a worker holding the current durable execution lease/fencing generation may advance progress. Lease loss stops dispatch/progress mutation until a new valid claim is established. Polling is bounded and isolated from ordinary read workloads.

## 11. Broker/log-directory maintenance

There is no invented generic broker read-only/cordon primitive. Kafdeck exposes only operations backed by tested Kafka/provider capabilities.

A decommission workflow must materialize an evacuation plan and prove current preconditions before irreversible dispatch:

- broker/log directory still exists and matches identity,
- affected replicas are enumerated,
- target placement satisfies configured safety constraints,
- no required target is unavailable or excluded,
- replica/ISR/durability guardrails pass,
- target disk/broker concentration thresholds pass where evidence exists.

Material drift makes the plan stale. CRITICAL approval expires with the preview.

## 12. Cross-cluster transfer and replication integration

A transfer job is not an unrestricted pipe. It binds explicit source/destination clusters, topic mappings, bounded selection semantics, rate/byte/time/concurrency ceilings, schema/serialization behavior when supported, destination behavior and audit identity.

Raw transferred records remain data-plane material, not durable operation-state data. If restart/resume requires provider-supported offset/checkpoint identifiers, store only safe checkpoint metadata.

MirrorMaker 2/provider replication is integrated through typed capability adapters. Kafdeck does not reimplement continuous replication. Changes to replication topology use the same preview/approval/execution/audit pipeline.

## 13. Failure semantics

The v0.5 result vocabulary remains authoritative. v0.6 long-running operations additionally record progress state without weakening terminal semantics.

- a provider rejection known before dispatch => definitive failure,
- timeout before any possible dispatch may use bounded retry,
- timeout/lost response after possible dispatch => `ExecutionUnknown`,
- partial per-target application => `PartiallyApplied`,
- provider accepted but verification cannot establish final state => `AppliedUnverified`,
- verified target state => `AppliedVerified`.

Reconciliation may later move an ambiguous operation to a stronger evidence-backed terminal state, but may not silently redispatch the same potentially-applied intent.

## 14. Provider capability model

Every capability is independently discovered and versioned. A Kafka-compatible endpoint does not imply support for Kafka security administration, reassignment, log-directory maintenance or replication integration.

The compatibility matrix must record at least:

- capability identifier,
- provider/profile,
- tested version,
- read/plan/execute/verify support,
- known limitations,
- evidence source/test fixture,
- whether failure semantics are strong enough for governed execution.

Unknown or partial capability fails closed for mutation execution.

## 15. API/OpenAPI principles

- no mutation uses HTTP GET,
- public contracts use discriminated typed intents,
- planning/preview endpoints cannot accept arbitrary provider method/path/request bodies,
- Idempotency-Key remains required for mutation workflow creation,
- confirmation and approval reference server-owned operation/preview identities,
- cookie-authenticated writes require anti-CSRF controls,
- RFC 9457 Problem Details and stable machine-readable error codes remain mandatory,
- long-running operations expose bounded status/progress resources; clients never own the polling/execution state machine,
- cancellation is permitted only when the typed provider operation has a safe pre-dispatch or provider-supported cancellation boundary.

## 16. Test and compatibility gate

Planning requires tests/evidence for:

- closed authorization mapping for every v0.6 operation kind,
- closed server-owned risk floor mapping,
- CRITICAL independent approval,
- stale-plan detection,
- lease/fencing takeover safety,
- process crash/restart during long-running work,
- provider timeout before/after dispatch,
- partial reassignment/decommission outcomes,
- SCRAM secret non-persistence/non-leakage,
- cross-cluster authorization conjunction and exfiltration controls,
- Kafka version/provider capability matrix,
- bounded polling/concurrency/load isolation.

The planning package is admitted only when RFC/product/security/runtime/ADR/API/test/implementation documents agree; ROADMAP and approval log are reconciled; required exact-head CI is successful; required review threads are resolved; fresh CODEOWNER approval applies to the exact head; and the PR merges through protected `main` with the expected-head guard.
