# RFC-0004 — v0.4 Consumers, Schemas & Ecosystem Read Views

- **Status:** PROPOSED
- **Target:** v0.4
- **Scope authority:** Issue #99 — owner approved 2026-09-21
- **Tracker:** Issue #100
- **Language:** English

## 1. Summary

Kafdeck v0.4 expands the released read-only control plane with consumer-group diagnostics, a full read-only Schema Registry explorer, and bounded read-only ecosystem views for Kafka Connect and ksqlDB.

v0.4 does not add a mutation path. Every new adapter exposes only explicit read methods, is capability-gated, bounded, cancellable, subject to v0.2 authorization, and isolated so a slow external endpoint cannot starve Kafka metadata or v0.3 record reads.

## 2. Goals

v0.4 MUST provide:

1. consumer groups, state, members and assignments,
2. committed offsets, end offsets and per-partition/aggregate lag,
3. inactive/stalled diagnostics with evidence and limitations,
4. produce-vs-consume rate comparison only when a trustworthy configured metrics provider supplies both values,
5. rebalance observations; historical analysis only when a history provider exists,
6. Schema Registry subjects, versions, references and schema detail,
7. schema diff and compatibility inspection without mutation,
8. Kafka Connect cluster, connector and task read-only status,
9. Connect error summaries / task traces when exposed by the configured API,
10. ksqlDB discovery and metadata only; no statement/query execution,
11. topic catalog/documentation metadata foundations,
12. REST/OpenAPI/operator-UI parity,
13. explicit authorization, safe errors, audit metadata and compatibility evidence.

## 3. Non-goals

v0.4 does NOT provide:

- consumer offset reset/shift/delete/commit,
- record produce/replay,
- Schema Registry create/update/delete/config mutation,
- Connect connector create/update/delete/pause/resume/restart,
- ksqlDB SQL execution, query editor or persistent-query mutation,
- arbitrary server-side JavaScript or a Kafdeck SQL engine,
- mandatory durable metrics/rebalance history,
- multiple Connect clusters per Kafka profile,
- payload persistence/indexing,
- any masking bypass or weakening of v0.3 record controls.

Multiple Connect clusters and full lifecycle management remain later roadmap work.

## 4. Authorization

v0.4 adds independent actions:

- `consumer.read`
- `schema.read`
- `connect.read`
- `ksql.read`
- `catalog.read`

Resource scoping uses existing cluster/resource-pattern semantics.

Examples:

- consumer group name is the resource for `consumer.read`,
- schema subject is the resource for `schema.read`,
- connector name is the resource for `connect.read`,
- ksqlDB metadata resources use stable Kafdeck-owned resource identifiers,
- topic name is the resource for `catalog.read`.

No new action implies `record.read` or `record.export`.

## 5. Consumer-group model

Kafdeck obtains group/member/assignment and committed-offset information through Kafdeck-owned Kafka read ports.

Lag for partition p is:

`max(0, endOffset(p) - committedOffset(p))`

with explicit states for missing committed offsets, deleted topics/partitions, authorization denial and partial observations.

No consumer instance is created for group membership, no subscription is joined, and no offset is committed.

Group diagnostics are evidence based. `Stable`, `PreparingRebalance`, `CompletingRebalance`, `Empty`, `Dead` and provider-reported states are preserved where available; Kafdeck does not infer an authoritative state from lag alone.

## 6. Metrics and history

Produce-vs-consume rate comparison is optional.

A rate is shown only when:
- a configured metrics provider returns a bounded observation,
- the measurement window/timestamp is known,
- units and source are explicit.

Without such evidence the result is `Unavailable`, not zero and not estimated from a single snapshot.

Historical rebalance analysis follows the same rule. v0.4 ships no mandatory durable history store. Current observations may be shown; history appears only through an explicit history provider.

## 7. Schema Registry explorer

The existing v0.3 read-only registry integration is expanded into a general read port.

Supported views:
- subjects,
- versions,
- schema metadata/type/id,
- references,
- referenced-by relationships where supported,
- compatibility mode inspection,
- deterministic textual/structural diff.

The adapter uses GET/read-only endpoints only. Compatibility inspection MUST NOT use APIs that mutate compatibility settings.

Diff is computed locally from already-authorized schema material. Parsing is bounded by size/depth/count caps.

## 8. Kafka Connect

Each Kafka cluster may configure at most one optional Connect profile in v0.4.

Read-only endpoints expose:
- Connect worker/version identity where available,
- connector names,
- connector config with secret-like fields redacted,
- connector status,
- task status,
- task error/trace text subject to safe-size/redaction rules.

The adapter exposes no generic HTTP passthrough and no mutating verb.

## 9. ksqlDB

Each Kafka cluster may configure at most one optional ksqlDB profile.

v0.4 is discovery/metadata only:
- server info / health where exposed,
- streams/tables/query metadata only through explicitly supported read-only endpoints or safe metadata statements if the provider offers a true non-mutating metadata API.

If a provider requires arbitrary SQL execution to discover metadata, that capability is reported unsupported in v0.4 rather than executing user-supplied SQL.

## 10. Topic catalog foundations

Catalog metadata is Kafdeck configuration-owned and read-only in v0.4.

Initial fields may include:
- description,
- owner/team,
- domain,
- tags,
- documentation URL/reference,
- data classification label.

Catalog metadata never grants Kafka or record permissions.

No database is required for v0.4 catalog foundations.

## 11. Load and isolation

Consumer, Schema Registry, Connect and ksqlDB workloads have distinct bounded concurrency from metadata and record-read paths.

Every external request has:
- validated base URL,
- fixed endpoint construction,
- timeout/deadline,
- cancellation,
- response-size cap,
- bounded pagination/item count,
- no redirect to untrusted origins,
- secret-safe diagnostics.

No user may provide an arbitrary URL.

## 12. Failure semantics

Stable categories include:
- Kafdeck authorization denied,
- Kafka authorization denied,
- unsupported capability,
- external profile not configured,
- upstream unavailable/timeout,
- malformed upstream response,
- partial result,
- stale/unknown offsets,
- metrics unavailable,
- history unavailable.

Safe errors never include credentials, connector secret values, schema credentials, payload values, cookies or tokens.

## 13. API and UI

Versioned API contracts expose read-only resources and explicit observation/limitation metadata.

The operator UI must not display a mutating control for v0.4 resources.

Direct API route authorization remains authoritative.

## 14. Compatibility

Kafka consumer-group behavior is validated across the existing release matrix:
- Tier 1: Kafka 4.3.1 / 4.2.1 / 4.1.2
- Tier 2: Kafka 3.9.2

Schema Registry / Connect / ksqlDB compatibility claims are provider-profile evidence, not blanket Kafka compatibility claims.

## 15. Exit criteria

RFC-0004 implementation is complete only when:
- new actions are default-deny and independently scoped,
- no offset/schema/connect/ksql mutation surface exists,
- lag/partial semantics are deterministic,
- registry diff/compatibility inspection is bounded and read-only,
- upstream SSRF/credential/redaction tests pass,
- API/UI parity and safe failure states pass,
- Kafka matrix and applicable ecosystem integration suites pass,
- representative load/latency evidence is recorded,
- exact-head governance passes,
- release decision is handled separately.
