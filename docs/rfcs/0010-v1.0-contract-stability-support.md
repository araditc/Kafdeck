# RFC-0010 — v1.0 compatibility and bounded support policy

- Status: **Proposed; owner decision pending.** No new Stable designation, support promise or v1.0 release is effective merely because this planning document is merged.
- Scope: V1-1 and the policy portion of V1-5 in [#469](https://github.com/araditc/Kafdeck/issues/469). Stabilize delivered v0.9 surfaces; no new feature family, provider parity or general plugin SDK.
- Baseline: main `27dce53ddaeca3c6b0d40a6d798a1a6ca06ec6fa`. G06/E01/Q01 remain admitted; exact final RC/media acceptance remains separate.

## Proposed decision

At v1.0 admission, freeze **explicitly enumerated documented contracts**, not every handler or internal implementation detail. Retain existing URL/contract labels when the application becomes 1.0.0. Components such as Terraform retain independently selected versions; application 1.0 does not silently make a 0.x component stable.

| Surface | Proposed v1.0 classification and exact boundary |
| --- | --- |
| Versioned public REST/OpenAPI and admitted non-browser read/mutation/declarative/governance families | Stable only for the enumerated admitted method/path, typed payload/response, documented error/status and authorization semantics, including declared bounds. Generated OpenAPI and current parity/deny tests remain part of selection. No arbitrary route/Bearer parity is implied. |
| CLI | Stable for enumerated commands/options, JSON fields and exit codes. Help prose, human table formatting/order and timing are not machine contracts. No arbitrary HTTP path or direct provider fallback. |
| Managed onboarding/users/connections and browser session/CSRF/navigation | Retain G03's Experimental dashboard-coupled status; reliable regression coverage does not grant stable third-party or CLI management API status. No authorization relaxation. |
| Terraform | Retain released provider 0.8.0 independently. Its admitted notification-subscription resource/data source, schema version 1 and explicit version-0 migration remain bounded component contracts; no additional resource lifecycle, public Registry or arbitrary import is promised. Final component stability/version selection is explicit. |
| MCP | Freeze only enumerated tool names, schemas, protocol and effect-enable behavior selected for the release. Current protocol is 2025-06-18; stdio alone grants no backend permission. No generic SQL/HTTP/shell tools, raw record bodies or automatic human approval. |
| Configuration / Helm | Documented validated operator keys, secret-reference syntax, CLI flags and selected chart values are public operator contracts. Keep configuration paths and precedence explicit. Internal DI types, private persistence records and undeclared environment variables are Internal. |
| Managed file / mutation database | G06/ADR-0011 format freeze and source-bound schema/migration contracts govern support; these are operator recovery contracts, not public database APIs. Private tables/JSON are not a client integration surface. |
| UI and provider internals | Navigation journeys, accessibility and error truthfulness are acceptance behavior. DOM/CSS/test IDs, generated cursors' internal encodings, process paths, diagnostics and provider-library implementation details are Internal. |

Unlisted surfaces receive **no implicit Stable designation**. Resolve dynamic/conditional inventory and documented-vs-mapped discrepancies before V1-1 closes. The [source/contract map](../implementation/v1.0-contract-inventory.md) distinguishes observed declarations from proposed classifications.

## SemVer and deprecation

For a Stable 1.x contract, incompatible method/path removal, required input addition, field type/meaning change, closed-enum expansion, CLI exit reassignment or lost supported behavior requires a major contract/component change and a documented migration. Optional additive output is minor-compatible only where clients are explicitly required to ignore unknown output fields; closed schemas/fingerprints retain their own negotiation/version rules. Do not pretend a new permission requirement is harmless merely because a response shape is unchanged.

For planned removal, propose a documented deprecation in at least one released minor **and** at least 90 days before removal; retain the old behavior through that window. Removal still requires the applicable major version. Emergency security containment may deny unsafe effects immediately with an advisory, reason and upgrade guidance; it never bypasses owner release admission or permits silent meaning changes. Experimental changes still need release notes and safe explicit failures, but do not carry the Stable compatibility guarantee. Internal symbols are not client extension points.

## Upgrade / support proposal

- Initial supported upgrade is immutable v0.9 -> selected v1.0 media, after final RC-bound V1-4 acceptance. Development-candidate G06 proof is reusable targeted evidence, not a signed-media pass.
- Later 1.x release selection must state its supported direct predecessor and test changed migration/recovery behavior before claiming that upgrade. No automatic direct upgrade from every historical version, mixed old/new writers, universal zero downtime or down-migration is promised. Rollback restores verified backups plus original binaries/configuration and fenced workers.
- Community support/security fixes target the latest released supported minor line and its current patch; older lines have no automatic LTS/backport entitlement. Announce the change from pre-1.0 support explicitly when 1.0 is published. Backports require an explicit issue/selection and fresh affected checks. No response-time, delivery-date or commercial SLA is created.
- Kafka/provider/OS/CNI/database support is exactly the admitted tested cells, with version-specific evidence. KAF-02 retains deployment-tested egress. No blanket provider, cloud IAM, multi-Pod application HA or architecture claim follows from compilation alone.

## Acceptance work after owner decision

1. Admit the finite policy and exact Stable/Experimental/Internal selection; publish it in support/security/release guides.
2. Complete dynamic runtime route/CLI/MCP/config inventory against their authoritative producers and add compatibility checks only for the admitted surfaces. Reuse existing OpenAPI/parity/schema/exit/error tests where source-bound; do not mirror implementations or replay successful W82/media campaigns.
3. Close V1-1 only after its evidence and normal PR CI/review/main admission. V1-5 additionally needs final supported cells and candidate scans; V1-4/V1-6/V1-7 remain separate RC/media/owner gates.

This proposal is reviewable without changing runtime behavior. Product-owner acceptance is required by GOVERNANCE sections 3–5 for the new compatibility/support commitment; an automated CODEOWNER approval is not substituted for that product decision.
