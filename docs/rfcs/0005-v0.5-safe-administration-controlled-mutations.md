# RFC-0005 — v0.5 Safe Administration & Controlled Mutations

- **Status:** PROPOSED FOR GOVERNED ADMISSION
- **Target:** v0.5
- **Scope authority:** Issue #121 — owner approved 2026-09-21
- **Tracker:** Issue #122
- **Language:** English

## 1. Summary

Kafdeck v0.5 introduces its first governed mutation surfaces. The release extends the existing identity, RBAC, audit, bounded-load and provider-capability boundaries rather than creating a privileged administration bypass.

Every mutation follows the same server-authoritative pipeline:

`Request -> Authentication -> Authorization -> Capability Check -> Validation -> Risk Classification -> Preview -> Confirmation/Approval -> Execute -> Verify -> Audit`

A mutation is represented as a durable Kafdeck operation. The operation binds the actor, cluster, typed intent, target-resource set, preview evidence, risk decision, confirmation/approval evidence, idempotency identity, execution state and verification result.

Mutation mode requires durable Kafdeck persistence. A deployment without a writable supported persistence provider remains fully usable for released read-only capabilities, but v0.5 mutation endpoints are disabled.

## 2. Goals

v0.5 MUST provide governed support for:

1. topic create, supported topic-configuration alteration, partition increase and topic deletion,
2. bounded bulk topic operations,
3. bounded single/batch/template record production with schema validation where configured,
4. consumer-group offset reset/shift and group/offset deletion where supported,
5. Schema Registry schema registration/update/delete and compatibility administration where supported,
6. Kafka Connect create/update/delete and pause/resume/restart operations where supported,
7. DeleteRecords-based bounded purge/truncate using explicit per-partition offsets,
8. timestamp purge only after timestamps are resolved to explicit offsets and frozen into the preview,
9. typed authorization actions rather than a broad generic administrator bypass,
10. deterministic risk classification with policy able to raise, never lower, the built-in risk floor,
11. server-generated previews bound cryptographically to immutable normalized intent,
12. explicit confirmation and, where required, independent approval,
13. durable idempotency, conflict detection and safe ambiguous-outcome handling,
14. post-operation verification where observable,
15. append-only security audit evidence and safe operational telemetry,
16. API/UI parity for admitted mutation surfaces.

## 3. Non-goals

v0.5 does NOT provide:

- broker maintenance, replica reassignment or preferred leader election,
- Kafka ACL, SCRAM or quota administration,
- unrestricted shell / kafka-cli / kcat execution,
- arbitrary provider REST passthrough,
- generic provider-native `AlterConfigs` escape hatches,
- arbitrary server-side code,
- ksqlDB statement/query mutation,
- automated remediation/self-healing,
- Terraform-provider publication,
- MCP mutation tools,
- public runtime plugin loading,
- cross-cluster replication/clone jobs,
- a guarantee that external Kafka/provider operations are transactionally reversible,
- blind retry of a mutation after external dispatch when the outcome is ambiguous.

Those remain later-roadmap work or require a separate RFC.

## 4. Authorization model

v0.5 adds independent actions:

- `topic.create`
- `topic.alter`
- `topic.delete`
- `record.produce`
- `consumer.offset.alter`
- `consumer.delete`
- `schema.create`
- `schema.alter`
- `schema.delete`
- `connect.create`
- `connect.alter`
- `connect.delete`
- `records.purge`

The existing cluster/resource-pattern model remains authoritative. Read actions never imply mutation actions. Mutation actions never imply `record.read` or `record.export`.

Collection/bulk requests are authorized per target. The server does not execute an authorized subset of a request that the caller represented as one atomic intent unless the typed operation explicitly defines partial semantics and the preview states that behavior.

## 5. Risk classification

Risk is computed server-side after authorization/capability/validation. Clients may not submit or lower their own risk class.

Built-in floors:

| Operation | Risk floor |
| --- | --- |
| Create one topic | LOW |
| Alter ordinary topic configuration | MODERATE |
| Increase partitions | HIGH |
| Delete topic | CRITICAL |
| Produce bounded records | MODERATE |
| Alter/reset consumer offsets | HIGH |
| Delete consumer group/offsets | HIGH |
| Register schema/version | MODERATE |
| Alter compatibility mode | HIGH |
| Delete schema subject/version | HIGH; permanent/hard delete is CRITICAL |
| Create/update connector | MODERATE |
| Pause/resume/restart connector/task | MODERATE |
| Delete connector | HIGH |
| DeleteRecords purge/truncate | CRITICAL |

Risk escalators include:
- multiple targets / bulk scope,
- security or durability-sensitive configuration keys,
- destructive or irreversible provider semantics,
- permanent deletion flags,
- target count/byte count above configured thresholds,
- provider capability uncertainty.

Deployment policy may raise a risk class or require stronger approval. It may not lower the built-in floor.

## 6. Durable operation state

Mutation mode requires a writable supported Kafdeck persistence provider under ADR-0004.

A durable operation records:
- immutable `OperationId`,
- requester principal identity,
- cluster/provider identity,
- typed operation kind,
- normalized non-secret intent,
- cryptographic digests for ephemeral/sensitive execution material,
- target-resource keys,
- observed precondition/resource fingerprints,
- risk decision and reasons,
- preview hash and expiry,
- required confirmation/approval policy,
- confirmation evidence,
- approval/rejection evidence,
- idempotency key binding,
- execution claim/fencing generation,
- dispatch timestamps,
- result/error classification,
- verification evidence,
- audit correlation identifiers.

Kafka record values, record keys, secret connector fields, tokens and credentials are not persisted merely to support preview/approval.

Operations whose execution requires ephemeral payload/secret material require that material to be re-submitted at confirmation/final execution and hash-match the admitted preview. v0.5 does not invent a hidden plaintext payload database.

## 7. State machine

Canonical states:

`Previewed -> AwaitingConfirmation -> AwaitingApproval? -> Ready -> Executing -> terminal`

Terminal/result states include:
- `AppliedVerified`
- `AppliedUnverified`
- `PartiallyApplied`
- `ExecutionUnknown`
- `Rejected`
- `Expired`
- `Cancelled`
- `StalePreview`
- `FailedBeforeDispatch`
- `FailedDefinitive`

Rules:
- confirmation cannot execute an expired or changed preview,
- approval cannot be replayed against another operation,
- an approver cannot satisfy a required independent-actor approval for their own operation,
- cancellation is allowed only before irreversible external dispatch begins,
- after dispatch begins, ambiguous timeout/lost response becomes `ExecutionUnknown`, not “failed/not applied”,
- `ExecutionUnknown` is not blindly re-dispatched; verification/reconciliation must determine the next safe action.

## 8. Preview binding and TOCTOU protection

The preview is generated from a canonical normalized mutation intent plus:
- cluster identity,
- typed operation kind,
- target-resource set,
- relevant current resource fingerprints/configuration,
- resolved offsets for timestamp-based offset/purge operations,
- risk decision,
- server policy version,
- expiry.

The server computes a SHA-256 preview digest over canonical data and stores it with the operation. Confirmation supplies the operation identity and digest/challenge; the server re-checks persisted state.

Immediately before external dispatch, Kafdeck re-observes capability and material preconditions. If relevant state drift changes the admitted meaning/blast radius, execution stops as `StalePreview` and a new preview is required.

Out-of-band Kafka/provider changes cannot be prevented; they are treated as an expected concurrency boundary.

## 9. Confirmation and approval

All mutations require an explicit preview followed by confirmation.

Default rules:
- **LOW:** same-actor explicit confirmation.
- **MODERATE:** same-actor explicit confirmation with complete preview.
- **HIGH:** same-actor typed target confirmation; deployment policy may additionally require a distinct approver.
- **CRITICAL:** typed target confirmation plus a distinct eligible approver is mandatory.

CRITICAL mutation capability is disabled when Kafdeck cannot durably record independent approval evidence or when the active identity mode cannot establish two distinct principals.

Approval expires with the preview. A changed preview invalidates previous confirmation/approval.

## 10. Idempotency

Preview creation requires an `Idempotency-Key` for mutating workflows.

Binding key:
`principal + cluster + operation-kind + idempotency-key`

- same key + same canonical intent returns the existing operation,
- same key + different canonical intent returns conflict,
- execute/dispatch is claimed atomically by `OperationId`,
- concurrent workers may not both dispatch the same operation,
- mutation retries after a definitive pre-dispatch failure may be allowed,
- mutation retries after dispatch are never automatic when outcome is ambiguous.

Idempotency is a Kafdeck safety property, not a claim of exactly-once semantics from Kafka/provider APIs.

## 11. Conflict control

Kafdeck computes canonical resource lock keys such as:
- `cluster/topic/<topic>`
- `cluster/group/<group>`
- `cluster/schema/<subject>`
- `cluster/connect/<connector>`
- `cluster/topic/<topic>/partition/<n>/purge`

Before execution, the operation acquires durable conflict claims in deterministic key order. Conflicting active operations are rejected/queued according to the typed operation policy; v0.5 defaults to explicit conflict rather than hidden serialization.

A lock only coordinates Kafdeck operations. Provider-side/out-of-band changes remain protected by pre-dispatch revalidation.

## 12. Topic administration

Typed ports may expose only admitted operations:
- create topic with explicit partitions/replication/settings,
- alter allowlisted supported topic configuration keys,
- increase partitions,
- delete topic.

There is no public generic “send arbitrary AdminClient request” contract.

Topic delete is CRITICAL. Partition increase is HIGH because it is not generally reversible and may alter key distribution/order characteristics.

Bulk topic operations are finite, explicitly enumerated and preview each target/result. No wildcard destructive operation is executed from an unmaterialized pattern.

## 13. Record production

Record production is bounded by configured record-count and byte ceilings and independent per-cluster producer bulkheads.

Requirements:
- `record.produce` authorization on the target topic,
- schema-aware validation when explicitly requested/configured,
- headers/key/value included in preview metadata only to the safe extent permitted,
- payload material is not written to audit/logs/problem details,
- payload bytes are not durably persisted by default,
- confirmation/execution re-submits any ephemeral payload material and hash-matches the preview,
- producer acknowledgements and returned partition/offset are recorded as execution evidence when available.

A timeout after produce dispatch is potentially ambiguous; Kafdeck does not retry blindly.

## 14. Consumer administration

Offset mutation preview MUST materialize target group/topic/partition and current/target offsets.

Timestamp targets are resolved to explicit offsets before confirmation. The preview displays direction/delta and missing/out-of-range states.

Consumer offset mutation is HIGH because moving offsets may cause replay or skipped processing.

Kafdeck must verify group/provider conditions required by the underlying API and return Unsupported/Conflict rather than forcing unsafe behavior.

## 15. Schema Registry administration

Typed registry mutation ports may support:
- schema registration/new version,
- compatibility-mode changes,
- subject/version deletion where provider semantics are explicit.

Preview includes subject/version/type/reference graph summary and compatibility evidence where available.

Permanent/hard deletion, when a provider supports it, is CRITICAL. Kafdeck does not pretend a provider soft-delete is equivalent to permanent deletion or vice versa.

## 16. Kafka Connect administration

Typed Connect mutation ports may support:
- create/update connector,
- pause/resume/restart connector/task,
- delete connector.

Secret-like configuration values are never returned in preview/log/audit. The server displays field names and redacted/change indicators.

No generic upstream HTTP endpoint is exposed. Redirect/origin/size/deadline protections from v0.4 remain in force.

## 17. Controlled purge

Purge uses Kafka DeleteRecords semantics only where capability is proven.

The operation is represented by explicit `topic/partition -> beforeOffset` targets.

Timestamp-based requests:
1. resolve timestamp to offsets,
2. record the resolved offsets in the preview,
3. require CRITICAL confirmation/independent approval,
4. revalidate target partitions/capability,
5. dispatch DeleteRecords using the frozen offsets,
6. verify low-watermark/evidence where available.

There is no “undo purge” claim.

## 18. HTTP/API contract principles

Mutation HTTP methods are never GET.

The API exposes a typed mutation-operation resource, not a generic provider command tunnel. OpenAPI uses discriminated typed intent schemas for admitted operation kinds.

Cookie/session-authenticated mutation requests require anti-CSRF protection in addition to authorization.

Responses use RFC 9457 Problem Details and stable machine-readable mutation error codes.

Execution is server-controlled once the operation has satisfied required confirmation/approval. There is no privileged direct-execute endpoint that bypasses state checks.

## 19. Failure semantics

Stable operation/result classes include:
- AuthorizationDenied
- CapabilityUnsupported
- ValidationFailed
- StalePreview
- ConfirmationRequired
- ApprovalRequired
- ApprovalExpired
- ApprovalRejected
- Conflict
- FailedBeforeDispatch
- UpstreamRejected
- ExecutionUnknown
- PartiallyApplied
- AppliedUnverified
- AppliedVerified

“Timeout” alone does not imply whether the provider applied a change.

## 20. Audit and observability

Audit records:
- operation ID/correlation ID,
- actor and independent approver identities,
- cluster/resource,
- operation kind,
- risk decision/reasons,
- preview hash,
- state transitions,
- idempotency conflict outcome,
- dispatch/verification outcome.

Audit/log/traces exclude credentials, session cookies/tokens, connector secret values and record payloads.

Metrics use bounded-cardinality operation/risk/outcome dimensions rather than raw topic/group names as labels.

## 21. Load isolation

Mutation execution uses a separate bounded per-cluster executor/bulkhead from metadata/read-record/ecosystem-read paths.

No unbounded task fan-out. Bulk operations are finite and enforce target/byte/request ceilings.

Provider retries are limited to failures known to occur before external dispatch. Once dispatch may have occurred, Kafdeck prefers `ExecutionUnknown` to an unsafe retry.

## 22. Compatibility

Kafka mutation support is capability-profile based and validated against the release compatibility matrix.

Schema Registry / Connect mutations are enabled only for tested provider profiles and operation kinds. A configured URL does not imply write compatibility.

## 23. Deployment behavior

- read-only features remain available without a database,
- enabling v0.5 mutation mode requires writable supported persistence,
- SQLite supports standalone/single-instance mutation execution,
- PostgreSQL is required for multi-instance/HA mutation execution,
- CRITICAL mutations require durable independent-principal approval capability,
- fail-closed startup/configuration validation disables mutation mode when these prerequisites are not met.

## 24. Exit criteria

Planning is admitted only when:
- RFC/product/security/runtime/API/test/implementation documents agree,
- ADR-0006 records durable mutation-state requirements,
- roadmap and approval log are reconciled,
- exact-head required CI passes,
- required CODEOWNER approval is fresh,
- all required review threads are resolved,
- the planning PR merges through protected `main`.

Implementation is then authorized under Issue #122 workstreams.

v0.5 release/tag/publication remains a separate explicit later decision.
