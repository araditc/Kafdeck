# RFC-0002 — v0.2 Operator Identity and RBAC

- **Status:** PROPOSED
- **Target:** v0.2
- **Scope authority:** Issue #57 — Option 2 accepted
- **Supersedes:** RFC-0001 sequencing only where identity/OIDC/RBAC were deferred to v0.5
- **Created:** 2026-09-20
- **Language:** English

## 1. Summary

Kafdeck v0.2 adds human operator identity and fine-grained authorization while preserving the v0.1 Kafka safety boundary.

v0.2 remains:

- Kafka read-only,
- metadata-only,
- out-of-band from producer/consumer traffic,
- air-gap/on-premise friendly,
- free of Kafka mutation APIs,
- free of record production/consumption and payload browsing.

The accepted roadmap change advances Operator Identity/RBAC from the previously deferred v0.5 scope into v0.2.

## 2. Goals

v0.2 MUST provide:

1. standards-based operator authentication through OIDC,
2. Authorization Code flow with PKCE, state and nonce protections,
3. server-controlled authenticated sessions,
4. a canonical operator identity keyed by OIDC issuer + subject,
5. configuration-driven role definitions and role bindings,
6. default-deny authorization,
7. authorization by action and resource scope,
8. cluster-scoped access control,
9. topic/resource pattern scopes where a resource name is part of the existing read API,
10. explicit authorization outcomes in API/UI behavior,
11. authenticated audit identity for security-relevant actions,
12. upgrade compatibility with v0.1 Local/Token deployment modes,
13. fail-closed behavior when identity/claims/policy are invalid or ambiguous,
14. no browser exposure of OIDC refresh/access tokens,
15. tests proving that identity/RBAC cannot introduce Kafka mutation or payload access.

## 3. Non-goals

v0.2 does NOT provide:

- local username/password database,
- password reset or credential recovery,
- direct LDAP bind authentication,
- direct SAML implementation,
- runtime RBAC administration UI/API,
- Kafka ACL administration,
- Kafka topic/configuration/group mutations,
- record production/consumption or payload browsing,
- server-side PII masking pipeline,
- approval workflows for destructive operations,
- public plugin SDK,
- multi-tenant SaaS identity model.

LDAP/AD may later be integrated through an OIDC-compatible identity provider or a separately accepted provider RFC.

## 4. Access modes and compatibility

v0.2 retains explicit deployment access modes:

### Local

Loopback/local-only access. This is a deployment boundary and does not create a human identity.

### Token

The v0.1 deployment-token mode remains available for backward compatibility and controlled single-principal deployments. The token is not a human identity and does not acquire OIDC/RBAC semantics.

### OIDC

OIDC is the v0.2 human-identity mode.

In OIDC mode:

- operator API/UI access requires a valid authenticated OIDC-backed session,
- the deployment token MUST NOT satisfy operator RBAC authorization,
- operator permissions are derived only from the accepted Kafdeck authorization policy,
- the deployment token may remain applicable only to explicitly documented deployment/bootstrap boundaries and MUST NOT become an RBAC bypass.

## 5. OIDC posture

Accepted v0.2 protocol posture:

- OpenID Connect discovery over configured issuer metadata,
- Authorization Code flow,
- PKCE,
- exact redirect URI validation,
- state and nonce validation,
- issuer validation,
- audience/client validation,
- signature/JWKS validation,
- bounded clock skew,
- no implicit flow,
- no Resource Owner Password Credentials flow,
- no OIDC access or refresh token in browser storage.

Kafdeck uses standard ASP.NET Core OIDC/cookie facilities behind Kafdeck-owned identity interfaces. External authentication-library types do not become domain/application contracts.

## 6. Session model

The browser receives only a secure Kafdeck session cookie.

Required cookie properties:

- HttpOnly,
- Secure for non-loopback HTTPS deployments,
- SameSite policy compatible with the accepted OIDC redirect flow,
- bounded lifetime,
- session rotation on successful authentication,
- no credential/token material exposed to JavaScript.

OIDC protocol tokens required by the server are held server-side for the active session and are not persisted as user-visible application data.

v0.2 targets a single Kafdeck application instance/session authority. Shared multi-replica session storage is deferred until a scaling RFC requires it.

## 7. Canonical operator identity

Authorization identity is keyed by:

`(issuer, subject)`

Display name, preferred username and email are presentation attributes only and MUST NOT be authorization keys.

Normalized identity may include:

- issuer,
- subject,
- display name,
- email when provided,
- configured group/role claim values,
- authentication time,
- session ID.

Missing, oversized or malformed required claims fail closed.

## 8. Authorization model

Authorization is default-deny.

v0.2 policy is configuration-driven and immutable at runtime. Runtime policy mutation is deliberately excluded until audited administrative workflows exist.

Conceptual model:

```text
Role
  -> Permissions[]

Permission
  -> Action
  -> ResourceType
  -> Scope

Binding
  -> Subject or exact external group
  -> Role
```

Initial actions map to existing read capabilities, for example:

- `system.read`
- `cluster.read`
- `broker.read`
- `topic.list`
- `topic.read`
- `topic.config.read`
- `broker.config.read`

The permission vocabulary contains no Kafka write action in v0.2.

Scopes may constrain:

- configured cluster IDs,
- resource type,
- deterministic topic/resource glob patterns where relevant.

Regex-based policy execution is not required for v0.2. Pattern matching MUST be bounded and deterministic.

## 9. Role bindings

Bindings may target:

- exact canonical subject identity,
- exact configured OIDC group/role claim value.

No automatic trust is placed in arbitrary role names sent by an identity provider. External claims are mapped through explicit Kafdeck configuration.

Unknown groups/claims grant no permissions.

v0.2 does not provide a runtime UI/API to edit bindings.

## 10. Enforcement

Authorization is enforced server-side before application handlers return protected resource data.

The UI MAY hide unavailable controls/resources for usability, but UI state is never an authorization boundary.

Required rules:

- cluster selector shows only authorized clusters,
- direct access to an unauthorized cluster/resource fails without returning protected metadata,
- configuration-read tabs/endpoints require their specific permission,
- authorization denied is distinct from Kafka ACL denied,
- caching cannot cross authorization scopes,
- authorization decisions cannot be bypassed by alternate HTTP routes.

## 11. Audit identity

v0.2 introduces structured security audit events containing authenticated operator identity where available.

At minimum, record:

- login success/failure,
- logout/session termination,
- authorization denial,
- security-relevant configuration reads where policy requires audit,
- policy/configuration validation failures,
- use of legacy Token mode when remote access is enabled.

Audit output MUST exclude secrets, OIDC tokens and browser cookies.

v0.2 requires a structured audit sink/export contract, not a full in-product historical audit UI or tamper-evident ledger.

## 12. Kafka boundary

Identity/RBAC changes Kafdeck authorization, not Kafka privileges.

The Kafka adapter remains read-only and the v0.1 regression rule remains active:

- no non-GET Kafka administrative route,
- no mutation command/port,
- no producer/consumer payload path.

Kafdeck RBAC cannot elevate the configured Kafka principal beyond Kafka-side ACLs.

## 13. Air-gapped and on-premise posture

OIDC configuration MUST support an operator-supplied private/on-premise issuer.

Kafdeck must not require public Internet access, hosted identity SaaS or external telemetry.

Discovery/JWKS access is limited to the configured issuer endpoints and follows bounded timeout/retry behavior.

## 14. Failure semantics

Authentication failures return an authentication challenge or RFC 9457 problem response as appropriate.

Authorization failures return a stable authorization-denied response without leaking protected resource details.

OIDC provider unavailability does not silently fall back to deployment-token operator access in OIDC mode.

Invalid authorization configuration fails startup or policy activation closed.

## 15. Compatibility and migration

Existing v0.1 Local/Token configurations continue to start unless they violate existing safety rules.

OIDC mode is opt-in through explicit configuration.

No v0.1 release artifact is modified.

## 16. Exit criteria

RFC-0002 implementation is complete only when:

- OIDC protocol/security tests pass,
- session-cookie security tests pass,
- authorization matrix tests pass,
- cross-cluster authorization isolation tests pass,
- direct-route bypass tests pass,
- legacy Local/Token compatibility tests pass,
- Kafka mutation-route regression tests remain green,
- payload-access regression tests remain green,
- security threat-model review is approved,
- operator documentation is complete,
- exact-head quality, CodeQL and applicable integration gates are green.
