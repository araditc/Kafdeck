# Declarative subscription CLI contract — v0.8

This contract is implemented for the first `NotificationSubscription` family.
Runtime activation, registered sources/owners, current authorization and the
durable backend remain required. Parsing a file grants no authority. Exact
integration acceptance is tracked separately from the grammar contract.

Activation also requires an explicitly enrolled deployment generation and a
matching external recovery anchor. Keep the anchor outside database backup or
restore directories. Restoring ownership/plan/lease rows cannot automatically
reactivate an older generation. A fenced operator recovery must explicitly
admit the intended generation; manifest fields and CLI consent cannot perform
this admission. An unknown operation is reconciled from an existing immutable
commit receipt, never by repeating the subscription write.

## Closed manifest

```yaml
apiVersion: kafdeck.io/v0.8
kind: NotificationSubscription
metadata:
  deploymentRef: production-a
  name: ops-lag
  ownerRef: team-ops
spec:
  destinationRef: ops-notifier
  state: Active
  eventClasses: [Operational, Mutation]
  eventTypes:
    - consumer.lag.alert
    - mutation.state-changed
```

JSON has exactly the same object structure. Identifiers and exact event filters
retain the existing notification contract's ASCII/case rules. Classes are
`Operational`, `Mutation`, `Security`, `Slo`, `DataQuality`; desired state is
`Active` or `Paused`. Duplicate classes/types are rejected. Empty `eventTypes`
means all types in the selected classes. `Retired` is terminal and cannot be
requested or reversed by this grammar.

The finite YAML subset admits two-space metadata/spec mappings, block string
sequences or one-line bracketed string sequences, plain identifier scalars,
JSON double-quoted strings and single-quoted strings. Comments are allowed.
It rejects all anchors/aliases/tags/merge keys before constructing maps/lists;
there is no graph expansion. Flow maps, document directives, multiple
documents, multiline scalars, tabs, unexpected indentation and implicit
objects are rejected. This is intentionally not a general YAML interpreter.

Both formats reject unknown/duplicate keys, malformed Unicode, secret/provider
fields, unknown versions/families, excessive bytes/depth/nodes/strings and
out-of-contract identities. Limits are 16 KiB source bytes, depth 6, 256 decoded
nodes and 1024 characters per scalar. Diagnostics never echo input values.
Canonical JSON has fixed property order and normalized filter-set ordering.
The SHA256 desired fingerprint includes deployment and owner references.

## Commands

Every file command takes an explicit registered source, source-revision hash
and expected ownership revision. These are lookup/CAS inputs; the server must
resolve current registration and provenance rather than trusting the file or
CI identity. No CLI command executes Git, a shell, code, SQL or provider URLs.
Use a pipeline checkout pinned to the approved commit and manifest path.

```text
kafdeck declarative validate --manifest-file desired.yaml --source registered-source --source-revision <64-lowercase-hex> --ownership-revision 0
kafdeck --service-profile public.json declarative observe --manifest-file desired.yaml --source registered-source --source-revision <hash> --ownership-revision 0
kafdeck --service-profile public.json declarative drift --manifest-file desired.yaml --source registered-source --source-revision <hash> --ownership-revision 0
kafdeck --service-profile public.json declarative import --manifest-file desired.yaml --source registered-source --source-revision <hash> --ownership-revision 0 --idempotency-key <stable-request-key>
kafdeck --service-profile public.json declarative plan --manifest-file desired.yaml --source registered-source --source-revision <hash> --ownership-revision <current-revision> --idempotency-key <stable-request-key>
kafdeck --service-profile public.json declarative apply <server-plan-id> <exact-plan-fingerprint>
kafdeck --service-profile public.json declarative recover <server-plan-id> <exact-plan-fingerprint>
kafdeck --service-profile public.json declarative show <server-plan-id>
kafdeck --service-profile public.json declarative capabilities
kafdeck --service-profile public.json declarative source-show <registered-source> --resource <resource-id>
kafdeck --service-profile public.json declarative source-advance <registered-source> <expected-generation> <expected-revision> <expected-source-hash> --manifest-file desired.yaml
```

`validate` runs locally without loading credentials or opening a socket. All
remote commands require the existing registered human/service OIDC flow.
Files are validated before any authentication/network activity and converted
to canonical JSON for the named API. File extension selects JSON/YAML;
`--format json|yaml` explicitly selects one. Arbitrary requests/routes are not
accepted. `import` is the alias of `import-preview` and produces a governed
preview, never an immediate adoption effect.

Plans use the existing operation envelope: `operationId` is the immutable
server plan ID and `previewHash` is its fingerprint. Reuse `operations status`,
`confirm`, `approval`, `approve`, `reject` and `cancel`. A plan/fingerprint is
never reconstructed from a caller's effects document. Apply sends the exact
fingerprint to the named stored-plan endpoint.

`show` is the exact initiating principal's metadata-only stored-plan read and
does not require an apply grant. An independently eligible human can inspect
the exact sealed before/after/change/policy projection only while approval is
outstanding; this does not grant ordinary cross-principal reads or execution.
`capabilities` reports current activation and
the explicitly admitted family/lifecycle matrix. Neither command can choose
an arbitrary URL, caller identity or execution contract.

Source pins are fixed by default. An operator must separately enable
`AllowRevisionAdvance` for a registered source before an authenticated caller
with current `DeclarativeSourceManage` and exact `NotificationRead` grants can
advance it. This does not require or grant apply authority. Read the exact
generation/revision/hash receipt with `source-show`, then pass those expected
values to `source-advance`. The backend computes the new canonical manifest
hash and commits a generation/revision CAS; stale/replayed CAS or a different
source/owner/resource is denied. Initial bootstrap uses the empty GUID,
revision zero and the trusted configured baseline hash only when the backend
admits that exact registration. The command never trusts a caller's new hash.

Planning may bootstrap an absent source at the configured baseline, but never
changes an existing source pin. It reuses the exact initially observed source
generation/revision/hash; a concurrent advance or A→B→A is a conflict. Changing
deployment configuration alone does not overwrite an existing durable pin;
use the explicitly authorized source-advance workflow.

An allowed pipeline can therefore advance A→B→A without editing deployment
configuration for every Git commit. Older immutable plans remain bound to
their original source generation/revision and cannot gain authority from a
later return to the same content. Revision advancement never implicitly
imports, plans, approves or applies. Read current status after uncertainty;
do not blindly retry the previous CAS or effect.

`recover` is a separate explicit receipt lookup/reconciliation. It can resolve
an unknown operation only from a trusted matching immutable commit receipt
under current requester/source/owner/approval/policy authority. An absent
receipt remains a conflict/unknown; this command never repeats the effect or
creates a replacement plan.

## Finite GitOps reconciliation

```text
kafdeck --service-profile public.json declarative reconcile --manifest-file desired.yaml --source registered-source --source-revision <hash> --ownership-revision <current-revision> --idempotency-key <stable-request-key> --yes
```

Reconciliation first observes current authorized drift and ownership. An owned
`InSync` resource exits successfully without a new plan, approval or write.
This also requires the backend's `sourceInSync: true` proof of the exact current
source generation and revision; an old ownership source binding needs a newly
governed plan even when the product fields already match.
An unowned existing resource requires explicit import. Unavailable or denied
evidence never authorizes a plan. Without `--yes`, a needed change returns its
immutable plan for review. With `--yes`, it makes at most four requests:
observe, plan, confirmation when required,
and apply only when the same ID/fingerprint is `Ready`. `--yes` is explicit
consent to confirmation/apply under current backend policy. It never grants
approval authority, lowers risk or substitutes a service for a human.
`AwaitingApproval` stops with exit 6; a separately authenticated eligible human
must inspect/approve the exact preview. Executing/unknown outcomes stop with
exit 7. There is no polling loop, automatic approval, silent plan refresh,
retry-after-uncertainty or background controller. The external pipeline owns
bounded scheduling and must inspect durable status before any new request.
Transport failure can also leave a dispatched operation ambiguous; inspect
the original durable operation instead of assuming non-application.

Observation/drift preserve all seven truths. `InSync` exits 0;
`OutOfSync`, `Missing`, `Conflict` exit 8; `Unknown` exits 7;
`Inaccessible` exits 3; `Unsupported` exits 4. Missing is only an authorized,
current exact lookup result. Failed access or unavailable evidence never
becomes an empty resource or automatic create. Mutation outcomes retain the
existing pending/unknown/expired/partial exit categories.

## Family boundaries

| Family | Declarative contract | Destructive lifecycle |
| --- | --- | --- |
| NotificationSubscription | Closed validate, observe/drift, governed import/plan/apply; activation and accepted backend evidence required | Destroy/delete, transfer/relinquish and Retired reversal are not admitted |
| DataQualityPolicy | Observed-only candidate; no ownership/import/apply | Unsupported |
| KafkaTopic | Existing interactive read/mutation does not confer declarative ownership | Unsupported |
| ACL / SCRAM / ConnectProfile | Existing blocked/unsupported capabilities retained; no manifest family | Unsupported |

No parser/CLI success establishes release readiness, remote provider support,
owner registration, HA fencing or an accepted real effect. The server's
capability/activation and durable status remain authoritative.
