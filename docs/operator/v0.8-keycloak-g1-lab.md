# W67 G1 genuine Keycloak bearer read laboratory

This is an isolated, explicitly enabled local acceptance profile for the first
W67 vertical. It does not admit a production issuer or establish full A1/A2,
A3–A6 acceptance. Browser cookies and antiforgery keep their existing paths.

## Pinned environment

- Keycloak **26.8.1**, official ZIP SHA256
  `4cd312c889af358a819a74a6c6f068f9ea159a6959e49924607cec95cfd4c1a4`.
- Temurin **21.0.12.1+1**, Windows x64 JDK ZIP SHA256
  `f9d6e191ab098c0d416e7d588a24420a8621cd2f4720dab2459b8b7b2d2d8b4e`.
- Exact lab issuer `https://localhost:18443/realms/kafdeck-g1`.
- Exact API audience `kafdeck-api-g1`; no additional audience is admitted.
- Service client `kafdeck-g1-service`, signed RS256 `private_key_jwt`
  client authentication, no client secret or password grant fallback.
- Service subject `f51b26b6-1152-4e2b-b18a-7c46b94c1c02` in the imported lab realm.
- Public PKCE client is created as a future A3 fixture; no human CLI acceptance
  is claimed by this setup.

The realm and credentials are disposable. The preparation script generates a
two-day lab TLS root/server certificate and client key under the ignored
`deploy/dev/.generated/g1/identity` directory. No OS trust store is changed.
The server certificate still undergoes hostname and chain validation using the
explicit lab root. Never configure a blanket certificate acceptance callback.

## Run

Use PowerShell 7 and the verified extracted JDK/Keycloak distributions:

```powershell
./deploy/dev/prepare-keycloak-g1.ps1 -KeycloakHome <verified-keycloak-directory>
$env:JAVA_HOME = '<verified-jdk-directory>'
$env:KC_HTTPS_KEY_STORE_PASSWORD = Get-Content ./deploy/dev/.generated/g1/identity/https-password.txt -Raw
& '<verified-keycloak-directory>/bin/kc.bat' start --http-enabled=false --http-host=127.0.0.1 --https-port=18443 --hostname=https://localhost:18443 --https-key-store-file=<absolute-path-to-identity/https.p12> --import-realm
```

Run the server as a hidden background process when automating this sequence.
Keep its generated database and import directory inside the ignored lab area.
The server must finish realm import before the acceptance test runs.

```powershell
$env:KAFDECK_KEYCLOAK_G1_LAB = (Resolve-Path ./deploy/dev/.generated/g1/identity/lab.json).Path
dotnet test tests/Kafdeck.Architecture.Tests/Kafdeck.Architecture.Tests.csproj --filter FullyQualifiedName~V08W67BearerReadTests -m:1
```

The real-IdP test explicitly skips with an explanation when this environment
variable is absent. The ordinary negative tests still run. This prevents a green
offline suite from being reported as real Keycloak evidence.

The integration test obtains the access token from Keycloak's real TLS token
endpoint using a signed client assertion, checks that replaying the same assertion
is denied, starts the shipped API entry point on loopback port 18086, and exercises
the existing v1 endpoints. Access tokens and assertions remain in memory. The
evidence JSON contains status codes and safe environment identifiers, and the
test checks that token/assertion bytes never appear in host logs or HTTP bodies.

## Runtime admission and authorization

`Kafdeck:NonBrowserRead:Enabled` defaults to `false`. Enabling requires an exact
HTTPS `Issuer`, `ApiAudience`, optional deployment-owned `TrustedCaPemFile`, and
1–128 finite `Registrations`. Every registration needs exact `Id`, `OwnerId`,
`Subject`, `ClientId`, `Enabled`, `ExpiresAtUtc`, and finite `ReadActions`.
This registry is separate from existing `Kafdeck:Authorization` direct subject
bindings; both gates must authorize a read. Keycloak roles/groups are ignored.

The registration is re-read at token admission and every backend authorization
decision; disabling/removing/expiring it denies subsequent requests. A trust
issuer/audience change requires restart and denies requests until then. Existing
RBAC remains the configured immutable policy snapshot and changes by host
restart, matching current backend policy behavior. Registration ID, expiry and
owner are never supplied by the caller.

Initial route admission is deliberately explicit:

| Existing endpoint | Required backend action |
| --- | --- |
| GET `/api/v1/system/info` | `SystemRead` |
| GET `/api/v1/system/health` | `SystemRead` |
| GET `/api/v1/clusters/{clusterId}` | `ClusterRead` for exact cluster |
| GET `/api/v1/clusters/{clusterId}/health` | `ClusterRead` for exact cluster |
| GET `/api/v1/clusters/{clusterId}/capabilities` | `ClusterRead` for exact cluster |
| GET `/api/v1/clusters/{clusterId}/brokers` | `BrokerRead` for exact cluster |
| GET `/api/v1/clusters/{clusterId}/brokers/{brokerId}` | `BrokerRead` for exact cluster |

Other routes, all writes, operation/status, approvals, browser-session endpoints,
record/configuration reads and cluster collections remain unadmitted to bearer.
Bearer plus any cookie or deployment credential is rejected before selecting a
scheme. A validated bearer is a typed service identity, without browser session
claims; it cannot satisfy `OperatorSessionContextFactory`. Read authorization runs
before legacy Local/Token mode's permissive operator fallback. Responses use the
same backend endpoint, filtering and masking as the existing route.

## JWT and key lifetime contract

The verifier requires RS256, approved `kid`, signed `typ=Bearer`, exact
issuer/subject/client/audience and mandatory finite `iat`/`exp`. Original token
lifetime is at most 15 minutes and clock skew at most 30 seconds. Duplicate
security claims, additional audiences, ID tokens, client assertions as access
tokens and token-controlled `jku`/`x5u`/`jwk`/`crit` are rejected.

**Explicit contract adjustment for actual Keycloak tokens:** JWT `nbf` is optional.
When absent, the verifier uses mandatory signed `iat` as the activation time.
When present, `nbf` must be a nonnegative integer before `exp` and cannot be in the
future beyond allowed skew or precede `iat` beyond the same 30-second window.
This preserves mandatory issuance-time validation and original lifetime bounds.
The real lab evidence records whether Keycloak emitted `nbf`; offline tests cover
absence and malformed/future values. Earlier planning text listing `nbf` among
validation claims is interpreted with these explicit optional-claim semantics.

Discovery issuer and JWKS URL must exactly match the configured realm and its
Keycloak certs path. Verified TLS, no redirects/proxy, ten-second HTTP timeout,
64 KiB documents, at most sixteen published keys/eight admitted RSA signing keys,
and RSA 2048–4096 bits bound trust ingestion. JWKS is cached for at most 60 seconds.
Refresh failure after that denies authentication; stale keys are never extended.
Unknown new keys are denied until successful refresh. Removal/revocation of an
issued access token is not instantaneous; key-cache and access-token lifetime
bounds are explicit. Full rollover/offline/HA topology acceptance is still A6.

## Honest acceptance boundary

The first vertical proves a genuine Keycloak-issued token can reach a real
Kafdeck host, produce an allowed GET, and receive cross-cluster RBAC denial.
Single-node client assertion replay is an additional negative; it does not prove
concurrent first-use, HA replay protection, restart, rolling upgrade or rotation.
PKCE human login, full read inventory/pagination parity, mutation/approval/status,
PostgreSQL/HA and production trust admission remain outstanding. Keep W67 #216
open until all A1–A6 evidence exists on protected main.
