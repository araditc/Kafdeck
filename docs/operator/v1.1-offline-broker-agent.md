# Remote offline agent installation and upgrade in Kafdeck 1.1

Source builds containing [dashboard Fleet onboarding](fleet-dashboard-onboarding.md) can perform the network, encrypted-credential and restricted-host preparation through the UI. The manual procedure below remains supported for the immutable 1.1.0 release and preconfigured hosts.

Fleet previews and applies an offline monitoring agent package to one selected, verified broker per cluster. The same control works for systemd and Docker Compose. It waits for Kafka health, restored in-sync replicas and a fresh JVM start-time metric from the broker's configured monitoring source before reporting completion.

## Prepare a host and package

1. [Register the broker host and verify its service binding](v1.1-broker-host-registration.md).
2. Generate a dedicated SSH key for the agent lifecycle. On that host as root run `sh tools/broker-host/install-agent.sh /path/to/agent-installer.pub`. Keep the key separate from the host discovery and log-read key. Deploy the private key as a protected Kafdeck server secret reference.
3. Transfer the agent JAR offline after verifying it against the provenance of the package you obtained. For the supplemental Windows bundle or its extracted JAR, use the outer ZIP checksum and the JAR digest in `bundle-manifest.json`. For an internally built JAR, use the approved digest from your package review. Install it as a root-owned, mode `0644` file named `<sha256>.jar` under `/var/lib/kafdeck-agent/packages`. Add the exact version and digest to the host and Kafdeck catalogs. The helper checks the actual bytes and Premain class locally before preparing a change.
4. Set up a distinct monitoring source per broker and place the agent properties and protected token according to the [agent guide](kafka-agent.md). Use the same source and token through the upgrade. Configure the intended broker runtime user to read them. Use a private credential file, and keep the agent directory and its ancestors root-owned and unwritable by the Kafka user. Protect the properties from writes by non-root users.

For a first install, create a root-owned empty `jvm.args` in the agent directory. Append `@/opt/kafdeck-monitor/jvm.args` to the existing `JDK_JAVA_OPTIONS` for the intended service. Retain other JVM options. The integration must already be active in the running broker for Fleet to verify it. For systemd, use the same directory path on the host and in the JVM. For Compose, mount the host **directory** read-only at the JVM path. A file-only bind mount would continue to reference its old inode. Fleet can also upgrade a running broker already using the canonical `-javaagent:<directory>/kafdeck-kafka-agent.jar=<directory>/agent.properties` argument.

Create root-owned `/etc/kafdeck/agent-targets.json` with the registered target and a bounded maintenance window. Example timestamps are UTC Unix seconds and must be replaced for your maintenance window.

```json
{
  "version": 1,
  "packages": {
    "1.1.0": "<sha256>"
  },
  "targets": {
    "office-broker-2": {
      "hostDirectory": "/srv/kafdeck-agent/kafka-2",
      "runtimeDirectory": "/opt/kafdeck-monitor",
      "maintenanceFrom": 1795021200,
      "maintenanceTo": 1795024800
    }
  }
}
```

In `Kafdeck:BrokerHosts`, configure the lifecycle credential separately from the host probe credential. Grant permissions explicitly even for an installation owner. These settings sit beside the existing SSH allowlist and probe credential.

```json
{
  "AgentInstallerUserIds": ["9fabe09a-f3c0-4e1b-b760-0cb299c8b6fc"],
  "AgentTargets": [{
    "ClusterId": "office",
    "BrokerId": 2,
    "MonitoringInstance": "office-broker-2",
    "CredentialId": "office-agent-installer",
    "ExpectedBrokers": 3
  }],
  "AgentPackages": [{"Version": "1.1.0", "Digest": "<sha256>"}]
}
```

The operator must also have cluster access. Give the Kafka administration identity full topic metadata and topic configuration visibility, including internal topics. Kafka metadata can omit topics for which the caller lacks permission. Use a credential with complete visibility for this operation. Keep the target's monitoring instance unique to that broker.

## Install, upgrade and observe

1. Select the cluster and open **Fleet → Offline broker agent**. Choose the staged package and preview the current version, target digest, launch changes and restart requirement.
2. Review the supported service, maintenance window and affected partitions. A restart is blocked if expected brokers or a controller are missing, replicas are out of sync, or taking that broker out would bring an affected partition below its configured minimum ISR. A single-replica partition on the selected broker blocks the restart.
3. In the approved window, confirm the restart and apply. Only the approved unit or container restarts. The host helper replaces the JAR atomically and, on a first install using the argument file, writes the fixed agent argument. It does not edit Kafka configuration, other JVM flags, credentials, the Compose project or other services.
4. Select **Check agent operation** until Kafka health and a fresh metric are verified. A restart request or a running process alone is insufficient. Check Monitoring for the same source.

After a disconnect, reopen Fleet for the same cluster. Kafdeck can restore the pending plan for the same authorized account from its protected server-side record. Include the `<ManagedIdentity.StateFile>.agent-operations.json` sidecar and the existing data protection keys in the protected backup scope.

**Check agent operation** reads the recorded execution state. **Retry the same agent request** resumes safe work from the same plan. If restart intent was persisted and the reply went missing, the helper observes the service and never dispatches a duplicate restart. If the old instance remains and the outcome cannot be established, pause further changes and investigate the service manager. Preserve the operation journal and package for review. Do not remove the journal to force a retry.

If the plan expires while publishing the package and the host has recorded no restart intent, select **Check agent operation**, then **Preview pending change in the current maintenance window**. Fleet rechecks the same operation, package, broker instance and ISR. Confirm the new preview to continue. A preview for a package already installed can be confirmed outside the maintenance window because it authorizes no restart.

For the rollout sequence, permissions and fault recovery, see [Fleet rollout and incident recovery](v1.1-fleet-operational-recovery.md).
