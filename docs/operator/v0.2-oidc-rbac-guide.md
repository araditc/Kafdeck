# v0.2 Operator OIDC and RBAC Guide

Kafdeck v0.2 adds OIDC-backed operator identity and default-deny RBAC while preserving the read-only Kafka boundary.

## Access modes

`Local` preserves loopback-only v0.1 behavior. `Token` preserves the v0.1 deployment-token boundary for non-loopback deployments. `Oidc` authenticates individual operators and evaluates Kafdeck RBAC. A deployment token is not an operator identity and cannot be configured as an OIDC fallback.

## OIDC configuration

Configure `Kafdeck:Deployment:AccessMode=Oidc` and provide `Oidc:Issuer`, `Oidc:ClientId`, optional `Oidc:ClientSecret` as a secret reference, optional `Oidc:GroupClaim`, and the required scopes. Kafdeck uses Authorization Code + PKCE, validates discovery/JWKS/state/nonce, keeps the application session server-side, and does not expose OIDC protocol tokens through the browser API.

Non-loopback OIDC deployments require HTTPS. Use a secret reference such as `env:KAFDECK_OIDC_CLIENT_SECRET`; never place secret values in committed configuration.

## RBAC example

~~~json
{
  "Kafdeck": {
    "Authorization": {
      "Roles": [{
        "Id": "prod-viewer",
        "Permissions": [
          { "Action": "cluster.read", "ClusterIds": ["prod"] },
          { "Action": "broker.read", "ClusterIds": ["prod"] },
          { "Action": "topic.list", "ClusterIds": ["prod"] },
          { "Action": "topic.read", "ClusterIds": ["prod"], "ResourcePatterns": ["payments.*"] }
        ]
      }],
      "SubjectBindings": [{
        "Issuer": "https://idp.example",
        "Subject": "operator-subject",
        "RoleIds": ["prod-viewer"]
      }],
      "GroupBindings": [{
        "ExternalGroup": "kafka-readers",
        "RoleIds": ["prod-viewer"]
      }]
    }
  }
}
~~~

Permissions are additive but remain action-specific. Topic read does not imply topic configuration read. Configuration reads require their dedicated permission in addition to visibility permissions. Unbound identities and ungranted actions/resources fail closed.

## Private and air-gapped IdPs

The configured issuer, discovery document and JWKS endpoints must be reachable from the Kafdeck backend. Private CA trust must be installed at the operating-system/container trust layer; Kafdeck does not provide a disable-TLS-verification switch. Browser access must also be able to reach the IdP authorization/logout endpoints used for redirects. For disconnected environments, operate a private OIDC authority whose discovery/JWKS and browser endpoints are available inside the enclave.

## Audit

v0.2 emits structured security audit events for OIDC login success/failure, logout, RBAC denials, sensitive configuration reads and legacy deployment-token boundary events. Audit fields intentionally exclude OIDC tokens, cookies, deployment tokens and Kafka credentials.
