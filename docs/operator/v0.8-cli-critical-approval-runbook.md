# W67 CRITICAL TopicDelete and distinct human approval

TopicDelete always requires CRITICAL governance: the original requester confirms
the server-derived exact target, then a different eligible human approves the
immutable preview before the requester can execute. Machines cannot approve.
Changing CLI client or switching to a browser session does not make the same
issuer/subject a different human.

## Deployment admission

Enable the durable mutation engine and bearer trust, then explicitly enable
`Kafdeck:NonBrowserRead:GovernedMutationsEnabled`. Requester registrations need
`MutationActions: ["TopicDelete"]` (optionally also `"TopicCreate"`) and current
direct backend TopicDelete permission on the exact cluster/topic.

Separately enable `Kafdeck:NonBrowserRead:GovernedApprovalsEnabled`. The second
human needs an active exact `HumanRegistrations` entry with an owner, finite
expiry and `ApprovalActions: ["TopicDelete"]`. The human's direct backend role
needs **both** `MutationApprove` and `TopicDelete` with applicable cluster/resource
scopes. An approver does not need a mutation registration grant. For example:

```json
[
  { "action": "MutationApprove", "clusterIds": ["dev"], "resourcePatterns": ["orders-demo"] },
  { "action": "TopicDelete", "clusterIds": ["dev"], "resourcePatterns": ["orders-demo"] }
]
```

Both activation switches default to false. Service registrations cannot contain
ApprovalActions. Expired or revoked registrations, missing actions, policy changes
and out-of-scope resources fail closed. The exact approver registration and
direct permissions are checked again before provider dispatch; durable approval
evidence is not an eternal grant.

## Commands

Use a disposable topic and two real human accounts:

```text
kafdeck --oidc-profile requester.json topics delete-preview dev orders-demo --idempotency-key <unique-key>
kafdeck --oidc-profile requester.json operations confirm <id> <hash> --challenge <server-target>
kafdeck --oidc-profile approver.json operations approval <id>
kafdeck --oidc-profile approver.json operations approve <id> <hash>
kafdeck --oidc-profile requester.json operations execute <id>
kafdeck --oidc-profile requester.json operations status <id>
```

Both public profiles can name the same PKCE client. Sign in as the second human
for approval commands. Confirmation and pending approval inspection return typed
`awaitingApproval`, exit **6**. Approval becoming Ready returns **0**. Execution
before approval returns conflict **8**. Wrong hashes conflict; same-human, service
and unauthorized approval are rejected. The approver cannot execute another
actor's operation. IDs, hashes and typed targets come from the server preview.

Requests reject actor overrides and unknown fields. Delete preview and execution
accept no body. Dedicated bearer routes reject cookie/deployment credential
collisions; existing browser routes retain session and antiforgery boundaries.
A browser reviewing a new bearer operation also needs current direct
MutationApprove and underlying resource scopes.
