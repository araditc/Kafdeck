# G2 physical PostgreSQL failover and backup restore laboratory

This is a controlled local laboratory, with real native PostgreSQL processes,
physical streaming replication, synchronous commits, physical backup verification,
fenced promotion and a separate restored database. It does not activate production
notification HA or close N4/N5/A6. Existing `g2/postgres` and Keycloak data are not
modified. Every scenario uses a fresh directory; no action deletes, resets,
reformats or overwrites an existing database or backup.

## Runtime and topology

`deploy/dev/prepare-postgres-g2-recovery.ps1` requires PowerShell 7 and existing
PostgreSQL 16–19 native tools of one identical runtime version. Windows defaults
to the previously checksum-verified portable PostgreSQL 17.11 binaries under
`deploy/dev/.generated/g2/postgres/pgsql/bin`. Linux uses `pg_config --bindir`, or
an explicit `-BinDirectory`; no OS package installation is performed. The manifest
records the actual runtime version, rather than claiming every platform ran17.11.

Default fresh root: `deploy/dev/.generated/g2-recovery/postgres`.

| Node | Loopback port | Role |
| --- | --- | --- |
| primary | 15433 | Initial writable primary; permanently fenced before promotion |
| standby | 15434 | Physical synchronous replica, then promoted primary |
| restore | 15435 | Independent verified backup restore, read-only and quarantined |

All listeners bind `127.0.0.1`. Initialization uses random SCRAM credentials and
a dedicated non-superuser replication role. Password files, replication passfile,
private connection strings, database files, backups and raw logs remain in the
ignored lab root. Linux sets the root/data directories private and secret files
mode600. Never upload that directory as a general CI artifact.

## Action contract

```powershell
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action Prepare
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action Status
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action Sync
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action Backup
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action Failover -PrimaryStopMode immediate
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action Restore
./deploy/dev/prepare-postgres-g2-recovery.ps1 -Action Stop
```

Pass the same `-OutputDirectory` and `-BinDirectory` on later calls when using
custom paths. `Prepare` alone accepts fresh custom `-PrimaryPort`, `-StandbyPort`
and `-RestorePort`; later actions follow the recorded endpoint manifest.

- **Prepare** refuses an existing directory or occupied port, initializes a new
  primary, creates the replication identity, and seeds the standby with real
  `pg_basebackup -X stream -R` and a physical slot. `pg_verifybackup` must pass.
  After streaming is observed, it enables `synchronous_commit=remote_apply` and
  `synchronous_standby_names='FIRST 1 (g2_standby)'`. A committed marker, `sync`
  member and physically replayed LSN are required before success is reported.
- **Sync** waits for actual `pg_last_wal_replay_lsn()` to reach a primary WAL
  barrier. Optional `-TargetLsn` accepts a validated LSN. It cannot succeed from
  an application clock or a rewritten recovery timestamp.
- **Backup** takes a new physical streaming base backup from the currently
  writable primary and verifies its manifest. `latest-backup.json` records its
  directory, manifest SHA256, WAL ranges, source endpoint and private connection
  file reference. Backups are never reused as writable nodes or overwritten.
- **Failover** requires a replay barrier, stops the old primary (`fast` or
  `immediate`), verifies exact data-directory shutdown and a closed old TCP port,
  persists fencing evidence, then promotes the standby. It checks writable role
  and checkpoint timeline. The script never restarts the fenced old primary.
  It implements no failback, rewind or automatic election.
- **Restore** verifies the exact saved backup manifest again and copies the
  backup into a fresh restore directory. It persists `restore-quarantine.json`
  before startup and sets `default_transaction_read_only=on`. Automatic sender
  activation is forbidden. A restored `Pending` row is not proof that a remote
  side effect never occurred after the backup. An external operator-controlled
  sender interlock must reject startup before database initialization; database
  read-only mode is additional protection, not an authorization mechanism.
- **Start** resumes only admitted nodes. Once fencing is recorded it starts only
  the promoted node, never the old primary. **Stop** targets only this manifest's
  data directories and preserves all data/evidence.

Native control startup is hidden on Windows and waits only for bounded `pg_ctl`,
avoiding inherited descendant stream handles. SQL connection timeout is5s,
statement timeout20s, replay observation35s, and node control waits at most45s.
The calling acceptance harness must additionally bound whole actions.

## Test integration and evidence

`lab.json` format1 contains `primary`, `standby`, `restore` objects with `name`,
`port`, `dataDirectory`, and `connectionStringFile`; `activeEndpoint` and
`oldPrimaryFenced` describe the controlled transition. Credentials are loaded
privately from those files; do not print connection strings. The manifest also
references `latestBackupFile`, `fenceFile` and `restoreQuarantineFile`.

Every existing manifest is validated before action dispatch: endpoint names and
distinct ports, exact owned data/credential/metadata paths, and absence of linked
path components. Initialized nodes must match the recorded PostgreSQL system
identifier in both local control data and the live endpoint when available.
Restore also requires the same system identifier and canonical backup child.
A modified manifest cannot redirect pg_ctl or restore copying to another cluster.
The separate fence record remains authoritative if an action stops between
writing it and replacing the manifest. Start never revives that old primary;
writer/restore activation also refuses a fenced primary that becomes reachable.

Sender scenarios must run serially with a fresh output directory per scenario.
Always invoke Stop in cleanup and retain the directories. Three separate
scenarios are needed: failover before claim, abrupt sender loss after a complete
physical POST with the InFlight claim confirmed on standby, and backup-before-
effect followed by restore after the live effect. Store-level contention alone
does not prove these physical process histories.

Sanitized native evidence files are `replication-evidence.json`,
`latest-sync-evidence.json`, `promotion-evidence.json`, `restore-evidence.json`,
and the backup's adjacent `base-*-evidence.json`. Do not upload connection files,
passwords, passfiles, raw logs, data directories or backup contents. Sender proof
must additionally retain its exact tests, physical POST/receipt counts, durable
states, revisions, attempts and explicit restore interlock refusal.

The native validation uses separate15436/15437/15438 ports and simple fixture
markers to verify replication/restore mechanics. These markers are not a product
notification proof. External failover managers, storage/power faults, PostgreSQL
replication over TLS, continuous WAL archival/PITR, production routing, automatic
fencing, database restore reconciliation and other mutation families remain
separate acceptance work.

The local17.11 native run verified an immediate stop of the old primary, timeline2
promotion, three committed markers on the promoted node and only the two backed-up
markers on the restored node. A write on the restored node was rejected. Safe
evidence is `artifacts/g2-recovery/native/postgres-native-failover-restore-evidence.json`.
The hardened controls then stopped both nodes successfully. A separate deliberately
malformed manifest pointing at the protected old data directory was refused before
native node control; `postgres-manifest-guard-evidence.json` records that refusal.
Both validation and default fixtures are stopped with all data retained, leaving
the default ports available for serial physical sender scenarios.

The workflow follows PostgreSQL's official [standby and synchronous replication
documentation](https://www.postgresql.org/docs/17/warm-standby.html),
[pg_basebackup](https://www.postgresql.org/docs/17/app-pgbasebackup.html), and
[replication configuration reference](https://www.postgresql.org/docs/17/runtime-config-replication.html).
