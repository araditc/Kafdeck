# v0.4 Operator Guide — Consumers, Schemas & Ecosystem Read Views

## 1. Authorization

v0.4 adds five independent actions:

- `consumer.read`
- `schema.read`
- `connect.read`
- `ksql.read`
- `catalog.read`

These actions do not grant record payload access. Existing `record.read` and `record.export` remain separately authorized and continue to use the v0.3 masking boundary.

Collection routes perform a cluster/action preflight before upstream enumeration and then filter/re-authorize individual resources. If RBAC removes returned resources, the response is explicitly marked partial.

## 2. Consumer groups

Consumer views use Kafka Admin read APIs and do not join consumer groups.

Kafdeck reads:
- group state,
- members,
- assignments,
- committed offsets,
- partition end offsets.

Kafdeck does not:
- subscribe as a group member,
- commit offsets,
- reset/shift/delete offsets,
- produce records.

Lag is calculated only when the committed offset is within the observed log range. Missing/out-of-range/unavailable/unauthorized observations remain explicit and are excluded from aggregate lag.

## 3. Consumer diagnostics

Diagnostics are evidence based.

A diagnostic may use:
- current group state,
- current bounded lag projection,
- an optional metrics provider,
- an optional history provider.

Default deployments do not require a metrics or history backend.

If metrics/history are absent, Kafdeck reports them unavailable. It does not estimate a rate or fabricate a historical trend from a single snapshot.

## 4. Schema Registry

The v0.4 explorer can read:
- subjects,
- versions,
- schema IDs/types/content,
- references,
- compatibility mode.

All registry operations are GET/read-only.

Schema diff is computed locally and bounded.

Compatibility inheritance is reported only after Kafdeck first checks subject-specific configuration and then falls back to global configuration on a subject-config not-found response.

## 5. Kafka Connect

Configure one optional Connect profile per Kafka cluster.

Read views include:
- worker identity/version,
- connector names,
- connector state,
- task state,
- bounded safe task trace,
- fail-closed safe configuration.

Connector plugins may define arbitrary config keys and embed credentials in unexpected values. Therefore Kafdeck exposes clear values only for an explicit allowlist of known operational fields; every other field is `[REDACTED]`.

No create/update/delete/pause/resume/restart action exists.

## 6. ksqlDB

Configure one optional ksqlDB profile per Kafka cluster.

v0.4 reads only genuine GET metadata endpoints used for server identity and health.

Kafdeck does not send SQL or statement text. If stream/table metadata requires a statement endpoint, Kafdeck reports that capability unsupported.

## 7. Topic catalog

Topic catalog foundations are immutable configuration-owned metadata.

They may include description, owner, domain, tags, documentation reference and classification.

Catalog metadata is descriptive and does not grant topic, record or ecosystem authorization.

## 8. External endpoint safety

Schema Registry, Connect and ksqlDB profiles:
- use validated deployment configuration,
- do not accept user-supplied upstream URLs,
- reject cross-origin redirects,
- use bounded response sizes and item counts,
- honor deadline/cancellation,
- isolate concurrency by provider/cluster,
- keep credentials out of responses/errors/audit.

Use HTTPS for remote endpoints when credentials are configured.

## 9. Partial and unavailable states

Operators should treat `partial`, `unsupported`, and `unavailable` as first-class states.

A filtered or incomplete observation is not evidence that no additional resource exists.

## 10. Audit

OIDC authorization denials, including collection preflight denials, are audited without leaking provider credentials or resource payload data.
