# Upgrade to v0.2 Operator Identity and RBAC

## Compatibility posture

v0.2 preserves v0.1 `Local` and `Token` access modes. Existing deployments do not become OIDC deployments merely by upgrading. Kafka access remains metadata/configuration read-only.

## Staying on Local or Token

If `AccessMode` is omitted, legacy configuration inference remains: no deployment access-token reference selects Local; a configured deployment access-token reference selects Token. This path preserves the v0.1 boundary and does not create an operator identity.

## Moving to OIDC

1. Establish a reachable OIDC authority and register Kafdeck as a confidential or appropriate server-side web client.
2. Configure HTTPS for every non-loopback Kafdeck listener.
3. Set `AccessMode=Oidc`, issuer, client ID, secret reference where required, scopes and optional external-group claim.
4. Remove the deployment access token. OIDC mode rejects configurations that also provide it.
5. Define roles and explicit subject/group bindings. Start with the minimum actions and cluster/resource scopes required.
6. Validate sign-in, sign-out, unauthorized (401), Kafdeck RBAC denied (403) and Kafka ACL denied behavior before production cutover.
7. Verify security audit delivery and operational log retention.

Restart invalidates active v0.2 sessions by design. Durable shared session state and durable audit history are not part of v0.2.

## Rollback

Rollback is a deployment configuration decision: restore the previously validated v0.1-compatible Local/Token configuration and version. Do not attempt to make a deployment token satisfy an OIDC operator session.
