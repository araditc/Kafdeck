# Fleet rollout and incident recovery

For host registration, log access, agent setup and broker settings in one sequence, start with the [Fleet quickstart](v1.1-fleet-quickstart.md).
Fleet selects one configured agent target per Kafka cluster. Treat each broker change as a maintenance operation. Advance the configured target after the previous broker's pending operation is resolved and the next broker has a current maintenance window, verified service binding and unique monitoring source.

## Operator access

| Task | Authority | Audit correlation |
| --- | --- | --- |
| Read a broker's service logs | Cluster access and the operator ID listed in `Kafdeck:BrokerHosts:LogReaderUserIds` | Actor, cluster, broker, log-read request and result |
| Install or upgrade an agent | Cluster access and the operator ID listed in `Kafdeck:BrokerHosts:AgentInstallerUserIds` | Actor, cluster, broker, operation ID, authorized dispatch, uncertain reply and observed recovery |
| Preview and apply a supported Kafka setting | Configuration read and alter authority for the target in the governed mutation runtime | Requester, target, mutation operation ID and readback outcome |

Assign log and agent permissions independently. Managed owners or managers can exercise registered-target configuration writes where enabled. The Kafka credential for that workflow needs the appropriate Admin API rights. Review the audit result by operation ID. Keep private keys, monitoring tokens, protected plans and raw service logs outside shared evidence.

## Recover the selected operation

| Fleet observation | Operator action |
| --- | --- |
| SSH response interrupted | Reopen the cluster under the account that dispatched the change. Check the saved operation and its last confirmed stage. If a restart intent was observed, keep the operation pending and inspect the service and its journal. |
| Kafka or replicas have not recovered | Open the selected broker's service logs. Restore the unit or container and verify cluster health and replica synchronization. Check the same operation again. |
| Kafka healthy and fresh metric pending | Check the configured monitoring instance, JVM agent and ingestion route. Restore the delivery path and check the same operation until a fresh metric matches the observed JVM start. |
| Broker health and fresh metric verified | Confirm the audit outcome. Recheck the next broker's current metadata, expected broker count and replica safety before staging another operation. |

Keep the protected recovery sidecar, data-protection keys and host operation journal. The last confirmed stage is historical and the current health display can report a later regression. An unavailable or inconsistent host observation keeps the operation pending when progress has already been confirmed. Fleet hides the retry control during post-dispatch recovery.

## One-broker pilot

Start with a read-only check of the target mapping, expected broker count, leader and replication state, full ISR and each affected partition's surviving ISR against `min.insync.replicas`. Review single-replica and internal partitions and save the sanitized preflight. Proceed only in the approved window with a safe target, a known package digest and a recovery owner. Record process and metric evidence for the selected broker and check that sibling start times are preserved. Run deliberate outages in isolated fixtures.
