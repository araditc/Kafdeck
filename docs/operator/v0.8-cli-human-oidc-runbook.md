# W67 human CLI browser sign-in

The CLI supports a per-command Authorization Code + PKCE sign-in. Access tokens
remain in memory for that command and are disposed with its HTTP client. There
is no token cache, password grant, client secret or browser-cookie forwarding.

Create a public profile outside secret material:

```json
{
  "issuer": "https://sso.example.test/realms/kafdeck",
  "audience": "kafdeck-api",
  "clientId": "kafdeck-cli",
  "trustedCaPemFile": "/operator/approved-ca.pem"
}
```

Omit `trustedCaPemFile` to use normal operating-system TLS trust. The optional
file supplies a specific root trust store; certificate chain and hostname
verification remain enabled. The profile accepts only those four public fields,
and requires an exact HTTPS issuer and explicit API audience. The API origin
also requires HTTPS except for numeric loopback laboratory origins.

```text
kafdeck --url https://kafdeck.example.test --oidc-profile public-profile.json system info
```

The default browser opens for sign-in. Stdout retains the existing JSON result
contract; credentials, authorization codes, ID/access tokens and PKCE verifier
are never printed. The profile cannot be combined with `--token-file` or
`KAFDECK_ACCESS_TOKEN`. Those remain legacy deployment credentials.

## Identity-provider registration

Register a public client with authorization-code flow only, S256 required,
implicit/direct-access grants disabled, `openid` enabled, and an audience mapper
that emits exactly the configured Kafdeck API audience in access tokens. The ID
token audience remains the public CLI client. Register numeric loopback redirect
`http://127.0.0.1/oauth/callback` using the IdP's supported ephemeral-port matching
rule; do not allow arbitrary hostnames, interfaces or callback paths.

The access token must also contain the stable human `sub` claim. In Keycloak,
removing all default client scopes can remove the access-token subject mapper
even while the ID token still contains `sub`. Retain the supported `basic` scope
or explicitly configure `oidc-sub-mapper` with `access.token.claim=true` in the
pinned realm. A subject present only in the ID token is insufficient: the CLI
and backend reject an access token without its own signed stable subject.

The CLI binds `127.0.0.1` on port zero before browser navigation and obtains the
actual bound port. It verifies the exact callback path, Host/port, unpredictable
state and issuer, tolerates at most eight rejected callback attempts, exchanges
the code once with its S256 verifier, and validates signed ID-token nonce plus
signed API-access-token issuer/audience/client/subject and original lifetime.
ID tokens are never sent to Kafdeck as API bearers. The flow has a three-minute
deadline; callback request size and per-connection lifetime are bounded.

## Backend registration and current permissions

Human CLI identities must be registered separately from automation service
identities in `Kafdeck:NonBrowserRead:HumanRegistrations`. Each entry has an exact
`Id`, `OwnerId`, `Subject`, `ClientId`, `Enabled`, `ExpiresAtUtc` and bounded
`ReadActions`. The global issuer/audience/CA configuration and default-off
`Enabled` flag are shared with the admitted non-browser trust profile.

An identical issuer/subject/client cannot appear in both human and service
registries. Backend authorization requires both the active registration and
current direct subject RBAC for the exact action/resource. IdP roles or groups
cannot add authority. Collection preflight does not replace per-resource
filtering. Audit identity distinguishes CLI humans from automation services;
neither creates a Kafdeck browser session or session cookie.

The initial human read inventory covers the typed existing CLI system, cluster,
topic, consumer-group and schema commands. Sensitive record/configuration reads
and unrelated routes are not implicitly admitted. Existing JSON, topic pagination
and API error categories are retained. An authenticated human with insufficient
scope receives the existing authorization error exit category.

## Governed effect admission

The first explicitly admitted effect family is TopicCreate, behind separate
default-off `Kafdeck:NonBrowserRead:GovernedMutationsEnabled` and per-registration
`MutationActions: ["TopicCreate"]`, together with current direct RBAC. The dedicated
`/api/v1/automation/...` routes use the existing planner and durable mutation
engine. They do not accept cookie or deployment credentials. Browser mutation
routes retain antiforgery checks.

Preview ownership binds the exact original issuer/subject/client/registration;
confirmation and physical dispatch recheck that identity, registration, current
resource permission, immutable preview, policy fingerprint and provider state.
CRITICAL operations remain `AwaitingApproval` until independently eligible human
approval. The same human cannot satisfy distinct approval by switching from CLI
to a browser session. An automation service is never converted into an operator
identity or used as a human approver. TopicDelete and separate human approval
admission are described in `v0.8-cli-critical-approval-runbook.md`; other mutation
families remain separate work.

The named first-family commands are:

```text
kafdeck --url https://kafdeck.example.test --oidc-profile public-profile.json topics create-preview dev orders-demo 1 1 --idempotency-key <unique-intent-key>
kafdeck --url https://kafdeck.example.test --oidc-profile public-profile.json operations confirm <operation-id> <preview-hash>
kafdeck --url https://kafdeck.example.test --oidc-profile public-profile.json operations execute <operation-id>
kafdeck --url https://kafdeck.example.test --oidc-profile public-profile.json operations status <operation-id>
```

Use the operation ID and exact preview hash returned by the backend, and provide
`--challenge` only when the returned confirmation requires that exact target.
Each command signs in independently; the stable registered identity owns the
operation across short-lived token changes. There is no generic HTTP path or
raw JSON body option. The CLI TopicCreate shape accepts 1–100000 partitions
and a positive bounded replication factor. Topic create/alter configuration,
partition increase, cancel and reject commands are documented in
`v0.8-cli-topic-lifecycle-runbook.md`; the backend retains all risk/current-state
checks and remaining provider acceptance is tracked separately.

Machine output remains the typed backend JSON. Exit categories distinguish
authorization (`3`), remote failure (`4`), transport (`5`), awaiting independent
approval (`6`), executing/unknown external effect (`7`), conflict/stale preview
(`8`), expiry (`9`) and partial/unverified effect (`10`). These states never
trigger an automatic execute retry. Query status and use the existing operator
recovery workflow for ambiguous effects.

This runbook describes implementation boundaries. Consult the G2 acceptance
evidence for the real IdP/provider cases that have actually passed; it does not
claim completion of W67 A1–A6 or authorize v0.8 publication.
