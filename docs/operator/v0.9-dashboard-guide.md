# v0.9 dashboard: Kafka connections and everyday operations

Complete [initial owner setup and Keycloak sign-in](managed-identity-setup.md) first. The unauthenticated UI shows setup/sign-in, not the cluster dashboard. Connection history belongs to the signed-in identity/browser and is not a saved password store.

## Register and select a Kafka cluster

1. Sign in as the initial administrator and open **Kafka connections**.
2. Enter a unique connection name, such as `Office Kafka`, and the bootstrap brokers as comma-separated `IP:port` entries. For a new registered target, all addresses must be in `ConnectionWorkspace.RegistrationNetworks`. Include every advertised broker address in the network/egress design. Preconfigured targets remain available to authorized users through the target selector.
3. Select `PLAINTEXT`, `SSL`, `SASL_PLAINTEXT` or `SASL_SSL`. Supply the mechanism and credentials when SASL is selected, and CA/client-certificate material required by the selected TLS profile. These are Kafka credentials, separate from Keycloak sign-in. The protocol/mechanism must match the broker listener.
4. Choose **Test connection**. A successful test reports actual broker/topic metadata. Failure does not create a usable cluster: check advertised listeners, firewall/egress, certificates, SASL and Kafka ACLs.
5. Save/register and open the successful connection. It is selected in the dashboard, appears in the cluster selector and opens **Topics**. This is a live management dashboard, not only the last test's metadata summary.
6. Use **Recent connections** to refill settings; re-enter secrets when required. Changing connection fields requires a fresh test. Grant other users the saved target in **Manage users**.

An owner may register new targets; other users can use targets assigned to them. Registration accepts at most 16 distinct bootstrap entries. Names, brokers, protocol and mechanism persist in managed identity state. Kafka credentials remain in the current session's server-memory lease for up to 30 minutes; they are not saved in browser history or the registered connection definition. After lease expiry/restart, reopen the connection workspace and test with credentials again. This differs from protected persisted credentials for optional HTTP services below.

Kafka may advertise changed addresses after registration. KAF-02 remains conditionally admitted **only with tested host/CNI egress**; CIDR input validation alone is insufficient. Verify an allowed connection succeeds and an out-of-CIDR destination is denied from the actual runtime. The release's K3s/kube-router evidence is not a blanket claim for other CNIs or Service DNAT. [Accepted boundary](../security/v0.9-w78-independent-review.md)

## Topics and manual messages

Choose a topic in **Topics** to inspect partitions, leaders/replicas and live configuration. The topic's **Messages** view performs bounded reads by partition/offset/time and supports the configured projections, masking and export permissions. Browsing does not commit a consumer group's offsets.

Use **Publish message** to enter the key/value/headers, review the exact preview and submit when authorized. Record the acknowledged partition/offset. If the outcome is unknown, inspect/reconcile the operation before retrying; do not assume a timeout means the message was not sent.

Topic create/configuration/partition changes, delete and purge remain governed operations. Enabling sign-in or registering a cluster does not automatically enable mutations. See [controlled administration](v0.5-safe-administration-guide.md). Critical operations require a different authorized account's approval.

## Consumer groups

Open **Consumers**, select a group, and inspect its state, members, assignments, committed/end offsets and lag per partition. Missing commits or unavailable metrics are shown explicitly. To reset offsets, inspect the requested target and preview, verify that group activity permits the operation, then follow the governed confirmation/approval flow. Use a disposable group when validating a new installation.

## Schema Registry

As owner, select the registered cluster, open **Schemas** and **Configure Schema Registry**. Enter its base URL, choose no authentication, Basic or Bearer, provide credentials and use **Test connection** before saving. Authenticated non-loopback endpoints require HTTPS; the endpoint's resolved addresses must be allowed by the installation network policy and its certificate trusted by the runtime.

Select a Subject, version and schema content. To add a version, choose the schema type, enter its content/references, run the compatibility check and inspect the result before registration. Compatibility success is not write authorization. Registration and destructive lifecycle actions retain their current capability, mutation and approval checks.

## Kafka Connect

In **Ecosystem**, choose **Configure Kafka Connect** for the selected registered cluster. Test and save its base URL and authentication. Inspect connector status, tasks, traces and sanitized configuration. Create a connector using an installed plugin and valid configuration; use the validation/preview flow, then inspect task status after execution.

Update configuration or use Pause, Resume, Restart/task restart and Delete only where the provider and current mutation policy support them. Secrets remain redacted. A Kafka bootstrap address is not a Connect REST address. Connect must be deployed separately; adding Kafka does not install it. Static multi-profile configuration remains documented in [README](../../README.md#optional-kafka-connect).

## ksqlDB: Streams, Tables and SELECT

Configure/test/save the selected cluster's ksqlDB URL and authentication in **Ecosystem**. Refresh the catalog to list Streams and Tables. ksqlDB is an external service, not embedded in Kafdeck.

The query panel accepts bounded read-only SELECT. Choose **Only new messages** for events arriving after the query starts, or **Read from beginning** for existing retained events. A successful query with no rows does not prove an earlier message was read.

To verify an actual record, use a disposable stream:

1. As owner, use **Create Stream**, select its topic/format/columns and submit. Inspect creation status and refresh the catalog. Direct creation is available only with inactive governance/policy and a verified matching Kafka cluster ID.
2. In that topic's **Publish message** form, send a uniquely identified JSON value, for example `{"message":"kafdeck-docs-probe-1"}`, matching the stream columns. Save the acknowledged partition/offset.
3. Return to ksqlDB, select **Read from beginning**, and run `SELECT * FROM YOUR_STREAM EMIT CHANGES LIMIT 1;`. For a nonempty topic, use a suitably bounded SELECT/filter that selects the unique probe. Confirm the message value itself appears in the result.
4. For **Create Table**, define the required primary key and compatible key/value formats. Publish a matching nonempty Kafka key and value to its topic, then inspect the table through a bounded SELECT. Keep a delete/tombstone distinct from an empty value.
5. Cancel a running query when finished. Clean up disposable resources through the authorized lifecycle; never delete an existing business topic as test cleanup.

An active governance generation or enabled policy blocks this direct Stream/Table creation path. General SQL DDL/DML is not enabled through the read-only SELECT editor. Service failure, cluster-ID mismatch or an uncertain write outcome must be resolved before retrying creation.

## Settings, persistence and navigation

The owner configures registered HTTP endpoints; read access and writes remain scoped. URL/authentication settings persist in the private managed state. Basic/Bearer secrets are ASP.NET Data Protection-protected and are not returned to the browser. On edits, leaving credentials blank retains them only when the endpoint/authentication still match; re-enter credentials when changing those fields or after loss of the matching key ring.

Each navigation item renders its own dashboard page: Overview, Brokers, Topics, Consumers, Schemas, Ecosystem, Fleet, Automation, Ownership catalog, Governance policy, Requests and Measured attribution. Changing the selected cluster changes the scope; asynchronous refresh should preserve the current page/form, with explicit errors instead of silently substituting another cluster.

Catalog, policy, requests and attribution workflows are described in [catalog/policy contracts](../api/v0.9-catalog-policy-runtime.md) and [request/attribution contracts](../api/v0.9-requests-attribution-runtime.md). Attribution records measurements and estimates; it is not a billing or payment system. CLI, Terraform and MCP retain the same current authorization and approval boundaries.
