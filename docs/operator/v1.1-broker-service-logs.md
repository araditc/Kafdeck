# Broker service logs in Kafdeck 1.1

The Brokers page can read a time window from a broker's verified systemd unit or Docker Compose container. Start with [host registration and broker binding](v1.1-broker-host-registration.md).

## Grant access

1. On each host, update the restricted helper. Use the current `tools/broker-host/install.sh` for a new host. For a host with an older discovery-only helper, run `sudo sh tools/broker-host/upgrade-logs.sh` from the checked-out source. Existing SSH keys and broker services are kept in place.
2. In the root-owned `/etc/kafdeck/host-targets.json` catalog, add `"logs": true` to each existing service entry approved for log reads. Only enable units or containers whose journal or standard output is appropriate for the selected operators. A service that logs only to private files needs a supported service log configuration before it can be observed.
3. In the Kafdeck server configuration, grant the dedicated log permission to the selected managed user IDs. Use the Keycloak ID of the Kafdeck managed account. These are the IDs returned to the owner by the managed users inventory. Existing cluster access is also required. An owner needs the explicit log grant as well.

Example under `Kafdeck:BrokerHosts`, alongside the existing host networks and credential aliases.

```json
{
  "LogReaderUserIds": ["9fabe09a-f3c0-4e1b-b760-0cb299c8b6fc"],
  "LogSources": [
    {
      "ClusterId": "office",
      "BrokerId": 1,
      "MonitoringInstance": "office-broker-1"
    }
  ]
}
```

Replace `office` with the Kafdeck cluster ID. For a dashboard-registered connection, use its `connection-…` ID. `LogSources` is optional and adds an alert link for an exact monitoring instance in that cluster. Configure a unique mapping per broker and confirm the agent reports under that instance. Cluster-wide alerts and unmapped instances have no broker log link.

## Diagnose a broker

1. Select a cluster and open **Brokers → Broker service logs**. You can also open a broker from its verified binding in Fleet.
2. Choose the broker and enter start and end times in UTC. Select **Read service logs**.
3. From **Monitoring → Alerts**, select **Open broker logs** on a mapped alert. It opens the same view around the alert event, starting five minutes before the event. For a recent alert the end is capped at the current time.
4. If the limit is reached, narrow the time range. An empty window means no entries were returned within that range. Check the unit or container log configuration if a known event is missing.

The window is at most one hour within the last 48 hours. One response returns up to 200 entries and about 48 KiB of encoded log rows. The helper enforces a separate raw byte cap and a 10-second deadline. For systemd the source is the local journal for the exact registered unit. For Compose it is the Docker log stream of the running container verified against its project, service and Kafka identity.

Entries containing recognizable passwords, tokens, cookies, authorization values, credential URLs, key material markers or control characters are replaced with `[REDACTED]`. Configure applications to keep secrets out of service logs, since a value with no recognizable pattern cannot be reliably identified. The response is marked no-store. Audit records contain the account, broker, result and correlation ID. They do not store the log body.

If a service stops, changes during the read or no longer matches the registered broker and current Kafka cluster metadata, Kafdeck discards the result. Verify the binding and approved log source in Fleet before retrying.
