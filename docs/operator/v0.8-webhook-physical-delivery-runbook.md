# W66 opt-in physical Webhook delivery

This slice adds a hosted sender for server-owned typed HTTPS Webhook
profiles. `Kafdeck:Notifications:WebhookDeliveryEnabled` defaults to `false`.
Observation and subscription management remain independent opt-ins.
This is partial N1 laboratory evidence; N2–N5 and complete W66 acceptance remain open.

## Admission and operation

Enable notification persistence and OIDC operator access using the observation
runbook first. Configure at least one exact server-owned `Webhook` destination
with a normalized HTTPS endpoint and approved event classes. Authentication must
be explicitly `Anonymous` (the compatible default) or `Bearer`. Then explicitly set
`WebhookDeliveryEnabled=true`. The host rejects HA mode, profiles with implicit
credential semantics, and activation with notification persistence disabled.
Other active provider families require their own separate explicit delivery
flags; inactive profiles may remain in the catalog. See the
[six-provider delivery runbook](v0.8-notifier-provider-delivery-runbook.md).
Bearer profiles require an exact configured binding and server-owned `env:` or
absolute mounted `file:` reference. There is no anonymous fallback for a missing,
disabled, revoked, invalid, overlong or unreadable credential. The admitted Bearer
token grammar is bounded to 4096 ASCII token characters; arbitrary headers,
Basic/HMAC schemes and caller-selected authorization syntax are unsupported.

## Authenticated profile and credential lifecycle

The server-owned destination accepts `WebhookAuthentication=Bearer`,
`CredentialBindingId=<opaque-versioned-id>` and optional `Enabled=false`.
Its matching `CredentialBindings` entry has `DestinationId`, `BindingId`,
`SecretReference` and optional `Enabled=false`. Values remain secret references;
never put an actual token into source, profile JSON, support output or screenshots.
The worker resolves the admitted reference only at dispatch and attaches the
credential only as the private HTTP `Authorization: Bearer` header.

For a governed rotation, provision a new secret version, change the opaque
binding ID (for example `ops-webhook-v1` to `ops-webhook-v2`) and update its exact
server-owned reference. Restart with the new configuration after the owner has
reviewed the destination and credential changes. The profile fingerprint includes
the authentication mode and binding ID: pending work routed under the old
revision becomes `UnknownExternalEffect`, never retargeted or blindly resent.
Create new approved events under the newly admitted profile to prove delivery.
Changing only mounted-file contents intentionally preserves the binding identity
and makes subsequent resolutions read the new value; it does **not** invalidate
pending intents. Prefer versioned binding rotation when pending-work fencing is
required.

Disable a destination with `Destinations:<index>:Enabled=false` and restart; new
routing skips it and its pending delivery cannot send. Disable/revoke a binding
with `CredentialBindings:<index>:Enabled=false` and restart; credential resolution
fails closed before any socket. Remove the referenced mounted file or revoke the
provider-side token to cut off later resolution/delivery. A token already read or
an in-flight physical request cannot be recalled by a file/config edit. This slice
does not claim hot cross-node revocation, a governed runtime profile mutation API,
or atomic cancellation of an external side effect.

Default enabled anonymous profiles keep their original revision fingerprint
byte-for-byte. Explicit Bearer authentication or disabled state changes it.

Production registration uses system DNS and the socket dialer. Each request
retains its configured hostname for TLS/SNI and Host, validates the complete DNS
snapshot against the public-address policy, and connects only to a fresh approved
IP pin. Redirects, proxy use, cookie handling, arbitrary headers, arbitrary paths,
private/loopback/metadata IP destinations and response-body persistence remain
prohibited. The TLS stack validates the platform certificate chain and hostname.
No production configuration can replace the DNS lookup or dialer with the test
fixture mappings, and no certificate verification callback is installed.

Configured Webhook paths can themselves contain confidential material. The
transport writes bounded HTTP/1.1 directly over the approved pinned TLS stream;
HttpClient EventSource and Activity instrumentation never receives the private
request URI or Authorization header. Telegram uses the same private wire for its
protocol-required token path. No process-wide telemetry suppression is used.
Laboratory tests install real EventSource and Activity listeners, prove both
listeners observe a separate nonsecret canary, and check actual TLS sends for
credential/path leakage using safe boolean assertions.

Create scoped subscriptions through the existing governed management API.
Server-authored approved event projections can be routed through
`NotificationRoutingCoordinator`; arbitrary event payloads are rejected by the
durable routing store. This slice does not connect every product event producer.
The hosted service scans a bounded due page each second and retains the worker's
existing per-destination durable rate, concurrency, payload and retry budgets.
Each complete dispatch has a 20-second default deadline covering event/profile
reads, DNS and HTTPS; the HTTP transport's own 15-second limit remains in place.
The dispatch deadline is always shorter than the stale-claim recovery threshold.
A deadline produces terminal `UnknownExternalEffect`, requests cancellation and
allows the worker cycle to finish even if an asynchronous resolver ignores it.
Late DNS completion cannot start an HTTP send because the adapter checks the
cancelled dispatch token before transport.

Outstanding dispatch tasks, including timed-out tasks that ignore cancellation,
retain an admission slot until they actually finish. Their total is bounded by
the configured worker delivery concurrency across cycles. If every slot remains
occupied, further work stays `Pending` without incrementing its attempt count;
it resumes when capacity returns. Cancellation is not proof that an underlying
noncooperative operation stopped, and it never authorizes an automatic replay.

Read delivery evidence through the existing scoped observation API. A successful
physical 2xx response becomes `Delivered` with event ID, destination ID, payload
fingerprint, attempt count and the canonical safe outcome in the durable ledger.
Provider response bodies and headers are not retained.

If the process stops after claiming a row, recovery classifies a stale `InFlight`
row as `UnknownExternalEffect` after the existing two-minute threshold. An
ambiguous send is never automatically returned to the due queue. Reconcile the
external effect before any operator-approved follow-up; do not reset it to
`Pending` or blindly replay. Disable the opt-in and restart to stop admitting new
sends; already delivered effects remain in the ledger.

## Repeatable physical laboratory

Run from the repository root with the installed .NET 10 SDK:

```powershell
dotnet test tests/Kafdeck.Architecture.Tests/Kafdeck.Architecture.Tests.csproj --no-restore --filter FullyQualifiedName~V08W66HostedWebhookTlsTests --logger "console;verbosity=normal"
```

`Hosted_worker_physically_posts_with_verified_tls_and_persists_receipt` starts a
real Generic Host with the same DI extension and hosted worker as the API. It
persists an approved event and subscription in SQLite, performs an actual HTTPS
POST over TCP to an isolated TLS provider, verifies configured SNI/Host and JSON
event identity, receives HTTP 204, and reopens the store to verify `Delivered`.

The laboratory substitutes only DNS observation and TCP routing: a policy-valid
`1.1.1.1` pin is routed by a test-only dialer to an isolated loopback listener.
It does not connect to that public IP. HTTP/TLS are physical; HTTP responses are
not produced by a mock HTTP handler. The ephemeral private CA is trusted only by
that fixture's client chain policy; hostname, EKU, expiry and certificate checks
remain active. No private key, CA certificate or local trust-store change persists.
This proves host-to-ledger transport behavior, not public network reachability.

The interrupted-send case stops the first host after the provider reads the full
POST but before a response, verifies durable `InFlight`, restarts with the same
SQLite database and advances the worker's test clock past the recovery threshold.
It verifies `UnknownExternalEffect`, one physical POST and zero automatic resends.
Additional physical TLS negatives reject a wrong hostname and an untrusted CA
before HTTP reaches the provider. A physical HTTP 302 to a loopback destination
is not followed and retains `UnknownExternalEffect` after one attempt: a redirect
does not prove the recipient performed no side effect.
Existing pin, SSRF, exact-origin,
credential, rate, concurrency and payload tests remain required regression gates.

The authenticated fixture `V08W66AuthenticatedWebhookTlsTests` additionally proves
two physical Bearer POST acknowledgements across a versioned binding rotation,
old-intent fencing, disabled/revoked/missing-secret denial and absence of credential
material in event bodies and ledger files. Tests generate credentials in disposable
local storage and report only safe booleans/counts.

The fixture is a local transport laboratory. It is not evidence of six-provider
acceptance, PostgreSQL/HA recovery, complete credential governance, deployment
owner production admission, protected-main integration or release readiness.
