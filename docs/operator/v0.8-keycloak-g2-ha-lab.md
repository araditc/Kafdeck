# G2 genuine two-node Keycloak laboratory

This disposable Windows laboratory uses the already verified Keycloak **26.8.1**
ZIP and Temurin **21.0.12.1+1**, two independent runtime directories, the G2 realm
and TLS/client keys, and the separate PostgreSQL **17.11** `g2_keycloak` database.
No Docker, Windows service, public network listener or OS certificate-store
change is required. Runtime files and credentials remain under ignored
`deploy/dev/.generated/g2/keycloak-ha`.

## Prepare

First prepare the ordinary G2 identity fixture with `prepare-keycloak-g2.ps1`
and the portable PostgreSQL fixture with `prepare-postgres-g2.ps1`. Then run:

```powershell
./deploy/dev/prepare-postgres-g2.ps1 -Action Start
./deploy/dev/prepare-postgres-g2.ps1 -Action PrepareKeycloak
./deploy/dev/start-keycloak-g2-ha.ps1 -Action Prepare
./deploy/dev/start-keycloak-g2-ha.ps1 -Action Start -Node node-a
```

The launcher verifies the original Keycloak archive SHA256
`4cd312c889af358a819a74a6c6f068f9ea159a6959e49924607cec95cfd4c1a4`
before extracting either runtime. A fresh shared database imports the realm on
node A. Wait for its verified HTTPS discovery to become ready before starting B:

```powershell
curl.exe --fail --cacert deploy/dev/.generated/g2/identity/ca.pem `
  https://localhost:19443/realms/kafdeck-g2/.well-known/openid-configuration
./deploy/dev/start-keycloak-g2-ha.ps1 -Action Start -Node node-b
```

The identity manifest must pin its own existing `realmImportFile`. The launcher
copies that exact realm file and rejects a missing pin; it never takes an import
from a shared mutable Keycloak runtime directory. Keep each fixture's realm,
keys, and manifest together when preparing another identity laboratory.

The database password and PKCS#12 password are read inside the hidden child
process into environment variables. They are never process command arguments.
Each node gets a separate log and recorded launcher PID/start time; stopping a
node targets only that recorded process tree. The launcher does not reset a
database or silently refresh imported identities.

| Node | HTTPS endpoint | Cluster bind | Failure detector |
| --- | --- | --- | --- |
| `node-a` | `https://localhost:19443` | `127.0.0.1:7800` | `127.0.0.1:57800` |
| `node-b` | `https://localhost:19444` | `127.0.0.1:7810` | `127.0.0.1:57810` |

Both nodes use the exact canonical issuer
`https://localhost:19443/realms/kafdeck-g2`, audience `kafdeck-api-g2`, shared
PostgreSQL database, distributed `ispn` caches and `jdbc-ping`. Embedded cluster
mTLS remains enabled with automatic certificate management. Per-node database
pools are limited to 2–8 connections. See Keycloak's official
[distributed cache guide](https://www.keycloak.org/server/caching) and
[configuration reference](https://www.keycloak.org/server/all-config).

## Required proof

Verify trusted HTTPS discovery on **both** endpoints and exact issuer equality.
Require a two-member ISPN view and completed rebalance in both node logs; two
independent local-cache processes are insufficient. Generated `ha-lab.json`
contains safe endpoints and file references for the acceptance harness.

The local 2026-10-16 setup observed both trusted HTTPS endpoints, matching issuer,
two-member cluster views, loopback TCP addresses and JGroups certificate reload.
Sanitized topology evidence is `artifacts/g2/keycloak-ha-topology-evidence.json`.
Topology startup alone does not accept assertion replay, key rotation, rolling
upgrade or A6. Actual replay tests must synchronize identical first-use assertions
across both nodes, require exactly one exchange to succeed, deny consumed
assertions on either node, and repeat after restart while the original assertion
remains valid. Never extend production assertion lifetime merely to pass a slow
restart, and keep token/assertion/password bytes out of evidence.

```powershell
./deploy/dev/start-keycloak-g2-ha.ps1 -Action Status
./deploy/dev/start-keycloak-g2-ha.ps1 -Action Stop -Node node-b
./deploy/dev/start-keycloak-g2-ha.ps1 -Action Start -Node node-b
./deploy/dev/start-keycloak-g2-ha.ps1 -Action Stop
```

This proves only the tested local topology. External load balancers, PostgreSQL
replication/failover, supported version upgrades and production trust admission
require their own acceptance evidence.
