# Install and operate the Kafdeck v0.9 candidate

Kafdeck 0.9.0 is available for evaluation from source and from the retained CI artifacts. The published version is listed in [GitHub Releases](https://github.com/araditc/Kafdeck/releases). Use the [v0.8 installation instructions](../../README.md#getting-started) for the released image. The v0.9 candidate still needs final platform, offline-install and release approval.

## Choose an installation path

| Path | Use it for | What you need |
| --- | --- | --- |
| Build the container locally | An evaluation on a developer workstation | Git, Docker, and access to the build dependencies |
| Load a retained container | An evaluation of the exact CI build | Docker, the Linux amd64 or arm64 archive, and access to its build evidence |
| Run from source | A native Windows, Linux, or macOS development environment | The .NET SDK selected by [global.json](../../global.json), Node.js 24, and npm |
| Install the chart | A Kubernetes evaluation with an external Kafka cluster and identity provider | Helm, a verified image digest, a namespace with working NetworkPolicy, and the configuration and storage below |

The [distribution matrix](../operations/v0.9-distribution-recovery.md#componentplatform-admission-matrix) distinguishes tested scenarios from support still awaiting admission. Build success alone does not establish support for a self-contained binary on a platform.

## Run a local container

Check out the candidate revision recorded with the evidence. Build it with Docker from the repository root.

```sh
git clone https://github.com/araditc/Kafdeck.git
cd Kafdeck
git checkout --detach ba00168341d75e67ec2b05a0de6fc616700ff688
docker build -t kafdeck:0.9.0-candidate .
```

To use the CI build, download the archive for your architecture from the [candidate build](https://github.com/araditc/Kafdeck/actions/runs/42899843799). Compare its SHA256 with `archiveSha256` in the accompanying `oci-native-startup.json` before loading it. Use `sha256sum` on Linux, `shasum -a 256` on macOS, or `Get-FileHash -Algorithm SHA256` in PowerShell. This verifies the retained bytes. Official signature verification is a separate step for production or offline media.

```sh
docker image load --input kafdeck-linux-amd64.docker.tar.gz
docker image tag kafdeck:w81-fixture kafdeck:0.9.0-candidate
```

Use the arm64 filename on an arm64 Docker host. For a loopback-only evaluation, first [start the demo Kafka broker](../../README.md#1-start-a-container-reachable-kafka-for-evaluation) or substitute a broker reachable from the container. Set the deployment token in the current shell, then run:

```sh
export KAFDECK_DEPLOYMENT_TOKEN="$(openssl rand -hex 32)"
docker run --rm --name kafdeck --network kafdeck-demo \
  --publish 127.0.0.1:8080:8080 \
  --env KAFDECK_DEPLOYMENT_TOKEN \
  --env Kafdeck__Deployment__ListenUrls__0=http://0.0.0.0:8080 \
  --env Kafdeck__Deployment__AccessMode=Token \
  --env Kafdeck__Deployment__AccessToken=env:KAFDECK_DEPLOYMENT_TOKEN \
  --env Kafdeck__Clusters__0__Id=local \
  --env Kafdeck__Clusters__0__BootstrapServers__0=kafdeck-kafka:19092 \
  --env Kafdeck__Clusters__0__SecurityProtocol=Plaintext \
  kafdeck:0.9.0-candidate
```

Open `http://127.0.0.1:8080/#access_token=YOUR_TOKEN` with the generated token in the fragment. Check `http://127.0.0.1:8080/healthz`, then open **Topics** and verify a known topic. A healthy HTTP listener alone does not verify Kafka or login.

For a native run, follow the [Windows and Unix source instructions](../../README.md#building-from-source) after checking out the candidate revision. For persistent installations, mount configuration and secrets read-only and place writable state on a dedicated volume. The preceding container command is an evaluation with disposable application state.

## Configure sign-in and Kafka

For a shared installation, use HTTPS with a trusted certificate, an [OIDC client and role bindings](v0.2-oidc-rbac-guide.md), and a Kafka identity scoped to the required clusters. Confirm that the browser can reach the identity provider and that the API can reach its discovery and JWKS endpoints. Store credentials using [server-side secret references](../../README.md#secret-references).

- For **managed Keycloak**, follow the [initial administrator and user setup](managed-identity-setup.md). Issue the one-time setup code from the configured host, create the first administrator, then sign in and grant users access to the relevant clusters.
- For **externally managed OIDC**, assign role and cluster bindings in the deployment configuration before testing sign-in. Use a viewer account to confirm read-only access separately from an operator account.
- For a **registered Kafka connection**, enter the bootstrap brokers and security settings, test the connection, then save it and select it in the dashboard. Use a TLS configuration and the broker's SASL mechanism where required. Approved CIDRs and host egress rules must cover the intended brokers, including their advertised addresses.
- In **Topics** and **Consumers**, use previews before publishing a test message, resetting offsets, or applying administrative changes. Use a disposable topic and group when checking a new installation. The [governed administration guide](v0.5-safe-administration-guide.md) covers confirmation and approval.
- Configure [Schema Registry](../../README.md#optional-schema-registry), [Kafka Connect](../../README.md#optional-kafka-connect) and [ksqlDB](../../README.md#optional-ksqldb) only for clusters that use them. Verify the service address and identity before registering a schema or changing a connector. Start ksqlDB verification with a bounded read-only SELECT.

For integrations, use the [human CLI sign-in guide](v0.8-cli-human-oidc-runbook.md) or the [MCP operator guide](v0.8-mcp.md). Their authentication flows carry forward. Use the package version and SHA256 recorded for the candidate instead of the v0.8 example package versions.

## Install with Helm

Use `kafdeck-0.9.0.tgz` from the [Helm lifecycle artifact](https://github.com/araditc/Kafdeck/actions/runs/42899843799). Check its SHA256 against `chartSha256` in `helm-lifecycle.json`. Import the verified image into a registry reachable from the cluster and use the digest for the image in that registry.

Prepare the following objects in the target namespace before installing:

| Chart values | Required input |
| --- | --- |
| `image.repository`, `image.digest`, `image.pullSecret` | The registry repository, verified digest, and optional existing pull secret |
| `publicHost`, `oidc.issuer`, `oidc.clientId` | The HTTPS host, trusted issuer, and configured browser client |
| `operatorConfigMap` | A ConfigMap containing `appsettings.Production.json` |
| `credentialsSecret`, `tlsSecret` | Existing Secrets for credentials and for the `tls.pfx` and `tls-password` keys. PostgreSQL requires a `postgres-connection` credential key. |
| `kafka.clusterId`, `kafka.bootstrapServers`, `kafka.protocol` | The cluster ID and broker addresses using `Ssl` or `SaslSsl` |
| `persistence.provider`, `persistence.existingClaim` | `Sqlite` or `PostgreSql`, and a precreated writable claim. The candidate chart runs a single replica for either provider. |
| `network.ingressNamespaces`, `network.egress` | The approved ingress namespaces and egress CIDRs and ports for the identity provider, brokers, database and enabled services |

Set these values in `kafdeck-values.yaml` using the [chart schema and defaults](../../deploy/helm/kafdeck/values.yaml). Keep credential values out of that file. The chart exposes a ClusterIP Service on port 443. Configure the route to it separately and preserve the configured host and HTTPS.

```sh
helm template kafdeck ./kafdeck-0.9.0.tgz --namespace kafdeck --values kafdeck-values.yaml
helm upgrade --install kafdeck ./kafdeck-0.9.0.tgz \
  --namespace kafdeck --values kafdeck-values.yaml --wait --timeout 5m
kubectl --namespace kafdeck rollout status deployment/kafdeck-kafdeck --timeout=5m
```

Check HTTPS health through the configured host, sign in, and verify Kafka metadata with the intended role. Check that the namespace enforces the expected egress rules before admitting external broker connections.

To remove an evaluation release, run `helm uninstall kafdeck --namespace kafdeck`. The precreated claim and configuration objects remain in the namespace. Keep them with the backup until recovery has been verified.

## Upgrade, roll back, or install offline

1. Record the running version, image digest, configuration, persistence provider, and status of outstanding operations. Schedule maintenance and stop the old application and background writers before starting the candidate.
2. Make a verified database backup and test its restore separately. For SQLite, use a consistent backup and include the matching application state. For PostgreSQL, record the backup and recovery point. Keep the matching Keycloak realm and managed identity state where applicable.
3. Start the candidate against a restored copy first. Verify migration, sign-in, read access, and the recorded state of pending or uncertain operations. Admit a fresh generation in quarantine when required by the [restore procedure](../operations/v0.9-distribution-recovery.md#upgrade-and-restore).
4. If the upgrade fails, stop the candidate. Restore the verified pre-upgrade backup into an isolated location and restart with the original binary and configuration. Resolve uncertain external effects before dispatching the operation again.

For a disconnected deployment, stage the image, chart, platform packages, dependencies, SBOM, provenance and signatures together. Verify the signed manifest with the approved trust material before transfer and again inside the enclave. Confirm that private DNS, Kafka, the database and OIDC can be reached locally. The [air-gap procedure](../operations/v0.9-distribution-recovery.md#air-gap-and-supply-chain) describes admission for final signed media.

## Troubleshoot the first start

| Symptom | Check |
| --- | --- |
| Browser cannot open the UI | The bind address, port mapping, allowed host, HTTPS certificate and mounted configuration |
| Sign-in loops or returns unauthorized | The configured issuer, certificate trust, browser client redirect settings and the user's role and cluster bindings |
| Kafka metadata works but topics or groups fail | The advertised listener addresses as seen by Kafdeck, egress policy, TLS/SASL, and Kafka ACLs |
| Kubernetes pod fails to start | Pod events, exact image digest and pull secret, ConfigMap key, TLS Secret, claim permissions, and the persistence configuration |
| An operation stays uncertain | The recorded operation status and provider evidence. Reconcile the effect before a retry. |
