# W66 Notification Observation — Operator Activation and Recovery Runbook

> **Scope:** v0.8 work-in-progress, **read-only** notification observation surface.
> This is a governed operational procedure, **not** authorization to publish v0.8
> or to enable delivery workers, provider transports, subscription management,
> or arbitrary outbound webhooks.

## 1. Safety and authority

- `Kafdeck:Notifications` is absent/disabled by default. With it disabled,
  notification persistence is **not initialized** and routes are not mapped.
- Enabled notification observation requires `Kafdeck:Deployment:AccessMode=Oidc`,
  a valid logged-in operator, an applicable **scoped** `NotificationRead` grant,
  and resource-scoped `NotificationRead` for **both** a subscription and its
  destination. The collection preflight accepts a matching **scoped** grant;
  do **not** add a separate unscoped grant just to make listing work. An
  unscoped grant also permits every subscription/destination, so grant it
  only for intentionally global notification readers. Delivery detail
  requires destination authorization.
- A browser's tab-visible Notifications section is **not** an authorization
  decision: every API call is authorized by the backend. A 401 clears retained
  notification UI state; returning to the browser tab revalidates the session.
- No write/management REST surface or notification worker is activated by this
  configuration. Neither a token-only deployment nor a local-mode operator may
  use notification observation.
- Sensitive provider request IDs, raw event bodies/headers, passwords, webhook
  URLs and credential values must not be surfaced through these APIs, UI
  screenshots, support tickets or log exports.

## 2. Configuration checklist

The deployment's `Kafdeck:Notifications` configuration is parsed into:

| Key | Read-only contract |
| --- | --- |
| `Enabled` | `false` unless intentionally admitted by the operator |
| `Provider` | `Sqlite` (standalone) or `PostgreSql` (standalone/HA) |
| `ExecutionMode` | `Standalone` or `HighAvailability` |
| `SqliteDatabasePath` | Absolute path for SQLite only; never share one SQLite store across HA nodes |
| `ConnectionString` | Secret reference for PostgreSQL only; no plaintext in source or telemetry |

The validator rejects SQLite HA, a relative SQLite path, SQLite with
PostgreSQL credentials, PostgreSQL without a secret-referenced connection
string, mixed provider credentials and enabling observation outside OIDC
mode. When disabled, do **not** leave a notification database path or
credential configured. Keep database data and backups separate from Kafka
broker state and protect them as control-plane material.

Before enabling: confirm the operator IdP/roles, database version and backup,
configuration ownership, and a **documented, executable, authorized**
rollback/reconciliation plan. If there is no available procedure for legacy
unresolved deliveries, **stop admission and escalate** rather than inventing
one. Use a
single-instance SQLite layout only for standalone operation. Confirm the
PostgreSQL connection secret is resolved only by the server and points to the
correct approved environment.

## 3. Startup admission and database upgrade

The notification startup path initializes/preflights the **delivery ledger
first**, then the routing/subscription store. The order is mandatory: the
delivery preflight rejects an unresolved legacy v1 delivery before routing
v1→v2 schema migration commits. Reversing the order can strand an existing
v1 runtime behind a partially upgraded routing database.

1. Stop writes and take a restorable database backup/snapshot with schema
   version and queue-state evidence.
2. Inventory v1 `Pending`, `Failed` and `InFlight` delivery records,
   including ambiguous external effects. **Never silently delete** them.
3. If unresolved v1 records exist, **stop the upgrade with Notifications
   disabled**, retain the compatible data/binary and backup, and escalate to
   the W66 owner/security/operations incident process. The current Kafdeck
   host exposes **no notification delivery worker, drain/reconciliation API,
   or executable v1 queue-clearance procedure**; do **not** represent one as
   available. A separately reviewed, executable reconciliation procedure
   with evidence of provider effect, idempotency and authorization is a
   prerequisite to resuming this upgrade. Do not clear rows, resubmit
   ambiguous deliveries, or create a new store as a workaround.
4. Start the new binary with Notifications disabled; validate ordinary
   cluster/record read behavior and authentication first.
5. Enable Notifications only with the approved provider, mode and database.
   Fail-closed startup on schema/secret/connection errors is an expected
   protective outcome; do not fall back to ephemeral in-memory stores.
6. Check initial database readback and the specific resource-scoped operator
   roles before exposing the UI. For HA, verify that all nodes use the same
   supported PostgreSQL schema and approved secret reference.
7. Record config version, application revision, schema revision, operator
   role/scoping proof and successful smoke checks in the deployment record.

An unresolved old delivery may correspond to a real external provider action.
Never resubmit it blindly. Respect the durable ledger's
`UnknownExternalEffect` and revision-binding protections.

## 4. Read-only smoke and authorization tests

The admitted endpoints are:

- `GET /api/v1/notifications/subscriptions` — bounded, default 50 and hard
  maximum 500; optional `maxResults`, `afterSubscriptionId`, `state`
  and `eventClass` filters.
- `GET /api/v1/notifications/subscriptions/{subscriptionId}` — one
  permission-checked subscription snapshot, including exact `eventTypes`.
- `GET /api/v1/notifications/deliveries/{notificationId}/{destinationId}`
  — metadata-only ledger status (state, attempts, revision, timestamps,
  outcome code and whether destination revision is bound).

Verify with separate test identities:

1. **Disabled:** notification URLs are not registered and no notification
   persistence startup occurs; the navigation item remains absent.
2. **OIDC missing:** enabling observation fails config validation; no
   Local/Token fallback can disclose subscription/ledger metadata.
3. **No applicable scoped grant:** subscription listing is denied **before**
   persistence access. A scoped `NotificationRead` grant is sufficient for
   collection preflight but does not bypass per-resource checks. Do not add
   a global/unscoped grant to make a restricted operator's list visible.
4. **Resource-scoped grant:** subscription detail requires authorization on
   its ID **and** its destination; ledger detail requires destination access.
   A hidden ID must not become discoverable through a 403-vs-404 oracle.
5. **Partially authorized page:** `authorizationFiltered=true` indicates
   an incomplete result. When the server marks
   `continuationRestricted=true`, the UI must not show, store, fabricate
   or submit an inaccessible raw continuation ID.
6. **Session expiry/cross-tab logout:** a 401 hides the operator identity
   and all retained notification observation. Restoring tab focus rechecks
   OIDC before any previously authorized panel can reappear.
7. **Projection:** assert no provider request IDs, payloads, raw headers,
   secrets, addresses, webhook target URLs or transport bodies are returned.
8. **No writes:** absent write routes must not be interpreted as a partially
   functioning management API; do not bypass them through direct DB edits.

Use test fixtures/synthetic delivery identifiers. The UI's delivery lookup
requires the exact notification UUID and authorized destination ID and does
not support unbounded search.

## 5. Incident response and rollback

- **401 / stale identity:** remove cached operator-visible evidence, renew the
  IdP session through normal login, and reapply all resource RBAC checks.
- **403 / restricted resource:** verify the exact scoped subscription and
  destination `NotificationRead` grants with the security owner. Collection
  preflight derives admission from any applicable scoped grant; **no separate
  unscoped collection grant is required**. Never broaden to wildcard/global
  roles as a troubleshooting shortcut.
- **Invalid pagination or protected cursor:** refresh the bounded list with
  valid filters after authorization is corrected; do not guess hidden IDs.
- **Schema mismatch / unresolved v1 queue:** leave observation fail closed,
  preserve the compatible binary, schema, backups and ledger evidence, and
  escalate to W66 operations/security owners for a **separately admitted,
  executable** reconciliation/rollback plan. No drain endpoint or worker
  exists in this host. Do not invent a recovery command, manually mutate the
  queue, blindly retry effects, or downgrade a migrated schema without a
  verified full database restore procedure.
- **Unknown external delivery effect:** triage against durable provider and
  ledger evidence. Never infer that an ambiguous send is safely retryable.
- **Database outage:** disable observation; do not switch to memory or a
  separate SQLite file that creates a second history.

Rollback is a **planned database restore and compatible binary procedure**,
not a blind downgrade of a v2 database. Restore data, schema and node
configuration as one consistent unit; preserve evidence of external effects.
