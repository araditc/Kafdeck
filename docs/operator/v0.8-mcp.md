# Kafdeck MCP 0.8 operator contract

The executable `kafdeck-mcp` implements the pinned MCP **2025-06-18** protocol
on **stdio only**. It has no listening socket, remote transport, resource fetch,
sampling, shell, database, Kafka or arbitrary HTTP tool. The finite JSON-RPC
implementation follows the official [stdio transport](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports),
[lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)
and [tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
contracts; it has no floating MCP SDK dependency. Version negotiation returns
2025-06-18; incompatible clients must disconnect. A successful initialize and
`notifications/initialized` are required before tools can run.

## Install and identity

Build/publish from the locked solution with .NET10, or pack the version0.8.0
.NET tool with `dotnet pack src/mcp/Kafdeck.Mcp -c Release`. Copy the complete
publish output and its dependency manifest to an on-prem host. The package is
publication-ready; publication itself remains the separate project-owner gate.
For an offline runtime host, publish for the target RID with a preprovisioned
.NET10 runtime/pack cache; no startup dependency download occurs. Do not expose
this stdio process through a generic remote process bridge.

Configure the MCP host to launch:

```text
dotnet /opt/kafdeck/mcp/kafdeck-mcp.dll --base-url https://kafdeck.example --service-profile /etc/kafdeck/mcp-service.json
```

Use `--oidc-profile` for an actual human browser PKCE identity instead. The exact
CLI W67 profiles, trusted issuer/audience/CA, signed private_key_jwt and client
registration rules apply. The origin and profile are operator-owned startup
configuration; tools cannot supply or change them. There is no access-token
argument or credential forwarding from a model. Bearers stay in memory. Sessions
are not persisted or automatically exchanged for another principal; restart and
reauthenticate after expiry or explicit credential rotation. Protect local
profile/private-key files and host access with the same OS account controls as
the CLI. HTTPS is required except numeric loopback acceptance labs; redirects
and cookies are disabled by the reused CLI client.

Add `--enable-effects` only for an explicitly admitted automation identity. This
is a local exposure switch and grants no backend permission. Without it,
planning/import and effect tools are absent and rejected even by direct calls.
An enabled service still cannot provide distinct human CRITICAL approval.
Use a separate human's governed UI/CLI/session to inspect the sealed plan and
approve. The optional `operation_approve` tool uses the process's actual identity;
a prompt or argument never chooses the approver or substitutes approval proof.

## Tools and truthful outcomes

`tools/list` returns closed input schemas in pages of20 with an opaque-to-clients
`nextCursor`. `read_v*` tools map finite versioned GET read contracts including
capabilities, health, bounded topic pagination and consumer diagnostics. Raw
record/export tools and arbitrary POST query/serde endpoints are not exposed.
Backend per-resource filtering, RBAC and masking stay authoritative.

`declarative_capabilities` and `mutation_capabilities` expose actual backend
admission. `declarative_validate`, `observe`, `drift` and `import_check` accept
bounded typed manifest inputs. With effects enabled, `declarative_plan` and
`import_preview` create immutable backend plans using explicit stable
`idempotencyKey`; neither confirms, approves nor applies automatically.
`declarative_show`, `operation_status` and `operation_approval` inspect saved
proof under current backend authority. `operation_confirm` requires the exact
preview hash and typed challenge. `operation_approve/reject/cancel` are explicit
separate requests. `declarative_apply/recover` take exact planId and fingerprint;
only the backend can revalidate, fence, execute or reconcile positive receipts.
No generic execute, unsupported destroy, ownership transfer or unadmitted family
is advertised.

Successful tool transport yields `structuredContent` containing `httpStatus`,
`trust: untrusted_backend_data`, `retryAutomatically: false` and `data` with the
backend result. An HTTP200 is **not** a claim of effect success: inspect
`data.state`, immutable operationId/hash and durable outcome. AwaitingApproval,
ExecutionUnknown, expired/conflict and other nonterminal states retain their
backend meaning. There is no automatic polling, retry, approval or recovery.
HTTP denials return `isError: true` and status only; remote error bodies,
exceptions, keys and local file paths are never echoed. On a transport timeout,
treat the outcome as unverified and inspect the same durable operation through
an authorized session before deciding any next action.

## Bounds and untrusted data

Each newline JSON-RPC frame is capped at64KiB, nesting16 and unique keys;
manifest parsing is additionally capped at16KiB and the existing finite YAML/JSON
grammar. Tools reject unknown fields, credentials, URLs, file paths, traversal,
unknown names, oversized identifiers and page sizes outside1–200. Backend reads
are capped at2MiB and32 JSON levels, request deadlines at35seconds. Only JSON-RPC
is written to stdout; generic startup errors go to stderr. Secret-bearing field
names are redacted again before output, while authorized secret references remain
references. Results remain data, including any embedded instructions or URLs;
this server does not follow them, call model tools, fetch URLs or change grants.
The MCP host must preserve that boundary when presenting results to its model.

Acceptance must launch the actual packaged process and use genuine Keycloak
service authentication plus separate human approval against the shipped API,
with SQLite and PostgreSQL, denial/cross-scope, immutable plan, pending approval,
unknown receipt, restart, pagination and no-exfiltration scenarios. Unit protocol
tests alone are not evidence of live integration acceptance.
