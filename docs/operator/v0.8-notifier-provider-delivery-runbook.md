# Opt-in typed provider delivery and credential rotation

These are work-in-progress v0.8 local transport contracts. They do not close
W66, admit production tenant credentials, authorize external messages, or publish
v0.8. Full provider/lifecycle/HA/product acceptance remains tracked in the
[G2 evidence matrix](../implementation/v0.8-w66-g2-authenticated-webhook-evidence.md).

## Activation and configuration

Notification observation still requires OIDC operator access and configured
persistence. Physical activation is independently default-off:

| Setting | Admitted active profiles |
| --- | --- |
| `WebhookDeliveryEnabled` | Webhook, with explicit Anonymous or Bearer authentication |
| `HttpProviderDeliveryEnabled` | Slack, MicrosoftTeams, Telegram, PagerDuty |
| `EmailDeliveryEnabled` | Email with a typed implicit-TLS SMTP profile |

Physical host activation accepts standalone SQLite/PostgreSQL. Explicit
`HighAvailability` requires PostgreSQL, a secret-referenced connection and a
valid external generation interlock; SQLite HA and unguarded HA are rejected.
Stop/fence old-primary senders before manual promotion, keep identical admitted
profiles/configuration on participating nodes, and use the
[recovery procedures](v0.8-notification-recovery-interlock.md) for restored state.
Disabled destination profiles may remain in a mixed catalog. An active
profile from a family whose switch is off cannot accidentally send.

Destination definitions use the existing exact `DestinationId`, `Provider`,
`DisplayName`, `EnabledEvents`, opaque `CredentialBindingId` and optional
`Enabled=false`. Add only the following closed family-specific fields:

| Family | Additional server-owned fields | Credential reference material |
| --- | --- | --- |
| Webhook | `ConfiguredEndpoint` exact HTTPS origin/path; `WebhookAuthentication=Bearer` for authentication | Raw Bearer token, without the `Bearer ` prefix; Anonymous has no credential binding |
| Slack | `ProviderResourceId` exact encoded C/G/D channel ID | Slack Bearer token with reviewed channel membership and `chat:write` authority |
| MicrosoftTeams | `ProviderResourceId` exact team GUID; `ProviderSecondaryResourceId` closed `19:...@thread.tacv2` channel ID | Graph delegated token with reviewed `ChannelMessage.Send`; general app-only posting is not supported |
| Telegram | `ProviderResourceId` exact canonical numeric chat ID | Raw bot token in its official numeric-bot-ID/secret format; named mutable chat aliases are not admitted |
| PagerDuty | No arbitrary target URL or event action | Exact Events API v2 integration routing key, 32 hex characters; trigger-only notifications |
| Email | `EmailRecipientAddress`; nested `Smtp` object with `Host`, optional `Port` (465 default), `SenderAddress`, `Username` | SMTP password for mandatory SASL PLAIN over verified implicit TLS |

Each credential binding has exactly `DestinationId`, `BindingId`,
`SecretReference` and optional `Enabled=false`. `SecretReference` accepts only
preprovisioned `env:NAME` or an absolute mounted `file:` reference. Never put a
token, password, arbitrary provider URL or header into a request, profile field,
support export or source file. Unsupported fields and nested raw credential
material fail closed. SMTP passwords are bounded UTF-8 without control characters;
the complete SASL command must fit its 512-byte limit. SMTP sender/recipient use a
closed common ASCII mailbox subset; quoted/display-name addresses are not admitted.

The four HTTP provider origins and methods are fixed by code. They are not
arbitrary configured Webhooks. SMTP is implicit TLS only; cleartext, STARTTLS
downgrade, unauthenticated relay and arbitrary SMTP commands are not supported.
The existing public-IP/DNS policy applies: private/on-prem destination exceptions
need a separately admitted allowlist contract and are not silently enabled here.

## Provisioning and rotation

1. Review the exact destination/recipient, provider identity, action scopes,
   credential owner, secret mount permissions and authorized event classes.
2. Provision a new opaque versioned binding ID and server-owned secret reference.
   Validate the provider-side token/role outside Kafdeck's notification body.
3. Configure the matching profile and binding, with physical switches initially
   false. Verify normal TLS trust, exact host ownership and persistence/schema.
4. Enable only the reviewed family switch and restart. Route a new approved safe
   event and verify its physical provider receipt and durable terminal state.
5. For rotation, provision a new secret version, change the binding ID and its
   matching reference, and restart after review. Existing pending intents under
   the old fingerprint are fenced as unknown; do not retarget or blindly resend.
6. Disable a destination with `Enabled=false`, or revoke a binding with its own
   `Enabled=false`, then restart. A missing/unreadable/revoked secret cannot fall
   back to anonymous. Reconcile in-flight effects separately.

Changing only mounted-file contents preserves the binding identity and affects
later resolution. It does not fence pending work or atomically recall a secret
already read. Teams token refresh and provider-side revocation/tenant permission
changes remain provider-owner responsibilities; this transport does not mint or
refresh those external credentials. Runtime governed destination/credential
selection, shared CAS/audit and cross-node revocation are independently opt-in;
see the [governance operator guide](v0.8-notification-governance-operator-guide.md).
Their integrated acceptance evidence remains separate from restart-based
credential provisioning.

## Receipts, failures and telemetry

Successful transport acknowledgement means provider acceptance, not proof of
downstream delivery/incident processing. Strict validated receipts become a
SHA-256 fingerprint in `ProviderReceiptFingerprint`; raw request IDs remain
prohibited in the ledger. Provider response bodies/URLs/headers never become
operator error text. Conclusive authentication/request rejection is terminal
`Exhausted`; ambiguous status, throttling, malformed/mismatched receipt, timeout
or missing final acknowledgement is terminal `UnknownExternalEffect`.

An unknown outcome must be reconciled with the provider before any fresh governed
follow-up. Do not reset it to Pending or automatically replay a possibly accepted
event. A complete dispatch deadline bounds DNS through receipt handling, and
unfinished noncooperative operations retain concurrency admission until completion.

Telegram requires its token in a private API path and PagerDuty requires a routing
key in a private body field. Telegram and configured Webhooks bypass HttpClient
HTTP diagnostics with bounded raw HTTP over pinned TLS, since configured
Webhook paths can also contain confidential material. No global telemetry suppression is used. Never
add raw wire dumps, URI/body/header logging or exception detail exports to these
transports. Laboratory tests install actual HTTP EventSource/Activity listeners
and report only safe booleans and counts.

## Schema upgrade and operational limits

Schema v3 adds a nullable safe receipt fingerprint to v2. Initialization migrates
atomically; v2 pending intents keep their original destination revision and state.
The existing v1 untrusted-backlog drain/reconciliation gate remains enforced.
Older binaries reject v3. Stop old senders, take a consistent backup, validate
the migration with sends disabled, then activate the reviewed configuration.
Automatic mixed-version rollback or restoring an old ledger after external
delivery is not an accepted recovery procedure; reconcile effects first.

The local contract laboratories cover all six transport families, credentials,
wire formats, TLS and durable acknowledgement/unknown states. They do not prove
external tenant grants, SaaS reachability, arbitrary SMTP interoperability,
automatic failover, safe rolling upgrades or full operator UX acceptance. The
guarded PostgreSQL HA, process-loss/promotion and restore scenarios have separate
required evidence; protocol fixture counts do not stand in for those cases.
