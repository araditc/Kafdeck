# Dynamic broker settings in Fleet

This workflow is available in [Kafdeck 1.1.0](../releases/v1.1.md). See the [Fleet quickstart](v1.1-fleet-quickstart.md) for related broker operations.
Select the Kafka cluster, then open **Fleet → Dynamic broker settings**. Enable the governed mutation runtime and grant both `ClusterConfigRead` and `ClusterConfigAlter` on the target. The Kafka client also needs the broker's `DescribeConfigs` and `AlterConfigs` permissions. Fleet uses the cluster's existing Kafka connection directly. SSH registration is optional for this workflow.

| Setting | Accepted values | Scope | Expected effect |
| --- | --- | --- | --- |
| `log.cleaner.backoff.ms` | Whole milliseconds from 0 to 3,600,000 | Broker override | Changes how long the Kafka log cleaner waits when it finds no work. Higher values can delay compaction. Lower values make idle cleaner checks more frequent. |

Kafka applies a broker override dynamically. Fleet shows the cluster default as the inherited source when Kafka reports one. Cluster-default writes require an unnamed broker resource, which the pinned librdkafka client rejects. [Apache Kafka broker configuration](https://kafka.apache.org/39/configuration/broker-configs/#updating-broker-configs), [librdkafka 2.16.0 resource validation](https://github.com/confluentinc/librdkafka/blob/v2.16.0/src/rdkafka_admin.c#L2695-L2702)

1. Choose the broker. Enter the intended value and select **Preview configuration change**.
2. Review the exact target, effective value and source, and expected value and source. Confirm the preview, then select **Apply configuration change**. Observe the verified value and source. The mutation journal records the configuration target and outcome.
3. After a verified set, select **Preview restore**. Fleet proposes the previous override at the same scope or removes the new override so Kafka resumes inheritance. You can also deliberately remove an existing override with **Remove override and inherit**. Review and confirm a restore as a separate operation.
4. If Fleet reports a stale preview, preview again against the latest Kafka observation. If a dispatch is unverified or its outcome is unknown, inspect the current value and source before proposing another change.

Kafka's read and alter requests are separate. Fleet rechecks the effective value, source and Kafka cluster identity directly before dispatch. Coordinate writers that operate outside Kafdeck during the change window.

The browser workflow uses experimental preview routes and the existing governed mutation lifecycle. The restore preview accepts a verified set operation ID for the same scope. When using the API after leaving the page, use the recorded operation ID and the current settings to request a restore preview.

- `GET /api/v1/clusters/{clusterId}/broker-config/settings` lists the keys, ranges and scopes.
- `POST /api/v1/clusters/{clusterId}/broker-config/preview` takes the key, scope `brokerOverride`, broker ID, and the command `set`, `inherit` or `restore`. Supply the string `value` for `set` or `restoreOperationId` for `restore`. Send the standard browser CSRF and idempotency headers.
- Use the returned operation ID and preview hash with the existing confirm, execute and status routes.
