# Operator Guide — v0.5 Safe Administration

## 1. Operating posture

v0.5 introduces controlled mutation and therefore changes Kafdeck from an
observation-only administration surface into a privileged control plane. Mutation
must remain explicitly enabled, OIDC-authenticated, least-privilege authorized,
durably persisted and fail-closed.

The operator rule is simple: **a successful preview is not permission to skip the
rest of the governed lifecycle**. Confirmation, independent approval where
required, current authorization, current preconditions, durable execution claim
and post-dispatch outcome handling remain mandatory.

No v0.5 operator procedure may introduce a generic Kafka CLI/AdminClient command,
provider REST proxy, arbitrary serializer/script/SQL/JavaScript execution surface,
or direct HTTP-to-provider bypass.

## 2. Mutation lifecycle

For every mutation:

1. identify the exact cluster and typed mutation action;
2. create a bounded preview and inspect its materialized target set, risk class,
   warnings and preconditions;
3. confirm the exact preview challenge/hash before expiry;
4. for CRITICAL or policy-elevated operations, obtain approval from a distinct
   eligible principal;
5. allow Kafdeck to re-evaluate the current requester and all frozen
   authorization targets immediately before dispatch;
6. allow Kafdeck to re-observe relevant preconditions immediately before
   dispatch; stale state must produce `StalePreview`, not best-effort mutation;
7. execute only through the admitted typed mutation handler;
8. inspect the durable result and safe provider/verification evidence;
9. reconcile any unknown, partial or unverified result before attempting a new
   operation on the same resource.

Do not treat a previously approved operation as an evergreen authorization grant.
If the current request identity is missing or no longer authorized, dispatch must
remain denied.

## 3. Risk and independent approval

Server-owned risk floors are authoritative. A caller, UI, role or external policy
input may raise risk but cannot lower the built-in floor.

Topic deletion and controlled purge are CRITICAL. Permanent destructive schema
operations and other policy-sensitive mutations may also be escalated. CRITICAL
operations require a second eligible principal; the requester cannot approve the
same operation.

Before approving a CRITICAL operation, the approver must independently verify:

- cluster and exact materialized targets;
- irreversible/destructive warning state;
- preview expiry and freshness;
- expected blast radius;
- whether a safer non-destructive operation exists;
- that the operation is still needed at approval time.

Approval is not a substitute for pre-dispatch authorization or stale-preview
revalidation.

## 4. Record production

Governed record production accepts only bounded single/batch/template-assisted
material through the typed production workflow.

Raw Kafka key/value/header bytes are ephemeral execution material. They must not
be copied into issue comments, audit notes, application logs, durable mutation
state or diagnostic evidence. The durable operation binds material through HMAC
digests and safe metadata.

If the client re-submits execution material, it must digest-match the admitted
preview. A mismatch is a pre-dispatch failure and must never be overridden.

Schema validation, when configured, is fail-closed. Provider acknowledgements may
prove individual records; a batch with only some proven records must remain
partial rather than being reported as fully successful.

## 5. Schema Registry and Kafka Connect

Only admitted typed provider profiles and fixed provider routes are valid mutation
surfaces. Operators must not work around an unsupported provider/profile by
adding user-selected URLs, methods or arbitrary provider bodies.

Provider redirects are rejected. Raw provider error bodies are not authoritative
operator evidence because they may contain secrets. Use the normalized result
code, bounded safe evidence and provider-side administration tools for deeper
investigation when necessary.

Kafka Connect configuration may contain credentials. Treat all unrecognized
configuration values as sensitive unless Kafdeck explicitly projects them as
safe.

## 6. Controlled purge / DeleteRecords

Purge is irreversible and always CRITICAL. The preview must materialize an
explicit finite set of topic/partition/before-offset targets. Unresolved timestamp
selectors, out-of-range offsets or an over-bound target set must fail before
confirmation.

A purge preview may become stale if a relevant low watermark changes. Kafdeck
must revalidate immediately before dispatch. Do not bypass a `StalePreview` by
manually forcing the old target set; create a new preview and repeat the governed
flow.

Post-dispatch readback can be verified, partial or inconclusive. Only a verified
post-condition is `AppliedVerified`.

## 7. Handling `ExecutionUnknown`

`ExecutionUnknown` means an external side effect **may already have occurred** but
Kafdeck cannot safely prove the final provider state. Common causes include:

- timeout after dispatch started;
- provider task continuing after the request deadline;
- process interruption after the dispatch marker;
- null or malformed provider result;
- lost or otherwise ambiguous provider response.

When an operation is `ExecutionUnknown`:

1. **do not retry it blindly** and do not create an equivalent replacement merely
   because the UI/API request failed;
2. preserve the operation and its conflict/resource claim according to the
   mutation state machine;
3. inspect safe Kafdeck evidence: dispatch marker, target set, timestamps,
   acknowledged/verified counts and normalized provider result code;
4. inspect provider truth independently using the provider's normal
   administrative/read interfaces;
5. determine whether the intended post-condition is proven, disproven or still
   ambiguous;
6. only after reconciliation may a new preview be created, and that new preview
   must re-evaluate authorization, risk, preconditions and idempotency normally.

Never rewrite `ExecutionUnknown` into `FailedBeforeDispatch` simply to make a retry
possible.

## 8. `PartiallyApplied` and `AppliedUnverified`

`PartiallyApplied` means Kafdeck has positive evidence that some but not all
members of a bounded multi-target operation were applied. Treat the successful
subset as real external state before deciding on remediation.

`AppliedUnverified` means the provider accepted or may have applied the operation,
but the bounded verification/readback did not prove the complete post-condition.
It is not equivalent to failure.

Compensation is valid only when a specifically typed operation has an admitted
safe inverse. Operators must not invent generic rollback commands.

## 9. Persistence, claims and HA

Mutation state is operationally critical data. The persistence store contains the
state required to prevent duplicate or conflicting execution, including
idempotency bindings, execution generations/leases and resource claims.

SQLite mutation mode is standalone only. Do not run it as a multi-instance HA
mutation store. Multi-instance mutation execution requires the admitted
PostgreSQL posture.

Do not manually delete or edit live mutation rows/claims to unblock work. An
unknown operation retaining a claim is a safety control, not stale garbage by
default.

When a process is interrupted, recovery distinguishes pre-dispatch from
post-dispatch interruption. Only the former may safely become a definitive
pre-dispatch failure. Post-dispatch interruption must remain unknown until
reconciled.

## 10. Backup and restore

Back up the mutation persistence database with the same operational rigor as any
other control-plane state that protects idempotency and external side effects.
The backup plan must include the schema and all mutation-operation/idempotency/
claim state needed for recovery.

The HMAC material-digest secret is deployment-owned secret material and must be
protected by the deployment's secret-management/backup process. It must never be
stored inside normal mutation audit/provider evidence merely to simplify restore.

After restoring mutation persistence:

1. start mutation execution in a controlled/fail-closed posture;
2. verify database schema compatibility before enabling new mutation admission;
3. verify the deployment has the intended material-digest secret;
4. review operations that were `Executing`, `ExecutionUnknown`, partial or
   unverified at backup time;
5. allow lease/recovery logic to classify interrupted execution rather than
   clearing claims manually;
6. reconcile potentially applied external operations against Kafka/provider truth
   before enabling conflicting replacement work;
7. verify OIDC/RBAC policy and provider profiles before re-enabling mutation.

If restored state and the deployment digest secret do not agree, execution
material validation must fail closed. Do not add a digest-bypass recovery mode.

## 11. Upgrade and migration operations

Before an upgrade that changes mutation persistence or execution behavior:

- capture a current database backup;
- identify outstanding `Executing`, `ExecutionUnknown`, partial and unverified
  operations;
- avoid beginning new destructive/CRITICAL work during the maintenance window;
- ensure the target version understands the persisted mutation schema/state;
- apply only repository-supported migration steps;
- validate read-only access to operation history before reopening mutation;
- verify exact authorization actions and provider profiles after configuration
  migration;
- perform a low-risk bounded mutation before restoring normal administrative
  traffic.

Never downgrade across a mutation-state schema boundary unless the target version
explicitly documents compatibility. Preserve the database and investigate rather
than destructively editing state to force an older binary to start.

## 12. Authorization operations

Mutation permissions must be granted as explicit typed actions scoped to the
smallest practical cluster/resource patterns. Read permissions do not confer
mutation permission, and a broad role label such as `admin` must not be treated as
an authorization shortcut.

For consumer offset/group changes, authorization covers the exact group plus all
explicit topic targets. For record production, the exact topic is a
`record.produce` target. Destructive operations must never rely on an unbounded
wildcard at execution time.

Changes to OIDC subject/group mappings or mutation roles can invalidate a preview
before dispatch; that is expected. Current authorization wins over historical
approval.

## 13. Incident and evidence handling

Operational evidence should use:

- operation ID and preview hash;
- requester and approver identities as recorded by the application;
- cluster/resource identifiers;
- risk class/reasons;
- state transitions and timestamps;
- safe normalized provider evidence;
- verification outcome.

Do not paste raw Kafka records, connector secrets, authorization headers, cookies,
tokens or raw provider error bodies into durable incident notes unless they are
handled through a separately governed secret/evidence process outside Kafdeck.

## 14. Readiness and release boundary

W40 may establish that the v0.5 candidate is technically ready, but readiness does
not grant release authority. Until explicit owner release approval is provided,
operators and maintainers must not create the v0.5 tag, promote OCI images,
publish a GitHub Release or otherwise publish the release candidate.
