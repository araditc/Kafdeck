# Install and upgrade Kafdeck 1.1.0

Use the [stable v1.1.0 release](https://github.com/araditc/Kafdeck/releases/tag/v1.1.0) for the signed native, OCI and Helm media. The [release verification instructions](../../README.md#releases-and-supply-chain) show how to verify the manifest offline and check the payload hashes before copying files into an isolated environment.

| Target | Install media |
| --- | --- |
| Fresh Windows Server x64 | Supplementary `kafdeck-offline-1.1.0-win-x64.zip` and its matching checksum |
| Linux with systemd | `media/native/<rid>/kafdeck-api-ui-1.1.0-<rid>.tar.gz`, with `linux-x64` or `linux-arm64` |
| Docker or Podman | Released GHCR digest, or the verified amd64/arm64 image archive in `media/oci/` |
| Kubernetes | `media/helm/kafdeck-1.1.0.tgz` and the released OCI image |

## Windows Server offline

Get the supplemental ZIP and `.zip.sha256` together. The ZIP includes Kafdeck, Java 21, PostgreSQL, Keycloak, the WinSW wrappers, prerequisites and the Kafka Java agent. The included original native archive is covered by the v1.1.0 signature. The supplemental ZIP and its installer files have a separate checksum inventory.

- **Fresh server:** Verify the ZIP, extract to a new folder, and run `Install-Kafdeck.ps1` in Windows PowerShell as Administrator. The script installs all three services and prints the HTTPS address and first-admin code. [English guide](windows-offline-install.md) · [Persian RTL guide](windows-offline-install.fa.md).
- **Existing 1.0.0 Windows Services installation:** Run `Upgrade-Kafdeck.ps1` from the new extracted folder under the original installation account. It takes a verified cold backup, updates the application, starts the services and automatically restores the original installation if health checks fail. [English upgrade guide](windows-offline-upgrade.md) · [Persian RTL upgrade guide](windows-offline-upgrade.fa.md).

## Prepare a manual deployment

For Linux, Docker or manually installed Windows, provision a reachable Kafka cluster, a trusted HTTPS certificate and a dedicated Keycloak realm using the [managed identity guide](managed-identity-setup.md). Configure a browser client and a separate user-management client. Use the application HTTPS origin in the Keycloak redirect URLs. Provision external PostgreSQL if you select that persistence provider.

Start with the [managed configuration template](examples/v0.9-managed-appsettings.json). Set the real OIDC issuer, credential file paths and Kafka registration CIDRs. Keep TLS material and client secrets on private paths readable by the service, and keep application state and Data Protection keys on persistent writable storage. Configure `Kafdeck:DataProtection:KeyDirectory` explicitly on a new installation. For an existing installation retain the original key ring and its application-name context. Put every enabled file-backed database in a persistent directory. Enforce and test egress to broker-advertised destinations from the actual deployment network.

Use the following settings in the examples below. Port 8080 serves HTTPS.

| Setting | Example |
| --- | --- |
| `Kafdeck:Deployment:ListenUrls:0` | `https://0.0.0.0:8080` |
| `Kestrel:Certificates:Default:Path` | `/run/secrets/kafdeck-tls.pfx` |
| `Kestrel:Certificates:Default:Password` | The PFX password supplied privately, such as through a protected environment file |
| `Kafdeck:ManagedIdentity:StateFile` | `/var/lib/kafdeck/identity-state.json` |
| `Kafdeck:DataProtection:KeyDirectory` | `/var/lib/kafdeck/keys` |

## Linux with systemd

Create a dedicated non-login `kafdeck` service account. Create `/opt/kafdeck/1.1.0` for the release, `/etc/kafdeck` for configuration and `/var/lib/kafdeck` for state. Give the service account write access to the state directory and read access to its configuration and secrets. Keep the release binaries owned by root. For native installation, change the sample `/run/secrets` paths to a persistent, restricted directory such as `/etc/kafdeck/secrets`.

Create the Data Protection directory before starting the app or issuing the setup code. For a fresh installation:

```sh
sudo install -d -m 0700 -o kafdeck -g kafdeck /var/lib/kafdeck/keys
```

Extract the verified archive for the host architecture. For x64:

```sh
sudo tar -xzf media/native/linux-x64/kafdeck-api-ui-1.1.0-linux-x64.tar.gz -C /opt/kafdeck/1.1.0
sudo ln -sfn /opt/kafdeck/1.1.0 /opt/kafdeck/current
```

Place your configuration in `/etc/kafdeck/appsettings.Production.json`. Save the following as `/etc/systemd/system/kafdeck.service`. The example reads the TLS password from the private application configuration. You can supply private environment variables via a restricted systemd `EnvironmentFile=` if needed.

```ini
[Unit]
Description=Kafdeck API and dashboard
Wants=network-online.target
After=network-online.target

[Service]
User=kafdeck
Group=kafdeck
WorkingDirectory=/etc/kafdeck
Environment=ASPNETCORE_ENVIRONMENT=Production
ExecStart=/opt/kafdeck/current/Kafdeck.Api --contentRoot /etc/kafdeck --webroot /opt/kafdeck/current/wwwroot
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now kafdeck
sudo systemctl status kafdeck
sudo journalctl -u kafdeck -n 50 --no-pager
```

For a new deployment issue the first-admin code under the same identity and environment as the service. If the unit uses an environment file, make its required settings available to the command as well.

```sh
sudo -u kafdeck env ASPNETCORE_ENVIRONMENT=Production \
  /opt/kafdeck/current/Kafdeck.Api --contentRoot /etc/kafdeck --issue-setup-code
```

## Docker Compose

The published multi-architecture image reference is:

```text
ghcr.io/araditc/kafdeck@sha256:478887bd2daa6ba3f3c6a76a73db8af8cf55a50d61b1be06ff4e655d28a27e65
```

On a connected host authenticate to GHCR with an account that can pull the image. For offline use, verify the signed image archive and load the one for the target host. Use the image reference that `docker load` reports in `.env` and set `KAFDECK_PULL_POLICY=never`. Podman users can import the same archive with `podman load`.

```sh
docker load --input media/oci/amd64/kafdeck-linux-amd64.docker.tar.gz
```

Keep `appsettings.Production.json`, the `secrets/` directory and the `state/` directory beside this `compose.yaml`. Restrict the config and secret ACLs, and allow the container's service UID (1654 for the released Linux image) to read them and write to `state/`. Configure endpoints that resolve and are reachable **inside the container**. The host's loopback address is not the container's route to Kafka or Keycloak.

```yaml
services:
  kafdeck:
    image: ${KAFDECK_IMAGE:?Set KAFDECK_IMAGE in .env}
    pull_policy: ${KAFDECK_PULL_POLICY:-missing}
    restart: unless-stopped
    ports:
      - "8080:8080"
    volumes:
      - ./appsettings.Production.json:/app/appsettings.Production.json:ro
      - ./secrets:/run/secrets:ro
      - ./state:/var/lib/kafdeck
```

For a fresh deployment, pre-create the configured key ring directory on the host. Compose mounts it as `/var/lib/kafdeck/keys`. For the default Linux image user:

```sh
sudo install -d -m 0700 -o 1654 -g 1654 state state/keys
```

For the registry deployment set `KAFDECK_IMAGE` in `.env` to the digest above. Then run:

```sh
docker compose config
docker compose up -d
docker compose logs --tail=50 kafdeck
docker compose exec kafdeck dotnet /app/Kafdeck.Api.dll --contentRoot /app --issue-setup-code
```

Run the last command only for initial setup. A /healthz response confirms API availability. Use the HTTPS origin and its trusted certificate to verify Keycloak login and Kafka connectivity separately.

## First administrator and Kafka cluster

1. Open the configured Kafdeck HTTPS address, use the 15-minute code to create the first administrator with an email and password, then sign in through Keycloak. Initial setup sends no verification email.
2. Open **Kafka connections**, enter bootstrap servers and select the security protocol. Supply any SASL/TLS settings, run **Test connection**, then save and select the cluster.
3. Use **Manage users** for user roles and cluster assignments. Configure Schema Registry, Kafka Connect and ksqlDB for that cluster as needed.
4. Open **Monitoring** to enroll metric sources. The [Java 21 agent guide](kafka-agent.md) covers broker installation. Use [Fleet quickstart](v1.1-fleet-quickstart.md) for broker hosts registered and mapped in Kafdeck.

## Upgrade or recover Linux, Docker and Helm

1. Verify and stage the target media. Preserve the old binary/image/chart and configuration. Stop application writers and take a consistent backup of state, key ring, files, and the relevant databases and Keycloak realm. Follow the [distribution and recovery runbook](../operations/v0.9-distribution-recovery.md) for provider migrations, writer fencing and generation reconciliation.
2. **Linux:** Extract into a new version directory. With the service stopped, switch `/opt/kafdeck/current` to the new directory and restart the unit. Keep the same service identity, content root, state and configuration.
3. **Docker:** Pull or load the verified replacement image before the maintenance window. Stop the app, update `KAFDECK_IMAGE` and run `docker compose up -d` with the same configuration, secret and state mounts. Preserve your previous image reference and state.
4. **Helm:** Use the [chart instructions](../../deploy/helm/kafdeck/README.md) and your reviewed values, exact image digest, TLS, identity, existing storage and enforced egress policy. Render and inspect the chart before running `helm upgrade --install kafdeck ./media/helm/kafdeck-1.1.0.tgz -n kafdeck -f operator-values.yaml --wait`. The chart uses one application replica.
5. Verify HTTPS, sign in with the existing account, open a saved Kafka cluster and check its metadata and monitoring. If recovery is required, restore the matching pre-upgrade application version, configuration and state together before readmitting writers. A Helm release rollback or image switch alone does not revert a database migration.
