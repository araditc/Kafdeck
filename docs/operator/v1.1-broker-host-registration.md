# Register SSH hosts and verify broker services

This is **v1.1 development, step 1 ([#485](https://github.com/araditc/Kafdeck/issues/485))**, not a feature in the immutable v1.0.0 installation packages. The accepted scope is [RFC-0011](../rfcs/0011-v1.1-broker-host-management.md).

An installation administrator can register a pinned SSH host in **Fleet**, discover its approved running Kafka services, and bind each service to a broker in the selected Kafka cluster. Both Linux **systemd without Docker** and **Docker Compose** use the same interface. One host can contain several brokers.

This step only observes and records identities. Log reading, monitoring-agent installation, configuration changes and restart jobs belong to the following roadmap steps. The probe below is a small read-only host helper, not the Java monitoring agent.

## 1. Prepare a dedicated read-only account on each Linux host

Requirements: OpenSSH server, Python 3, sudo, and either systemd or Docker Compose. Docker is not required for systemd. A trusted host administrator performs this one-time preparation at the server console or through an existing authorized administration session.

Generate a dedicated SSH key on the Kafdeck server. Keep the private key accessible only to its service account and administrators. Transfer **only the public key** to the Kafka host. Do not reuse an administrator's general-purpose key.

Create an approved service catalog, for example `host-targets.json`:

```json
{
  "version": 1,
  "targets": [
    { "id": "broker-1", "adapter": "systemd", "unit": "kafka.service" }
  ]
}
```

For three Compose brokers on one host, replace `targets` with:

```json
[
  { "id": "broker-1", "adapter": "compose", "project": "my-kafka", "service": "kafka-1" },
  { "id": "broker-2", "adapter": "compose", "project": "my-kafka", "service": "kafka-2" },
  { "id": "broker-3", "adapter": "compose", "project": "my-kafka", "service": "kafka-3" }
]
```

Use actual Compose project/service labels, not guessed container names. The helper requires exactly one running container for a selected project/service pair. Review the catalog, then run from a trusted checkout:

```sh
sudo sh tools/broker-host/install.sh ./host-targets.json ./kafdeck-probe.pub
```

The script creates `kafdeck-probe`, a root-owned authorized-key file with a forced command, and a sudo rule for **one fixed helper with no arguments**. SSH forwarding, interactive shell, arbitrary commands and SFTP are not granted by that key. It does not change or restart Kafka. It refuses to take over an existing `kafdeck-probe` account.

Installed files:

| Path | Purpose |
| --- | --- |
| `/usr/local/libexec/kafdeck-host-entry` | Accepts only `kafdeck-host-probe-v1` |
| `/usr/local/libexec/kafdeck-host-probe` | Fixed bounded read-only identity probe |
| `/etc/kafdeck/host-targets.json` | Root-owned allowlist of services |
| `/etc/sudoers.d/kafdeck-probe` | Exact helper invocation only |
| `/var/lib/kafdeck-probe/.ssh/authorized_keys` | Restricted public key; root-owned |

Root access is confined to this helper because observing another user's JVM process and container filesystem can require it. The account is not a member of the Docker group. Host administrators should review these files and their ownership. Updating the approved catalog is a privileged host administration task in this increment.

## 2. Obtain the trusted host fingerprint

On the actual Kafka host's trusted console:

```sh
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Retain the complete `SHA256:...` value. Confirm it through a trusted administrator or console. **An unauthenticated `ssh-keyscan` result alone does not establish trust.** Kafdeck rejects a different key before SSH authentication. Do not replace a pin just to suppress a mismatch: investigate host replacement or key rotation first.

## 3. Configure Kafdeck's network and credential bindings

Enable the feature in a managed-identity deployment and configure explicit destination CIDRs. For example, in the Kafdeck service configuration (substitute your host and protected absolute key path):

```json
{
  "Kafdeck": {
    "BrokerHosts": {
      "Enabled": true,
      "AllowedNetworks": [ "192.0.2.10/32" ],
      "Credentials": [
        {
          "Id": "office-read-only",
          "Authentication": "privateKey",
          "Secret": "file:C:/Kafdeck/secrets/office-probe-key"
        }
      ]
    }
  }
}
```

`Secret` and optional `Passphrase` accept existing `file:` or `env:` secret references. The UI receives only `Id` and authentication method, never secret references or contents. An existing appropriately restricted account can use `Authentication: "password"`; the supplied installer intentionally provisions key authentication. Never configure a broad administrator account as the probe account.

The feature defaults to disabled. Restart the Kafdeck application service after changing its configuration. Keep deployment egress restrictions in place; allowing a management address here does not change the deployment's Kafka egress policy. Host registration accepts literal IP addresses, not DNS names, and only configured CIDRs.

## 4. Register and bind in Fleet

1. Sign in as the installation administrator and select the Kafka cluster.
2. Open **Fleet → Broker hosts → Register SSH host**.
3. Enter a display name, IP, SSH port, `kafdeck-probe`, the trusted fingerprint, and a credential alias from the list.
4. Select **Verify and register host**. A successful SSH probe is required before the host is persisted.
5. Select the registered host and **Discover approved services** when needed.
6. Choose a service and the corresponding broker from the selected cluster, then **Verify and bind broker**.
7. Repeat for each broker. Reloading the page retains verified bindings.

Before a binding is written, Kafdeck probes SSH again and compares the service's cluster ID and broker ID with fresh Kafka metadata. A different cluster, different broker, stopped/ambiguous service, unavailable identity, changed SSH key or concurrent registry revision prevents the write. An approved service can belong to only one binding. Reverification can refresh an existing binding.

Verification records a **dated observation**, not a permanent guarantee that a service has remained unchanged. No host mutation operation is offered in this step. Subsequent operation implementations must reverify their exact target immediately before execution.

## Identity observation and supported layouts

For systemd the helper checks active state and MainPID. For Compose it selects the exact project/service labels and running container PID. In both cases it identifies the `kafka.Kafka` JVM command, reads its absolute configuration path through `/proc/PID/root`, and compares `node.id`/`broker.id` with `meta.properties` in every configured log directory. All directories must agree on cluster identity. PID/start time and service/container association are checked again after observation.

This requires a JVM broker launched with one absolute configuration filename and explicit absolute `log.dirs` or `log.dir` values. Wrapper processes left as MainPID, command-line property overrides, auto-assigned broker IDs, ambiguous scaled Compose services, escaped identity paths and missing/mismatching metadata are reported as **Identity unavailable**, not guessed. Host administrators remain trusted; this is not remote attestation against a compromised root account.

Bounds: 64 hosts, 1,024 bindings, 32 approved services per host, four concurrent SSH probes, a 20-second overall probe deadline, and bounded 64-KiB output channels. No configuration contents, private keys, passwords or raw provider exceptions are returned to the browser or audit.

## Persistence, audit and troubleshooting

The registry is the versioned `<ManagedIdentity.StateFile>.hosts.json` sidecar, beside the existing managed-identity state. Include it in the same protected backup/restore scope. It stores credential aliases, not credential material. Preserve the separate protected key files/environment configuration as part of your secret recovery procedure.

Registry updates use revision comparison and an atomic file replacement. Successful registration/binding audit events enter a durable outbox in the same write; retries can deliver an event more than once with the same correlation ID. Audit availability errors must not be interpreted as proof that a registry change did not happen: reload before retrying.

| Result | Action |
| --- | --- |
| Feature disabled | Configure `BrokerHosts.Enabled`, CIDRs and credential aliases on the server |
| Host key mismatch | Verify the real server key out of band; never blindly accept a new pin |
| Probe unavailable | Check SSH reachability, dedicated account, file permissions and fixed helper installation |
| Identity unavailable | Check the approved service is running and uses a supported JVM/configuration/data layout |
| Cluster/broker mismatch | Select the correct service/broker; inspect the actual running service and cluster metadata |
| Revision conflict | Reload the registry and review current bindings before retrying |

Automatic host-key replacement and general host lifecycle editing are not provided by this increment. Do not edit live registry JSON to bypass verification.
