# v0.8 verified mutation notification source

This G2 slice connects persisted `AppliedVerified` mutation results to the existing subscription router and delivery ledger. It is a partial N5 implementation: other product event families, UI management, and product-source HA admission remain open.

## Activation

Set `Kafdeck:Notifications:ProductEventsEnabled=true` (environment variable `Kafdeck__Notifications__ProductEventsEnabled=true`) explicitly. The default is off: the repository creates no product outbox tables and registers no source worker. An invalid boolean fails startup. Activation requires notification observation and administration mutations to be enabled, with **both execution modes set to Standalone**. The existing authentication, authorization, persistence, and physical sender activation requirements still apply.

Physical delivery additionally requires a configured destination profile, an active subscription accepting event class `Mutation` and type `mutation.state-changed`, and the applicable physical delivery flag. Disabling the physical sender does not disable capture; monitor the bounded queue and loss counters.

## Durable contract

The mutation repository writes minimal event metadata in the same database transaction as a successful version-checked terminal save. Failed CAS writes, rolled-back terminal saves, ambiguous outcomes, and unverified effects emit no verified event. The notification contains the approved static template and event identity; canonical intent, operation identity, requester identity, resource values, and credentials are not projected.

Enabling capture does not backfill historical operations. Events arise from successful eligible saves while capture is enabled. Disabling capture preserves existing database rows; re-enabling the source resumes bounded processing, including explicit expiry accounting.

The event identity is stable for the source database identity, operation identity, and terminal version. The pump reads unacknowledged rows directly, without a clock-based high watermark. It routes before acknowledging. An interruption between those operations replays the same identity through existing durable routing and delivery idempotency.

The source has finite defaults: 10,000 pending events, a batch of at most 50, a five-second cycle deadline, and 24-hour retention measured using the source database clock. Before each event it checks the delivery backlog against a 10,000-row budget and reserves room for the router's maximum 500-subscription fanout. This is standalone backpressure; it is not a cross-host reservation protocol.

Overflow and expiry preserve the real terminal mutation result. They increment durable aggregate loss counters and record the last loss time. Missing destinations, profile mismatches, and truncated routing retain the source row for retry until its retention expires. The worker logs aggregate loss changes and generic cycle failures without raw source metadata or provider error text.

## Operator status

When activated, `GET /api/v1/notifications/product-events/status` returns deployment-wide `pending`, `expiredPending`, `routed`, `expired`, `overflowed`, and `lastLossAtUtc` fields. `pending` counts all unacknowledged rows; `expiredPending` is its expired subset awaiting pump maintenance. The read does not remove events or update loss counters. It requires a deployment-wide notification management grant; a subscription-scoped grant does not expose global counts. No raw event or mutation identity is returned.

Treat increasing `expired` or `overflowed` counts as notification loss requiring investigation. Check active subscriptions, destination compatibility, delivery backlog, credentials, and sender activation. A delivered notification is evidence of notification transport; it does not independently prove the underlying Kafka effect.

## Proof boundaries

`V08G2ProductNotificationTests` covers atomic rollback, CAS uniqueness, disabled activation, excluded ambiguous states, capacity/expiry loss accounting, read-only status, delivery backpressure, and replay from a real persisted terminal transition through subscription routing to a physical local TLS provider and reopened durable receipt. An actual Generic Host case also verifies product-source activation with every physical sender disabled: the source routes and acknowledges one event into a durable `Pending` record with attempt count zero, without registering a delivery worker or transport dispatcher. Its product operation is a domain fixture; these cases do not execute Kafka. A separate real provider mutation proof is required for complete product-event provenance. PostgreSQL cases require `KAFDECK_TEST_POSTGRES`; absent local infrastructure is explicitly skipped by the required-lab attribute rather than reported as a successful physical proof.

Successful physical-source and PostgreSQL cases emit sanitized `product-source-tls-evidence.json` and `postgres-product-outbox-evidence.json` in `artifacts/g2` (or `KAFDECK_G2_EVIDENCE_DIRECTORY`). These contain counts, terminal states, runtime facts, and explicit fixture limitations, without raw operation identities, intent, credentials, or wire bodies.

The genuine human Kafka scenario in `V08G2HumanCliLiveTests` additionally uses `G2KafkaProductNotificationBridge`: the actual shipped API captures and routes its real verified Kafka TopicCreate while its physical senders are disabled. The fixture requires one durable `Pending` delivery and source acknowledgement, stops the API process, then opens that same queue in a second production sender host with the controlled TLS dialer. Its required evidence is `human-kafka-product-notification-evidence.json`. Execution of that test, with both real Keycloak and Kafka gates present, is required before claiming the complete tested chain; its implementation or an offline skip is insufficient. It covers one SQLite TopicCreate path, without implying other families, PostgreSQL effect, provider SaaS receipt, mutation recovery, database restore, or HA admission.
