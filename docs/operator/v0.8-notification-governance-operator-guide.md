# Notification destination and credential governance

This is an independently opt-in management surface. It selects immutable
server-provisioned profile versions; it never accepts token material, secret
locators, URLs, HTTP headers, SMTP commands or provider payloads from a browser.
The N2/N5 runtime and protected-main evidence remain tracked in the G2 ledger.
Protocol fixtures establish real TCP/TLS and provider-contract behavior. They do
not establish ownership of an external tenant or delivery to a human recipient.

## Provision approved versions

Keep the existing typed `Destinations` and `CredentialBindings` entries. Provision
separate source profile IDs and versioned secret references for each approved
version. A source profile's endpoint, provider recipient, authentication mode and
binding are immutable. Mount credentials privately on every sender node before
making a version available; never paste credentials into Kafdeck or support logs.

Example management mapping (the referenced profiles must already exist):

```json
{
  "Kafdeck": {
    "Notifications": {
      "Governance": {
        "Enabled": true,
        "Candidates": [
          { "CandidateId": "ops-v1", "DestinationId": "ops", "ProfileId": "ops-source-v1" },
          { "CandidateId": "ops-v2", "DestinationId": "ops", "ProfileId": "ops-source-v2" }
        ]
      }
    }
  }
}
```

Governance additionally requires OIDC, enabled notification persistence and
`ManagementEnabled=true`. Physical family switches stay independent. With
governance enabled, only mapped logical destination IDs enter the runtime
catalog. An unselected source profile is not an alternative sending path. A
destination with no durable selection cannot send. Provision all intended
logical destinations before activating this feature on an existing deployment.
Stop every previous sender before initial admission. A binary that predates this
feature is not a governance participant and must not run alongside it. Keep the
admitted configuration and external restore authority through upgrades; changing
or disabling the opt-in is an operator deployment action, not a safe rollback.

All nodes must have identical candidate profile and secret-reference identities.
The durable selection binds the private provisioning fingerprint, including its
reference identity. A node with a different candidate definition fails closed;
there is no static configuration fallback. Secret contents are resolved only at
dispatch, using the selected exact binding. Changing an existing mounted secret
without changing its approved version is not an audited version rotation.

## Operator workflow

1. Sign in with current `NotificationManage` authority for the logical
   destination. Read permissions do not grant management. A scoped manager sees
   only matching destinations; it does not receive global hidden counts.
2. Open **Notification destination and credential management**, reload current
   state, choose the approved version and desired destination/credential states.
3. Review the exact current revision and intended change, then confirm. The
   backend repeats current authorization and executes a shared database CAS.
   A stale revision returns409; reload and review again instead of blind retry.
4. A successful change advances the generation and appends exact actor, policy,
   version and state audit in the same transaction. No provider message is sent
   by a management request. The UI projects actor fingerprints rather than raw
   external identity strings. The latest1000 audit rows per destination are
   retained; central security audit retention is a separate operator policy.
5. Create, pause or retire subscriptions through the existing CAS panel. Changing
   destination requires permission on both the previous and new destinations.
   A manage-only operator does not gain notification body/evidence read access.

The typed routes are:

| Route | Authority and result |
| --- | --- |
| `GET /api/v1/notifications/management/destinations` | Current manage collection grant, then exact per-destination filtering; opaque versions/provider metadata only |
| `PUT /api/v1/notifications/management/destinations/{destinationId}` | Current exact manage grant, same-origin antiforgery and closed candidate/revision/enable flags |
| `GET /api/v1/notifications/management/destinations/{destinationId}/audit` | Current exact manage grant, bounded revision cursor, at most100 rows |

## Rotate, revoke and disable across nodes

Provision v2 on all nodes, then select v2 with the current shared revision.
Generation changes prevent a previously routed v1 intent becoming valid again.
Old enabled intents meet the original-revision fence and become unknown rather
than being retargeted to v2. New events use the selected v2 profile. Verify the
new physical receipt and durable evidence independently.

Revoke using **Credential enabled=false**, or pause the destination using
**Destination enabled=false**. Every node reads the shared authority before new
claims. The resolver rereads it around private secret I/O, and every concrete
transport obtains the current profile again before delivery. Authority is
checked again after DNS/TCP/TLS and immediately
before HTTP credential/message bytes, and before SMTP AUTH and DATA. The shared
revision check composes with the independent restore activation interlock.
Missing, disabled, revoked or changed authority never downgrades to anonymous. A message already
started or accepted externally cannot be recalled by a later database change;
reconcile it before creating any new effect. Revoking a local selection does
not invalidate a token at its external issuer: revoke that token there as well.

Restore/failover operations additionally require the independent external
generation interlock and physical fencing described in the
[recovery runbook](v0.8-notification-recovery-interlock.md). Governance does not
replace restore authority or approve its own restored state.

## Per-provider operation and rotation acceptance

Use approved static event templates. Record only safe receipt fingerprints and
ledger outcomes, never raw request bodies, tokens or provider replies.

| Provider | Provisioning and positive check | Rotation/revoke and negative checks |
| --- | --- | --- |
| Webhook | Exact HTTPS host/path, verified SNI/certificate, explicit Bearer mode with matching server reference (or explicitly approved Anonymous); confirm one POST and2xx receipt | Select new bound version, verify new Bearer credential; old version fenced; revoked/missing reference never falls back to Anonymous. Reject redirects, private/unapproved addresses, wrong host/cert and stale pins |
| Email | Exact SMTP host, implicit TLS465, reviewed sender/recipient and SASL PLAIN identity; confirm authenticated submission and final250 acknowledgement | Provision a new SMTP password reference/version; verify exact new AUTH, then revoke old credential at SMTP owner. No STARTTLS/cleartext/unauthenticated fallback. Missing final acknowledgement remains unknown; accepted submission does not prove mailbox delivery |
| Slack | Fixed Slack API origin and `chat.postMessage`; exact reviewed C/G/D channel, owner-controlled token with `chat:write` and channel membership; verify `ok=true`, exact channel and bounded message timestamp | New token/reference version, then provider-side old-token revocation. Check denied auth, channel mismatch, malformed/duplicate/oversized response and throttle ambiguity. Do not treat HTTP200 alone as success |
| Microsoft Teams | Fixed Graph origin, exact team GUID and reviewed channel ID; delegated credential with reviewed `ChannelMessage.Send`; verify201 and bounded message identity | Refresh/provision new delegated token outside Kafdeck and select its new version. Verify tenant/channel membership and old-token revocation. App-only ordinary posting is not silently substituted.401/403 are conclusive rejection; malformed/missing receipt stays unknown |
| Telegram | Fixed Bot API origin, canonical numeric chat, exact bot owner token; verify `ok=true`, bounded message ID and exact numeric recipient | Provision new bot token/reference version, verify ownership and chat membership, then revoke old token at BotFather/provider. Token belongs only in the private bounded wire path; HTTP diagnostics must not record it. Reject wrong chat, malformed receipt and mutable named-chat targets |
| PagerDuty | Fixed Events API v2 trigger, reviewed integration routing key and event-ID dedup key; verify202, success and exact dedup receipt | Provision new routing key/reference version and disable old integration key externally. Reject wrong/missing dedup receipts, invalid auth/request, malformed payload response and ambiguous throttling; do not add arbitrary event actions or URLs |

The contract laboratories cover each row with actual local provider TCP/TLS
fixtures and strict positive/negative mappings. External tenant grants, SaaS
egress, SMTP vendor differences and downstream delivery require the selected
deployment's operator checks and are recorded as environment limitations. They
are not additional universal gates replacing the original fixture-based N3
acceptance definition.

## Evidence boundaries

The frontend verification checks TypeScript, the production bundle and74 tests,
including approved-choice rendering, forbidden secret/endpoint inputs and
rejected path/cursor input. Those checks do not establish browser authentication
or physical delivery. The composed acceptance fixture separately requires a
genuine Keycloak browser session, current CSRF-protected profile/subscription
changes, actual CLI/Kafka mutation completion, the durable product-event outbox,
API process restart and an authenticated TLS receipt. PostgreSQL and SQLite
results are recorded separately; a compiled fixture is not an accepted result.

Mutation capability metadata at
`GET /api/v1/automation/capabilities/mutations` is a bounded inventory protected
by SystemRead. Its named routes describe the existing supported UI/API surface;
they confer no authority and still require current identity, RBAC, policy,
provider capability and governed lifecycle admission. Inherited Fleet/quota
limitations remain explicit. Job/generator reconciliation routes that still
return501 are excluded from material execution capability claims.
