# Kafdeck v0.1 operator guide

## Scope and safety boundary

Kafdeck v0.1 is a read-only Kafka Cluster Explorer. It exposes no Kafka mutation route or operator control. Deploy it with Kafka credentials that have only the metadata/configuration permissions required for exploration. Do not grant topic creation, deletion, alteration, record production, consumer-group mutation, or ACL mutation permissions.

## Single-image deployment

The repository root `Dockerfile` builds the React operator UI and the .NET API into one OCI image. The API serves the UI from `wwwroot`; `/healthz` is the liveness endpoint.

The application defaults to loopback binding. A container that publishes port 8080 must explicitly bind Kafdeck to the container interface and, because this is a non-loopback binding, must also configure the accepted deployment access-token secret reference. Keep the token outside the image and deployment manifest.

```sh
docker build -t kafdeck:v0.1 .
docker run --rm -p 127.0.0.1:8080:8080 \
  -e Kafdeck__Deployment__ListenUrl=http://0.0.0.0:8080 \
  -v "$PWD/config:/app/config:ro" \
  -v "$PWD/secrets:/run/secrets:ro" \
  kafdeck:v0.1
```

The mounted configuration must define `Kafdeck:Deployment:AccessToken` using an accepted environment-variable or mounted-file secret reference. The example publishes only to host loopback; expose it beyond the host only through an approved TLS-protected management boundary.

For browser use with token mode, open the UI once with the token in the URL fragment, for example `/#access_token=<deployment-token>`. Fragments are not sent in HTTP requests. The UI immediately removes the token from the address bar, keeps it only in `sessionStorage`, and sends it as `X-Kafdeck-Access-Token` on `/api` requests. Closing the browser session clears this storage. Do not put the token in a query string, bookmark, screenshot, log, or persistent browser storage.

Use immutable image digests in production. Run the container as its image-defined non-root user and keep configuration/secrets mounts read-only.

## Configuration and secrets

Configuration is loaded by the existing Kafdeck configuration loader. Secret values must be supplied by secret references supported by the application; never commit passwords, access tokens, private keys, client-key passphrases, or inline secret values to deployment manifests.

Recommended production controls:

- bind only to the intended management interface;
- require the deployment access token for remote access;
- prefer TLS/mTLS or SASL over TLS for Kafka;
- mount CA/client certificate/key material read-only;
- use a distinct least-privilege Kafka principal per environment/cluster;
- keep PLAINTEXT and SASL_PLAINTEXT limited to explicitly accepted isolated development networks.

### Connection patterns

TLS/mTLS: configure `Ssl` and reference the CA/client certificate/key through mounted secret paths. SASL PLAIN or SCRAM: configure `SaslSsl`, select the accepted mechanism, and resolve the password from a secret reference. No example in this guide embeds a credential value.

## Local development

Install .NET SDK 10.0.100+, Node.js 24+, Docker and Docker Compose. Restore/build the backend with `dotnet restore Kafdeck.slnx` and `dotnet build Kafdeck.slnx`. For the UI, run `npm ci` then `npm run build` from `src/frontend`. The repository Kafka smoke harness under `tests/integration/kafka` is the authoritative containerized integration path and is also exercised by CI.

## Compatibility

The W10 release-validation matrix verifies the accepted Tier 1 Kafka 4.3.1, 4.2.1 and 4.1.2 lines and Tier 2 Kafka 3.9.2, across the accepted transport/authentication combinations. Tier 1 must be recalculated against Apache Kafka supported releases when a release candidate is cut; the W10 matrix remains historical evidence for the validated source head.

## Air-gapped operation

Kafdeck has no runtime dependency on a public SaaS service. For an air-gapped environment, mirror the exact OCI image digest and all required Kafka CA/client certificate material into the controlled environment, export configuration separately, verify the transferred image digest before import, and keep secret material out of the image. Build-time package feeds are not required at runtime. If rebuilding inside the air gap, mirror the .NET, npm and base-image dependencies first and preserve lockfiles and image digests as provenance evidence.

## Troubleshooting

If `/healthz` is unavailable, verify the configured listen URL, port mapping, container process and deployment access boundary. A Docker port mapping cannot reach an application that is still bound only to container loopback. If the UI loads but API calls return 401, provide the deployment token through the fragment bootstrap described above and verify the configured server-side token secret reference. If a cluster is unavailable, verify DNS/routing, broker advertised listeners and the configured operation deadline. For TLS failures, validate CA trust, certificate validity/SANs and client-key permissions. For SASL failures, verify mechanism and principal mapping without logging the secret. `Unauthorized` on configuration reads means the Kafka principal lacks the required read permission; do not broaden it to mutation permissions. Stale responses after transient Kafka failures are expected only within the bounded stale policy and are explicitly marked stale.

## Known limitations

v0.1 is intentionally read-only and does not create/delete/alter topics, records, groups, ACLs or broker configuration. Compatibility is limited to the release matrix above. Availability reflects Kafka/admin-read reachability and bounded snapshot semantics, not end-to-end producer/consumer application health. The deployment access token is a deployment boundary, not a general identity platform.

## Release evidence

A v0.1 release candidate is acceptable only when the exact source head has green quality-gate, CodeQL, dependency-review, Kafka smoke/compatibility, container build and release supply-chain evidence. The release workflow builds the release image once; SBOM generation and vulnerability scanning target that exact candidate digest, and signing binds the same published digest. Unfixed High/Critical findings remain blocking. Phase 0 administrative controls and the no-mutation invariant must be re-verified before release.
