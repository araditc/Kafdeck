# W67 topic configuration, partition and stop commands

The governed bearer topic surface includes create, configuration alteration,
partition increase and delete. It uses the existing planners, server-owned risk,
immutable preview, provider preconditions and durable engine. Every request still
requires current registration, exact original actor, resource RBAC and policy.
The actual SQLite and PostgreSQL + Keycloak + Kafka verticals passed configuration, reset,
partition, cancel/reject and preview-preserving API restart scenarios. See
`../implementation/v0.8-w67-topic-lifecycle-evidence.md` and the acceptance ledger
for precise local proof and remaining provider/HA/recovery cases.

## Explicit grants

Enable `NonBrowserRead.Enabled`, the durable mutation engine and the separate
`GovernedMutationsEnabled` switch. A registration may request only the admitted
`TopicCreate`, `TopicAlter` and `TopicDelete` mutation actions. Partition increase
uses **TopicAlter** as in the existing browser workflow. Current direct backend
permissions must cover the same action, cluster and topic. A read grant or CLI
profile never grants mutation authority.

TopicDelete keeps its separate CRITICAL human approval gates. Configuration
changes that affect durability can raise risk to HIGH, and partition increase
has a HIGH floor. Supply the server's exact typed target when required; the CLI
does not select risk or approval requirements.

## Closed configuration options

Create and alter accept repeated `--config key=value` with unique keys. Alter
also accepts `--reset-config key`, representing a JSON null reset to provider
default. Set/reset of the same key is a duplicate and fails before authentication.
Reset is not admitted for create, and configuration options cannot be used on
other commands. Values are bounded to 256 characters; raw JSON, actor overrides
and generic provider commands are not accepted.

The nine keys match the existing authoritative backend policy:

`cleanup.policy`, `retention.ms`, `retention.bytes`, `segment.ms`, `segment.bytes`,
`min.insync.replicas`, `max.message.bytes`, `delete.retention.ms`,
`min.cleanable.dirty.ratio`.

The backend validates values, current provider support, sensitive/read-only
configuration and mutable topic identity before admission. Resetting a key never
bypasses those checks or the key's risk classification.

```text
kafdeck --service-profile service.json topics create-preview dev orders-demo 1 1 --config segment.bytes=1048576 --idempotency-key <create-key>
kafdeck --oidc-profile human.json topics alter-preview dev orders-demo --config retention.ms=60000 --idempotency-key <alter-key>
kafdeck --oidc-profile human.json topics alter-preview dev orders-demo --reset-config retention.ms --idempotency-key <reset-key>
kafdeck --oidc-profile human.json topics increase-partitions-preview dev orders-demo 2 --idempotency-key <increase-key>
```

Create and increase counts are bounded to 1–100000. The backend additionally
requires an increase target above the observed current count. Confirm and execute
only the returned operation ID, hash and exact required challenge.

## Cancel and reject

```text
kafdeck --oidc-profile requester.json operations cancel <id> <hash>
kafdeck --oidc-profile approver.json operations reject <id> <hash>
```

Cancel requires the exact original actor, current topic grant, current policy and
preview hash. The domain permits only Previewed, AwaitingConfirmation,
AwaitingApproval or Ready. A revoked approver does not prevent an otherwise
authorized original owner from stopping a Ready plan. Cancellation grants no
provider authority, and cannot clear Executing, ExecutionUnknown or terminal
state. Concurrent state changes still use the repository's version checks.

Reject is a human-only command for AwaitingApproval TopicDelete. It uses the same
independent human registration, MutationApprove and TopicDelete scope checks as
approve. A service or the requesting human cannot reject as an independent actor.
The actual rejector and authorization evidence remain durable.

Successful intentional cancel/reject commands return **exit 0** with typed
Cancelled/Rejected status. This reports that the requested stop succeeded; it
does not claim a provider effect succeeded. Later `operations status` for those
states retains **exit 4**. Wrong hashes, invalid states and concurrent transitions
return **8**; authorization denial returns **3**. ExecutionUnknown remains **7**
for every command and never triggers a resend or uncertainty clear.

Other mutation families, complete read/provider parity, PostgreSQL effect
failover/restore, identity lifecycle and remaining A1–A6 acceptance stay in scope.
