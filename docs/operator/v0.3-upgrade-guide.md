# Upgrade Guide — Kafdeck v0.2 to v0.3

- **From:** v0.2 Operator Identity/RBAC
- **To:** v0.3 Safe Data Explorer + Server-Side Masking

## 1. Upgrade posture

v0.3 adds the first Kafka record-payload read surface. Existing v0.2 metadata-only permissions do not automatically acquire payload access.

The upgrade is therefore designed to be opt-in for record data:

- existing cluster/topic metadata roles remain metadata roles,
- `record.read` must be granted explicitly,
- `record.export` must be granted separately,
- masking policies are evaluated on the server,
- payload persistence/indexing is not introduced by the upgrade,
- Kafka mutation is not introduced by the upgrade.

## 2. Before upgrading

Record the current v0.2 deployment configuration and verify:

- configured cluster profiles,
- Local/Token/OIDC access mode,
- OIDC issuer/client/secret references where applicable,
- v0.2 role and binding configuration,
- Kafka principal ACLs,
- deployment health and compatibility evidence.

Do not add Kafka write ACLs for v0.3. Safe Data Explorer requires read capability only.

## 3. Authorization migration

No v0.2 permission implies record access.

After upgrading, explicitly decide which roles receive:

- `record.read`,
- `record.export`.

Keep permissions constrained by cluster and topic scope.

A recommended sequence is:

1. upgrade with no record permissions,
2. verify v0.2 metadata workflows,
3. configure masking for sensitive topics,
4. grant `record.read` to a narrow test/operator role,
5. verify browse/tail audit events,
6. grant `record.export` only if required.

## 4. Access modes

### OIDC

OIDC remains the preferred enterprise multi-user mode. Record authorization uses the existing canonical operator identity and Kafdeck policy evaluator.

### Local

Local mode remains a deployment boundary and is not converted into a human identity model.

### Token

Token mode remains a compatibility deployment boundary. The deployment token is not promoted into OIDC identity/RBAC semantics.

The v0.3 record endpoints preserve these access-mode distinctions; do not use Token mode as an OIDC bypass.

## 5. Schema Registry configuration

Schema Registry is optional and read-only in v0.3.

Configure it only when schema-assisted Avro, Protobuf or JSON Schema decoding is required.

Registry credentials must use the accepted secret-reference mechanism. No registry credential should be placed in browser-visible configuration, role policy, audit output or API payloads.

Full Schema Registry lifecycle management is not part of v0.3.

## 6. Masking migration

Before granting record access to sensitive topics, define the required masking policy.

v0.3 policy semantics are fail-closed:

- exact structured paths are preserved,
- exact Kafka header names are preserved,
- masking traversal is bounded,
- when required structured masking cannot be applied safely, clear payload is not returned.

There is no v0.3 permission that bypasses an active masking rule.

## 7. Kafka principal requirements

Kafdeck's configured Kafka principal needs only the Kafka-side read/describe capabilities required by the selected record targets.

The upgrade does not require:

- Produce,
- topic alteration/deletion,
- consumer-group offset commit/reset,
- ACL administration,
- Kafka internal state topics for Kafdeck persistence.

Kafdeck does not subscribe as a durable consumer group and does not commit offsets.

## 8. Data and persistence

v0.3 does not add a payload database migration.

Record bytes and decoded values remain ephemeral application memory for the bounded operation. Payload indexing/historical persistence requires a future approved RFC.

Application persistence for identity/configuration/audit remains governed by the existing architecture baseline.

## 9. Network and deployment considerations

When Schema Registry is enabled, permit Kafdeck to reach only the configured registry endpoint through the intended network path.

Air-gapped/private deployments remain supported. v0.3 does not require a public cloud service or Internet-hosted identity/registry provider.

## 10. Post-upgrade verification

Verify the following before broadening record permissions:

1. v0.2 sign-in/session behavior remains correct.
2. Existing metadata roles can still browse only their authorized cluster/topic metadata.
3. A metadata-only role receives a Kafdeck authorization denial for record payload access.
4. A narrow `record.read` role can browse only its configured target.
5. Kafka ACL denial remains distinguishable from Kafdeck RBAC denial.
6. Masked fields do not appear in browse, tail, export, logs, audit, Problem Details or telemetry labels.
7. Live-tail disconnect cancels server-side work.
8. Bounded page/export limits return explicit partial/limit outcomes.
9. `record.read` without `record.export` cannot export.
10. No Kafka producer, offset commit or mutation capability has appeared.

## 11. Rollback

If v0.3 record-data behavior is not ready for a deployment, remove/withhold `record.read` and `record.export` grants and disable optional record integrations as applicable.

Because v0.3 does not require payload persistence or Kafka mutation, record-data exposure can be disabled without reversing Kafka-side data changes performed by Kafdeck.

Use the standard release rollback procedure for binary/configuration rollback. Preserve audit/security evidence generated during the attempted upgrade.

## 12. Compatibility evidence

The release-decision package must include fresh exact-head evidence for the accepted Kafka compatibility matrix:

- Kafka 4.3.1 — Tier 1,
- Kafka 4.2.1 — Tier 1,
- Kafka 4.1.2 — Tier 1,
- Kafka 3.9.2 — Tier 2.

Compatibility is a tested capability profile, not a blanket claim for every Kafka-compatible service.
