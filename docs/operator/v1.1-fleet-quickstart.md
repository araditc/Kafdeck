# Fleet quickstart for Kafdeck 1.1

Use Fleet to map Kafka brokers to verified Linux services, read bounded logs, install or upgrade the monitoring agent remotely, and make supported Kafka configuration changes. Start with a [working Kafdeck installation](v1.1-installation-guide.md), a managed administrator account and a connected Kafka cluster.

## 1. Connect and verify a Linux host over SSH

Have a host administrator prepare the restricted discovery helper and root-owned target catalog using the [host registration guide](v1.1-broker-host-registration.md). Use the released source for the helper scripts. The approved target names depend on how Kafka is run.

| Kafka deployment | Catalog entry | Service and logs |
| --- | --- | --- |
| Linux with systemd | `adapter: systemd`, exact unit such as `kafka.service` | One selected systemd unit and its journal |
| Docker Compose on Linux | `adapter: compose`, exact project and service labels | One verified running container and its Docker log stream |

Get the SSH host key fingerprint from a trusted host console. In Kafdeck's configuration enable `Kafdeck:BrokerHosts`, allow the management IPs and set a private SSH credential reference. Restart Kafdeck to load the configuration. Use distinct credentials for discovery and agent installation.

In the dashboard select the cluster, open **Fleet → Broker hosts → Register SSH host**, and enter its literal IP, port, restricted account, trusted fingerprint and credential alias. Choose **Verify and register host**. Find its approved service, select the matching Kafka broker ID and choose **Verify and bind broker**. Repeat for each broker, including hosts that run several brokers. The helper checks the selected service against Kafka's observed identity.

## 2. Read the broker's service logs

Enable logs on the approved host catalog entry, grant cluster access and list the operator in `LogReaderUserIds`. In **Brokers → Broker service logs**, pick the verified broker and a UTC time window. A configured monitoring-source mapping also enables **Open broker logs** on matching alerts. The service reads the approved journal or container source in bounded windows. [Log permissions and limits](v1.1-broker-service-logs.md).

## 3. Install or upgrade the agent remotely

1. Prepare the [restricted lifecycle helper and target configuration](v1.1-offline-broker-agent.md) on the Linux host. Stage the approved Java agent JAR under `/var/lib/kafdeck-agent/packages/<sha256>.jar`. Configure the package digest and authorized maintenance window in the host catalog and configure the corresponding operator, credential and package in Kafdeck.
2. Create a dedicated **Monitoring** source per broker and configure its properties and token on that host. For a first install, prepare the JVM argument-file hook. On **systemd**, the argument file is at its Linux host path. In **Compose**, mount its containing directory read-only at the JVM path. Verify the running process carries the prepared hook before trying the Fleet action.
3. In **Fleet → Offline broker agent**, choose the staged version, preview the changes and review restart preflight. Apply to the configured verified broker in its maintenance window. Fleet blocks restarts when the selected broker hosts a single-replica partition, when removing it would violate minimum ISR, or when cluster health is insufficient.
4. Use **Check agent operation** until Kafka health, replica recovery and a fresh JVM metric from that source are verified. In **Monitoring → Sources** confirm the expected broker is reporting. Move to the next broker only after this operation is resolved.

Package staging and initial broker JVM wiring are host preparation steps. Fleet applies and verifies the approved package remotely; it uses the host's local staged file. [Agent build, properties and JVM support](kafka-agent.md).

## 4. Change and restore a Kafka setting

Open **Fleet → Dynamic broker settings**. This workflow uses the Kafka Admin API through the selected cluster connection. It requires both Kafdeck configuration permissions and the Kafka credential's `DescribeConfigs` and `AlterConfigs` permissions.

Select the broker, preview a value, confirm and apply, then review the effective value and its source. Use **Preview restore** to restore the previous override or inheritance. Kafdeck 1.1 supports a per-broker `log.cleaner.backoff.ms` override, within the documented range. [Supported setting, readback and restore](v1.1-dynamic-broker-settings.md).

## 5. Recover a pending operation

When an SSH reply is lost or a restart is still pending, reopen Fleet under the same authorized account and use **Check agent operation**. Inspect the assigned unit or container and its logs if health does not recover. Confirm fresh metrics before making another broker change. Keep the operation records and Data Protection keys with the deployment backup. [Rollout preflight and incident recovery](v1.1-fleet-operational-recovery.md).

Release acceptance covered Linux/systemd without Docker and an isolated Docker Compose pilot on the Arad Office host. This acceptance applies to the recorded service and maintenance conditions. [Release scope and evidence](../releases/v1.1.md).
