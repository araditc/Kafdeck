# Notification recovery interlock: refusal-only contract

This optional interlock adds an explicit operator barrier for a declared restore.
It does not detect an undeclared database rollback, approve production HA, or
provide an accepted reconciliation/resume workflow. Existing deployments that
omit it keep their existing behavior; restoring an old ledger with sending
enabled remains unsupported.

## Independent authority

Physical delivery can configure both `DeliveryInterlockPath` (absolute path) and
`DeliveryInterlockSha256` (exact 64-character SHA-256). The file is an operator
owned, application read-only mount outside the database and its backup/restore
boundary. Provision its identity and permissions separately from the restored
data. Its entire content is bounded to 1,024 bytes and has this closed shape:

```json
{"version":1,"generation":"00000000-0000-0000-0000-000000000001","state":"active"}
```

Use a newly generated nonempty generation, rather than the illustrative value.
No unknown/duplicate fields, missing data, malformed JSON or non-active state is
admitted. The hash pins the exact immutable file bytes, including whitespace.
Replacing the anchor with another generation invalidates old configured hashes.
No credential or provider endpoint belongs in the anchor.

The database must separately contain an offline-enrolled singleton
`notification_delivery_generation` with `id=1` and a canonical GUID `generation`.
The sender only reads this metadata. Startup, status reads, schema initialization
and transport paths never create, enroll, reconcile or advance it. A missing
table/row, invalid generation, unavailable database, different generation or
external quarantine denies activation. Fresh-laboratory enrollment uses explicit
fixture SQL before any sender is started; that is not a runtime operator API.

The check runs before hosted startup and claims, and at every concrete physical
transport boundary. Webhook/Telegram recheck before private HTTP bytes, SMTP
before authentication and message DATA, and other HTTPS families before sending
the guarded request. A check cannot recall bytes already sent or a credential
already used; hot atomic cancellation/revocation is not claimed.

## Declared restore procedure and current refusal boundary

1. Stop and physically fence every sender and the superseded database primary.
2. Preserve the external anchor outside the backup boundary. Replace it with a
   new generation in a quarantined state **before** restoring database files.
3. Restore the backup into a separate, read-only quarantined database. An old
   `Pending` row may describe an event already accepted externally; its restored
   state cannot authorize a fresh send.
4. Verify the old configured hash fails against the new anchor. Verify a new
   configured hash cannot bypass quarantine. Even an active new-generation file
   with a matching new hash must fail against the restored old database epoch.
5. Retain the quarantine while the owner reconciles provider-side effects and
   every restored unresolved intent. Do not advance the database generation or
   reset unknown effects merely to make the sender start.

This batch implements and tests refusal. It does not implement an admitted
offline enrollment tool, governed receipt reconciliation, terminal fencing of
all restored unresolved intents, generation advancement or safe resumption.
Those remain explicit N4/N5 acceptance work. Copying an old database together
with its old external authority is outside this contract; the anchor must remain
independent. A malicious operator who replaces both authorities is not prevented
by an application read-only check.

## Actual recovery laboratory

The separate recovery lab creates a real synchronous PostgreSQL primary and
physical standby, verifies an actual base backup and supports old-primary
fencing, promotion and restore to a third read-only node. The sender harness is
a separate OS process using the production hosted worker/dispatcher/TLS code.
Its network mapping and private CA are test-only. Abrupt process termination
after a complete TLS POST is distinct from graceful host shutdown.

Recovery tests require `KAFDECK_G2_RECOVERY_ROOT`; optional
`KAFDECK_G2_RECOVERY_BIN` selects same-version PostgreSQL tools. Each scenario
uses a fresh child directory, retains its evidence and stops only its own lab.
The actual native Windows PostgreSQL 17.11 run passed all three process-host/TLS
recovery scenarios and 15 interlock checks. See the
[evidence and exact limitations](../implementation/v0.8-w66-g2-recovery-evidence.md).
Linux exact-head CI/protected-main acceptance and safe resumption remain open.
