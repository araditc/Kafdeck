# W67 service CLI with private_key_jwt

The shipped CLI accepts a public service profile and obtains a fresh token for
each command. The backend still requires a live registered **service** principal,
exact issuer/audience/client/subject, and current direct resource permissions.
The profile and signing key do not create backend authority or human approval.

```json
{
  "issuer": "https://idp.example/realms/operations",
  "audience": "kafdeck-api",
  "clientId": "kafdeck-automation",
  "expectedSubject": "the-exact-service-account-subject",
  "privateKeyFile": "/secure/runtime/client-private-key.pem",
  "trustedCaPemFile": "/secure/runtime/optional-root-ca.pem"
}
```

`trustedCaPemFile` is optional when platform trust already validates the issuer
and API. Protect the referenced private key with the operating system's file
permissions. Do not commit it or place its PEM contents into this JSON profile.
Profiles, private keys and CA files each have a 16 KiB read limit. Profiles reject
unknown, duplicate, incorrectly typed or missing fields. RSA keys must include
private material, be 2048–4096 bits, and use exponent 65537. Encrypted-key
passwords, shared secrets and access-token arguments are not supported.

```sh
kafdeck --url https://kafdeck.example --service-profile service-public.json system info
```

The client verifies HTTPS discovery and the fixed issuer token/JWKS endpoints,
creates one RS256 assertion with exact client issuer/subject, exact token-endpoint
audience, a fresh random `jti`, and a 45-second lifetime, and submits it once as
`client_credentials` with `private_key_jwt`. The complete flow has a 45-second
deadline; headers and response documents are bounded. It does not open a browser
or retry an assertion. Signed access tokens must have the exact expected subject,
API audience and authorized client, trusted issuer/key, and bounded valid times.
Credentials remain in memory and errors do not print the IdP response.

`--service-profile`, `--oidc-profile`, `--token-file` and
`KAFDECK_ACCESS_TOKEN` cannot be combined. A failed service exchange does not fall
back to another credential source.

The implemented named topic create/alter/increase/delete and requester lifecycle commands
also accept this profile. They require the default-off backend governed mutation
switch, the service registration's explicit matching mutation grant, and current
resource RBAC. They use the same durable preview, exact actor, policy, confirmation,
approval, dispatch and status engine as the human CLI. A service never satisfies
the distinct human approver requirement. Typed approval commands require a human
PKCE profile and separate approval authority. Other effect families remain outside
the current admitted CLI surface.

The genuine private_key_jwt → shipped CLI/API → Kafka TopicCreate scenario passed
on protected main PR #330 (`d762bd4c41e11567afe9ad4996c97f41fd5997f6`), including
idempotency, wrong-hash denial, positive topic readback and exact durable service
attribution. It establishes this selected SQLite vertical. Other effect families,
the complete provider/HA/restart/restore/rotation/revocation matrix and the whole
W67 workstream remain open; new extension proof is tracked separately.
