# Upgrade Guide — Kafdeck v0.4 to v0.5

## 1. Upgrade posture

v0.5 is a security-boundary change. v0.4 is read-only; v0.5 can perform governed
external mutations. Do not treat this as a routine in-place feature toggle.

The safe default during upgrade is that mutation remains disabled until identity,
authorization, persistence, provider profiles, recovery behavior and operator
procedure have been validated for the target deployment.

Existing v0.1-v0.4 read permissions and masking behavior remain independent.
Granting existing read actions must not grant any v0.5 mutation action.

## 2. Recommended rollout sequence

1. back up the existing deployment configuration and all persistent application
   state;
2. deploy the v0.5 binary with mutation disabled;
3. verify existing v0.1-v0.4 read-only workflows and authorization/masking
   regressions;
4. configure the mutation persistence posture appropriate to the deployment;
5. configure the deployment-owned material-digest secret through the normal
   secret-management channel;
6. validate OIDC access mode and explicit mutation RBAC actions;
7. configure only the typed provider mutation profiles actually required;
8. enable mutation for a narrowly scoped operator/cluster/resource set;
9. execute one bounded, low-risk test mutation and verify durable state,
   idempotency, dispatch evidence and readback;
10. grant additional typed mutation actions incrementally;
11. enable destructive/CRITICAL operations only after independent-approval and
    `ExecutionUnknown` runbooks have been exercised.

Do not begin the rollout by granting a broad administrative role across all
mutation actions.

## 3. Identity and authorization migration

v0.5 mutation execution requires the admitted OIDC identity posture. Current
request identity is re-evaluated immediately before dispatch; persisted historical
identity data is not used to reconstruct missing OIDC claims/groups.

Mutation authorization uses typed actions. Examples include topic administration,
record production, consumer offset/group administration, Schema Registry
mutation, Kafka Connect mutation and controlled purge. Read actions remain
separate.

Migration rules:

- create explicit mutation permissions rather than deriving them from read roles;
- scope permissions by cluster and resource pattern as narrowly as practical;
- provide independent eligible approvers for CRITICAL operations;
- do not bind the requester and sole approver capability to one identity if the
  deployment intends to perform CRITICAL operations;
- validate that role/group changes take effect at dispatch time, not only at
  preview time.

## 4. Persistence migration

Mutation mode requires durable operation/idempotency/claim state.

SQLite is supported only for the admitted standalone mutation posture. Do not
upgrade a multi-instance deployment by sharing one SQLite mutation database.
Multi-instance/HA mutation execution requires the admitted PostgreSQL posture.

Before enabling mutation:

- verify the target database is writable;
- verify the application-supported schema/migration process has completed;
- verify only one mutation instance can use a standalone SQLite store;
- for PostgreSQL, verify all instances point to the same intended durable store
  and can coordinate idempotency/resource/cluster claims;
- verify database backup and restore procedures include mutation state.

Do not manually seed or delete claim/idempotency rows as an upgrade shortcut.

## 5. Material-digest secret

Raw record payloads and provider secrets are not durable mutation state by
default. Ephemeral execution material is bound to the admitted preview by HMAC
material digests.

The digest secret is deployment-owned secret material. It must be available after
restart/restore whenever the deployment expects to validate material for an
already admitted operation. Keep it in the deployment's secret-management system,
not in repository configuration, logs, audit events or provider evidence.

Changing the digest secret can intentionally make old ephemeral material fail
validation. That is safer than accepting material under the wrong key. Plan key
rotation around outstanding admitted operations; do not introduce a compatibility
bypass that accepts both raw material and unmatched digests.

## 6. Provider profile migration

Kafka, Schema Registry and Kafka Connect mutation remain typed/capability-bound.
Upgrade does not authorize a generic provider endpoint.

For Schema Registry and Connect:

- retain the existing validated deployment-configured origins;
- admit mutation only for an explicitly supported mutation provider profile;
- keep redirect rejection and bounded response handling enabled;
- do not add caller-selectable upstream URLs or arbitrary HTTP methods/bodies;
- keep provider credentials in the existing secret-resolution boundary.

A read-only provider profile that is not admitted for mutation must continue to
fail closed when a mutation is attempted.

## 7. Record production migration

Record production is a new privileged action, not an extension of `record.read`.
Grant `record.produce` only to exact topic scopes that require it.

Validate configured record count, value/key/header and aggregate material limits
before rollout. Hard server caps remain authoritative even when deployment policy
chooses smaller limits.

Raw key/value/header material must not be moved into durable staging as part of an
upgrade or operational convenience. Re-submission must continue to digest-match
the preview.

## 8. Destructive operation migration

Topic delete and controlled purge are CRITICAL. Permanent destructive schema
operations can also be elevated by the server risk floor.

Before enabling destructive actions:

- verify independent approval with two distinct eligible principals;
- verify exact target materialization and typed-target confirmation;
- exercise stale-preview rejection;
- verify operators understand that purge has no generic undo;
- exercise the `ExecutionUnknown` procedure without performing a blind retry.

Do not enable destructive actions merely because non-destructive mutation passed
smoke testing.

## 9. In-flight operation handling during upgrade

Avoid deploying a mutation-execution change while intentionally starting new
CRITICAL work.

Before maintenance, inventory operations that are:

- awaiting confirmation/approval;
- ready/claimed for execution;
- executing;
- `ExecutionUnknown`;
- partially applied;
- applied but unverified.

After restart, allow the durable recovery/lease logic to classify interrupted
execution. A pre-dispatch interruption may become a definitive pre-dispatch
failure; a post-dispatch interruption must remain `ExecutionUnknown` until
reconciled. Do not clear claims solely because their original process is gone.

## 10. Backup and restore validation

A v0.5 restore drill should verify more than application startup.

Validate that restored state preserves:

- operation and preview identity;
- confirmation/approval state;
- idempotency bindings;
- execution generation/lease state;
- resource and cluster claims;
- dispatch markers and outcome classification;
- bounded safe provider/verification evidence.

Then verify the restored deployment has the intended OIDC/RBAC policy, provider
profiles and material-digest secret.

Potentially applied operations must be reconciled against Kafka/provider truth
before conflicting work is re-admitted. A restore must never transform unknown
post-dispatch work into a retryable pre-dispatch failure.

## 11. Rollback

Rollback from v0.5 to v0.4 is not equivalent to the v0.4-to-v0.3 rollback because
v0.5 may have durable mutation state and may already have changed external
systems.

Before rolling back:

1. stop admitting new mutation work;
2. inventory executing/unknown/partial/unverified operations;
3. reconcile potentially applied external side effects;
4. preserve a backup of the v0.5 mutation persistence store;
5. confirm the target older version will not attempt to interpret unsupported
   mutation configuration/state;
6. remove or disable v0.5-only mutation configuration before starting an older
   binary when required by that version;
7. retain mutation audit/history and database backup for incident/reconciliation
   purposes.

Rolling back the Kafdeck binary does **not** roll back Kafka, Schema Registry or
Kafka Connect side effects that v0.5 already applied.

Do not destructively rewrite mutation persistence to make an older binary appear
compatible.

## 12. Post-upgrade acceptance

Before declaring the deployment operational for v0.5 mutation, verify:

- existing read-only flows and masking still behave as expected;
- mutation defaults to deny for an ungranted principal;
- a read-only principal cannot perform mutation;
- current-request authorization is rechecked at dispatch;
- CRITICAL self-approval is rejected;
- stale preview is rejected before dispatch;
- idempotent replay returns the governed prior operation/result rather than
  dispatching a duplicate side effect;
- unknown provider outcome remains `ExecutionUnknown`;
- raw payload/secret sentinels are absent from durable state/log/audit evidence;
- persistence backup/restore procedure is documented and owned;
- operators know the `ExecutionUnknown`, partial/unverified and destructive-action
  procedures.

## 13. Release boundary

Completing a deployment upgrade test or W40 readiness review does not authorize a
repository release. The v0.5 tag, OCI promotion, GitHub Release and other
publication actions remain explicitly owner-gated.
