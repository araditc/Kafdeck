# Upgrade Guide — Kafdeck v0.3 to v0.4

## 1. Upgrade posture

v0.4 adds read-only consumer/schema/ecosystem capabilities. It does not add Kafka or ecosystem mutation.

Existing v0.3 record permissions and masking rules remain unchanged.

## 2. Authorization migration

New permissions are opt-in:

- `consumer.read`
- `schema.read`
- `connect.read`
- `ksql.read`
- `catalog.read`

Do not infer these permissions from `topic.read`, `record.read`, or administrative metadata roles.

Recommended rollout:

1. upgrade with no new v0.4 permissions,
2. verify v0.1-v0.3 workflows,
3. configure optional Schema Registry / Connect / ksqlDB profiles,
4. grant one new read action at a time to narrow cluster/resource scopes,
5. verify partial/denied/audit behavior,
6. expand only when operationally required.

## 3. Kafka permissions

Consumer views need Kafka-side read/describe capabilities appropriate to consumer groups and topic offsets.

Do not grant offset-alteration or produce rights merely for v0.4.

## 4. Schema Registry

The existing v0.3 read-only Schema Registry profile is reused and expanded for subject/version browsing.

No schema lifecycle rights are needed.

Remote basic-auth registry profiles require HTTPS except loopback development endpoints.

## 5. Kafka Connect

Connect is optional.

A v0.4 cluster profile can configure one Connect endpoint.

Connector config is fail-closed redacted; do not rely on v0.4 for retrieving connector secrets.

No connector mutation rights are required or used.

## 6. ksqlDB

ksqlDB is optional.

A v0.4 cluster profile can configure one ksqlDB endpoint.

Kafdeck v0.4 never sends SQL/statement requests. Deployments that expose no genuine read-only metadata endpoint will show metadata discovery as unsupported.

## 7. Topic catalog

Catalog entries are configuration-backed. No persistence migration is required.

Adding a catalog entry does not alter RBAC.

## 8. Persistence

v0.4 does not require a new database or Kafka internal state topic.

Optional metrics/history providers remain absent by default.

## 9. Rollback

Because v0.4 introduces no mandatory state migration and no mutation workflow, rollback to v0.3 primarily means restoring the prior Kafdeck binary/configuration.

Remove v0.4-only Connect/ksql/catalog configuration before starting an older binary that does not understand those settings.

No Kafka offset/schema/connector changes require compensation because v0.4 does not perform them.
